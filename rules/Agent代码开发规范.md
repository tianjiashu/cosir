# Agent 代码开发规范

> 技术栈无关。目标：整洁、可维护、不堆积技术债。
> 核心矛盾：Agent 倾向"最快完成功能"而非"最优维护代码"，本规范纠正这一倾向。

---


### 第零铁律（最高优先级）

**目标**：一切改动以结构合理、清晰、简洁、高效为最终目标，支撑项目长期稳定迭代。开发工作量不是取舍依据：不因改动大、文件多、要改名而选较差的结构，「最小改动」「零新增依赖」「不动既有代码」都只是手段。需要权衡的只有运行时成本、数据与行为风险，以及能否分阶段验证。

**适用时机**：新增功能、修复缺陷、重构都先按本条定路线再动手。任务类型按入口定；调查中类型变了（修复的根因在契约或结构 → 按重构执行，新增发现现有结构容不下 → 先重构再新增）写进调查结论；实施中途发现原路线或类型不成立，停下重新定。

**按任务类型定调查重点**：

- **修复：先定根因层级。** 问题出在哪一层、哪个事实源、哪条契约，就在那里解决；不在症状处打补丁，也不在调用链多处各补一刀。表象出现的位置不等于根因所在：根因可能是局部逻辑、契约或整体结构，在契约或结构时按重构的要求执行。
- **新增：先定归属再写。** 查已有能力与事实源，确定新功能落在哪一层、谁拥有新事实、影响哪些契约；再判断现有结构能否自然容纳——需要特例、旁路或第二个事实源才放得进去时，先重构再新增。不预留扩展点（见「抽象按需引入」）。
- **重构：先定终态再动手。** 说清目标结构与动机（解决哪个结构性问题）；查清全部调用方与消费方；区分「行为不变」与「有意改变的行为」并分别说明；大重构拆成每步可验证的阶段。

**调查方法**（三类共用）：

- **从点到面**：眼前的缺陷或缺口常是一类问题的一角，而「看起来局部、落点明确」正是一角的典型样子。定路线前先分清它是实现缺陷（写错了）还是设计不足（漏了某个维度，如取消、重启、并发、删除等生命周期分支，或契约没写清）；再按同一根因或隐含假设——而非同一现象——找其他出现点：仓内同类写法、同一契约的其他消费方、依赖同一假设的代码。最低要求是能说清「为什么别处没有这个问题」；说不清，或出现以下结构性信号时，按结构问题查清全貌，不在单点上找答案：同类问题反复出现或需多处同步修补；修复要靠特例、标志位或某个隐含前提才成立；同一事实有两个来源或靠手工同步；依赖方向反了、循环依赖或模块知道不该知道的内部细节；职责放在哪层都说得通；测试需要大量无关上下文。
- **深度与风险相称**：跨层或跨进程边界、涉及事实源 / 状态机 / 契约、初判置信度低、改动会改变契约或数据，出现任一情形都不凭第一层代码定路线；确属局部（「从点到面」已排除是一类问题）且证据确凿时直接定路线，不为走流程而深挖。
- **按方向深读**：链路方向沿上游调用链（谁产生输入、谁保证契约）、下游消费方（谁读取、改动波及谁）、仓内同类写法与已有能力，读到事实源或信任边界；结构方向看职责边界、事实源归属、依赖关系与数据流，对照本文件的架构边界。对全貌的结论（问题属于哪一类、有哪些出现点、根因在哪层）不再变时停止——只对眼前这一点的结论不再变，不算查完。
- **按需委派**：运行环境支持子 Agent 时，由主 Agent 按「独立调查方向数 × 单方向阅读量」决定是否委派、委派几个（一个方向一个子 Agent，不重叠；疑似结构问题或一类问题时单设结构方向）；单方向、少量文件时自己读。简报只给现象、证据或需求，不写主 Agent 倾向哪个结论；有多个候选解释时并列给出、不排序，要求子 Agent 独立判断并找出反例或其他解释；子 Agent 只读不改，返回带 `文件:行` 的证据、对调查对象的判断（修复为根因层级，新增为归属，重构为影响面）、同类出现点和可选解法。
- **汇总核对**：子 Agent 结论是线索不是证据，主 Agent 抽查关键论断引用的代码，冲突处补查；再按「判断方法」选路线，按「交付要求」交付。

**判断方法**：

- **比较两条路线。** 「结构化改造」调整职责、边界或数据流，让问题不再可能出现、需求自然落位；「补丁式修复」在现有结构上局部修正。补丁仅在问题确属局部、现有结构本身合理、且不引入新特例或隐式耦合时可取；否则走结构化改造。
- **查全貌不等于改全貌。** 调查范围按全貌定，改动范围按目标定：同一根因的出现点在根因处一并解决；与本次目标无关的记入问题清单、向用户说明，不在本次处理。执行途中新发现的问题按同一规则归入。
- **以结构为准绳，不以改动量为准绳。** 自问：改完后下一次同类需求是否更容易做、更难做错；读者是否更快找到真实逻辑。
- **加法与减法并重。** 引入新路径时同步删除被取代的旧路径、死代码、只剩单实现的抽象与过时注释，不让新旧两套并存。
- **复用优先于自造。** 先查项目已有能力，再看成熟方案（编辑器、图表、虚拟化等通用复杂能力尤其如此）；依赖既非目的也非禁区，以是否适配项目、是否降低长期维护成本取舍。
- **有取舍，不求面面俱到。** 聚焦主路径与真实风险，低概率情形在一处边界兜住即可（见「不层层防御校验」）。

**交付要求**：动手前（或改路线时）交用户确认：调查结论与问题清单（发现缺陷或设计缺口时必附；每条写明现象、证据 `文件:行`、根因层级或归属与置信度、待验证假设，同类出现点逐条列出并标明本次处理还是记下及理由）、选定路线及理由、影响范围（涉及模块、契约 / 数据 / 行为变化、需同步的测试与文档）、改动账本（新增；删除；可选的精简；文件、目录与命名调整，没有就写「无」），以及刻意不做的部分；实施中保持目标聚焦，不顺手夹带无关改动。

## 三条铁律

1. **单一职责** — 一个文件只做一件事，按职责而非行数判定。
2. **路径即语义** — 只看完整路径就能知道文件做什么、属于哪层，也能猜到新功能该放哪。目录表达能力域，文件名表达这一件事；同一概念全仓同一个词；不用 `utils`、`common`、`helper`、`manager` 这类没有信息的名字（语言或框架约定除外）。职责变了就改名和搬家。
3. **可排查日志** — 系统中必须存在可排查问题的日志文件。

> **各维度同等重要，不设固定优先级。** 正确性、可排查性、单一职责、路径语义、可读性、性能——这些维度都不可牺牲，不存在「为了 A 可以放弃 B」的固定取舍链。当维度间出现张力时，以第零铁律为最终判据去权衡，而不是机械地按某条优先级链压低某一维度。

---

## 一、单一职责

**不限行数，限职责。** 判定法：用一句话描述文件做什么——出现"和/并且/以及"或多个动词，就是多职责，必须拆分。

- 800 行只做"CSV 解析" → 合格；150 行混了路由+逻辑+SQL → 屎山。
- 一个文件只有一个变更理由。因不同需求反复改同一文件 → 职责过多。
- 函数超 60 行、参数超 5 个、嵌套超 3 层 → 检查是否该拆分。
- 开发过程中可以、也应该持续拆分文件和目录；当职责边界变清晰时，立即调整目录结构，不等到“以后整理”。
- 文件变清晰但目录变混乱，同样不合格（路径标准见铁律「路径即语义」）。

## 二、复用优先于自造

> 受第零铁律校准：本原则是**不可解除的底线**。第零铁律允许「大胆引入外部依赖、大胆做大改动」，但**正是为了复用成熟能力、避免自研轮子**；两者同向，不存在冲突。切勿把第零铁律误解为「可以自己手写通用复杂能力」。

写任何非 trivial 逻辑前，**必须依次三查**：

1. **查代码库** — 已有相同/相似实现？有就复用或扩展，不平行重写。
2. **查生态库** — 有成熟、被广泛使用的库？引入它。自己实现仅在：需求极特殊 / 方案过重 / 有安全问题时，且**必须注释说明原因**。
3. **查标准库** — 语言内置已提供？优先用，减少外部依赖。

- 重复逻辑出现 3 次以上 → 提取公共函数（Rule of Three，避免过早抽象）。
- 新引入依赖必须锁定版本，评估是否值得增加外部依赖。

## 三、防膨胀

每次改文件前自问：
- 加的是新功能还是改已有功能？新功能不属于此文件职责 → **新建文件**。
- 这个修改是否让文件承担新职责？是 → **停，拆分或新建**。
- 是在"添加代码"还是"堆积代码"？只 append 不审视结构 → **停，先重构**。

- 每次修改让代码比之前更好或至少不更差（Boy Scout Rule）。
- **禁止**"先堆上去以后再整理"——以后不会整理。
- 注释只解释**为什么**，不解释**是什么**。需要大段注释说明逻辑 → 代码该重构了。
- 拆分不是重构洁癖，而是控制复杂度的正常开发动作；发现文件、目录、函数职责变宽时，应同步拆分。

## docstring 约定【必须中文】【**主线任务**执行用户指令，**支线任务**发现docString漂移，并向用户说明，不擅自主动改】

注释与 docstring 是本仓的「记忆」：优先记录**不明显**的信息——设计决策（为什么这样写、为什么不能那样写）、上下游链路契约（谁保证什么输入、谁消费什么输出、边界与事实源在哪）、复杂逻辑的取舍，以及非显而易见的约束与副作用。

- **记不明显的，不记明显的。** 简单代码逻辑（一眼看懂的赋值、循环、返回）与函数名已自解释的简单职责，不必为「凑完整」而写；复杂逻辑（为何分这几步、算法或方案取舍）可以且应当说明。
- **决策与链路契约优先于逻辑复述。** 比「做了什么」更重要的是「为什么这么做、与上下游怎么衔接、踩过什么坑」。例如为何必须在某操作前判定集合、某状态事实源在别处、重复发起会造成什么副作用。
- **避免膨胀，保持精炼。** 没有不明显信息时，短句或省略都好过套话；不堆砌字段清单、参数逐一翻译或显而易见的描述。
- 公共模块、类、函数覆盖以下维度中**适用且不显然**的部分：负责什么与不负责什么、输入/输出语义、持久化/进程/线程/网络/全局状态副作用、可能抛出的异常及调用方处理、生命周期的初始化/关闭/取消/重试/恢复、边界转换规则。

如果**注释**或者**docstring**与**代码事实**不一致，则必须修正注释以及docString 与代码事实对齐；若仅复述明显逻辑、无记忆价值，应删减而非保留。

## 五、分层架构

```
表现层 → 只做：输入校验、调用业务层、格式化输出
业务层 → 只做：业务规则、流程编排
数据层 → 只做：增删改查、数据映射
基础设施层 → 只做：外部系统交互
```

- 上调下，下不调上，禁止跳层。Controller 不写业务逻辑，Service 不写 SQL。

### coding-agent Assistant Transport 目录约定

- `apps/backend/app/assistant_transport/` 是 Assistant Transport 协议相关实现的固定归属目录。
- Assistant Transport 的请求/响应模型、`set` / `append-text` 等协议操作、状态流组装、传输订阅，以及为保证传输状态发布语义所需的事务协调代码，统一放在 `apps/backend/app/assistant_transport/` 下按职责拆分。
- `core`、普通领域 `service`、`models` 和 `storage` 不得依赖 Assistant UI 类型或协议细节；它们只处理领域事实、运行状态和持久化。
- Assistant Transport 可以调用领域服务和存储端口，但不得把 Transport 状态副本反向写成第二事实源，也不得在传输层之外复制协议投影逻辑。

## 六、可排查日志

**没有日志文件，就没有可维护系统。** 任何可运行系统都必须能在出问题后通过日志定位：发生了什么、发生在哪、影响了谁、下一步该查什么。

### 必须存在

- 项目必须有明确的日志落盘位置，例如 `logs/app.log`、`storage/logs/app.log`、`var/log/app.log`，或框架约定的日志目录。
- 日志目录和文件命名必须可预测，不能只输出到控制台、弹窗、toast、浏览器 DevTools 或第三方平台。
- 日志目录如需忽略提交，必须保留占位文件（如 `.gitkeep`）或 README，说明运行后日志写到哪里。
- 本地开发、测试环境、生产环境都必须有可查看的错误日志路径；生产可额外接入日志平台，但不能替代本地/服务端日志文件约定。

### 必须记录

- 启动、关闭、关键配置加载结果（不得输出 secret 原文）。
- 用户请求或任务入口：时间、模块、操作名、请求/任务 ID、关键业务 ID。
- 外部依赖调用：目标服务、操作名、耗时、状态码/错误码、失败原因。
- 异常路径：异常类型、错误信息、堆栈、上下文 ID、可重试状态。
- 关键状态变更：创建、更新、删除、发布、支付、权限变更、后台任务执行结果。

### 禁止记录

- 大体积原始请求/响应、二进制内容、无边界循环日志。
- 只有“失败了”“error”但没有上下文、堆栈或定位线索的无效日志。

### 实现要求

- 优先使用项目现有日志框架或语言生态成熟日志库，不手写散落的 `print/console.log` 当作系统日志。
- 日志必须分级：至少区分 `info`、`warn`、`error`；调试日志不得污染生产默认输出。
- 错误处理不能只返回错误给用户，必须同步写入日志文件；空 `catch` 和只吞错误都禁止。
- 后台任务、定时任务、队列消费者、CLI 脚本必须和 Web/API 一样写日志。
- 日志写入失败不能导致主流程静默失败，至少要有备用输出或显式错误。

## 七、Agent 编码纪律

**动手前**：看项目实际结构和约定 → 搜已有相似实现 → 确认可用依赖 → 理解需求边界。

**编码时**：一个文件只写一个职责；写到一半发现要加不相关的东西 → 新建文件；路径说不清职责就同步改名、搬家或拆分目录；能用库解决就用库；遵循项目已有风格；新增或修改函数时同步维护完整 docstring；新增可运行入口、后台任务或异常路径时同步补日志。

**交付前自检**：
```
□ 每个文件能否用一句话（不含"和"）描述职责？
□ 是否已搜索代码库/标准库/生态库，确认无重复实现？
□ 是否在已有文件中加了不属于其职责的代码？
□ 只看路径能否知道文件做什么？职责变了是否已改名或搬家？
□ 改动账本是否写清新增、删除与文件路径调整？
□ 是否有跨层调用或业务逻辑泄漏？
□ 每个函数是否都有完整且与当前实现一致的 docstring？
□ 错误处理是否完整（无空 catch）？边界情况是否考虑？
□ 新依赖是否必要且锁定版本？
□ 是否有注释掉的旧代码或无用代码？
□ 系统是否有明确日志文件路径？
□ 新增失败路径是否写入 error 日志，并包含定位所需上下文？
□ 日志是否避免输出 secret 和敏感个人信息？
```

## 八、开发-审查-测试闭环

**Agent 不能既当开发又当裁判。** 开发完成后，必须启动独立的审查 Agent 和测试 Agent，形成闭环验证。

### 流程

```
开发 Agent 完成编码
        ↓
  启动 审查 Agent（独立）
  启动 测试 Agent（独立）
        ↓
  审查通过？  测试通过？
    ↓ 是      ↓ 是
   继续检查   交付完成
    ↓ 否      ↓ 否
  修复问题 ←──┘
    ↓
  修复完成后，重新启动审查 Agent + 测试 Agent
    ↓
  循环，直到审查 + 测试均通过
```

### 审查 Agent 职责

- 对照本规范逐条检查代码（单一职责、路径语义、复用、防膨胀、docstring、分层、日志、禁止行为）。
- 重点检查：文件和目录职责是否清晰、是否存在重复实现、是否有跨层调用、函数 docstring 是否完整且同步、错误处理是否完整、日志是否可定位问题。
- 输出：通过 / 不通过 + 具体问题列表（附文件名和行号）。

### 测试 Agent 职责

- 执行业务逻辑层的单元测试；如无测试则先生成测试再执行。
- 检查边界情况覆盖（空值、越界、并发、异常路径）。
- 涉及错误处理、后台任务或外部依赖失败时，必须验证日志文件会产生可排查记录。
- 输出：通过 / 不通过 + 失败用例和错误信息。

### 规则

- 审查 Agent 和测试 Agent **必须独立启动**，不能是开发 Agent 本身或同一上下文。
- 开发 Agent **不得自行宣布"代码完成"**——必须有审查 Agent 和测试 Agent 的通过结论。
- 修复后**必须重新跑**审查 + 测试，不能"相信已经修好了"就跳过。
- 循环次数不设上限——有问题就修，修完再验，直到通过。

---

## 九、禁止行为

| 禁止 | 原因 |
|------|------|
| 一个文件堆完所有功能 | 违反单一职责 |
| 职责变了不改名、不搬家 | 路径不再说明文件做什么 |
| 手写标准库/成熟库已有的功能 | 重复造轮子 |
| 先堆代码承诺之后重构 | 以后不会重构 |
| 不看已有代码就开始写 | 重复已有逻辑、风格不一致 |
| Utils/Helper/Common 命名 | 变成垃圾桶 |
| 空 catch 块 | 吞错误，无法定位 |
| 函数没有 docstring | 无法快速理解职责、参数、返回值和副作用 |
| 修改函数后不更新 docstring | 文档误导后续维护 |
| 没有日志文件或只打印到控制台 | 出问题后无法复盘 |
| 错误日志没有上下文或堆栈 | 不能定位根因 |
| 日志输出 secret 或敏感个人信息 | 安全事故 |
| 跨层调用 | 违反分层 |
| 引入依赖不锁版本 | 构建不可复现 |
| 注释掉旧代码不删除 | 版本工具会记住历史 |
| **开发 Agent 自己宣布代码完成** | 既当开发又当裁判 |

---

> **一个文件一个职责，不靠行数靠职责判定。**
> **路径即语义：不看代码，只看路径就知道文件做什么。**
> **函数必须有完整 docstring，代码变了文档也要变。**
> **能复用就不手写，能站在巨人肩上就不自己当巨人。**
> **没有日志文件，就没有可排查系统。**
> **写完不自验，审查测试闭环过。**
> **以结构为尺：开发量不是理由，敢改、敢引依赖，但绝不重复造轮子。**
