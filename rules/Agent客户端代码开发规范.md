# Agent 客户端代码开发规范

> 本规范是 `rules/Agent代码开发规范.md` 的**客户端派生附录**，专用于 `apps/desktop/`（Tauri 2 + React + TypeScript + Vite）与 `packages/shared/`。
> 后端规范已声明「技术栈无关」，其五条铁律与审查/测试闭环对客户端**直接适用**；本文件只补强那些带着后端语境、直接套用会产生歧义或盲区的条款。
> 当本文件与后端规范冲突时，以**正确性、可排查性、不重复造轮子**优先；本文件未覆盖的部分，一律回退到后端规范。
> 关联文档：`rules/Agent代码开发规范.md`、`docs/desktop-client-development-plan.md`、`docs/ui-guidelines.md`、`AGENTS.md`。

---

## 五条铁律（直接套用，无需改）

1. **单一职责** — 一个文件只做一件事，按职责而非行数判定。
2. **不重复造轮子** — 能用成熟方案就不自己写。
3. **改动聚焦** — 只动该动的地方，不牵连无关代码；复用标准库/成熟开源方案优先于"自己写更短的代码"。
4. **目录结构清晰** — 开发过程中持续拆分文件与目录；目标是不看代码，只看目录就能知道项目能力模块和职责边界。
5. **可排查日志** — 系统中必须存在可排查问题的日志文件（前端语境见第六节）。

优先级：`正确性 > 可排查性 > 不重复造轮子 > 单一职责 > 目录结构清晰 > 可读性 > 改动聚焦 > 性能`

---

## 一、单一职责（前端映射）

**不限行数，限职责。** 判定法：用一句话描述文件做什么——出现"和/并且/以及"或多个动词，就是多职责，必须拆分。

- 一个 React 组件只渲染一个 UI 区域或一类 UI 元素；一个 hook 只封装一类副作用/状态；一个 store slice 只管理一类领域状态（如 `taskStore` 管任务、`eventStore` 管事件流）；一个 `services/*` 文件只负责一类外部通信（HTTP / SSE / 类型）。
- 一个文件只有一个变更理由。因不同需求反复改同一文件 → 职责过多。
- 组件超 200 行、hook 超 80 行、单组件 props 超 8 个、嵌套 JSX 超 4 层 → 检查是否该拆。
- **禁止** `components/Common.tsx`、`utils/Helper.ts`、`hooks/Misc.ts` 等模糊命名——职责垃圾桶的高发信号。纯工具函数只允许进 `lib/utils.ts`，且只放 `cn()` 这类与 UI 无关的纯函数；组件级逻辑一律放 `hooks/`。
- 目录结构必须表达业务能力、层次关系和职责边界（对齐 `docs/desktop-client-development-plan.md` 第 3 节）；目标是不看代码，只看目录就知道有哪些能力模块。

## 二、不重复造轮子（前端映射）

写任何非 trivial 逻辑前，**必须依次三查**（与后端规范一致）：查代码库 → 查生态库 → 查语言/框架内置。

- **优先用项目既定生态**：UI 用 shadcn/ui + Radix UI；样式用 Tailwind CSS；图标用 lucide-react；状态用 Zustand；HTTP 用原生 `fetch`（封装于 `services/api.ts`）；SSE 用 `fetch + ReadableStream`（封装于 `services/sse.ts`）；表单/校验用 zod；后续表格用 TanStack Table、长列表用 TanStack Virtual、命令面板用 cmdk、代码展示用 Monaco。
- **禁止**手写日期格式化、手写 class 合并、手写 fetch 重试/超时、手写可访问性原语（用 Radix）。这些成熟方案已在选型内，自己写即重复造轮子。
- 重复逻辑出现 3 次以上 → 提取公共函数或公共组件（Rule of Three，避免过早抽象）。
- 新引入依赖必须锁定版本，评估是否值得增加外部依赖；不引入与既定体系冲突的 UI 库（如 Ant Design / MUI 作为主体系被 `docs/ui-guidelines.md` 明确禁止）。

## 三、防膨胀（前端映射）

每次改文件前自问：
- 加的是新功能还是改已有功能？新功能不属于此文件职责 → **新建文件**。
- 这个修改是否让组件承担新职责（如 `ChatPanel` 里写 SSE 解析、在 `App.tsx` 里拼 API）？是 → **停，拆分或新建**。
- 是在"添加代码"还是"堆积代码"？只 append 不审视结构 → **停，先重构**。

- 每次修改让代码比之前更好或至少不更差（Boy Scout Rule）。
- **禁止**"先堆上去以后再整理"——以后不会整理。
- 注释只解释**为什么**，不解释**是什么**。需要大段注释说明 JSX/逻辑 → 组件或函数该拆分了。
- 拆分不是重构洁癖，而是控制复杂度的正常开发动作；发现组件、目录、hook、store 职责变宽时，应同步拆分。

## 四、函数 Docstring（前端映射为 TSDoc）

**每个导出函数/类型/组件都必须有完整 TSDoc，并且随着修改同步更新。**

- TSDoc 必须说明：目的、关键参数（`@param`）、返回值（`@returns`）、可能抛出的异常或失败状态（`@throws`）、重要副作用（如"写入 store""发起 IPC"）。
- 描述的是当前真实行为，不是历史行为；改函数时必须同步改 TSDoc。
- 不能只写"处理数据""执行逻辑"这种无信息内容。
- **`lib/` 纯函数一律强制 TSDoc**（如 `cn()` 需说明合并规则、入参类型、返回类型）。后端规范曾把此类列为审查可选项，客户端**升格为必须**，因为 `lib/` 纯函数最容易被漏写文档。
- 对外 API 封装、SSE 解析、store action、hook、IPC 调用、错误处理的 TSDoc 必须特别完整。
- TSDoc 不替代清晰代码；若 TSDoc 需解释大量实现细节，应优先考虑拆分函数/组件。

## 五、分层架构（前端映射）

后端规范的「表现层 → 业务层 → 数据层 → 基础设施层」映射为前端分层：

```
组件(表现层)  → 只做：输入校验、调用 hook/service、格式化渲染
hooks/services(业务层) → 只做：业务规则、流程编排、副作用封装、外部通信
stores(状态层) → 只做：领域状态增删改查、派生计算
Tauri/IPC(基础设施层) → 只做：与操作系统/后端进程/文件系统的交互
```

- **上调下，下不调上，禁止跳层**。组件不写业务逻辑、不直连 IPC 拼请求；`services/` 不写 JSX；`stores/` 不写网络请求；`hooks/` 不直连 Rust 命令（经 `services/` 封装）。
- 组件只通过 `hooks/` 或 `stores/` 拿数据，不直接 `fetch`、不直接 `invoke` Tauri 命令。
- 共享类型（事件枚举、Task 状态、API 路径常量）一律沉淀在 `packages/shared/ts`，前端与后端解耦引用，不在 `services/` 内重复定义。

## 六、可排查日志（前端补强）

**没有日志落盘，就没有可维护的前端。** 浏览器/WebView 没有文件系统落盘能力，必须用 Tauri 命令把日志写到 `logs/`。

### 必须存在

- 前端必须有**统一日志出口**：开发期打到 DevTools console 便于调试；生产期通过 Tauri 命令（Rust 侧）写入 `logs/`（与后端日志目录约定一致，如 `logs/desktop.log`）。
- **禁止**散用 `console.log` 当作系统日志、禁止只弹 toast/alert 提示错误。所有错误、关键状态变更、IPC 调用结果都必须经统一日志出口，由 Rust 侧落盘。
- 日志目录如需忽略提交，必须保留 `.gitkeep` 或 README，说明运行后日志写到哪里。

### 必须记录

- 应用启动、窗口创建、Tauri 命令注册结果（不得输出 secret 原文）。
- 用户操作入口：时间、模块（组件名）、操作名（如"创建任务""取消任务"）、task_id。
- 外部依赖调用：API 路径、操作名、耗时、状态码/错误码、失败原因（HTTP / SSE / Tauri invoke 均算）。
- 异常路径：异常类型、错误信息、堆栈、task_id、可重试状态。
- 关键状态变更：任务创建/运行/完成/失败/取消、SSE 连接建立/中断/重连、审批请求渲染、IPC 调用成功/失败。

### 禁止记录

- 明文密码、API Key、Token、Cookie、身份证号、银行卡、完整手机号等敏感信息。
- 大体积原始请求/响应、二进制内容、无边界循环日志。
- 只有"失败了""error"但没有上下文、堆栈或定位线索的无效日志。

### 实现要求

- 优先使用项目既有日志封装（前端 `lib/logger.ts` + Tauri 命令），不手写散落的 `console.log` 当系统日志。
- 日志必须分级：至少 `info` / `warn` / `error`；调试日志不得污染生产默认输出。
- 错误处理不能只 `toast` 给用户，必须同步经统一出口写日志；空 `catch` 和只吞错误都禁止。
- SSE 断流、IPC 调用失败、审批超时等前端特有异常路径，必须产生可排查日志。
- 日志写入失败（如 Tauri 命令异常）不能导致主流程静默失败，至少回退到 console 并标 `error`。

## 七、Agent 编码纪律（前端落地）

**动手前**：看 `apps/desktop/src` 实际结构和约定 → 搜已有相似组件/hook/service → 确认可用依赖（shadcn/Radix/TanStack/zod）→ 理解需求边界（对照 `docs/desktop-client-development-plan.md` 的 must/preserved/non-goal 三类边界）。

**编码时**：一个文件只写一个职责；写到一半发现要加不相关的东西 → 新建文件；目录结构不清晰就同步拆分；能用生态库解决就用库；遵循项目已有风格；新增/修改导出函数时同步维护完整 TSDoc；新增可运行入口、IPC 调用或异常路径时同步补日志。

**交付前自检**：
```
□ 每个文件能否用一句话（不含"和"）描述职责？
□ 是否已搜索代码库/标准库/生态库，确认无重复实现？
□ 是否在已有文件中加了不属于其职责的代码（如组件里写 SSE 解析）？
□ 是否需要拆分组件/hook/store 来保持结构清晰？
□ 是否有跨层调用（组件直连 IPC、service 写 JSX）？
□ 每个导出函数/组件是否都有完整且与当前实现一致的 TSDoc（含 lib/ 纯函数）？
□ 错误处理是否完整（无空 catch）？边界情况是否考虑（IPC 失败/SSE 断流/审批超时）？
□ 新依赖是否必要且锁定版本？是否引入了被禁止的 UI 体系？
□ 是否有注释掉的旧代码或无用代码？
□ 系统是否有明确日志文件路径（前端经 Tauri 落盘到 logs/）？
□ 新增失败路径是否写入 error 日志，并包含定位所需上下文（task_id/堆栈）？
□ 日志是否避免输出 secret 和敏感个人信息？
□ 共享类型是否沉淀在 packages/shared，未在本处重复定义？
```

## 八、开发-审查-测试闭环（前端补强）

**Agent 不能既当开发又当裁判。** 开发完成后，必须启动独立的审查 Agent 和测试 Agent，形成闭环验证（流程与后端规范第八节一致）。

### 审查 Agent 职责（客户端视角）

- 对照本规范与后端规范逐条检查（单一职责、目录结构、复用、防膨胀、TSDoc、分层、日志、禁止行为）。
- 重点检查：组件/hook/store 职责是否清晰、是否存在重复实现、是否有跨层调用（组件直连 IPC）、TSDoc 是否完整且同步（含 `lib/` 纯函数）、错误处理是否完整、日志是否经 Tauri 落盘且可定位问题、共享类型是否沉淀在 `packages/shared`。

### 测试 Agent 职责（前端补强）

- 用 **Vitest** 跑 `hooks/` 与 `services/` 的纯逻辑单测；用 **Testing Library** 做必要组件渲染测试。
- 检查边界情况覆盖：空值、越界、并发、异常路径（IPC 失败、SSE 断流、审批超时、回放去重/幂等）。
- 涉及错误处理、IPC 调用或外部依赖失败时，**必须验证日志会产生可排查记录**（经统一日志出口落盘）。
- 输出：通过 / 不通过 + 失败用例和错误信息。

### 规则

- 审查 Agent 和测试 Agent **必须独立启动**，不能是开发 Agent 本身或同一上下文。
- 开发 Agent **不得自行宣布"代码完成"**——必须有审查 Agent 和测试 Agent 的通过结论。
- 修复后**必须重新跑**审查 + 测试，不能"相信已经修好了"就跳过。
- 循环次数不设上限——有问题就修，修完再验，直到通过。

## 九、禁止行为（前端专属）

| 禁止 | 原因 |
|------|------|
| 一个组件堆完所有 UI + 逻辑 | 违反单一职责 |
| 组件里直连 IPC（`invoke`）或直连 `fetch` | 违反分层，业务泄漏到表现层 |
| 目录结构长期不拆分、不整理 | 职责边界会继续混乱 |
| 手写 shadcn/Radix/TanStack/zod 已有功能 | 重复造轮子 |
| 先堆代码承诺之后重构 | 以后不会重构 |
| 不看已有组件就开始写 | 重复已有逻辑、风格不一致 |
| `Common/Helper/Misc/Utils` 命名组件或 hook | 变成垃圾桶 |
| 空 catch 块 | 吞错误，无法定位 |
| 导出函数/组件没有 TSDoc（含 `lib/` 纯函数） | 无法快速理解职责、参数、返回值和副作用 |
| 修改函数后不更新 TSDoc | 文档误导后续维护 |
| 没有日志落盘或只用 `console.log`/toast 当系统日志 | 出问题后无法复盘 |
| 错误日志没有上下文或堆栈 | 不能定位根因 |
| 日志输出 secret 或敏感个人信息 | 安全事故 |
| 跨层调用（组件→IPC、service→JSX） | 违反分层 |
| 引入依赖不锁版本 | 构建不可复现 |
| 引入 Ant Design / MUI 作为主 UI 体系 | 与 `docs/ui-guidelines.md` 决议冲突 |
| 在 `services/` 内重复定义 `packages/shared` 已有类型 | 双源真理，易漂移 |
| 注释掉旧代码不删除 | 版本工具会记住历史 |
| **开发 Agent 自己宣布代码完成** | 既当开发又当裁判 |

---

> **一个文件一个职责，不靠行数靠职责判定。**
> **目录随职责演化持续拆分，不看代码也能看懂能力模块。**
> **导出函数/组件必须有完整 TSDoc，代码变了文档也要变（`lib/` 纯函数同样强制）。**
> **能复用生态库就不手写，shadcn/Radix/TanStack/zod 站在巨人肩上。**
> **没有日志落盘（经 Tauri 写 logs/），就没有可排查前端。**
> **组件不直连 IPC，分层：组件→hooks/services→stores→Tauri/IPC。**
> **写完不自验，审查测试闭环过。**
