# 目录组织规范（backend/app）

> 本规范是《Agent 代码开发规范》在 `apps/backend/app` 目录结构上的具体落地。
> 第一章定义整个项目的**单向依赖方向契约（总纲）**，后续每一章描述一个顶层目录的
> 契约与当前状态。每章均含「职责 / 子目录与关键文件 / 依赖方向 / 被谁依赖 / 当前偏差」。
> 标注「当前偏差」处为与契约不符、待修复项，属代码现状而非规范目标。

## 第一章 项目整体依赖方向契约

### 1.1 分层与方向（总纲）

后端自上而下分层，依赖**单向**、禁止反向或跳层：

```
api/          ──▶  core/  +  service/        （api 只依赖 core 与 service，不直接触 storage/tools）
core/         ──▶  service/  +  tools/  +  models/  +  config/  +  trace_infra/
service/      ──▶  storage/  +  models/  +  config/  +  trace_infra/  +  utils/
storage/      ──▶  models/  +  utils/         （数据层最底层）
tools/        ──▶  config/  +  models/  +  utils/  +  trace_infra/   （不依赖 service）
models/       ──▶  utils/  +  trace_infra/    （共享值对象地基，不依赖任何编排层）
config/       ──▶  models/  +  utils/         （轻量配置层，不依赖 storage/trace_infra/service/core）
utils/        ──▶  (leaf：零依赖)
trace_infra/  ──▶  (leaf：零依赖)
```

### 1.2 契约要点

1. **方向唯一**：上层依赖下层，下层绝不反向依赖上层；禁止跳层（如 `api` 直接 import `storage` 或 `tools`）。
2. **`models/` 是共享值对象地基**：被所有层共用，自身仅允许依赖 `utils/` 与 `trace_infra/` 两个更底层原语，禁止依赖任何编排层。
3. **`utils/` 与 `trace_infra/` 是纯 leaf**：零 `app.*` 依赖。
4. **`config/` 保持轻量**：仅依赖 `models/` + `utils/`，不向下耦合 `storage/` 或 `trace_infra/`（日志落盘所需的 `LogStore`/脱敏应经上层注入或下沉到 `utils/`）。
5. **`tools/` 是 `core` 依赖的下层**（契约/执行收口），不依赖 `service`；工具契约自包含于 `schemas/` 与 `tool_models/`。
6. **`storage/` 处于最底层**：只被 `core/`/`service/`/`api/`/`config/` 依赖，不得反向 import 编排层。
7. **`core/llm/`** 为 LLM 适配（属 core 的 Agent 相关基础设施），仅依赖 `app.models.runtime_message` 与 `app.tools.schemas`（外加 `app.config.settings` 读配置）。

### 1.3 循环依赖红线

禁止出现以下环，跨层 import 必须先确认方向，出现环即违规：

- `service↔storage`、`core↔service`、`core↔storage`（跳层）、`tools→service`、`models→编排层`、
  `config→storage`、`config→trace_infra`（配置层下沉）、`api→storage`、`api→tools`（跳层）。

## 第四章 models/（共享值对象地基）

### 4.1 职责
业务层值对象（dataclass / 枚举 / TypedDict），承载与编排无关的持久化/运行时数据结构。

### 4.2 子目录与关键文件
平铺、无子目录，一文件一 model：

| 文件 | 主对象 |
|------|--------|
| `log_entry_record.py` | `LogEntryRecord` |
| `log_query.py` | `LogQuery` / `LogSortOrder` |
| `log_query_result.py` | `LogQueryResult` |
| `runtime_message.py` | `RuntimeMessage` |
| `run_record.py` | `RunRecord` |
| `task_record.py` | `TaskRecord` |
| `turn_record.py` | `TurnRecord` |
| `trace_context.py` | `TraceContext` |
| `trace_event_record.py` | `TraceEventRecord` |
| `trace_span_record.py` | `TraceSpanRecord` |
| `workspace_record.py` | `WorkspaceRecord` |

### 4.3 依赖方向
- **允许**：`utils/`（to_text）、`trace_infra/`（ids）、包内互引。
- **禁止**：`api` / `core` / `service` / `storage` / `tools` / `config`（当前合规，0 处编排层 import）。
- **白名单**：`models` 仅可依赖 `utils` + `trace_infra` 两个底层原语。

### 4.4 被谁依赖
所有编排层（`storage` / `service` / `core` / `config` / `api`）均单向依赖 `models`。

### 4.5 命名规范（强制）

`models/` 是共享值对象地基，命名与封装遵循以下铁律，供审查 Agent 逐条核验：

1. **一个文件一个类（或一组强相关值对象）**：文件名必须与主值对象同名，且只承载一个主类。
   - 合格：`task_record.py` → `TaskRecord`；`trace_event_record.py` → `TraceEventRecord`。
   - 不合格：`models.py`（堆多个不相关 Record）、`factory.py`（工厂/适配逻辑混入值对象层）。
   - 例外：仅当一组值对象是同一概念的变体（如 `LogQuery` 与 `LogSortOrder`、枚举与其值对象），允许同文件平铺，但文件名须取共同主题名（如 `log_query.py`）。
2. **方法与变量尽量封装进类**：值对象相关的行为（构造、转换、校验、比较、序列化）优先写成类的**方法或 `@staticmethod`**，避免模块级散落函数操作另一个类的实例。
   - 合格：`RuntimeMessage.to_langchain()`（行为随类走）、`TaskRecord.mark_done()`（状态变更进类内）。
   - 不合格：`def to_langchain(msg: RuntimeMessage)` 游离在类外、`status` 字段被外部到处直接赋值。
   - 纯函数式值对象（dataclass）也应把"围绕该值的操作"收进类，保持"文件只承载一个类"的纯度。
3. **禁止非值对象逻辑**：`models/` 不得放服务、适配（LLM 桥接）、工厂、helper、常量聚合或 I/O。
   - 适配/工厂类（如 `build_chat_model`、`runtime_to_langchain`）属 `core/llm/`，不得放入 `models/`。
   - 跨层转换（ORM↔Record）属 `storage/crud/`，不得放入 `models/`。
4. **不可变优先**：值对象默认 `frozen=True`（dataclass）或 `@dataclass(frozen=True)`，确需可变时显式注释原因。枚举用 `StrEnum`（Python 3.11+）。
5. **聚合导出用相对导入**：`models/__init__.py` 仅做 `from .X import Y` 收口，不承载逻辑。

### 4.6 当前偏差
- **D7**：`models/factory.py` 与 `models/langchain_bridge.py` 为 0 字节空文件（本属 `core/llm` 职责），应删除（违反 4.5 第 3 条）。
- 建议：包内聚合导出（`__init__.py`）改用相对导入 `from .X import`。

### 7.5 工具契约约定（强制）

`ToolDefinition` 是工具契约的**单一事实来源**，模型可见结构一律由其投影，禁止平行类：

1. **模型投影统一走方法**：面向模型的工具结构（name / description / parameters_schema）统一由
   `ToolDefinition.to_model_tool_definition()` 投影，返回 `dict[str, Any]`，不得另定义
   `ModelToolDefinition` 之类平行值对象类（已决议移除，见 D3）。
2. **上层直接消费 `ToolDefinition`**：`core/llm/langchain_bridge.model_tools_to_langchain` 接收
   `list[ToolDefinition]`，**内部**调用 `to_model_tool_definition()` 投影后转 OpenAI 函数 schema；
   不得要求调用方预先转换或持有独立的模型工具类型。
3. **投影是 `ToolDefinition` 的方法而非模块函数**：围绕工具契约的派生/转换行为收进 `ToolDefinition`
   类内（符合第四章 4.5「方法尽量封装进类」），不在 `schemas/` 外散落转换函数。

领域服务编排层，只承载 `xxx_service` / `xxx_recorder` 等编排类，协调 storage CRUD、组装跨实体用例（级联删除、任务+首轮次原子创建）。不直接写 SQL、不承载 model/原语。

### 8.2 子目录与关键文件
| 位置 | 主类 | 做什么 |
|------|------|--------|
| `task/task_service.py` | `TaskService` | 任务创建（含首轮次原子创建）、状态管理 |
| `task/turn_service.py` | `TurnService` | 轮次创建/查询/状态更新 |
| `task/workspace_service.py` | `WorkspaceService` | 工作区 + 级联删除 |
| `trace/query_service.py` | `TraceQueryService` | 组合 TraceStore 与 JSONL 日志查询 |
| `trace/recorder.py` | `TraceRecorder` | trace event/span 写入门面（脱敏、canonical 名） |

### 8.3 依赖方向
- **允许**：`storage/`、`models/`、`utils/`、`config/`、`trace_infra/`。
- **禁止**：`core` / `api` / `tools`（当前合规，0 处）。

### 8.4 被谁依赖
`api/`、`core/`（core 对 `tool_execution` 的引用为悬空，见 D2）。

### 8.5 当前偏差
- **D7**：`service/task/records.py` 为 0 字节空文件（Record 已迁出），应删除。
- 业务 Record 已迁至 `app/models/`（合规），`service/models` 子目录已不存在。

| `runtime/runner.py` | `AgentRuntime` | 任务生命周期总控 |
