## 第一章 项目整体依赖方向契约

### 1.1 分层与方向（总纲）

后端自上而下分层，依赖**单向**、禁止反向或跳层：

```
api/          ──▶  core/  +  service/        （api 只依赖 core 与 service，不直接触 storage/tools）
core/         ──▶  service/  +  tools/  +  models/  +  config/  +  trace_infra/
service/      ──▶  storage/  +  models/  +  config/  +  trace_infra/  +  utils/  +  tools/   （tool_execution 编排 tools，合法）
storage/      ──▶  models/  +  utils/         （数据层最底层）
tools/        ──▶  config/  +  models/  +  utils/  +  trace_infra/   （不依赖 service）
models/       ──▶  utils/  +  trace_infra/    （共享值对象地基，不依赖任何编排层）
config/       ──▶  models/  +  utils/  +  storage/  +  trace_infra/   （通用轻量配置层；config/logging/ 聚合特例允许依赖 storage/trace_infra，不计入偏差）
utils/        ──▶  (leaf：零依赖)
trace_infra/  ──▶  (leaf：零依赖)
observability/──▶ service/ + tools/ + models/ + trace_infra/ + utils/   （core 子包，Langfuse 三方依赖唯一收口；core→service 为合法方向）
```

### 1.2 契约要点

1. **方向唯一**：上层依赖下层，下层绝不反向依赖上层；禁止跳层（如 `api` 直接 import `storage` 或 `tools`）。
2. **`models/` 是共享值对象地基**：被所有层共用，自身仅允许依赖 `utils/` 与 `trace_infra/` 两个更底层原语，禁止依赖任何编排层。
3. **`utils/` 与 `trace_infra/` 是纯 leaf**：零 `app.*` 依赖。
4. **`config/` 通用保持轻量**：仅依赖 `models/` + `utils/`；但 `config/logging/` 作为日志子系统聚合包属明确特例，允许依赖 `storage/`（LogStore 落库）与 `trace_infra/`（脱敏），不计入偏差。
5. **`tools/` 是 `core` 依赖的下层**（契约/执行收口），**不基于 LangGraph**；不依赖 `service`，工具契约自包含于 `schemas/` 与 `tool_models/`。
6. **`storage/` 处于最底层**：只被 `core/`/`service/`/`api/`/`config/` 依赖，不得反向 import 编排层。
7. **`core/llm/`** 为 LLM 适配（属 core 的 Agent 相关基础设施，基于 **LangChain**，是 LangGraph 的硬依赖基座），为 LangGraph 节点提供 chat model 与工具 schema；主要依赖 `app.models.runtime_message` 与 `app.tools.schemas`（外加 `app.config.settings` 读配置）。`core` 整体属于 LangGraph 体系。

### 1.3 循环依赖红线

禁止出现以下环，跨层 import 必须先确认方向，出现环即违规：

- `service↔storage`、`core↔service`、`core↔storage`（跳层）、`tools→service`、`models→编排层`、
  `config→storage`、`config→trace_infra`（配置层下沉；**`config/logging/` 聚合特例豁免**）、`api→storage`、`api→tools`（跳层）。
- `config→core` / `config→tools`：`config/configuration.py` 装配点存在该依赖（见 D14，待定性）；其余 config 模块不得反向依赖编排层。

### 4.5 命名规范（强制）

`models/` 是共享值对象地基，命名与封装遵循以下铁律，供审查 Agent 逐条核验：

1. **一个文件一个类（或一组强相关值对象）**：文件名必须与主值对象同名，且只承载一个主类。
   - 合格：`task_record.py` → `TaskRecord`；`mapped_log_record.py` → `MappedLogRecord`。
   - 不合格：`models.py`（堆多个不相关 Record）、`factory.py`（工厂/适配逻辑混入值对象层）。
   - 例外：仅当一组值对象是同一概念的变体（如 `LogQuery` 与 `LogSortOrder`、枚举与其值对象），允许同文件平铺，但文件名须取共同主题名（如 `log_query.py`）。
2. **方法与变量尽量封装进类**：值对象相关的行为（构造、转换、校验、比较、序列化）优先写成类的**方法或 `@staticmethod`**，避免模块级散落函数操作另一个类的实例。
   - 合格：`RuntimeMessage.to_langchain()`（行为随类走）、`MappedLogRecord.from_record()`（映射进类内）。
   - 不合格：`def to_langchain(msg: RuntimeMessage)` 游离在类外、`status` 字段被外部到处直接赋值。
   - 纯函数式值对象（dataclass）也应把"围绕该值的操作"收进类，保持"文件只承载一个类"的纯度。
3. **禁止非值对象逻辑**：`models/` 不得放服务、适配（LLM 桥接）、工厂、helper、常量聚合或 I/O。
   - 适配/工厂类（如 `build_chat_model`、`runtime_to_langchain`）属 `core/llm/`，不得放入 `models/`。
   - 跨层转换（ORM↔Record）属 `storage/crud/`，不得放入 `models/`。
4. **不可变优先**：值对象默认 `frozen=True`（dataclass），确需可变时显式注释原因。枚举用 `class X(str, Enum)` 形态（当前 `EventType` / `TurnStatus` 手写 `__str__` 返回 `self.value` 以兼容 pydantic 序列化，非 `enum.StrEnum`；若后续确认可移除手写 `__str__`，可迁移至内置 `StrEnum`）。
5. **聚合导出**：`models/__init__.py` 仅做 import 收口，不承载逻辑。

### 7.5 工具契约约定（强制）

`ToolDefinition` 是工具契约的**单一事实来源**，模型可见结构一律由其投影，禁止平行类：

1. **模型投影统一走方法**：面向模型的工具结构（name / description / parameters_schema）统一由
   `ToolDefinition.to_model_tool_definition()` 投影，返回 `dict[str, Any]`，不得另定义
   `ModelToolDefinition` 之类平行值对象类（已决议移除，见 D3 归档）。
2. **上层直接消费 `ToolDefinition`**：`core/llm/langchain_bridge.model_tools_to_langchain` 接收
   `list[ToolDefinition]`，**内部**调用 `to_model_tool_definition()` 投影后转 OpenAI 函数 schema；
   不得要求调用方预先转换或持有独立的模型工具类型。
3. **投影是 `ToolDefinition` 的方法而非模块函数**：围绕工具契约的派生/转换行为收进 `ToolDefinition`
   类内（符合第四章 4.5「方法尽量封装进类」），不在 `schemas/` 外散落转换函数。
4. **路径安全统一收口**：文件类工具（读/写/补丁/搜索/列目录/删除）的路径解析一律委托
   `tool_handler/security/project_path.ProjectPathResolver`，不得内联路径规则；workspace 外
   写/删由 path_escape 天然强制拒绝。
5. **内置工具继承 HandlerBase**：全部 9 个内置工具 handler 继承 `tool_handler/tool_base.HandlerBase`，
   声明类级元数据并实现 `execute`/`to_definition`；新增内置工具须遵循同一范式。
6. **分级隔离声明**：`ToolDefinition.execution_mode` 声明隔离策略——`process` 仅用于 execute_terminal
   等需 OS 级隔离（硬超时强杀）的工具，其余默认 `thread`（当前线程直跑、无子进程开销但无硬超时强杀）。
