一、结论先行
这次黑盒发现的四类问题里：

不算缺陷：after_seq/幂等/边界/容量/生命周期回收等，源码行为与观测一致（上一轮我记的"历史不驱逐"实为误解：会话有 1MB 环形缓冲上限 + sweeper，见 constant.py 的 MAX_RING_BUFFER_BYTES / DEFAULT_MAX_LIFETIME_SECONDS 与 terminal_session_service._on_output 的 popleft 驱逐，2000 行只约 140KB 未触顶）。
真正的缺口主要是"工具描述"：模型无法从描述得知几条关键约束（会话只活一轮、Windows 上 signal 不可用、输入不解码转义、输出含 ANSI、Unicode 输入可能被丢）。
Unicode 丢字符主要是"宿主行为"，代码只能加护栏：根因在 Windows PowerShell 的控制台输入路径，不在本仓的 Python/Rust 编解码。
所以建议是：描述为主、代码为辅。

二、逐项方案
1. Unicode 输入静默丢字符（符号/emoji）
链路与证据（源码）：terminal_session/write.py::encode_terminal_input 只做 data.encode("utf-8")；terminal_session_service.write 透传 bytes；worker.py::write 走 base64 控制帧；Rust terminal-worker/src/worker.rs → pty.rs::write → write_all 写 ConPTY。整条链全程 UTF-8、无过滤。

建议：

描述（主）：在 descriptions.py（describe_terminal_tool）里，对 system == "Windows" 增加一句"通过 PowerShell 会话输入时，符号/emoji 等非 ASCII 字符可能被丢弃；如需这类字符，请在 shell 内运行期生成（如 [char]0x2605/printf），不要直接键入；文本为主的交互优先用 cmd 会话"。这是零风险、对模型最有效的改进。
代码（辅，可选护栏）：在 write.py 增加"输入含可能被当前会话丢弃的非 ASCII 字符"的检测+告警（结构化日志 + 在 ToolObservation 里附一条 note），不拒绝调用。不建议试图在 service/sidecar 层"修复"——根因在 shell，改本仓无法保证效果。
2. 会话生命周期只活一轮（未在描述声明）
源码事实：terminal_session_service.start 记录 run_id；conversation_run_executor 在 run 结束的 finally 调 _close_run_terminals(run_id, ...)（cancel 路径也会）；initialize 注释明确"活终端不跨 backend 重启恢复"。这解释了"上一轮会话在下一轮变 NOT_FOUND"。

建议：描述。在 terminal_start 的描述（start.py / descriptions.py）注明"session 生命周期限于当前 Run；跨用户轮次需重新 terminal_start"，避免模型复用失效的 session_id。

3. terminal_signal 在 Windows 不可用（描述已覆盖，可再补输入法）
源码事实：Windows worker capabilities() 只返回 pty_io/terminal_query_dsr（worker.rs），故 signal 走"unsupported"分支；descriptions.py 已对 Windows 说明"不要用 terminal_signal，改用 terminal_write"。这部分描述已经是对的。

唯一可补：实测中断需要真实 ETX(0x03) 字节（terminal_signal 不支持、\u0003 字面不解码），而当前描述只说不解码、未点明"如何中断"。建议在 terminal_write 描述补一句"要中断长命令，可在 data 中直接放入控制字符 0x03（不要写成 \u0003）"。

4. terminal_read 输出含 ANSI（描述未提）
源码事实：read 返回的是 PTY 原始字节经 UTF-8（replacement）解码，含 PSReadLine 重绘/OSC 等控制序列。

建议：描述。read.py 描述补"输出为原始终端流，含 ANSI 控制序列"，提示模型按需清洗。
