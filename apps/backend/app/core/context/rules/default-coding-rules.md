# 默认代码开发规则

本文件是 coding agent 默认注入 system prompt 的代码开发规则。它不是项目规范全文，而是模型执行代码任务时必须优先遵守的高频约束。

目标：写出正确、可排查、职责清晰、可维护、可验证的代码；避免为了快速完成功能而堆积技术债。

优先级：正确性 > 可排查性 > 复用成熟能力 > 单一职责 > 目录边界清晰 > 可读性 > 改动聚焦 > 性能。

---

## 1. 执行总则

- 修改前先理解现有结构、职责边界、调用链、命名风格和测试方式。
- 只做当前任务需要的最小改动，不牵连无关代码、不做顺手重构。
- 不把猜测当事实；涉及代码行为、配置、边界条件时，以源码、测试和工具输出为准。
- 遇到冲突时，优先保持项目既有架构、分层、导入方向、日志规范和工具链约定。
- 不能验证时，必须说明已完成内容、未验证原因和剩余风险。

## 2. 单一职责

- 一个文件只承担一个清晰职责；职责按“它为什么存在”判断，不按行数判断。
- 如果一个文件需要同时描述“路由、业务逻辑、SQL、外部调用、格式化输出”等多个职责，应拆分。
- 函数超过 60 行、参数超过 5 个、嵌套超过 3 层时，必须检查是否需要拆分。
- 职责边界变清晰时同步调整目录或文件，不等待“以后整理”。
- 禁止使用 `Utils`、`Helper`、`Common`、`Misc`、`Manager` 等模糊命名，除非项目已有明确约定。

## 3. 不重复造轮子

写非 trivial 逻辑前，必须先判断是否已有成熟能力可复用，而不是直接手写。

依次检查：

1. **代码库**：项目内是否已有相同或相似实现？有则复用、扩展或收敛，避免平行实现。
2. **已有依赖**：项目已安装依赖是否提供该能力？优先直接使用。
3. **标准库/框架内置能力**：语言、框架或运行时是否已内置？优先使用内置能力。
4. **新增外部依赖**：只有当能力属于通用复杂能力，且前三者都不合适时，才评估引入成熟、广泛使用的外部库。

补充约束：

- 编辑器、图表、拖拽、富文本、表单校验、日期处理、Markdown 渲染等通用复杂能力，优先评估成熟外部库。
- Agent Runtime、Workflow、ToolDefinition、权限审批、checkpoint 语义等项目核心领域能力，优先保持项目内清晰建模，不轻易交给外部库接管。
- 重复逻辑出现 3 次以上，按 Rule of Three 提取公共函数或公共模块。
- 新依赖必须锁定版本；引入前评估维护活跃度、体积、许可证和与现有技术栈的契合度。
- 选择自实现时，必须在代码或交付说明中说明原因。

## 4. 防止代码膨胀

每次修改文件前先判断：

- 新功能是否属于该文件原职责；不属于则新建或选择合适文件。
- 当前修改是否让文件承担新职责；是则先拆分再实现。
- 是否只是继续 append 而没有审视结构；是则先收敛结构。

编码时遵守：

- 每次修改都让代码不更差。
- 不写“先堆上，之后再重构”的临时代码。
- 注释只解释为什么这样做，不重复解释代码已经表达清楚的内容。
- 大段注释用于解释复杂逻辑时，优先考虑重构命名、拆函数或拆模块。
- 不保留注释掉的旧代码；版本控制已经保存历史。

## 5. 函数文档

- 每个函数和方法必须有完整 docstring，并随实现变更同步更新。
- docstring 必须描述当前真实行为，至少覆盖：目的、参数、返回值、异常或失败状态、重要副作用。
- 不写“处理数据”“执行逻辑”这类无信息描述。
- 如果 docstring 难以写清，通常说明函数职责不清或命名不准，应先调整实现结构。

## 6. 分层架构

默认分层方向：

```text
表现层 -> 输入校验、调用业务层、格式化输出
业务层 -> 业务规则、流程编排
数据层 -> 增删改查、数据映射
基础设施层 -> 外部系统交互
```

规则：

- 上层可以调用下层，下层不能反向调用上层。
- 禁止跳层调用；发现跳层时，优先通过现有 service、runtime、tool 或 storage 边界收口。
- 不在表现层写业务规则，不在数据层写流程编排，不在模型值对象中写运行时调度逻辑。
- 新增模块时，目录名应表达能力边界，而不是表达临时实现细节。

## 7. 可排查日志

系统行为必须可复盘。新增关键路径、异常路径、外部调用或状态变更时，应同步补充日志。

必须记录：

- 启动/关闭、关键配置加载结果，但不得输出 secret。
- 用户请求、任务入口、操作名、请求 ID、任务 ID、trace ID 等定位信息。
- 外部依赖调用的目标服务、操作名、耗时、状态码和失败原因。
- 异常类型、错误信息、堆栈和关键上下文。
- 创建、更新、删除、权限变更等关键状态变更。

禁止记录：

- 明文密码、API Key、Token、身份证号、银行卡、完整手机号等敏感信息。
- 大体积原始请求/响应、二进制内容。
- 只有“失败了”或“error”但没有上下文、堆栈或定位线索的无效日志。

实现要求：

- 使用项目现有日志框架，不用散落的 `print` 充当系统日志。
- 错误处理必须保留异常上下文；禁止空 `catch` / 空 `except`。
- 后台任务、定时任务、CLI 脚本与 Web/API 一样需要可排查日志。
- 日志写入失败不能让主流程静默失败。

## 8. 交付前自检

交付前至少检查：

- 每个被修改文件是否仍能用一句话描述职责。
- 是否已经查过现有实现、已有依赖和标准库能力。
- 是否引入了不属于当前文件职责的代码。
- 是否存在跨层调用或业务逻辑泄漏。
- 新增或修改的函数 docstring 是否完整且与实现一致。
- 异常路径是否可诊断，是否有必要日志。
- 新依赖是否必要、锁定版本，并已说明原因。
- 是否删除了注释掉的旧代码和临时调试代码。
- 是否运行了与改动相关的测试、lint 或类型检查；不能运行时是否说明原因。

## 9. 禁止行为

| 禁止 | 原因 |
|---|---|
| 不看已有代码就开始写 | 容易重复实现、破坏风格和边界 |
| 一个文件堆完多个职责 | 违反单一职责，后续难维护 |
| 目录边界混乱仍继续追加代码 | 职责会持续失控 |
| 手写标准库或成熟库已有能力 | 重复造轮子 |
| 手写编辑器、图表、拖拽等通用复杂组件 | 维护成本高，已有成熟方案 |
| 为了显得高级引入抽象 | 增加理解成本和变更成本 |
| 跨层调用 | 破坏架构边界 |
| 空 `catch` / 空 `except` | 吞掉错误，无法定位 |
| 日志输出 secret | 安全风险 |
| 函数无 docstring 或 docstring 失真 | 误导维护者 |
| 引入依赖不锁版本 | 构建不可复现 |
| 写完不验证 | 交付没有闭环 |

---

一句话规则：先理解现有系统，再复用成熟能力；保持单一职责和清晰分层；异常可诊断，改动可验证。
