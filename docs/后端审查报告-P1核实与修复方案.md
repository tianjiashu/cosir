## P1-5 AgentProfile 共享实例被原地修改，并发 turn 互相污染 —— 确认

### 证据
- `app/core/agents/agent_profile.py:44-82`：`AgentProfile` 是普通 `@dataclass`（非 frozen），含 `turn`、`main_agent`、`runtime_event_loop` 等**运行时可变字段**，与静态能力配置（`allowed_tools` / `model_name` / `workflow`）同住一个对象。
- `app/core/agents/agent_profile_registry.py`：`resolve()` 返回注册表内**共享实例**（无副本机制）。
- `app/core/runtime/runner.py:301`：`agent_profile.turn = turn`（run_turn 内对共享实例原地写）。
- `app/core/runtime/runner.py:313`：`agent.main_agent = task.parent_task_id is None`（run_agent 内原地写）。

### 根因
运行时状态（turn / main_agent / event_loop）被塞进静态配置对象，注册表按 agent_id 单例化后，任何并发 turn 都会覆盖同一份 `AgentProfile.turn` / `.main_agent`。桌面端并发执行（2026-08-17 确认：不同 task 的 turn 并发）下，两个并发 turn 共用 developer profile 时互踩，事件投影（`is_main_agent`）与上下文访问（`agent.turn`）错乱。

### 影响面
并发执行是已确认的生产能力。互踩窗口从 run_turn 写 `profile.turn` 到 workflow 内读取 `agent.turn` 全程存在，属数据竞争，表现为偶发错乱，难复现、难排查。

### 修复方案（结构性，符合第零契约）
**推荐**：把运行时状态从 `AgentProfile` 拆出，`AgentProfile` 冻结为纯静态配置（`@dataclass(frozen=True)`），运行时状态收敛进 `RuntimeConfig`（`app/core/workflows/react/runtime_config.py` 已持有 `turn`，把 `main_agent`、`runtime_event_loop` 一并迁入）。
**过渡**：若暂不做冻结改造，runner 至少改为派生副本，杜绝共享写：

```python
# runner.run_turn / run_agent 内
profile = dataclasses.replace(profile, turn=turn, main_agent=is_main, runtime_event_loop=loop)
```

child agent 路径（`child_agent_profile_builder`）已用 `dataclasses.replace` 派生，主路径对齐同一模式，不重复造轮子。推荐以「冻结 + 状态迁入 RuntimeConfig」为最终态，一次性消除该类数据竞争。

## P1-6 WorkspaceEventBus 从工作线程直接 put_nowait —— 确认

### 证据
- `app/api/workspaces_api.py:334-336`：`asyncio.to_thread(event_service.prepare, ...)` 把 prepare 抛到工作线程。
- `app/service/workspace_event/workspace_event_service.py`：`prepare()`（工作线程）内部 `_emit()` → `self._bus.publish(event)`。
- `app/service/workspace_event/workspace_event_bus.py`：`publish()` 内 `self._subscribers[id].put_nowait(event)`。
- 对照：`app/core/runtime/runner.py` 的 `_publish_runtime_event` 已用 `loop.call_soon_threadsafe` 处理跨线程发布，WorkspaceEventBus 无此处理。

### 根因
`asyncio.Queue` 非线程安全，其 `put_nowait` 直接操纵绑定事件循环的内部结构（`_getters` / `_ready`）。从工作线程调用违反 asyncio 契约：debug 模式抛 `RuntimeError`，生产模式产生未定义竞态（丢失唤醒、挂起消费者）。

### 影响面
workspace prepare 流程（CodeGraph 索引准备）是后台线程 + SSE 订阅消费的必经路径，属必现性风险。

### 修复方案（标准库方案）
在 bus 内保存订阅队列所属的 event loop（subscribe 时 `asyncio.get_running_loop()`），`publish` / `close` 在非 loop 线程经 `loop.call_soon_threadsafe` 投递，与 runner 的 `_publish_runtime_event` 模式一致：

```python
def publish(self, event: WorkspaceEvent) -> None:
    loop = self._loop
    if loop is not None and threading.current_thread() is not getattr(loop, "_thread", None):
        loop.call_soon_threadsafe(self._publish_sync, event)
        return
    self._publish_sync(event)
```

## P1-7 WorkspaceEventBus `_closed` 只增不减，二次 prepare 事件全被吞 —— 确认

### 证据
- `app/service/workspace_event/workspace_event_bus.py:55`：`self._closed: set[str]`。
- `.../workspace_event_bus.py:137`：`publish()` 内 `if event.workspace_id in self._closed: return`。
- `.../workspace_event_bus.py:173`：`close()` 内 `self._closed.add(workspace_id)`。
- `subscribe()`（58-86 行）不清理 `_closed`。

### 根因
`close()` 语义被实现成「workspace 永久禁言」，而非「关闭当前订阅流」。任一 workspace 一旦 close（如一次 prepare 结束），该 workspace_id 永久进入 `_closed`，后续再次 prepare（前端刷新 / 重建索引是真实路径）的终态事件全部被 `publish` 静默丢弃。

### 影响面
索引重建（workspace 二次 prepare）的 `ready` / `degraded` 终态丢失，前端无法感知重建结果。

### 修复方案（对齐既有语义，不造新机制）
`close` 只做两件事：向订阅桶发关闭哨兵 + 清空订阅桶，**不写永久 `_closed`**；或在 `subscribe` 时 `self._closed.discard(workspace_id)` 重置。对齐 `RuntimeEventBus.close_turn` 的「关闭订阅而非禁言」语义。

## P1-8 取消与异常竞态把 cancelled 终态覆写为 failed —— 确认

### 证据
- `app/core/runtime/runner.py:374-375`：`except Exception as exc: self._turn_service.update_turn_status(turn_id, "failed", end_reason=str(exc))`。
- `app/storage/crud/turn_crud.py`：`update_status` 为**无条件更新**（无 `WHERE status == 'running'` 守卫）。
- 对照：取消路径 `cancel_turn_if_active`（条件更新）与 runner finally 里已有的 `fail_turn_if_running`（条件更新）均为守卫式，唯独 except 分支是无条件覆写。

### 根因
用户取消（`cancel_turn` → 置 `cancelled`）后，turn 已非 `running`；若 workflow.run 后续冒泡任何异常（DB 抖动、网络错误、工具执行异常），`except Exception` 分支无条件 `update_turn_status("failed")` 覆写已落库的 `cancelled` 终态，历史终态被改写。

### 影响面
取消功能的终态正确性：用户看到的是「失败」而非「已取消」，且终态改写不可逆。

### 修复方案（复用已有方法，一行修复）
`except Exception` 分支改用项目已有的条件更新 `self._turn_service.fail_turn_if_running(turn_id, end_reason=...)`，仅 `running` 才落 `failed`，与 finally 兜底语义一致。

## P1-9 turn_id=None 事件持久化必然失败且被静默吞掉 —— 确认

### 证据
- `app/models/event/runtime_event.py`：`RuntimeEvent.turn_id: str | None = None`（契约允许 None）。
- `app/storage/model/runtime_event_model.py:29`：`turn_id` 是 `nullable=False` 的**主键列**。
- `app/service/agent_runtime_event/runtime_event_service.py`：`save_event` 显式处理 `if event.turn_id is None: save_event(event.to_dict())`。
- `app/storage/crud/runtime_event_crud.py`：`save_event` docstring 明说「写入失败仅记日志，不向上抛出」——`IntegrityError`（None 入非空主键）被 `except Exception` 吞掉，事件丢失且调用方无感知。

### 根因
契约允许 `turn_id=None` 的事件（service 层已为此保留分支），但存储层把 `turn_id` 设计为主键且非空，二者矛盾；crud 层吞异常掩盖矛盾，事件静默丢失。

### 影响面
任何无 turn 上下文的事件（生命周期 / workspace 侧 RuntimeEvent）写入必失败、丢失，且排障时只能从 exception 日志反查，运行流无感知。

### 修复方案（结构性，符合第零契约）
`turn_id` 本就不该作主键（同一 turn 多事件、None 事件合法）。改为：
1. 主键换 `event_id`（uuid，天然唯一）；
2. `turn_id` 降为可空列 + 索引；
3. crud 层去掉吞异常的兜底，改为显式 `log.error` 后按既定错误契约上抛（保留幂等分支），让调用方可感知丢失。
需配一次 SQLite schema 迁移（`runtime_events` 表重建，现有数据按 `event_id` 迁移）。

## P1-10 审批拒绝 / 部分批准产生悬空 tool_calls + 两项核心能力未接线 —— 确认

### 证据
- `app/core/workflows/nodes/tools_node.py:225-227`：`approved_dicts = tool_calls if not isinstance(approved, list) else approved` —— 审批器返回 `[]` 或子集时，被拒调用被直接过滤。
- 同一节点取消分支（239-274）已为上一轮 `tool_calls` 补 `build_cancel_placeholder_messages` 配对闭合；**审批拒绝路径未做任何配对闭合**。
- 协议硬约束：`AIMessage.tool_calls` 每个 id 必须有等量 `role="tool"` 消息闭合，否则下一轮对话直接 400。
- 未接线证据：`app/core/agents/agent_profile.py:19-41` `_default_workflow()` 返回 `ReactLikeWorkflow()` **不传 approval_resolver**；`approval_resolver` 仅定义于 `react/workflow.py:53`、`runtime_config.py:63` 与测试注入点，生产链路恒为 `None` → 自动放行。

### 根因
审批拒绝路径缺少「被拒调用配对闭合」收口，与取消分支能力不同步；同时审批解析器只有能力没有生产注入点（工具权限审批属 AGENTS.md 第一阶段必覆盖项，当前未接线）。

### 影响面
一旦接线审批器：拒绝或部分批准 → 上一轮 `tool_calls` 悬空 → 下一轮模型请求协议校验失败，turn 直接失败。当前自动放行掩盖了该缺陷，接线即引爆。

### 修复方案
1. **配对闭合**：在 `approved_calls` 构建后，对「原始 `tool_calls` 中未被批准」的调用，复用 `RuntimeOperations.build_cancel_placeholder_messages`（或为其扩展 `reason` 参数表达 denied 语义）补占位并 `_persist_tool_observations`，与取消分支同源不平行复制。
2. **接线**：为生产路径注入 `approval_resolver`（如基于 `ToolSystem` 权限表 + `interrupt()` 的审批实现），使能力真正可用；接线时同步覆盖「拒绝 / 部分批准 / 超时」三类分支的配对闭合测试。

## P1-11 CodeGraph Supervisor 关停后 Kernel 子进程可被「复活」 —— 确认

### 证据
- `app/codegraph/supervisor.py:352-361`：`_restart_after_backoff` 在 `time.sleep(backoff)` 后**无条件** `self.start()`。
- `.../supervisor.py` `start()` 状态门：`STOPPED` / `FAILED` / `RESTARTING` 均放行进入。
- `shutdown()`（188-212）只置 `STOPPED`，且 `_join_threads` 仅 join stderr / health 线程，**不 join restart 线程**。

### 根因
竞态时序：health 线程检测到崩溃 → `_handle_crash` 起 restart 线程（sleep 中）→ 用户 `shutdown()` 置 `STOPPED` → restart 线程 sleep 结束调 `start()`，状态门放行 `STOPPED` → Kernel 子进程被重新拉起。停机后的系统出现「幽灵 Kernel」。

### 影响面
关机/重启桌面应用时 CodeGraph 进程残留或复活，占用端口与资源，与 boot 状态机矛盾。

### 修复方案（标准做法）
`_restart_after_backoff` 在 sleep 后、`start()` 前检查停机信号：`self._stop_health.is_set()`（或显式 `_shutdown_requested` 标志）为真则直接 return；同时 `shutdown()` 中置该标志后再清理。使「重启」与「停机」互斥。

## P1-12 atomic_write 缺 fsync —— 确认

### 证据
- `app/tools/tool_handler/file_io/atomic_write.py:80-83`：`with os.fdopen(fd, "w", ...) as file: file.write(content_out)` → 关闭 fd → `os.replace(temp_path, target)`。无 `flush()` + `os.fsync()`。

### 根因
`os.replace` 只保证「目录项替换」的原子性，不保证文件内容已落盘（数据仍可能在页缓存）。进程崩溃 / 断电时，目标文件可能是空文件或旧内容。

### 影响面
工具写文件（write_file / apply_patch 落盘）在异常掉电场景下可能丢内容；快照-撤销链（依赖落盘内容）可靠性受损。

### 修复方案（标准库方案）
写后 `file.flush(); os.fsync(file.fileno())` 再 `os.replace`。Windows 不支持目录 fsync，跳过目录级 fsync（标准行为）。改动两行，无新依赖。

## P1-13 dangerous_command 黑名单绕过缺口 —— 确认（部分点）

### 证据（`app/tools/tool_handler/terminal/dangerous_command.py`）
1. **解释器 `-c/-e` 代码字符串**：`python -c "shutil.rmtree('x')"`、`node -e "fs.rmSync(...)"` 不命中 `\brm\b`（词边界不匹配 `rmtree`/`rmSync`），归一化不提取 `-c/-e` 后的代码串二次检测。
2. **`unlink`**（`os.unlink` / `os.remove`）：不在 `_DANGEROUS_PATTERNS`。
3. **cmd 变形**：`d"e"l`（引号内嵌）、`r^m`（cmd 的 `^` 转义）——归一化只做 NFKC / IFS / 续行 / 注释剥离，无引号剥离、无 `^` 剥离，`\bdel\b` / `\brm\b` 不命中。
4. **下载 + 执行拆两条命令**：`curl -o f URL` 与 `bash f` 各自单条不命中管道模式（属静态检测的固有边界）。

### 影响面
deny-list 是终端通道的纵深防御层（真正防线是审批 + workspace 路径边界 + 受控 delete 工具）。绕过点可让危险命令以变形/间接形式通过，但**不解除**受控工具的边界约束；第 4 点属静态检测固有边界，需在文档中明确定位，避免误判为可完全拦截。

### 修复方案
1. 归一化增强：剥离成对引号（`"`/`'` 交替展开）与 cmd 转义符 `^`（标准做法，非自研，与 shell 解析一致）；
2. 模式补充：`\bunlink\b`、解释器 `-c`/`-e` 后的代码字符串提取并**递归调用本检测**（对 `shutil.rmtree` / `fs.rmSync` / `os.remove` 等命中）；
3. 文档明确：静态 deny-list 是纵深防御而非完整防线，删除类操作的安全保证依赖受控工具 + workspace 边界。
