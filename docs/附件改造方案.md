## 1. 最终职责边界

```text
图片附件：
前端选择图片
  → POST 上传到 workspace/.cosir/Attachment
  → 后端计算 SHA-256
  → asset_id = SHA-256
  → Assistant Transport 发送 image locator

普通附件：
前端选择本地文件
  → 不上传、不复制
  → 输入框显示内联 token
  → 发送前 token 替换为本地文件路径
  → 后端只收到 text
```

后端实际收到的逻辑内容只有：

```text
input text：包含普通附件路径
img：图片 locator 列表
```

在现有 Assistant Transport 中对应为 `text` part 和 `image` part，不再存在 `file` part。

## 2. 图片附件设计

### 文件命名

```text
asset_id = SHA-256(原始图片字节)
```

全部使用小写 64 位十六进制：

```text
cosir-attachment://6f5902ac237024bdd0c176cb93063dc...
```

目录结构：

```text
<workspace>/.cosir/Attachment/
├─ .uploading/.<随机名>.part
├─ .uploading/<sha256>.<source-ext>
├─ <sha256>.<normalized-ext>
└─ <sha256>.source.<source-ext>
```

哈希针对原始上传字节，不受原始文件名、MIME 或模型转换影响。

### 上传流程

修改 `AttachmentService`：

- 删除 SQLite 资产查询。
- 删除 `X-Idempotency-Key`。
- 流式计算 SHA-256。
- Pillow 校验真实图片格式、尺寸和大小。
- 以 hash 查找 workspace 附件目录。
- 同一 workspace 已存在相同 hash 时直接复用。
- 使用原子且不可覆盖的提交方式处理并发上传。
- 图片转换后继续沿用同一个 hash asset ID。

当前代码已经计算 SHA-256，但目前只用于附件表去重。[现有逻辑](H:\coding-agent\apps\backend\app\service\attachment\attachment_service.py:279)

### 内容读取

`GET /tasks/{task_id}/attachments/{asset_id}/content`：

- 只接受 64 位 hash。
- 根据 `task_id` 找到 workspace。
- 只在该 workspace 的 `.cosir/Attachment` 中解析文件。
- 继续保留路径越界、符号链接和 reparse point 防护。
- MIME 从真实图片或受控扩展名推导，不信任客户端传入值。

### 删除和 GC

图片属于 workspace 目录，因此同一 workspace 下不同 task 可能共享相同 hash。

删除时必须检查该 workspace 所有 task 的 `conversation_runs.image_paths`：

- 仍被任意 Run 使用：不删除文件。
- 没有任何 Run 使用：删除 hash 对应的主文件和 sidecar。
- 删除 workspace 时不执行图片附件清理，不增加新的处理逻辑。
- task 删除后的现有 orphan GC 可以保留，但只基于 `image_paths`。

当前 workspace 删除会主动调用附件 GC，需要移除这段调用。[当前调用](H:\coding-agent\apps\backend\app\service\task\workspace_service.py:263)

## 3. 普通附件设计

普通附件不进入 workspace 附件目录，也不调用图片上传 API。

### 前端数据结构

当前 `NewConversation` 和 `ComposerAttachmentButton` 最终只传递 `File`，导致原始路径丢失。[当前初始对话流程](H:\coding-agent\apps\desktop\components\new-conversation.tsx:116) [当前 Composer 流程](H:\coding-agent\apps\desktop\components\assistant-ui\elements\attachment.aui.tsx:331)

改为维护：

```ts
type LocalAttachment = {
  id: string;
  kind: "image" | "file";
  path: string;
  name: string;
  file?: File;
};
```

其中：

- 图片需要 `file`，用于预览和上传。
- 普通文件只需要规范化后的本地 `path`。
- 路径由 Tauri native picker 返回并规范化。
- 普通文件不读入 WebView，也不上传后端。

### 内联 token

当前实现使用重复的 `[[cosir-file]]`，删除或重排时容易和附件顺序错位。[当前实现](H:\coding-agent\apps\desktop\components\composer\inline-attachment-input.tsx:38)

改为使用唯一的内部 token：

```text
[[cosir-file:<opaque-id>]]
```

实际渲染为：

```text
这段代码来自 [ app.py × ]
```

发送前在前端 Transport 边界完成：

```text
[[cosir-file:file-123]]
↓
C:\workspace\app.py
```

最终传给后端的只是：

```text
请读取 C:\workspace\app.py
```

不发送普通附件的 `file` part，不发送附件 locator，不发送文件二进制。

### Token 颜色

当前代码只生成了 `.cosir-inline-file-token` 等 class，但项目 CSS 中没有对应样式，因此没有颜色。[当前 token 生成](H:\coding-agent\apps\desktop\components\composer\inline-attachment-input.tsx:49)

在 `apps/desktop/app/globals.css` 增加统一样式：

- 浅色背景和主题色文字。
- 暗色模式适配。
- 圆角、边框、内边距。
- 文件图标。
- 删除按钮 hover/focus 状态。
- `contenteditable="false"`，避免 token 被拆开编辑。

同时使用唯一 ID 映射路径，避免依赖附件数组下标。

## 4. 图片 UI

统一一个 `AttachmentPicker` 按钮，但按附件类型分两种展示：

### 图片

使用共享的 `ImageAttachmentCard`：

- 圆角边框。
- 图片缩略图 `object-fit: cover`。
- 右上角黑色圆形删除按钮。
- 上传中显示 loading。
- 上传失败显示错误态。
- 新建对话和已有对话 Composer 共用同一套视觉组件。

当前新建对话和 Assistant UI 各自有一套图片展示逻辑，应合并。[新建对话图片卡片](H:\coding-agent\apps\desktop\components\new-conversation.tsx:34) [Assistant UI 图片卡片](H:\coding-agent\apps\desktop\components\assistant-ui\elements\attachment.aui.tsx:176)

### 普通附件

只显示输入框内联 token，不显示图片卡片，也不上传 workspace。

### 统一按钮

统一 `AttachmentPicker`：

- 一次支持多选。
- 图片分类为 image。
- 其他文件分类为 file。
- 不再提供第二套图片专用按钮。
- 图片和普通文件共用选择入口。

## 5. Transport 和后端改造

### 前端发送边界

在 `use-runtime-transport.ts` 的 `prepareSendCommandsRequest` 中统一处理：

1. 读取 Composer 的附件和 token。
2. 普通附件 token 替换为本地路径。
3. 删除普通附件 part。
4. 保留图片 part。
5. 向后端发送纯 text + image。

这是最合适的边界，因为该函数本来就是前端请求发出前的 Transport 转换点。[现有边界](H:\coding-agent\apps\desktop\components\assistant\runtime\use-runtime-transport.ts:229)

### 后端删除内容

删除：

```text
AssistantFilePart
file_attachment_ids
cosir_file_ref
_FILE_ATTACHMENT_PLACEHOLDER
_expand_file_attachment_placeholders
AttachmentAssetModel
AttachmentAssetRecord
AttachmentAssetCrud
```

`transport_assistant_service.py` 只提取：

- 文本内容。
- 图片 locator。

### Run 持久化

保留：

```text
conversation_runs.image_paths
```

删除：

```text
conversation_runs.attachment_refs
```

因为普通附件已经变成 `input_text`，图片引用可以通过 `image_paths` 重建。

同步清理：

- `conversation_run_record.py`
- `conversation_run_service.py`
- `conversation_run_crud.py`
- `conversation_run_model.py`
- `run_event.py`
- `conversation_task_state_rebuilder.py`
- `task_service.py` 中对 `attachment_refs` 的处理
- `storage/init_schema.py` 中附件表和附件列初始化
- `service/depends.py` 中附件 CRUD provider

## 6. 文档和数据库

由于是绿地项目：

- 不添加旧 UUID locator 兼容。
- 不添加旧附件表迁移。
- 新数据库只创建当前模型。
- 开发验证时重新创建 `storage/app.sqlite3`。
- 更新附件方案文档，把 UUID 全部改为 SHA-256。
- 删除文档中普通文件上传和附件表相关描述。
- 必要时重新生成 `docs/api/openapi.json`。

## 7. 测试验收

后端：

- 相同图片字节、不同文件名得到相同 hash。
- 不同图片字节得到不同 hash。
- hash locator 必须为 64 位小写十六进制。
- 同 workspace 多 task 共享同一物理文件。
- 其他 task 引用时不能删除共享文件。
- 图片最终化后 locator 不变。
- source sidecar 和 orphan GC 正确。
- 非法 hash、路径穿越、符号链接被拒绝。

前端：

- 普通附件显示为彩色内联 token。
- token 可删除、重排、不串位。
- 文件名包含空格、中文、特殊字符时仍可正确替换路径。
- 图片显示为图二样式卡片。
- 两种附件只使用一个上传按钮。
- 发给后端的消息不包含 `file` part。
- 请求只包含 text 和 image。
- 失败重试时普通附件路径和图片都能恢复。

## 最终架构结论

```text
图片：
workspace 文件系统负责内容
SHA-256 负责身份
conversation_runs.image_paths 负责对话引用

普通附件：
只存在于当前前端 Composer
发送时转换为 input_text 中的本地路径
不进入附件目录，不进入附件表，不进入 image_paths
```

这套方案符合单用户本机架构，也与原附件设计中“不新增附件表”的方向一致。
