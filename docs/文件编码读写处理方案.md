# 文件编码读写处理方案（规划 v1）

> 状态：规划稿，待评审。本文档描述 coding-agent 在「读取 / 写入文件」时对字符编码的处理策略，
> 目标是在不意外改动用户文件的前提下，杜绝 Agent 写代码时的乱码问题。
> 配套代码改动一律留在工作区供 review，**不自动提交 Git**。

---

## 1. 背景与目标

观察其他 coding-agent 在写代码时出现「乱码」，根因几乎都是**字符编码在某一环节被错误解释**：
- 把 GBK 字节当 UTF-8 解码 → 替换字符 / 乱码；
- 流式写入时按块 `decode` 把多字节汉字截断在边界；
- 读取时用 `errors="replace"` 把非法字节悄悄变成 `U+FFFD`，再回喂模型 / 写盘，造成乱码自我繁殖。

对本项目做防御性审查后，发现两条真实隐患（已修，未提交）：

| 隐患 | 位置 | 现象 |
|---|---|---|
| 终端子进程强制 UTF-8 解码 | `terminal/local_backend.py` | Windows 下 GBK 输出被解成豆腐块（已改为读字节 + 回退解码链） |
| 源码读取滥用 `errors="replace"` | `read_file.py` / `content_search.py` | 非 UTF-8 文件被静默替换为 `U+FFFD`，污染模型上下文 |

本方案在此基础上，把「读」与「写」的编码处理做成**完整闭环**，原则如下。

---

## 2. 核心原则（经讨论确认）

1. **读转码 = 选对解码器，不是改文件。**
   读这一步只把磁盘字节用正确的编码解成字符，**磁盘文件字节一个都不动**。GBK 文件读完仍是 GBK，
   我们只是「正确地看懂了它」。这与「转换文件编码」是两回事——后者才改写磁盘。

2. **写回 = 按原文件编码写回，不意外改动用户文件的编码契约。**
   Agent 读了一个 GBK 文件、修改后写回，文件应当仍是 GBK（除非 Agent 显式要求改编码）。
   这与 VS Code 等编辑器的默认行为一致：打开时探测编码，保存时按原编码写回。

3. **显式优于隐式。**
   任何编码猜测都必须可被 Agent 感知（通过返回值标记），需要改变编码时由 Agent 显式指定，
   不允许静默漂移。

## 4. 方案设计

### 4.1 `read_file`：回退解码 + 编码标记

`_read_text_page`（`read_file.py:323` 附近）当前为：

```python
with path.open("r", encoding="utf-8", errors="strict") as file:
    ...
except UnicodeDecodeError:
    return TextReadResult(error="...不是合法 UTF-8...", reason="...")
```

改为**解码链**（与终端 `_decode_line` 同思路，但整文件一次解码）：

```python
raw = path.read_bytes()
text, used_encoding = _decode_with_fallback(raw)   # utf-8 → gbk → 系统编码
if text is None:
    return TextReadResult(error="无法以任何已知编码解码，疑似二进制文件",
                          reason="...请确认文件编码或转为 UTF-8 后重试")
# 正常分页逻辑；成功后标记实际使用的编码
return TextReadResult(content=..., encoding=used_encoding if used_encoding != "utf-8" else None, ...)
```

- 返回值新增字段 `encoding: str | None`（`TextReadResult`，`text_read_result.py`）：
  仅当**实际使用的不是 UTF-8** 时才非空，用于告知 Agent「此文件原始编码非 UTF-8」。
- 解码全部失败时返回明确错误（疑似二进制），**不做 `replace` 静默替换**。

### 4.2 `write_file`：检测原编码并写回

关键改动在 `atomic_write_text`（`atomic_write.py`）与 `write_file.py`：

1. **新增 `encoding` 参数**（默认 `"utf-8"`），写盘时使用该编码：
   ```python
   with os.fdopen(fd, "w", encoding=encoding, newline="") as file:
       file.write(content_out)
   ```
2. **目标文件编码探测**（替换原 `decode("utf-8", errors="replace")` 采样，约 `atomic_write.py:53-57`）：
   - 有 BOM → 按 BOM 判定（UTF-8 / UTF-16）；
   - 否则查**编码注册表**（4.3）是否已有该 path 的已知编码；
   - 否则用轻量探测：依次尝试 `utf-8 → gbk → 系统首选编码`，取第一个能干净解码者；
   - 全部失败 / 新文件 → 默认 `utf-8`。
3. **`write_file.py:155` 读旧内容做 diff 时也用探测到的编码**，避免 GBK 文件的 diff `before` 被 `replace` 污染。
4. **保留 `encoding` 显式参数**（经 `WriteFileArgs`）：Agent 想强制写成 UTF-8 或别的编码时显式传入，覆盖探测结果。

### 4.3 编码注册表（会话内）

- 新增 `file_io/encoding_registry.py`：内存字典 `Dict[abs_path, str]`，会话级生命周期。
- `read_file` 成功解码后调用 `registry.record(abs_path, used_encoding)`；
- `write_file` / `atomic_write_text` 探测时优先 `registry.lookup(abs_path)`，**已知编码优先于启发式猜测**，
  彻底消除「读→改→写」常见路径上的检测歧义。
- 进程重启即清空（不持久化，避免与磁盘真实状态不一致）。

### 4.4 `content_search`：保持跳过

批量搜索场景下一个 GBK 文件跳过不影响整体结果，无需转码，维持 `strict` + `continue`。

已实现（未提交），本方案维持现状，仅随整体评审一并提交。

## 5. 编码探测实现细节（轻量、零新依赖）

v1 不引入 `charset-normalizer`，复用项目已有的回退顺序：

```python
def _detect_encoding(raw: bytes) -> str:
    if raw.startswith(codecs.BOM_UTF8):  return "utf-8-sig"
    if raw.startswith(codecs.BOM_UTF16_LE) or raw.startswith(codecs.BOM_UTF16_BE): return "utf-16"
    preferred = locale.getpreferredencoding(False) or "utf-8"
    for enc in ("utf-8", "gbk", preferred):
        try:
            raw.decode(enc); return enc
        except UnicodeDecodeError:
            continue
    return "utf-8"
```

- 优势：GBK 与 UTF-8 的中文字节模式差异极大，实际误判率很低；
- 已知编码（注册表）命中时**不跑探测**，零歧义；
- 后续如需更广编码覆盖，可平滑替换为 `charset-normalizer`，接口不变。

## 7. 风险与权衡

- **写回探测误判** → 仅当注册表未命中且文件恰为歧义编码时发生；通过「已知编码优先 + BOM 优先」已压到很低，
  且误判风险低于「强制 UTF-8 必然改编码」。
- **注册表与磁盘不一致** → 仅会话内、不持久化，且只读已有 path 的缓存；外部改动文件后下次读会重新探测更新，影响可控。
- **`read_file` 旧测试需重写** → 因语义从「拒绝」变为「回退解码」，属预期内调整。
