# 服务端按文件拆分改造方案

## 文档目标

- 基于当前代码结构，给出一份面向实现的服务端改造方案。
- 重点回答“哪些文件要改、各自承担什么职责、为什么这样拆”。
- 不展开详细代码实现，只明确文件级职责边界、改造方向、落地顺序与验收要点。

## 适用范围

本方案覆盖：

- `workspace / task / turn` 主模型收敛
- `POST /tasks/{task_id}/turns` 与 `GET /turns/{turn_id}/stream`
- 运行时事件结构升级
- turn 级运行、回放、重连与恢复
- 工具事件时序下沉
- timeline / replay / trace / logs 的边界对齐

本方案不覆盖：

- 多模态输入
- 完整 subagent 协议扩展
- 完整 approval UI 交互
- 最终数据库迁移脚本细节

## 已确认约束

- 后端去掉 `session` 作为长期领域边界。
- 核心主键边界收敛为：`workspaceId / taskId / turnId`。
- `task` 是连续对话容器，`turn` 是一次完整运行单元。
- `POST /tasks/{task_id}/turns` 只创建 `pending` turn。
- `GET /turns/{turn_id}/stream` 负责启动 / 接入 / 回放。
- `message` 是用户可读内容单元，`event` 是运行事实，`timeline` 是显示投影。
- 日志层只保留 `trace_id` 作为顶层链路键，业务实体 ID 放入 `data` 或 trace 体系。

## 文件级改造方案

## 一、API 层

### 1. [apps/backend/app/api/tasks_api.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/api/tasks_api.py)

**当前职责**

- 暴露 task 创建、查询、事件、checkpoint、stream、cancel 端点。

**需要改什么**

- 从“task 直接运行”改成“task 容器 + turn 运行”。
- 保留 task 查询相关端点，但移除 `GET /tasks/{task_id}/stream` 的主职责。
- 新增：
  - `POST /tasks/{task_id}/turns`
  - `GET /turns/{turn_id}/stream`
  - `GET /tasks/{task_id}/turns`
- 任务首轮创建路径如果仍保留在 task API，也要让“创建 task”和“创建首个 turn”语义明确分开。

**为什么这样改**

- API 是外部契约边界，必须先反映 `task` 与 `turn` 的分离，后续 runtime/store 才不会继续被旧接口绑死。

**不建议做什么**

- 不要在同一个端点里继续混合“创建 turn”“启动运行”“历史回放”三种职责。

### 2. [apps/backend/app/api/schemas/CreateTaskRequest.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/api/schemas/CreateTaskRequest.py)

**需要改什么**

- 现有 `text + session_id` 模型要拆掉旧 `session` 语义。
- task 创建请求与 turn 创建请求分离：
  - task 创建模型只描述 task 容器创建所需字段
  - turn 创建模型只描述本轮输入所需字段

**为什么这样改**

- 请求模型是长期协议事实源，继续混用 `session_id` 会把旧心智持续扩散到 service 和前端。

### 3. [apps/backend/app/api/schemas/__init__.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/api/schemas/__init__.py)

**当前职责**

- 统一重导出 API schema，避免 `from app.api.schemas import X` 解析成子模块而不是模型类。

**需要改什么**

- 当新增 `CreateTurnRequest.py`、`CreateWorkspaceRequest.py` 等 schema 文件后，这里必须同步补充重导出。

**为什么这样改**

- 这是 schema 包的接线点，不纳入改造会导致新增 schema 无法按当前项目习惯稳定接入路由层。

### 4. 建议新增 `apps/backend/app/api/workspaces_api.py`

**职责**

- 只暴露 workspace 相关接口：
  - `GET /workspaces`
  - `POST /workspaces`
  - `DELETE /workspaces/{workspace_id}`
  - `GET /workspaces/{workspace_id}/tasks`
  - `POST /workspaces/{workspace_id}/tasks`

**为什么新增文件**

- workspace 已经是明确领域边界，不应继续塞进 `tasks_api.py`。
- 按职责拆开，后续沙箱、工作区选择器、删除级联都会更清晰。

### 5. 建议新增 `apps/backend/app/api/turns_api.py`

**职责**

- 只暴露 turn 相关接口：
  - `POST /tasks/{task_id}/turns`
  - `GET /turns/{turn_id}/stream`
  - `GET /turns/{turn_id}`

**为什么新增文件**

- turn 是新的运行主边界，单独成文件可以防止 task API 再次膨胀。

### 6. [apps/backend/app/api/app.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/api/app.py)

**当前职责**

- 装配 FastAPI 应用单例。
- 注册各域路由模块。
- 作为 `create_app()` 生命周期入口。

**需要改什么**

- 新增 `workspaces_api.py`、`turns_api.py` 后，这里必须同步注册。
- turn / workspace 新接口不能只停留在文件层，必须进入真实应用装配链。

**为什么这样改**

- 这是 HTTP 入口的总装配点，漏掉这里，新增接口不会真正生效。

### 7. [apps/backend/app/api/dependencies.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/api/dependencies.py)

**当前职责**

- 构建 runtime 依赖图。
- 将 store、trace、replay、tool runtime、logging 等服务接入 `AgentRuntime`。

**需要改什么**

- 当存储层升级为 `workspace / task / turn` 后，这里的依赖图必须同步调整。
- 如果拆出 `WorkspaceStore`、`TurnStore`、新的事件服务或新的 replay/timeline 服务，这里是统一接线点。
- `TextContextBuilder`、`TraceStore`、`ReplayService`、`ToolRuntime`、`AgentRuntime` 的新依赖关系都要在这里收口。

**为什么这样改**

- turn 语义不是只改路由和 CRUD 就能落地，真正的运行链路是在这里装配起来的。

## 二、运行时层

### 8. [apps/backend/app/core/runtime/runner.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/core/runtime/runner.py)

**当前职责**

- 创建 task
- 运行 task
- 持久化事件
- 同步 durable run / trace / checkpoint

**需要改什么**

- 运行主入口从 `run_task(task_id)` 收敛为 `run_turn(turn_id)`。
- 将“task 是否 pending”的旧判断，改为“turn 是否 pending / running / completed / failed / cancelled”。
- 把 replay 语义从“按 task 回放”切换为“按 turn 回放 + 按 task 聚合历史”。
- `create_task()` 不再隐式等价于“创建一条将被直接运行的单轮任务”。
- 运行与接入语义分离：
  - 创建 turn 不启动
  - stream 决定启动 / 接入 / 回放

**为什么这样改**

- runtime 是真实执行底座，只有这里切主边界，前端多轮对话才有坚实语义。

**不建议做什么**

- 不要在 `run_task()` 上继续包更多兼容分支。应该显式引入 turn 级入口，而不是把旧函数越补越肿。

### 9. [apps/backend/app/core/runtime/operations.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/core/runtime/operations.py)

**需要改什么**

- 把 `get_turn_for_task(task_id)` 改成显式面向 `turn_id` 工作。
- `record_event()` 不再只吃 `task_id`，要能稳定写入 `turn_id`。
- `create_checkpoint()`、`list_events()`、`list_steps_for_task()` 等围绕 task 的辅助调用，要明确哪些是 turn 内操作，哪些是 task 级聚合读取。

**为什么这样改**

- 当前 operations 已经是 workflow 的窄门面，是最适合完成“从 task 过渡到 turn”的隔离层。

### 10. [apps/backend/app/core/workflows/react_like.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/core/workflows/react_like.py)

**需要改什么**

- workflow 输入不再通过“task 找第一个 turn”获取当前运行上下文。
- 工具生命周期事件不要继续在 workflow 里伪造 started/completed 时间点。
- workflow 主要负责：
  - 模型步骤推进
  - 工具调用决策
  - 最终响应 / 失败 / 终态收束

**为什么这样改**

- workflow 应该描述执行策略，不应再承担底层生命周期补录职责。

### 18. [apps/backend/app/storage/crud/task.py](/Users/woaigugu/Documents/coding-agent/apps/backend/app/storage/crud/task.py)

**需要改什么**

- 不再继续向这个文件堆积 `workspace CRUD + turn CRUD + event CRUD`。
- 当前文件应只保留与 task 容器强相关的存取职责，并为独立 store 拆分创造清晰边界。

**为什么这样改**

- 当前 `SQLiteTaskStore` 已经同时承载 task / turn / step / event / checkpoint，多塞一层会直接违反项目规范里的单一职责要求。

**立即拆分建议**

- `crud/task.py`：只保留 task 容器 CRUD
- `crud/turn.py`：只承载 turn CRUD 与 turn 状态推进
- `crud/event.py`：只承载 event append / list / sequence 分配
- `crud/workspace.py`：只承载 workspace CRUD 与级联删除入口
- `crud/checkpoint.py`：如果 checkpoint 逻辑继续增长，也应独立拆出

**需要改什么**

- 为 workspace/task/turn/event 结构升级补迁移入口。

**为什么这样改**

## 服务端验收标准

- 后端不再依赖 `session` 作为长期领域边界。
- 能创建 workspace、在 workspace 下创建 task、在 task 下创建多个 turn。
- `POST /tasks/{task_id}/turns` 只创建 `pending` turn。
- `GET /turns/{turn_id}/stream` 能正确执行：
  - pending 启动
  - running 接入
  - completed / failed / cancelled 回放
- 同一个 `turnId` 不会被重复启动。
- `RuntimeEvent` 至少具备 turn 级关联和稳定排序能力。
- 工具 started / completed 事件尽量贴近真实执行边界。
