# 多语言语法检查守卫技术方案（代码检查 guard）

> 把 `patch_tool` 中当前内联的 `.py` `ast.parse` 软校验，抽成 `guard/` 下的多语言语法检查共享模块，并让 `write_file` / `patch_tool` 统一复用。技术选型用 **`tree-sitter` + 各语言官方 grammar 包**（Windows 预编译 wheel，覆盖 Python / JS / TS / Go / Rust / Java / C / C++ / C# / HTML / CSS）。
> 语义（2026-08-04 用户拍板）：**不硬拦截、落盘后检查、error 驱动**——命中语法错误时返回 `status="error"` 观察并携带结构化诊断，驱动 Agent 读取诊断后**自动二次调编辑工具覆盖修复**；坏代码允许落盘（与 `patch_tool` 既有 `.py` 行为一致），由 Agent 自修复闭环兜底。
> 依赖策略（已与用户确认）：内置官方 tree-sitter grammar 包（`uv` 锁版本），in-process 解析，不依赖本机编译器、不 spawn 子进程。
> 改动规模：中/大（新增模块 + 改动 2 个文件 + 新增测试 + 新增依赖），按 `AGENTS.md` 第八节须走**独立审查 Agent + 独立测试 Agent** 闭环。

## 一、背景与目标

当前仅 `patch_tool` 的 replace 模式对 `.py` 做 `ast.parse` 语法校验（追加 `[warning]` 告警），`write_file` 与 `patch_tool` 的 patch 模式均无任何语法兜底，其余主流语言的写入同样完全没有语法兜底。

目标：

- 把单语言、重复的语法校验，升级为多语言、单一来源的语法检查守卫，并消除现有重复实现。
- 用官方 tree-sitter grammar 包覆盖主流语言（Python / JS / TS / TSX / Go / Rust / Java / C / C++ / C# / HTML / CSS），并保留向更多语言扩展的零成本路径。
- 命中语法错误时返回 **error 观察 + 结构化诊断**，驱动 Agent 自修复（而非仅告警被动提示）。

设计取舍（已与用户确认）：

- **内置官方 tree-sitter grammar 包（uv 锁版本）**：`tree-sitter` 宿主 + 各语言官方 grammar 包（Python / JS / TS / Go / Rust / Java / C / C++ / C# / HTML / CSS），in-process 解析；**不依赖本机编译器、不 spawn 子进程**。选官方 grammar 包而非 `tree-sitter-language-pack`（实测后者不支持 Windows 平台，见 §4.1）。
- **不硬拦截、落盘后检查**：解析需读取已落盘字节，且不打断 Agent 写入半成品/大文件；坏代码允许落盘，由 Agent 自修复闭环兜底。
- **error 驱动**：命中语法错误返回 `status="error"` 观察，经扩展后的 `tool_error` 携带 `display_data["syntax_errors"]` 结构化诊断（行/列/类型/期望 token），`reason` 给出面向模型的英文自修复引导；Agent 读到后自动二次调 `patch`/`write_file` 覆盖。
- **只报语法级 parse error**：tree-sitter 对错误语法也能产出 partial AST（错误节点标 `ERROR`/`MISSING`），故只判「有语法错 + 错误节点行列 + 缺失 token 期望」，不报未定义符号/类型错误（语义诊断属未来 Lint，见 §十一）。

## 三、方案概述（高层次）

采用 **「语言映射表 + 统一解析内核」**：不再为每种语言写一个策略类，改为**一张扩展名→语言名映射表 + 一个统一 tree-sitter 解析内核**（`_build_language` 按语言名构造各官方 grammar 的 `Language`）。`guard/` 下新增共享模块，暴露纯函数 `check_source_syntax(path, content=None) -> SyntaxCheckResult`，两个工具 handler 直接复用，既消除重复、又守住单一职责。

**为什么用共享函数而非装饰器**：
`write_file` 入参是单文件 `content`+`path`；`patch_tool` 的 replace 模式是 `new_content`+`path`、patch 模式是一次性多文件 `after`。入参形态异构，统一装饰器 `param="content"` 并不贴合；且装饰器无法拿到 patch 内部算出的 `new_content`。故直接抽 `guard/syntax_check.py` 共享函数，在落盘后由两 handler 显式调用，改动更小、消除重复更直接，且守住 `guard/` 零业务依赖边界。

**调用时机**：在文件**落盘之后**调用（解析需读取已落盘字节），`path` 传已解析的绝对路径。

**内置解析器 vs 本机编译器**：
官方 grammar 包内置各语言 grammar（PyPI 预编译 wheel），`_build_language(name)` 构造 `Language` 后 `Parser(language)`，`check` 直接 `parser.parse(source_bytes)` 并读 `root_node.has_error` 与错误节点。**不再 spawn 子进程、不再 `shutil.which` 探工具、不再 `timeout` 兜底**。任何机器（装没装编译器）都生效。

**error 驱动（与既有 `[warning]` 的区别）**：
命中语法错误时，handler 经扩展后的 `tool_error(...)` 返回 error 观察：`error` 描述「发生了什么语法错误」，`reason` 给出「哪个文件哪一行缺了什么 + 如何修正」，`display_data["syntax_errors"]` 给结构化诊断（行/列/类型/期望 token）供前端展示与 Agent 结构化消费。**文件已落盘**，Agent 读到 error 后自动二次调 `patch`/`write_file` 覆盖修正。

> **选型说明（已实测调整，非原方案）**：原方案选 `tree-sitter-language-pack`（单包 371 语言），但**实测该包不支持 `windows-x86_64` 平台**（仅提供 linux/macOS 预编译 parsers，`get_parser` 抛 `DownloadError`）；本桌面端为 Windows，故改用**官方 grammar 包方案**（每个语言一个 PyPI wheel，提供 Windows 预编译、已验证可解析）。当前 `pyproject.toml` 无任何 tree-sitter 依赖，本项为**新增依赖**，全部锁版本 `==`。

### 4.2 API（已实测验证）

```python
from tree_sitter import Language, Parser
import tree_sitter_python as mod_python

language = Language(mod_python.language())   # 取该语言 grammar
parser = Parser(language)                     # 构造 parser
tree = parser.parse(source_bytes)             # parse
root = tree.root_node
root.has_error                                # 是否有语法错误
# 错误节点：node.is_missing（缺失 token，node.type 即缺什么）或 node.type == "ERROR"
# 已验证：`def f(:` → has_error=True，且 1 个 MISSING 节点 type=")" row=0 col=6
```

> 注意：官方 grammar 包为 PyPI 预编译 wheel（含 Windows），`Parser(language)` 构造成本主要在**首次**加载 native 库；方案保留模块级 `_PARSER_CACHE` 复用 parser，避免热路径重复初始化（见 §5.1）。TypeScript 包 API 为 `language_typescript` / `language_tsx`（无 `language()`），已在实现中处理。

### 4.3 语言分派：扩展名 → 语言名映射表

所有语言解析逻辑同构，差异只在「用哪个 grammar」。用一张映射表统一分派，**仅收录已安装 grammar 包的扩展名**（未装包的语言不列入，避免 `supported=False` 的无效条目）：

```python
_EXTENSION_TO_LANGUAGE = {
    ".py": "python", ".pyi": "python",
    ".js": "javascript", ".mjs": "javascript", ".cjs": "javascript",
    ".jsx": "jsx",          # 复用 tree-sitter-javascript grammar
    ".ts": "typescript", ".tsx": "tsx",   # 复用 tree-sitter-typescript（language_ts / language_tsx）
    ".go": "go", ".rs": "rust", ".java": "java",
    ".c": "c", ".h": "c", ".cpp": "cpp", ".cc": "cpp", ".hpp": "cpp",
    ".cs": "csharp",
    ".html": "html", ".htm": "html", ".css": "css",
}
```

**新增语言 = 加一行映射 + 在 `_build_language` 补对应 grammar 分支（或装包）**，零改动检查内核（Rule of Three / 即插即用）。

> **已实测语言名核实**（Windows 环境）：`.py/.pyi`→python、`.js`→javascript、`.jsx`→jsx（复用 js grammar）、`.ts`→typescript、`.tsx`→tsx、`.go`→go、`.rs`→rust、`.java`→java、`.c/.cpp`→c（C++ 复用 C grammar）、`.cs`→csharp、`.html`→html、`.css`→css，均验证可解析并检测 `ERROR`/`MISSING` 节点。

### 4.4 统一诊断收集

对 `root.has_error` 为真的情况，遍历 `ERROR` / `MISSING` 节点收集**结构化诊断**：

```python
@dataclass(frozen=True)
class SyntaxDiagnostic:
    language: str
    row: int            # 1-based 行（取自 tree-sitter 0-based start_point.row，须 +1 转换）
    column: int         # 0-based 列（tree-sitter start_point.column 原样）
    kind: str           # "unexpected" | "missing"
    message: str        # 人读英文诊断，如 "missing ')' at line 3 col 10"
    expected: str | None = None   # MISSING 节点缺的 token（node.type），驱动 Agent 精准修复
```

`SyntaxCheckResult`：

```python
@dataclass(frozen=True)
class SyntaxCheckResult:
    supported: bool                  # 是否支持该语言（False = 未知扩展名/grammar 加载失败 → 跳过）
    has_error: bool = False
    diagnostics: tuple[SyntaxDiagnostic, ...] = ()
```

**`apps/backend/app/tools/guard/syntax_check.py`**（单一职责：按扩展名分发到 tree-sitter grammar 做语法检查，返回 `SyntaxCheckResult`）

职责边界（显式声明"不负责"）：
- 不 import `tool_handler` / `tool_execute` 业务模块（维持 `guard/` 横切层零业务依赖）。
- 不内置编译器、不 spawn 子进程；不负责决定是否阻断（那是调用方按 `has_error` 决策）。
- 不负责把诊断拼进 `content` / 构造 `tool_error` / 写 `display_data`（那是调用方职责）。

内部结构（高层面，非代码）：
- `__all__ = ["MAX_CHECK_BYTES", "SyntaxCheckResult", "SyntaxDiagnostic", "check_source_syntax", "format_syntax_reason"]`：显式导出公共符号（模块内部）；**不**写入 `guard/__init__.py`。
- `MAX_CHECK_BYTES = 2 * 1024 * 1024`：体积门禁，超过则跳过检查（避免超大文件无谓解析）。
- `_EXTENSION_TO_LANGUAGE`：扩展名 → 语言名映射表（见 §4.3，仅收录已装 grammar 包的语言）。
- `_PARSER_CACHE: dict[str, Parser]`：语言名 → `Parser` 实例缓存，复用已构造的 parser，避免热路径重复初始化 grammar（官方 grammar 包首次加载 native 库成本较高）。
- `_build_language(name) -> Language | None`：按语言名构造 tree-sitter `Language`（各官方 grammar 包 import + `.language()`；TypeScript 用 `language_typescript`/`language_tsx`；C++ 复用 C grammar）。
- `_get_parser(name) -> Parser | None`：取/建语言 parser（带 `_PARSER_CACHE` 缓存）。
- `_language_for(path)`：按扩展名查 `_EXTENSION_TO_LANGUAGE`。
- `_format_diagnostic(node, source_bytes, language) -> SyntaxDiagnostic`：单个错误/缺失节点 → 结构化诊断（`MISSING` 的 `expected=node.type`）。
- `_collect_diagnostics(root, source_bytes, language)`：遍历 `ERROR`/`MISSING` 节点收集全部诊断。
- `check_source_syntax(path, content=None) -> SyntaxCheckResult`：按扩展名查映射表 → 体积门禁 → 读字节（`content` 优先，否则 `Path(path).read_bytes()`）→ 取/建 parser → `parser.parse` → 若 `root.has_error` 遍历 `ERROR`/`MISSING` 节点收集 `SyntaxDiagnostic` → 返回 `SyntaxCheckResult`。
- `format_syntax_reason(result) -> str`：按首个诊断生成英文自修复引导（模型可见 reason，驱动 Agent 二次编辑覆盖）。
- **拆分纪律**：各子函数职责单一，单函数不超 60 行、嵌套不超 3 层。

- 顶部新增 `from app.tools.guard.syntax_check import check_source_syntax`（并删除不再使用的 `import ast`）。

### 5.3 改动最小化核对

- 新增 `tree-sitter` + 各语言官方 grammar 包依赖（`pyproject.toml` + `uv.lock` 锁版本 `==`），其余不引入新调用链、不动 `tool_scheduler` / `tool_executor` / `runtime`。
- **`ToolObservation` 契约不变**；`display_data["syntax_errors"]` 走既有结构化 `display_data` 通道（`tool_call_finished` payload 的 `data` 字段由 `observation.display_data` 透传**前端**，见工具调用结果透传方案）；**`display_data` 不到模型**（`tool_execution_service` 序列化前 `clear_display_data`），故 Agent 自修复引导必须经模型可见的 `reason`/`content` 传递（见 §5.2 双通道分层）。**唯一契约侧改动** = `tool_error` 新增可选 `display_data` 参数（与 `tool_success` 对称）。
- `reason` 为英文（面向模型约定，**模型可见、驱动 Agent 自修复的唯一载体**），格式统一，引导 Agent 精准修复：`syntax error in <lang> at line X:Y (missing '<token>') — the file has been written; fix it with a follow-up edit`。
- 解析异常（如 grammar 加载失败）须写项目错误日志，不静默吞掉；仅「未知扩展名」与「体积超门禁」属预期跳过、返回 `supported=False`。
- 不再有 `subprocess.run` / `shutil.which` / `timeout` 任何代码，无子进程开销。

## 六、已知限制（须如实告知）

1. **只报语法级 parse error**：不报未定义符号/类型错误（语义诊断归未来 Lint，见 §十一）。这意味着「语法对但语义错」的代码不会触发本守卫——这是设计边界，不是缺陷。
2. **容错性导致漏报**：tree-sitter 对错误语法也能产出 partial AST，少数「轻微」语法问题可能被容忍而不标 `ERROR`，存在漏报可能（可接受）。
3. **错误定位粒度**：tree-sitter 只保证「有错 + ERROR/MISSING 节点行列」，不保证像编译器那样逐条列出所有精确诊断；按「全部 ERROR/MISSING 节点」实现，不夸大。
4. **坏代码允许落盘**：error 驱动但不拦截——语法错误的文件已写入磁盘，靠 Agent 读到 error 后二次覆盖修复。若 Agent 中断，坏文件会残留；这是「不硬拦截」语义的固有代价（与既有 `[warning]` 一致），但 error 语义使 Agent 更可能主动修复。
5. **依赖首次加载**：官方 grammar 包对应语言 grammar **首次构造 `Parser` 时加载 native 库有一次性成本**，方案用模块级 `_PARSER_CACHE` 缓存后续复用；首次命中某语言时可能有轻微延迟。
6. **新增依赖体积**：`tree-sitter` 宿主 + 10 个 grammar 包均为预编译 wheel，总增量几十 MB 级（各包独立、按需可移除单语言包缩小体积）。

## 十、风险与回滚

- 新模块 `syntax_check.py` 为纯函数、零业务依赖，失败仅导致「少一次语法检查」，不会破坏写入结果正确性；若某语言 grammar 误伤正常文件，删除对应映射表项即可，回滚点清晰。
- 无子进程、无 `shutil.which` 探工具，不存在「因检查器缺失导致写入失败」的风险（任何机器依赖一致生效）。
- error 驱动意味着语法错误的文件已落盘，若某语言 grammar 频繁误报（把合法代码判为错误），会导致 Agent 反复二次编辑——**风险兜底**：映射表只收录 grammar 质量可靠的语言；对误报高的语言可从映射表移除（即不检查该扩展名），不阻塞其它语言。
- 性能兜底：2MB 体积门禁 + `_PARSER_CACHE` 复用 parser；in-process 解析无 `timeout` 开销。
- 新增依赖风险：官方 grammar 包须锁版本；已在 Windows（win32）实测 `tree-sitter==0.26.0` + 10 个 grammar 包均可安装、解析、检测 `ERROR`/`MISSING` 节点，无平台 wheel 缺失问题（官方 grammar 包提供 Windows 预编译 wheel）。若未来某语言包在目标平台缺 wheel，移除该语言映射即可，不阻塞其它语言。

## 十一、未来扩展：Lint 工具（非本期，仅固化边界）

本期守卫只做**语法层**（tree-sitter parse error）。用户已明确规划一个**独立的 Lint 能力**，覆盖语义级诊断（未用变量 / 类型错 / 风格），走 LSP 或真实 linter（eslint / ruff / pyright / rust-analyzer 等）。本节仅固化其边界与形态，**不在本期实现、不预留抽象层**（YAGNI）。

### 11.1 与本期守卫的分层边界

| 能力 | 层 | 触发粒度 | 技术 | 阻断性 |
|---|---|---|---|---|
| 语法检查（本期） | `guard/` 横切模块 | 每次 edit 落盘后（同步） | 官方 tree-sitter grammar 包 | 不拦截（落盘后 error 驱动） |
| Lint（未来） | `tool_system` 注册 + `core` runtime 钩子 | 模型主动调用 / 每轮 turn-end（异步） | LSP / 真实 linter | 不阻断（被动诊断） |

关键区分：**tree-sitter（语法层）≠ LSP（语义/lint 层）**。本期 guard 已在每次编辑后跑 tree-sitter，已覆盖「语法可解析」；Lint 是语义级，须另走 LSP，不能复用本 guard 充当 lint。

**未来形态的分层契约（与现有规范兼容）**：未来 Lint 工具虽注册进 `tool_system`（属 `tools/`，合法），其「每轮 turn-end 自动触发」必须由 `core` runtime 经现有 `ToolScheduler` / `RuntimeOperations` 窄边界门面调度（即 `core → tools` 合法边，见 `rules/目录组织规范.md` 1.2 契约要点 5、9.3），**不得让 `tools/` 反向 import `core`**；该形态不突破 1.3 循环依赖红线（`core↔storage`/`tools→service` 等）。Lint 的自动触发逻辑若需放在 `core` 侧，仅消费 `ToolScheduler.execute` 接口，不新增 `tools → core` 依赖。

### 11.2 Lint 的双形态（用户规划）

1. **模型可主动调用**：lint 作为一等 `ToolDefinition` 注册进 `tool_system`，与现有内置工具同机制（契约单一事实来源、经 `core` 调度）。模型按 schema 自行决定何时调用。
2. **每轮对话结束自动跑**：在 `core` runtime 的 turn-end 钩子触发，复用同一 lint 逻辑，作为模型可能遗忘调用的安全网。

### 11.3 自动跑的约束（落地时须遵守）

- **非阻塞 / 后台异步**：LSP 启动 + 索引是重活，绝不可卡住回合结束；结果以事件/观察被动回传模型。
- **按本回合改动文件差集**：只对当轮 `turn` 改动的文件跑，避免全项目重扫；与模型主动调用做去重（同文件本回合已 lint 过不重复扫），避免浪费与噪音。
- **可配置开关**：v1 建议先只交付「可调用工具」形态，自动跑作为后续增强、默认关，契合本地桌面轻量定位。
- **不阻断落盘**：与语法 guard 一致，lint 诊断只告警、不阻断写入。

### 11.4 以后做（超出 Lint 双形态）

- **基线对比诊断**（参考 Claude Code `diagnosticTracking.ts`）：捕获编辑前基线，只回报 Agent 本轮新引入的问题，进一步降噪。本期不规划，待 lint 双形态落地验证后再评估。

### 11.5 禁止行为（边界纪律）

- 本期**不**为 lint 预留接口/抽象层；等真建时按 `ToolDefinition` 范式直接做，与既有工具同构。
- 不把语法 guard 误当作 lint 使用，也不在 `guard/syntax_check.py` 内掺入语义诊断逻辑（守住单一职责）。
