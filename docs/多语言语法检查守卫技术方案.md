# 多语言语法检查守卫技术方案（代码检查 guard）

> 把 `write_file` / `patch_tool` 中当前**重复内联**的 `.py` `ast.parse` 软校验，抽成 `guard/` 下的多语言语法检查共享模块，覆盖 Python / Java / Go / Rust / JS / TS / HTML / CSS 共 8 种语言。命中语法错误时，仅在成功观察的 `content` 尾部**追加英文告警**、不阻断落盘。
> 依赖策略（已与用户确认）：**内置 tree-sitter 解析器依赖（`uv` 锁版本）**，in-process 解析，不再依赖本机编译器、不再 spawn 子进程。
> 改动规模：中/大（新增模块 + 改动 2 个文件 + 新增测试 + 新增依赖），按 `AGENTS.md` 第八节须走**独立审查 Agent + 独立测试 Agent** 闭环。

---

## 一、背景与目标

当前仅对 `.py` 做 `ast.parse` 语法校验，且逻辑**重复**散落在 `write_file` 与 `patch_tool` 两个 handler 内部（违反 Rule of Three），其余 7 种主流语言的写入完全没有语法兜底。

目标：

- 把单语言、重复的语法校验，升级为多语言、单一来源的语法检查守卫，并消除现有重复实现。
- 覆盖 Python / Java / Go / Rust / JavaScript / TypeScript / HTML / CSS 共 8 种语言（含原方案零依赖下做不了的 CSS）。
- 发现错误时**仅告警、不阻断**（与现有 `.py` 行为完全一致），避免打断 Agent 写入半成品/大文件。

设计取舍（已与用户确认）：

- **内置 tree-sitter 解析器依赖（uv 锁版本）**：通过 `tree-sitter` 宿主 + 各语言 grammar 包（均 PyPI 预编译 wheel、跨平台一致、体积小）做 in-process 解析；**不依赖本机编译器、不 spawn 子进程**。`pyproject.toml` + `uv.lock` 须锁版本（属新增依赖决策）。
- **仅告警不阻断**：命中语法错误时把英文告警串追加到观测 `content` 尾部，落盘照常成功。
- **只报语法级 parse error**：tree-sitter 对错误语法也能产出 partial AST（错误节点标 `ERROR`/`MISSING`），故只判"有语法错 + 首个错误节点行列"，不报未定义符号/类型错误（相比编译器方案语义更浅、误报更少，契合软告警定位）。
- **v1 覆盖全部 8 种语言**：统一由 tree-sitter grammar 驱动，CSS 不再是盲区。

## 三、方案概述（高层次）

采用 **「策略模式 + 注册表」**：每种语言一个 `LanguageChecker` 策略对象，按「扩展名 → 策略」注册表统一分发。`guard/` 下新增一个共享模块，暴露纯函数 `check_source_syntax(path, content=None)`，两个工具 handler 直接复用，既消除重复、又守住单一职责。

**为什么用共享函数而非装饰器**：
`write_file` 入参是单文件 `content`+`path`；`patch_tool` 的 replace 模式是 `new_content`+`path`、patch 模式是一次性多文件 `after`。入参形态异构，统一装饰器 `param="content"` 并不贴合。当前两个 handler 各自内联 `ast.parse`（重复且只覆盖 Python），故直接抽 `guard/syntax_check.py` 共享函数 `check_source_syntax`，在落盘后由两 handler 显式调用，改动更小、消除重复更直接，且守住 `guard/` 零业务依赖边界。

**调用时机**：在文件**落盘之后**调用（解析需读取已落盘字节），`path` 传已解析的绝对路径。

**内置解析器 vs 本机编译器**：
`LanguageChecker` 构造时持有一个 tree-sitter `Parser` 实例（`Parser(language=grammar.language())`），`check` 直接 `parser.parse(source_bytes)` 并读 `root_node.has_error` 与错误节点行列，**不再 spawn 子进程、不再 `shutil.which` 探工具、不再 `timeout` 兜底**。任何机器（装没装编译器）都生效，且覆盖 8 种含 CSS。

## 四、grammar 矩阵（每种语言）

| 语言 | 扩展名 | grammar 包 | 解析调用 | 缺失处理 |
|---|---|---|---|---|
| Python | `.py` | `tree-sitter-python` | `parser.parse` → `root_node.has_error` 判错 | 内置依赖，无缺失 |
| Java | `.java` | `tree-sitter-java` | 同上 | 内置依赖，无缺失 |
| Go | `.go` | `tree-sitter-go` | 同上 | 内置依赖，无缺失 |
| Rust | `.rs` | `tree-sitter-rust` | 同上 | 内置依赖，无缺失 |
| JavaScript | `.js/.mjs/.cjs` | `tree-sitter-javascript` | 同上 | 内置依赖，无缺失 |
| TypeScript | `.ts/.tsx` | `tree-sitter-typescript` | 同上（`TypeScriptChecker.build_parser()` 按扩展名选 `language_ts()` / `language_tsx()`，见 §5.1） | 内置依赖，无缺失 |
| HTML | `.html/.htm` | `tree-sitter-html` | 同上 | 内置依赖，无缺失 |
| CSS | `.css` | `tree-sitter-css` | 同上 | 内置依赖，无缺失（原方案盲区，现覆盖） |

统一约定：所有语言走同一套 in-process 解析路径，`root_node.has_error` 为真时遍历错误/`MISSING` 节点（`node.type == "ERROR"` 或 `node.is_missing`）收集 `line:column` + 简短描述，返回英文告警串，格式统一为 `[syntax-check] <lang>: parse error at line X:Y`（`<lang>` 小写语言名，见 §5.3）。**告警非阻断**。

内部结构（高层面，非代码）：

- `__all__ = ["check_source_syntax"]`：模块显式导出公共符号（符合 Python 规范第五章），`__init__.py` 仅做薄壳 `from .syntax_check import check_source_syntax`，不写逻辑。
- `MAX_CHECK_BYTES = 2 * 1024 * 1024`：体积门禁，超过则跳过检查（避免超大文件无谓解析）。
- `class LanguageChecker(ABC)`：抽象基类，含 `name` / `extensions` / `build_parser()`（构造 tree-sitter `Parser`） / `check(path)`。
- 8 个具体策略：`PythonChecker` / `JavaScriptChecker` / `TypeScriptChecker` / `GoChecker` / `RustChecker` / `JavaChecker` / `HtmlChecker` / `CssChecker`（各约 15~25 行）。**CSS 现由 `tree-sitter-css` 内置覆盖，不再延后**。`TypeScriptChecker` 覆盖 `build_parser()`，按扩展名选 `tree-sitter-typescript` 的 `language_ts()`（`.ts`）或 `language_tsx()`（`.tsx`）；其余策略 `build_parser()` 返回固定 grammar 的 `Parser`。
- `_REGISTRY: dict[str, LanguageChecker]`：由具体策略实例按 `extensions` 展开构造（扩展名 → 策略）。
- `check_source_syntax(path: str, content: str | None = None) -> str | None`：落盘后按扩展名查注册表 → 体积门禁 → `pathlib.Path.read_bytes()` → `parser.parse` → 若 `root_node.has_error` 遍历错误/`MISSING` 节点收集 `line:column` → 返回英文告警串或 `None`。

## 六、已知限制（须如实告知）

1. **只报语法级 parse error**：不报未定义符号/类型错误（相比原编译器方案语义更浅，但作为软告警误报更少、与"不阻断"定位更契合）。
2. **容错性导致漏报**：tree-sitter 对错误语法也能产出 partial AST，少数"轻微"语法问题可能被容忍而不标 `ERROR`，存在漏报可能（可接受，因仅告警）。
3. **错误定位粒度**：tree-sitter 只保证"有错 + 首个/全部 ERROR 节点行列"，不保证像编译器那样逐条列出所有精确诊断；按"全部 ERROR/MISSING 节点"实现，不夸大。
4. **性能更优**：in-process 解析，无子进程、无 10s `timeout` 开销；仍保留 2MB 体积门禁。
5. **新增依赖体积**：需 `uv` 锁版本引入 `tree-sitter` + 8 个 grammar 包（各为预编译 wheel，总增量几十 MB 级，跨平台一致）。

- 注册表：`.py`→PythonChecker、`.ts`→TypeScriptChecker、`.css`→CssChecker 等映射正确；未知扩展返回 `None`。

## 十、风险与回滚

- 新模块 `syntax_check.py` 为纯函数、零业务依赖，失败仅导致"少一次告警"，不会破坏写入结果正确性；若某语言 grammar 误伤正常文件，删除对应 `LanguageChecker` 或调整 `build_parser` 即可，回滚点清晰。
- 无子进程、无 `shutil.which` 探工具，不存在"因检查器缺失导致写入失败"的风险（任何机器依赖一致生效）。
- 性能兜底：2MB 体积门禁，避免大文件无谓解析；in-process 解析无 `timeout` 开销。
- 新增依赖风险：grammar 包须锁版本；若某平台 wheel 缺失导致安装失败，可临时在 `pyproject.toml` 将该语言 checker 置灰（保留注册表其余 7 项），不阻塞其它能力。

## 十一、未来扩展：Lint 工具（非本期，仅固化边界）

本期守卫只做**语法层**（tree-sitter parse error）。用户已明确规划一个**独立的 Lint 能力**，覆盖语义级诊断（未用变量 / 类型错 / 风格），走 LSP 或真实 linter（eslint / ruff / pyright / rust-analyzer 等）。本节仅固化其边界与形态，**不在本期实现、不预留抽象层**（YAGNI）。

### 11.1 与本期守卫的分层边界

| 能力 | 层 | 触发粒度 | 技术 | 阻断性 |
|---|---|---|---|---|
| 语法检查（本期） | `guard/` 横切模块 | 每次 edit 落盘后（同步） | tree-sitter | 不阻断（仅告警） |
| Lint（未来） | `tool_system` 注册 + `core` runtime 钩子 | 模型主动调用 / 每轮 turn-end（异步） | LSP / 真实 linter | 不阻断（被动诊断） |

关键区分：**tree-sitter（语法层）≠ LSP（语义/lint 层）**。本期 guard 已在每次编辑后跑 tree-sitter，已覆盖"语法可解析"；Lint 是语义级，须另走 LSP，不能复用本 guard 充当 lint。

**未来形态的分层契约（与现有规范兼容）**：未来 Lint 工具虽注册进 `tool_system`（属 `tools/`，合法），其"每轮 turn-end 自动触发"必须由 `core` runtime 经现有 `ToolScheduler` / `RuntimeOperations` 窄边界门面调度（即 `core → tools` 合法边，见 `rules/目录组织规范.md` 1.2 契约要点 5、9.3），**不得让 `tools/` 反向 import `core`**；该形态不突破 1.3 循环依赖红线（`core↔storage`/`tools→service` 等）。Lint 的自动触发逻辑若需放在 `core` 侧，仅消费 `ToolScheduler.execute` 接口，不新增 `tools → core` 依赖。

### 11.2 Lint 的双形态（用户规划）

1. **模型可主动调用**：lint 作为一等 `ToolDefinition` 注册进 `tool_system`，与现有 7 个内置工具同机制（契约单一事实来源、经 `core` 调度）。模型按 schema 自行决定何时调用。
2. **每轮对话结束自动跑**：在 `core` runtime 的 turn-end 钩子触发，复用同一 lint 逻辑，作为模型可能遗忘调用的安全网。

### 11.3 自动跑的约束（落地时须遵守）

- **非阻塞 / 后台异步**：LSP 启动 + 索引是重活，绝不可卡住回合结束；结果以事件/观察被动回传模型。
- **按本回合改动文件差集**：只对当轮 `turn` 改动的文件跑，避免全项目重扫；与模型主动调用做去重（同文件本回合已 lint 过不重复扫），避免浪费与噪音。
- **可配置开关**：v1 建议先只交付"可调用工具"形态，自动跑作为后续增强、默认关，契合本地桌面轻量定位。
- **不阻断落盘**：与语法 guard 一致，lint 诊断只告警、不阻断写入。

### 11.4 以后做（超出 Lint 双形态）

- **基线对比诊断**（参考 Claude Code `diagnosticTracking.ts`）：捕获编辑前基线，只回报 Agent 本轮新引入的问题，进一步降噪。本期不规划，待 lint 双形态落地验证后再评估。

### 11.5 禁止行为（边界纪律）

- 本期**不**为 lint 预留接口/抽象层；等真建时按 `ToolDefinition` 范式直接做，与 7 工具同构。
- 不把语法 guard 误当作 lint 使用，也不在 `guard/syntax_check.py` 内掺入语义诊断逻辑（守住单一职责）。
