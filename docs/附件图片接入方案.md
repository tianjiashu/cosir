# 附件图片接入方案

> 状态：设计讨论稿
>
> 基线：2026-09-13 当前 working tree、`@assistant-ui/react@0.15.17`、`@assistant-ui/core@0.3.16`、前端 `assistant-stream@0.3.40`，以及后端 `assistant-stream==0.0.36`。
>
> 目标：为当前单用户、本机运行的桌面 Agent 接入图片附件；先解决图片上传、预览、发送、历史恢复、重启恢复和视觉模型路由，不把附件系统扩张成公网文件服务。

## 1. 结论先行

推荐新增一个本机附件资源子系统，并把 assistant-ui 的 `AttachmentAdapter` 作为唯一前端附件生命周期入口：

```text
WebView
  │  AttachmentAdapter.add(File)
  ▼
FastAPI localhost
  │  multipart upload + server validation
  ▼
workspace 资源区
  ├─ <workspace_root>/.cosir/Attachment/.uploading/        待发送原图（无数据库事实）
  ├─ <workspace_root>/.cosir/Attachment/<asset-id>.source.<ext>  转换源（需要时保留）
  └─ <workspace_root>/.cosir/Attachment/<asset-id>.<ext>  模型可用的最终图片

app.sqlite3
  └─ conversation_runs.image_paths                         Run 对最终图片的引用

发送时：
WebView ── image: "cosir-attachment://<asset-id>" ──▶ Assistant Transport
                                                            │
                                                            ▼
                                                    canonical context
                                                            │
                                                            ▼
                                             model boundary resolves to bytes/data URL
```

核心决策如下：

1. **浏览器 `File` 只存在于 assistant-ui composer 生命周期内**，不进入 SQLite、LangGraph checkpoint 或前后端领域层。
2. **图片在发送前先上传**，Assistant Transport 的 `add-message` 只携带短的、稳定的附件 locator，不携带 base64 二进制。
3. **locator 使用应用自有的 `cosir-attachment://<uuid>` scheme**。它不是公网 URL，也不是文件系统路径；前端预览和后端模型输入各自负责解析。
4. **图片二进制按 workspace 隔离，放在 `<workspace_root>/.cosir/Attachment/`；图片引用复用现有 `conversation_runs.image_paths`**。`.cosir` 是 workspace 的 Cosir 元数据区，`Attachment` 是由 workspace 初始化流程创建的应用管理子目录；不新增附件表，不把大字段写进 SQLite 或 Transport snapshot。
5. **Run/context/snapshot 仍保持现有事实所有权**：Run 负责执行生命周期，context 负责模型消息，Transport snapshot 负责前端读取；附件资源由独立 attachment service 负责。
6. **第一阶段只支持图片**，前端可用 `image/*` 接收可解码图片；最终格式由后端依据所选模型的 capability 校验或转换。PDF、普通文件、目录和远程 URL 继续走既有文件引用/工具路线，不借图片链路偷渡。

这比直接把 `File` 转 data URL 放进请求更适合本项目：它控制 JSON 体积，允许后端重启后恢复，也不会让外部模型尝试访问本机 localhost URL。

## 3. Assistant UI 官方契约结论

依据官方文档：

- [File Attachments](https://www.assistant-ui.com/docs/guides/attachments)
- [Custom attachment uploads](https://www.assistant-ui.com/docs/integrations/attachments/custom-adapter)
- [Adapters — Attachment adapter](https://www.assistant-ui.com/docs/runtimes/concepts/adapters#attachment-adapter)
- [Attachment element](https://www.assistant-ui.com/elements/attachment)
- [Attachment adapter API](https://www.assistant-ui.com/docs/api-reference/adapters/attachments)

### 3.1 Adapter 的生命周期

官方 `AttachmentAdapter` 的关键契约是：

```ts
type AttachmentAdapter = {
  accept: string;
  add(input: { file: File }): Promise<PendingAttachment>;
  send(attachment: PendingAttachment): Promise<CompleteAttachment>;
  remove?(attachment: Attachment): Promise<void>;
};
```

语义不是“点击按钮后把 File 直接放进 message”：

1. `add` 在用户选择文件时执行；可以上传并返回 `requires-action`，让 composer 暂存附件。
2. `send` 在用户提交消息时执行；返回 `complete`，并提供要进入用户消息的 content part。
3. `remove` 只负责用户发送前移除 pending 资源的清理；已发送消息的附件是消息事实，不应因为 composer remove 被删除。
4. `add` 可以是 async generator，以 `running/uploading/progress` 逐步更新 UI。
5. 添加失败可以通过 `composer.attachmentAddError` 事件得到 `no-adapter`、`not-accepted`、`adapter-error` 等原因。

当前项目应使用这个生命周期，不在 `Thread` 里自建 `File[]` state，也不让 `ComposerPrimitive.Send` 绕过 adapter。

### 3.2 Assistant Transport 能承载附件，但项目 converter 必须补齐

官方 adapter support matrix 将 Attachments 列为 Assistant Transport 支持能力。当前安装的 Assistant UI 源码也明确：

- `useAssistantTransportRuntime` options 有 `adapters.attachments`。
- `add-message` command 的用户 part 支持 `text | image`。
- runtime 会把 `message.content` 与 `message.attachments[].content` 合并；只把 text 和 image 转成 Assistant Transport user parts。

这说明接入点是确定的：

```ts
useAssistantTransportRuntime({
  ...transportOptions,
  adapters: { attachments: imageAttachmentAdapter },
});
```

但是官方 runtime 的 command 只保留 image part 的 `image` 字符串，不会把 attachment 的 `id/name/contentType` 作为独立字段传给当前项目后端。因此项目必须让 `image` 字符串本身成为可验证的稳定 locator，或者在项目自定义 wire 层增加附件描述。推荐前者，保持与现有 Assistant Transport 用户 part 兼容。

### 3.3 为什么不采用 data URL 作为长期方案

官方文档把 `SimpleImageAttachmentAdapter` 的 data URL 方案定位为适合小图片；生产上传文档明确推荐先上传到对象存储，再在 `send` 中传稳定 URL。对本项目做本机化改造后，等价方案是“先上传到当前 workspace 的 `.cosir/Attachment`，再传稳定 asset locator”。

data URL 不适合作为本项目的长期契约，原因是：

- base64 使 JSON 请求和日志排查都膨胀；
- 每次 resume/edit/fork 都可能重复传输大块数据；
- data URL 若进入 context 或 checkpoint，会把二进制写入本应保存消息结构的地方；
- 外部 provider 的请求体限制和本项目的 48 MiB/64 MiB 图片预算会同时受到影响；
- 无法把“上传成功”和“消息发送成功”分成可恢复的两个阶段。

### 3.4 当前 DeepSeek 的实际模型输入

DeepSeek 当前官方视觉文档显示：视觉模型使用 OpenAI-compatible Chat Completions 的多段 `content`；当前文档以 `deepseek-flash` 为视觉模型名，旧名 `deepseek-v4-flash-vision-exp` 仍可接受但已属于 legacy 别名，实际请求由最新 Flash 服务。当前仓库的 provider 清单仍注册旧名，因此实现附件前必须先核对并同步模型目录，不要只依赖旧配置名。

对本项目，最终发给 DeepSeek 的请求应等价于：

```json
{
  "model": "deepseek-flash",
  "messages": [
    {
      "role": "user",
      "content": [
        {"type": "text", "text": "请分析这张图片"},
        {
          "type": "image_url",
          "image_url": {
            "url": "data:image/png;base64,<由后端临时生成>",
            "detail": "auto"
          }
        }
      ]
    }
  ]
}
```

这里的关键不是让 DeepSeek 读取 workspace 路径，而是由后端在模型调用前做一次短生命周期转换。图片必须先根据最终选定模型的 `image_limit.supported_formats` 归一化，再生成 data URL：

```text
<workspace_root>/.cosir/Attachment/<asset-id>.png
        │
        ├─ AttachmentContentResolver 校验 workspace、asset、hash、格式和大小
        ├─ ImageFormatNormalizer 按 ModelCapability.image_limit.supported_formats 校验/转换
        ├─ 读取本机文件并生成 data:image/...;base64,...
        └─ 仅放入本次 model.astream(messages) 的 deep copy
```

因此以下内容都不能直接发给 DeepSeek：

- `C:\...\\workspace\\.cosir\\Attachment\\...` 等本机绝对路径；
- `cosir-attachment://...` locator；它只属于本项目 Transport/context 资源契约；
- `http://127.0.0.1:<dynamic-port>/...`；DeepSeek 云端无法访问用户本机；
- 把图片放进 `system` 或历史 `assistant` message。DeepSeek 视觉图片应只出现在当前 `user` message，历史 context 中保存的是 `cosir_image_ref`，每次请求前只把 user image ref 解析为 provider block。

DeepSeek 还支持 Files API 的 `file_id` 方式，适用于超过 inline 限制或同一图片反复请求的场景。但这会引入 DeepSeek 云端文件生命周期、远端 file id 缓存和删除同步；第一阶段仍建议使用 workspace 本地文件 + 单次 data URL。按官方限制，inline 请求体约 48 MiB，单张 inline 图片不超过 32 MiB；项目层应采用更低的可配置上限。以后确有大图或重复引用需求，再增加 DeepSeek-specific Files API adapter，不改变本地 asset 和 context locator 事实。

格式判断不能只看上传文件的扩展名或浏览器 MIME：Pillow 先根据文件内容检测真实格式，再与 `ModelCapability.image_limit.supported_formats` 比较。当前能力文件中，`deepseek-v4-flash-vision-exp` 的目标集合是 `jpeg/png/gif/webp`；`deepseek-v4-flash` 与 `deepseek-v4-pro` 的 `supports_image` 为 `false`，不能通过“转换成图片”绕过视觉能力门禁。provider 配置里的 `vision_input_format: openai_url` 只决定最终 content block 的形状，不决定允许的图片格式。

当前代码的最小接线点是：`ReactLikeWorkflow` 已把 provider 的 `vision_input_format` 放入 `RuntimeConfig`，`model_node` 已统一调用 `model.astream(messages)`；需要新增的是 model-input boundary 的 resolver，并把 `RuntimeContextManager.load_message()` 返回的消息 deep copy 转成 DeepSeek 所需的 `image_url` block。不能继续让 `ensure_run_user_message()` 只写纯文本，也不能在 `transport_assistant_service.prepare_run_start()` 中把 image part 丢进 `input_text`。

### 3.5 非图片只拼接参考路径，让 Agent 通过既有工具处理

你的建议适合作为当前版本的非图片策略：非图片不上传、不复制到 `.cosir/Attachment`，不解析文件内容；只把用户明确选择的路径作为文本追加到本轮 input：

```text
[参考附件]
H:\coding-agent\AGENTS.md
```

多个非图片附件使用重复的路径行即可：

```text
[参考附件]
H:\coding-agent\AGENTS.md
H:\coding-agent\docs\附件图片接入方案.md
```

模型收到的只是这段路径文本。它需要读取内容时，再自行调用现有 `read_file`、`search_files`、`list_directory` 或其它受控工具；工具返回的文件内容才进入后续模型上下文。这样既不把大文件内容塞进初始请求，也不需要为 PDF/DOCX/XLSX 维护一套解析器。

运行链路调整为：

```text
非图片选择
  → 得到用户明确选择的本机路径
  → 后端规范化并检查路径参数
  → 生成 “[参考附件]\\n<path>” 文本片段
  → 与用户文本拼接为 input_text
  → context 只保存这段文本
  → Agent 按需调用既有文件工具读取
```

边界必须明确：

- 非图片不产生图片 asset 或 `.cosir/Attachment` 文件；图片目录和 `image_paths` 只服务图片资源。
- 初始 Assistant Transport command 中只携带路径文本，不携带文件内容、base64、文件二进制或新的 `file` part；这正好兼容当前 runtime 自动转发 `text | image` 的事实。
- 路径不是授权令牌，也不是“模型可以任意读取机器文件”的新权限；工具执行仍遵循当前 permission 和路径解析策略。当前 `read_file` 已支持显式绝对路径的只读读取，方案不额外扩大其范围。
- 前端不能从普通浏览器 `File` 对象推断可靠的绝对路径；如果产品必须展示 `H:\...` 这种路径，应由桌面文件选择器或已知 workspace 文件入口提供路径，再交给后端校验。不能使用 filename 猜路径。
- workspace 内路径可以保留绝对路径以匹配当前工具行为；后续若需要 workspace 可迁移，再增加相对路径表示，但不要在本阶段同时引入两种语义。
- 路径只代表“参考附件”，文件不存在、是二进制或没有权限时，由工具返回稳定错误，Agent 自己决定询问用户或采取下一步；后端不预读、不自动摘要、不静默复制。

该策略也意味着非图片不需要 DeepSeek 原生文件能力：DeepSeek 只接收用户文本，以及图片时的 `image_url` block；非图片内容通过工具结果间接进入模型。

前端可以继续为非图片显示文件名/路径型附件 UI，但发送语义必须落成上述文本片段，不要依赖 assistant-ui `CompleteAttachment.content` 中的 `file` part，因为当前已安装 runtime 不会自动把它转发到项目 Assistant Transport。

## 4. 推荐架构

### 4.1 进程、数据与启动/停止

| 内容 | 归属 | 建议事实 |
|---|---|---|
| 文件选择、缩略图、上传进度 | WebView / assistant-ui runtime | 只持有当前 composer 的 pending 状态 |
| 上传、格式校验、尺寸校验、落盘 | FastAPI backend | 由 attachment service 负责，API 只做 schema/错误映射 |
| 图片二进制 | workspace 文件系统 | 上传原图先放在 `<workspace_root>/.cosir/Attachment/.uploading/`；若发生格式转换，绑定后保留 `<asset-id>.source.<source-ext>` 与模型可用的 `<asset-id>.<normalized-ext>`，均由 AttachmentService 管理 |
| 图片格式事实 | AttachmentService / Pillow | 根据文件内容检测真实格式；最终格式由 `ModelCapability.image_limit.supported_formats` 决定，不信任 MIME/扩展名 |
| 图片元数据 | workspace 文件系统 | MIME、尺寸、大小、hash 按需从最终图片检测；不新增附件表 |
| 对话中使用的图片集合 | `conversation_runs.image_paths` | Run 级 JSON 引用，支持历史、fork、edit；不新增关联表 |
| 非图片参考附件 | 当前 Run 的 `input_text` | 只追加 `[参考附件]` 与用户选择的路径，不复制、不预读、不建立图片 asset 关系 |
| 模型可见的图片 block | workflow/model input boundary | locator 在这里解析成 provider 要求的实际内容 |
| 预览图片 | FastAPI content endpoint | WebView 使用当前动态 backend base URL 拼接，不访问本地路径 |
| 进程启动/停止/重启 | Tauri Rust supervisor | 与现有 backend lifecycle 一致，不新增附件进程 |

workspace 初始化与后端崩溃/重启时：

- `WorkspaceService.create_workspace` 创建 `.cosir` 时同步幂等创建 `Attachment` 子目录；已存在时不覆盖、不清空、不改变其中已有文件。
- 对历史 workspace，后端启动或第一次上传前由 workspace/attachment service 做一次幂等补建；补建失败应返回 `ATTACHMENT_STORAGE_UNAVAILABLE`，不能把图片落到全局目录。
- workspace 根目录是用户项目目录，应用只负责自己创建的 `.cosir/Attachment`，不创建或删除 workspace 根目录。

- 完整图片文件继续存在，引用保存在 Run 的 `image_paths`；不需要恢复进程内附件 registry。
- `.uploading` 临时文件仅在对应 workspace 的 `.cosir/Attachment` 内清理，或按 mtime 做有限清理；不能扫描或删除 workspace 其它目录。
- 现有 supervisor 继续负责有限重启；遗留 active Run 按现有规则收敛为 `cancelled`，不会自动重放模型调用。
- 重新打开任务时，state rebuilder 从 Run/context/attachment 事实重建用户消息附件；前端重新 attach 现有 run。

### 4.2 数据模型

本项目可以不新增附件数据库表，直接复用现有 `conversation_runs.image_paths`：

```text
conversation_runs.image_paths
------------------------------
[
  ".cosir/Attachment/2f1c...a9.png",
  ".cosir/Attachment/8b72...10.jpg"
]

```

说明：

- `image_paths` 是当前 Run 的图片引用事实；只写发送最终化后的 workspace-relative 受控路径，不写暂存路径、绝对路径、data URL 或任意 locator。
- 图片文件名使用随机 UUID 加 capability 选定的受控扩展名，因此文件名同时承担稳定 id 作用；预览、模型解析和历史回放都从 workspace root 拼接，并检查路径仍位于 `.cosir/Attachment` 内。源格式转换前后 locator/id 不变。
- MIME、尺寸、大小和 hash 不作为强一致数据库事实；需要时从图片文件重新检测。文件缺失时 Run 以稳定错误结束，不能静默降级为文本。
- 同 workspace fork 复制 `image_paths` 字符串，不复制文件；跨 workspace fork 必须复制文件到目标 workspace 或明确拒绝。
- orphan GC 扫描 `.cosir/Attachment`，收集所有现存 Run 的 `image_paths` 后删除未被引用的最终图片、对应的 `.source` sidecar、`.uploading` 暂存原图和转换残留文件。GC 是旁路，不改变 Run 状态。
- 不新增 `attachment_assets`、`conversation_run_attachments` 或 cleanup 表；代价是无法高效查询单个图片的引用历史、无法保存独立 staged 状态和精确上传元数据，但对当前单用户本机规模可以接受。

`conversation_runs.image_paths` 的处理建议：

- 新 Assistant Transport 可以写入它，但只能写受控 workspace-relative 图片路径。
- 旧路径能力若仍有调用方，保留兼容读取并明确区分 legacy path attachment 与新 `.cosir/Attachment` 图片。
- 不要把 `cosir-attachment://` locator 或其它 asset id 写进这个字段；如果未来需要独立元数据，再单独评估是否新增表。

### 4.3 本机上传 API

建议新增薄 API 模块：`apps/backend/app/api/attachments_api.py`，该 API 只服务图片上传与预览；非图片参考附件不走上传 API。业务逻辑放在：

- `apps/backend/app/service/attachment/attachment_service.py`
- `apps/backend/app/storage/model/conversation_run_model.py` 的现有 `image_paths`
- 对应文件安全 resolver、schema、测试；本方案不新增 attachment ORM 表

接口建议：

```text
POST   /tasks/{task_id}/attachments
       Content-Type: multipart/form-data
       field: file
       response: { id, name, contentType, byteSize, width, height, locator, status: "staged" }

DELETE /tasks/{task_id}/attachments/{asset_id}
       只允许删除 `.cosir/Attachment` 中未被任何现存 Run 的 image_paths 引用的图片

GET    /tasks/{task_id}/attachments/{asset_id}/content
       返回图片字节，Content-Type 为服务端确认后的类型
```

上传 API 的边界：

- `task_id` 是 workspace 归属校验，不是认证机制；localhost 单用户不需要引入认证，但不能因此省略 task/path 关系校验。
- 上传先解析 `task_id` 对应 workspace，并确保 `<workspace_root>/.cosir/Attachment` 已由 workspace 初始化流程创建；然后写入 `.uploading` 下的随机临时文件，再流式限制大小，完成后由 Pillow 检测真实格式和尺寸。此时只完成安全暂存，不根据当前 UI 模型提前做不可逆转换。
- 客户端传来的 filename、MIME、扩展名只用于提示和初步过滤，不能作为真实格式事实。
- 用户点击发送时，后端以 Run 最终选定的 `model_name` 读取 `ModelCapability.get_capability(model_name)`；在创建 Run 事务前完成格式校验/转换，并把最终文件以 `<asset-id>.<normalized-ext>` 原子落盘。`cosir-attachment://<asset-id>` 保持不变，文件扩展名变化不泄漏到 wire locator。
- 最终化成功且 Run 的 `image_paths` 写入成功后，将发生转换的 `.uploading` 原图原子改名为 `<asset-id>.source.<source-ext>` 并保留；未发生转换时直接把它改名为最终文件。Run 创建失败时保留 `.uploading` 原图供重试，按 TTL/GC 清理。
- `GET content` 只能按 task + UUID 在 `.cosir/Attachment` 的暂存/最终受控文件中解析；不允许把用户输入直接拼成任意 filesystem path。
- 响应使用 `Cache-Control: no-store`；第一版不需要公网缓存、Range 下载或预签名 URL。
- 删除和 GC 失败只记录结构化日志，不阻塞已经成功的 Run；但不能静默删除仍有 Run 引用的图片，也不能越过 workspace 边界删除文件。

### 4.4 Assistant Transport wire 契约

新增 project-owned request part：

```python
class AssistantImagePart(BaseModel):
    model_config = ConfigDict(extra="forbid")

    type: Literal["image"]
    image: str  # cosir-attachment://<uuid>
```

建议用 discriminated union：

```python
AssistantUserPart = Annotated[
    AssistantTextPart | AssistantImagePart,
    Field(discriminator="type"),
]
```

校验规则：

- `image` 必须匹配 `cosir-attachment://` 加合法 UUID；第一阶段拒绝 `data:`、任意 `file:`、任意本地绝对路径和任意外部 URL。
- user message 至少有一个非空 text 或 image part；这样支持纯图片消息。
- text 仍沿用当前的去首尾空白和长度上限。
- part 数量和图片数量分别设上限；建议先复用现有 20 张预算，再按 provider 的 `max_images_per_request` 取更小值。
- `payload_hash()` 必须把 image locator 纳入 hash；同一 `(task_id, command_id)` 用不同图片提交时必须按现有幂等规则拒绝。
- 后端必须检查每个图片 locator 对应的 UUID 文件存在、真实类型为 image、路径位于当前 workspace 的 `.cosir/Attachment`；不能相信 locator 里的 UUID 就直接读盘。

Transport snapshot 建议增加**用户消息附件描述**，而不是把二进制或内部 context block 暴露给前端：

```json
{
  "id": "user-42",
  "role": "user",
  "parts": [
    { "type": "text", "text": "请分析这张图", "status": "completed" }
  ],
  "attachments": [
    {
      "id": "asset-uuid",
      "type": "image",
      "name": "diagram.png",
      "contentType": "image/png",
      "locator": "cosir-attachment://asset-uuid"
    }
  ]
}
```

这里的 `attachments` 是 Transport wire DTO，不是 Agent context 的镜像。它只供前端 converter 生成 assistant-ui `CompleteAttachment`：

```ts
{
  id,
  type: "image",
  name,
  contentType,
  content: [{ type: "image", image: locator }],
  status: { type: "complete" },
}
```

前端 `useAttachmentSrc` 再把 locator 解析为当前 `backendBaseUrl` 下的 `/tasks/{taskId}/attachments/{assetId}/content`。这样：

- Assistant Transport 发送给后端的仍是 locator；
- snapshot 中的 attachment 能带回文件名和类型；
- state rebuilder 不需要 IO；
- 重启或动态端口切换后，前端仍能用当前 runtime config 预览。

如果希望保持 snapshot 更小，也可以只放 `id/name/contentType/locator`；不要放 data URL。

### 4.5 图片格式校验与转换

`model_capabilities.json` 是模型图片能力的唯一配置来源，格式归一化不能依赖 provider 名称、前端 `accept` 或文件扩展名。实现建议新增内部组件 `ImageFormatNormalizer`，复用现有的 `ModelCapability` 解析器：

```text
model_name
  → ModelCapability.get_capability(model_name)
  → supports_image == true
  → image_limit.supported_formats
  → Pillow 按文件内容检测 source_format
  → source_format 已支持：保留/规范化后直接使用
  → source_format 不支持：选择 target_format 并转换
  → 重新检测输出格式、尺寸、大小后原子落盘
```

必须遵守以下规则：

- `supported_formats` 中的值按小写、无点号比较，例如 `jpeg`、`png`、`gif`、`webp`；Pillow 返回的 `JPEG` 应规范化为 `jpeg`。格式判断使用 `Image.open()`/`verify()` 的真实内容，不使用 `Path.suffix` 或请求 MIME 作为事实。
- `supports_image == false` 或 `image_limit`/`supported_formats` 缺失时直接返回 `VISION_NOT_SUPPORTED`，不能把图片转换后当作普通文本发送，也不能假设所有 provider 都支持图片。
- 已经在 `supported_formats` 中的图片不做无意义重编码；仍需执行尺寸、像素、单图大小和请求总量检查。provider 的 `vision_input_format` 只负责把最终文件转换为 `image_url` 等 wire block，不参与格式白名单判断。
- 不支持的静态图片按确定性策略选目标格式：有透明通道时优先 `png`，普通 RGB 图片优先 `jpeg`；目标不存在时再使用 `webp`/其它 capability 明确允许的格式。若目标只有 `jpeg` 而源图有透明通道，必须按显式背景色 flatten，不能让 Pillow 隐式丢失透明度。
- 动图不能静默只取第一帧。只有目标格式能够按当前策略保留动画时才转换；否则返回 `IMAGE_CONVERSION_UNSUPPORTED`，由用户改用静态图片或视觉模型支持的格式。
- 转换前使用 `ImageOps.exif_transpose` 固化方向；默认剥离 EXIF/GPS 等不需要发送给模型的元数据。输出扩展名、MIME、尺寸和大小必须由转换结果重新计算。
- 当前 DeepSeek 视觉能力的 `supported_formats` 为 `jpeg/png/gif/webp`，因此 JPEG、PNG、GIF、WebP 不转换；BMP、TIFF 等 Pillow 可解码但不在集合内的静态图片，在目标集合允许时转换为 PNG/JPEG。DeepSeek 非视觉模型仍然拒绝图片。

建议把 normalizer 的输出契约固定为纯值对象，避免转换逻辑渗入 Transport、context 或 CRUD：

```python
NormalizedImage(
    source_format="bmp",
    target_format="png",
    content_type="image/png",
    path=".cosir/Attachment/<asset-id>.png",
    width=1600,
    height=900,
    byte_size=...,
)
```

normalizer 只负责 capability 驱动的检测、转换和输出复检，不负责创建 Run、不写 SQLite、不发布事件；AttachmentService 负责文件安全与 sidecar，Run command service 负责把最终 `path` 写入现有 `image_paths`。

转换时机采用“上传暂存、发送最终化”：

1. `POST /attachments` 只验证真实图片并把原图写入 `.cosir/Attachment/.uploading/<asset-id>.<source-ext>`；返回稳定的 `cosir-attachment://<asset-id>`，不绑定具体输出扩展名。
2. `send`/Run 创建用例确定最终 `model_name` 后，从 capability 读取目标集合并执行校验或转换。
3. 成功后将最终图片原子写入 `.cosir/Attachment/<asset-id>.<target-ext>`；如果 `source_format != target_format`，同时将源图保存为 `.cosir/Attachment/<asset-id>.source.<source-ext>`。Run 事务只保存最终相对路径到 `conversation_runs.image_paths`。
4. 最终文件和 Run 引用都成功后，清理 `.uploading` 文件；转换源作为同一 asset 的 sidecar 保留，允许后续模型切换或 edit 重新转换。若失败则保留暂存文件，过期暂存和无引用 sidecar 由 GC 清理。

这样既避免用户上传后切换模型导致格式不匹配，也不需要新增附件表、staged 状态表或转换记录表。代价是发生转换的图片会占用两份文件空间；GC 必须按 asset id 成对清理最终文件和 source sidecar。

### 4.6 Canonical context 与模型输入

附件资源和 context 消息必须分层：

```text
持久化 context message:
  HumanMessage(
    content=[
      {"type": "text", "text": "请分析这张图"},
      {"type": "cosir_image_ref", "asset_id": "..."},
    ]
  )

模型实际输入:
  HumanMessage(
    content=[
      {"type": "text", "text": "请分析这张图"},
      {
        "type": "image_url",
        "image_url": {"url": "data:image/png;base64,..."},
      },
    ]
  )
```

推荐实现一个后端内部的 `AttachmentContentResolver`，位于 context/workflow 到 model 的边界：

- 只消费 project-owned `cosir_image_ref`；
- 校验 asset 元数据和文件 hash，通过 workspace 记录定位并读取 `<workspace_root>/.cosir/Attachment` 内的最终文件；若已有最终文件不再符合当前 capability，则从 `.source` sidecar 重新归一化到请求临时文件，不在 resume 过程中偷偷改写 Run 事实；
- 在 resolver 处再次以 `ModelCapability.get_capability(run.model_name)` 做最终防线，防止 capability 配置更新或旧 Run 绕过发送用例；
- 按 `vision_input_format` 转成当前 provider 支持的 LangChain content block；当前已知路径先实现 `openai_url`，其值可以是 data URL；
- 返回给模型的是 deep copy，不修改 context working copy，不把 data URL 回写 SQLite；
- provider 不支持图片、格式未实现或尺寸/体积超限时抛出稳定的 `VisionNotSupportedError`/`VisionImageError`，由 Run service 按现有错误收敛规则处理。

`model_node` 及其它模型调用日志不得直接序列化解析后的消息；必须把 `data:image/...;base64,...` 替换为 `{type: "image", format, byte_size, sha256_prefix}` 等脱敏描述后再记录。模型能看到完整图片，不代表日志、context、snapshot 或 SQLite 可以看到图片字节。

`RuntimeContextManager` 的建议变化：

- `ensure_run_user_message` 从只收 `text` 改为收结构化的 `UserInput`/`RunInput` value object；其中非图片参考路径已经合并在 `text` 中；
- 持久化时写 text block + image ref block；不写二进制；
- `load_message` 或紧邻的 workflow model-input boundary 执行 `resolve_for_model`；必须显式传入 provider/vision format，不能靠 manager 是否首次创建来推断；
- `content_to_text` 继续只抽取 text，图片不能被拼成路径或伪文本；
- context usage listener 对图片按元数据和统一估算口径计数，不能把 base64 字符长度当成精确 provider billing token。

这样可保持现有架构原则：context 是模型上下文事实，Transport snapshot 是前端投影，Run 状态仍只有 `ConversationRunModel.status` 一套事实源。

### 4.7 Provider/model 能力门禁

当前前端模型目录已经有 `supportsImage`，后端静态模型能力也有 `supports_image`。但两者都只是能力目录，不是模型连接测试结果。

发送前和后端启动 Run 时都做门禁：

1. 前端：当前选中模型不支持图片时，附件按钮可以隐藏或置灰，并显示简短提示。
2. 后端：无论前端如何表现，都重新校验 `model_name` 的 `supports_image` 和 provider 的 `vision_input_format`。
3. 后端失败应返回稳定错误码，如 `VISION_NOT_SUPPORTED` 或 `VISION_INPUT_FORMAT_UNSUPPORTED`，不返回 provider 原始异常。
4. 门禁失败不能删除已上传但尚未绑定 Run 的图片文件；用户换成视觉模型后可以重试。孤儿清理由 TTL/GC 负责。
5. `supports_image=true` 但 provider format 为空时，视为当前项目未实现，而不是尝试把图片当普通文本发送。

第一阶段只承诺已经有完整 provider 转换器的模型。不要因为 capability JSON 标记了图片能力，就自动声称所有 provider 都支持本地附件解析。

## 5. 前端落地设计

### 5.1 Adapter 的放置与稳定性

新增建议文件：

```text
apps/desktop/lib/assistant/attachments/
├─ image-attachment-adapter.ts
├─ attachment-locator.ts
└─ attachment-upload.ts
```

`image-attachment-adapter.ts` 只实现 assistant-ui adapter；它不读取 SQLite、不修改 Transport state、不参与 Run 生命周期。

adapter 由 `AssistantRuntimeSession` 按 `taskId + backendBaseUrl` 用 `useMemo` 创建，并注入 [`use-runtime-transport.ts`](../apps/desktop/components/assistant/runtime/use-runtime-transport.ts) 的 Assistant Transport options：

```ts
adapters: {
  attachments: imageAttachmentAdapter,
},
```

不要在每次 render 创建一个新 adapter；官方 runtime/remote thread list 会因 adapter identity 变化重载 runtime，可能取消进行中的 mutation。

### 5.2 `add`、`send`、`remove`

建议语义：

```ts
const imageAttachmentAdapter: AttachmentAdapter = {
  accept: "image/*",

  async *add({ file }) {
    // 1. 本地初步校验：MIME、大小、文件名长度（不作为最终格式事实）
    // 2. yield running/progress（XHR upload progress）
    // 3. POST /tasks/{taskId}/attachments
    // 4. yield requires-action；后端返回稳定 locator，content 暂不放 data URL
  },

  async send(attachment) {
    // add 只完成原图暂存；send 由后端按最终 model capability 校验/转换
    // 这里不重复传二进制
    // 返回 content: [{ type: "image", image: attachment.locator }]
  },

  async remove(attachment) {
    // 只对尚未被任何 Run 的 image_paths 引用的图片调 DELETE
  },
};
```

实际 TypeScript 类型可以通过 `PendingAttachment & { locator: string; assetId: string }` 扩展，不能把自定义字段写入 assistant-ui 的通用 wire 类型后再让后端依赖它；真正发给后端的唯一事实仍是 `image` locator。

上传进度建议采用 `XMLHttpRequest.upload.onprogress`，因为浏览器 `fetch` 对 request body upload progress 支持不稳定。adapter 将进度映射为官方 `running/uploading/progress` 状态；不需要为此新增上传进程或队列。

### 5.3 Composer 和消息渲染

在 [`thread.aui.tsx`](../apps/desktop/components/assistant-ui/elements/thread.aui.tsx) 的 Composer 中：

```tsx
<ComposerPrimitive.Root>
  <ComposerPrimitive.AttachmentDropzone>
    <ComposerAttachments />
    <ComposerPrimitive.Input />
    <ComposerAddAttachment />
  </ComposerPrimitive.AttachmentDropzone>
  ...
</ComposerPrimitive.Root>
```

用户消息中挂载：

```tsx
<MessagePrimitive.Root data-role="user">
  <UserMessageAttachments />
  <MessagePrimitive.Parts>...</MessagePrimitive.Parts>
</MessagePrimitive.Root>
```

编辑态 Composer 也要挂载附件列表和 add/dropzone，否则“历史消息有图，但点击编辑后无法保留/追加图片”。编辑时沿用 assistant-ui 对 complete attachment 的发送语义；后端 edit 用例必须把新 command 中的图片路径原子写入新的 Run `image_paths`。

`ComposerAction` 目前只用文本长度决定 send/resume/stop，必须改成：

```text
isDraftEmpty = text.trim().length == 0 && attachments.length == 0
```

否则纯图片消息会被误判为空，无法发送。

### 5.4 Locator 预览解析

`useAttachmentSrc` 的解析顺序建议：

1. pending attachment 有 `file`：创建 object URL，并在 effect cleanup 时 revoke；
2. complete attachment 的 image content 是普通安全 URL：按既有规则使用；
3. image content 是 `cosir-attachment://id`：解析 UUID，并用当前动态 `backendBaseUrl` 构造 content endpoint；
4. 任何未知 scheme：返回 `undefined`，显示 file fallback，不把未知字符串直接放入 `<img src>`。

这样避免 backend 重启换端口后历史消息仍引用旧端口，也避免将本地文件绝对路径暴露给 DOM。

### 5.5 Converter 和 optimistic state

需要同步修改：

- [`apps/desktop/lib/assistant/contract.ts`](../apps/desktop/lib/assistant/contract.ts)：增加 image part 和 user message attachment DTO。
- [`apps/desktop/lib/assistant/converter.ts`](../apps/desktop/lib/assistant/converter.ts)：把 snapshot user attachments 投影为 `ThreadUserMessage.attachments`；不要再固定 `attachments: []`；保留 image content 供 Assistant Transport 发送。
- optimistic pending message：从 command image parts 生成最小的 pending/complete attachment 投影，至少保留 locator；不要把原始 File 伪造回 snapshot。
- failed transport restore：现有 restore 只恢复 text。附件已在 upload-first 阶段落盘，失败后应让 composer 保留可重试的 attachment，或者通过明确的 `restoreNewMessage({ text, attachments })` 恢复；不能因为恢复 text 而丢掉用户已经上传的图片。
- [`apps/desktop/components/assistant-ui/elements/attachment.aui.tsx`](../apps/desktop/components/assistant-ui/elements/attachment.aui.tsx)：保留现有 UI 结构，补齐无 preview URL、unknown scheme、上传失败和键盘可访问性测试。

不要让 `TransportMessage` 直接暴露 `File`、object URL 或 backend absolute URL 作为持久化事实。

## 6. 后端落地设计

### 6.1 请求 schema 与 service 编排

`AssistantTransportRequest` 的纯 wire validator 负责：

- discriminator part 结构；
- locator 语法；
- text/image 至少一个；
- command id 唯一；
- 基础数量/长度预算。

`TransportAssistantService` / `ConversationRunCommandService` 负责：

- 从 image locator 提取图片文件名/路径；非图片路径已经是 input text 的一部分，不提取文件内容；
- 查 attachment service 验证图片 locator，并要求其属于当前 task 的 workspace；
- 用最终 `model_name` 获取 `ModelCapability`，执行 `ImageFormatNormalizer` 的格式校验/转换和图片限制校验；
- 先以临时文件 + 原子 rename 完成最终图片落盘，再在**同一个数据库事务**内创建/编辑 Run、创建 command 幂等记录、写入 Run 的 `image_paths`；文件系统与 SQLite 不宣称跨存储原子性；
- `image_paths` 只写最终化后的 workspace-relative 路径；转换输出未成功落盘时不得创建带图片的 Run；若随后 DB 事务失败，保留文件交给 orphan GC，不能留下可被 Run 引用的半成品状态；
- commit 后再发布 Run/snapshot 事件。

建议给 command service 增加结构化 `RunInput`，而不是继续向 `start_or_attach` 传单个 `input_text`：

```python
@dataclass(frozen=True)
class RunInput:
    text: str
    image_paths: tuple[str, ...]
```

其中 `text` 是用户正文加上非图片参考附件文本块（例如 `[参考附件]\\nH:\\coding-agent\\AGENTS.md`）；`image_paths` 只包含受控的 workspace-relative 图片路径。它属于 service/domain 边界，不属于 assistant-ui wire 类型。`ConversationRunRecord.input_text` 保存这段可恢复的文本（不保存非图片内容），图片路径复用现有 `image_paths` 持久化。

### 6.2 Workflow 和 context 的调用顺序

新 Run：

```text
Assistant request
  → parse text + image locators
  → validate task/asset/model capability
  → normalize each image against supported_formats
  → atomically persist final image
  → create command/run/image_paths (one DB transaction)
  → executor starts
  → RuntimeContextManager.begin_run(fresh)
  → ensure_run_user_message(RunInput)
  → model_node.load_message()
  → AttachmentContentResolver.resolve_for_model()
  → model.astream(resolved_messages)
```

resume：

- 不重复绑定或复制同一条 user message；
- 从持久化 context 或 Run `image_paths` 读取 image ref；
- 在每次真正调用模型前重新解析图片路径，文件不存在时以稳定错误结束，不能静默删除 image block 或降级为文本；
- 不根据“manager 是否已经存在”推断 fresh/resume。

edit：

- 先验证目标是 task 的 latest 可编辑 Run；
- command payload hash 包含新图片 locator；
- 同一事务清理旧 Run 的 context/message 轨迹，替换 Run 的 `image_paths`，重置 checkpoint thread；
- 旧图片路径如果没有其它 Run 引用，进入 orphan GC，而不是在 edit 事务内直接物理删除。

### 6.3 Snapshot rebuilder

`ConversationTaskStateRebuilder` 保持纯函数，不在 rebuild 中读取文件：

- 从 persisted Run 的 `image_paths` 或 HumanMessage 的 image ref block 读取图片路径与展示元数据；
- 生成 Transport `attachments` DTO；
- 只把稳定 locator 放入 attachment content；
- 不生成 data URL、不访问 workspace 文件系统、不读取磁盘；文件解析只发生在 model-input boundary。

如果当前 context 序列化格式不适合承载自定义 block，应先定义一个后端自己的 `ConversationUserInput` 序列化层，再转换成 LangChain `HumanMessage`；不要把 `@assistant-ui/*` 类型泄漏到 `core/context` 或 storage。

snapshot validator 要新增：

- message `attachments` 允许的字段集合；
- asset id/locator 格式；
- `type == image`、contentType `image/*`；
- attachment 顺序和唯一 id；
- 禁止未经治理的任意字段、data URL、绝对路径。

## 7. 安全、资源和错误策略

### 7.1 文件安全

- 所有上传落盘路径由后端根据随机 UUID 生成；禁止使用原始 filename 作为路径组成部分。
- 临时文件和正式文件都位于对应 workspace 的 `.cosir/Attachment`；正式文件名使用 asset id 或受控 storage key。
- 使用 `Path.resolve()` 后检查仍位于当前 workspace 的 `.cosir/Attachment` 内；禁止借助 `..`、符号链接或外部 storage key 越界。
- 限制单文件大小、单张尺寸、单次图片数和单次聚合大小；限制必须在流式读入阶段生效。
- Pillow 负责真实格式、尺寸和解压炸弹防护；不信任 MIME/扩展名。真实格式先与 `ModelCapability.image_limit.supported_formats` 比较。
- 格式不匹配时由 `ImageFormatNormalizer` 转换为 capability 允许的目标格式；转换必须使用临时输出文件 + 原子 rename，重新验证输出格式、尺寸和大小。剥离 EXIF/GPS 后，原始上传作为受控 `.source` sidecar 保留但不作为模型输入。
- 日志只记录 asset id、task id、run id、mime、byte size、校验结果和错误码，不记录图片内容、base64、token 或完整请求正文。

### 7.2 稳定错误码

建议至少定义：

| 错误码 | 场景 | retryable |
|---|---|---:|
| `ATTACHMENT_FILE_TOO_LARGE` | 上传超过单文件限制 | false |
| `ATTACHMENT_TYPE_UNSUPPORTED` | 不是可解码图片或真实内容不是图片 | false |
| `ATTACHMENT_IMAGE_INVALID` | 图片损坏、尺寸非法、解压风险 | false |
| `IMAGE_CONVERSION_UNSUPPORTED` | 没有保持语义所需的 capability 目标格式（例如动图无法安全转静态图） | false |
| `IMAGE_CONVERSION_FAILED` | Pillow 转换或输出复检失败 | true |
| `ATTACHMENT_NOT_FOUND` | locator 对应资源不存在 | false |
| `ATTACHMENT_NOT_OWNED` | asset 不属于当前 task/Run 使用范围 | false |
| `VISION_NOT_SUPPORTED` | 模型不支持图片 | false，换模型后重试 |
| `VISION_INPUT_FORMAT_UNSUPPORTED` | provider 转换器未实现 | false |
| `ATTACHMENT_STORAGE_UNAVAILABLE` | 本机目录不可写/读取失败 | true |
| `ATTACHMENT_ORPHAN_CLEANUP_FAILED` | GC 旁路失败 | 不影响主 Run |

前端只展示受控短提示，模型/provider 原始异常只进入后端结构化日志和受控 Run error，不经 Transport 原样回传。

### 7.3 生命周期和 GC

- 上传成功但用户未发送：`.uploading` 原图按 TTL 或 orphan GC 清理，例如 24 小时；不需要 staged 数据库状态。
- Run 创建前的格式转换输出若没有成功绑定到 `image_paths`，视为转换残留，由 GC 清理；不在数据库中记录转换状态。
- 若 asset 存在 `.source` sidecar，删除、fork、edit 和 GC 必须将它与最终文件作为同一 asset 处理，不能只删除其中一个。
- 用户点击 remove：调用 `DELETE`；只有确认没有任何 Run 的 `image_paths` 引用时才能删除。
- 已发送消息的图片不受 composer remove 影响。
- edit 替换图片后，旧路径只有在没有任何 Run 引用时才进入 GC。
- 同 workspace fork 复制 `image_paths` 字符串，不复制二进制；跨 workspace fork 必须复制图片到目标 workspace 或明确拒绝。
- 任务删除后，GC 根据剩余 Run 的 `image_paths` 清理无引用图片；物理删除只允许发生在对应 workspace 的 `.cosir/Attachment` 内。
- workspace 删除不删除 workspace 根目录；若要清理 `.cosir/Attachment`，必须先收集并安全删除该应用管理目录内的图片，失败时记录结构化日志并保留文件，不能递归删除用户 workspace。

## 9. 验收标准

### 功能

- 选择、拖放、粘贴图片均能进入 composer；上传过程中有进度或明确 pending 状态。
- 上传失败不会创建 Run；用户可以移除失败附件并重试。
- 文本+图片和纯图片消息都能发送。
- 非图片附件只向模型初始 input 追加参考路径，未拼接文件内容、未复制到 `.cosir/Attachment`；Agent 可按需调用现有文件工具读取。
- 图片真实格式由 Pillow 检测，并依据最终模型 capability 的 `image_limit.supported_formats` 校验；不匹配时转换为确定性目标格式，转换失败或无法保持语义时给出稳定错误。
- 对当前 DeepSeek 视觉模型，JPEG/PNG/GIF/WebP 直接使用；其它可解码静态图片在目标集合允许时转换，DeepSeek 非视觉模型不会因转换而接受图片。
- 支持图片的模型能够真正收到视觉 block；不支持图片的模型得到稳定提示，不会把图片当文本路径。
- 用户消息历史中显示文件名、缩略图和预览；assistant 消息不伪造附件。
- 关闭/重启后重新打开任务，图片仍可预览；resume 不重复上传、不重复追加 user message。
- edit、fork、task 删除后的 asset 引用和 GC 行为符合上面的关系模型。

### 边界和安全

- SQLite 中没有图片 blob、data URL 或 provider 请求正文。
- `conversation_runs.image_paths` 承载受控 workspace-relative 图片路径，不承载 data URL、绝对路径或任意 asset id。
- 聊天图片只出现在所属 workspace 的 `<workspace_root>/.cosir/Attachment`，不会写入 workspace 普通项目目录、触发项目文件扫描或污染 git diff。
- 非图片附件不产生图片 asset 文件；workspace 删除不会删除用户通过路径引用的原文件。
- 任意未知 locator、绝对路径、`data:`、外部 URL 都被拒绝或安全降级为不可预览。
- 日志没有密钥、token、base64 和完整图片内容。

### 测试

- 前端 Vitest：locator、converter、draft-empty、adapter 状态、错误恢复。
- 前端 Playwright：选择图片→上传→发送→消息预览→刷新/重连；纯图片消息；不支持模型。
- 后端 pytest：upload validation、asset CRUD、wire schema、payload hash、run binding、context serialization/resolution、snapshot rebuild、fork/edit/GC。
- Transport 集成：使用真实 assistant-stream 编解码，覆盖前后端当前锁定版本。
- 真实 Tauri 集成：至少验证动态 backend port 下 preview URL 和 backend restart 后重连；不能只把 Vite Playwright E2E 当作桌面生命周期测试。

## 10. 不建议的方案

### A. 直接把本地绝对路径发送给模型

不建议。外部 provider 无法读取本机路径；路径还会泄漏用户目录结构，并绕过 workspace/attachment 边界。

### B. 直接用 `data:image/...;base64` 贯穿 Transport、context、checkpoint

不建议。可以作为极小图片的临时 demo，但不满足长期的体积、恢复、可排查和 provider 预算要求。

### C. 直接上传到 workspace 项目目录

不建议。聊天附件虽然按 workspace 归属，但必须集中在受控的 `<workspace_root>/.cosir/Attachment` 子目录；不能落到 workspace 普通项目目录，否则会污染 git diff、触发 CodeGraph/文件扫描，并让用户文件与应用生成物混在一起。

### D. 只增加 `ComposerAddAttachment`，不扩展 snapshot/converter

不建议。当前 UI 组件虽能显示 pending 文件，但项目后端 schema 仍拒绝 image part，历史消息也会被 converter 丢掉。

### E. 把附件字段塞进 `TransportMetadata`

不建议。当前 metadata 主要承载工具生命周期/UI 投影；把用户附件混进去会混淆 context fact、Transport projection 和工具状态。附件应有自己的资源表和 user-message projection。

## 11. 需要在实现前确认的少量决策

方案主体不依赖这些选择，但实现前需要固定：

1. `WorkspaceService.create_workspace` 是否在创建 `.cosir` 时同步创建 `Attachment` 子目录；对历史 workspace 是否在启动或首次上传时幂等补建。建议直接纳入 workspace 初始化改造，而不是把它留给上传接口兜底。
2. 第一阶段单文件和单轮图片上限，建议先采用 20 MiB/20 张/按模型限制取小值，并由 Settings 配置化。
3. 是否在落盘时统一用 Pillow 重编码并移除 EXIF；推荐做，但要明确用户预览是否需要保留原始色彩/动画语义。
4. `image_paths` 是否已有旧 API 生产数据；这决定旧绝对路径的兼容读取范围，以及迁移到 `.cosir/Attachment` 的策略。

除上述参数外，不需要引入认证、对象存储、独立上传服务、云队列或新的桌面进程。
