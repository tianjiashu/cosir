# 文件变更实时显示与运行中可撤销方案

> 状态：待审计
> 日期：2026-08-05
> 关联决议（来自需求讨论，已与用户拍板）：
> - **C 方案**：turn 运行中实时显示文件变更，且运行中点「撤销」立即生效
> - **保留** checkpoint（turn 维度）过滤 UI
> - **不需要** 已保留清单（保留即从变更列表消失）
> - **失败 / 取消 turn 内的变更也保留**，与成功 turn 等价（可查看、可撤销）
> - **运行中撤销不弹确认框**，靠按钮 tooltip 提示撕裂风险
> - **实时性用后端增量广播**（`file_change_updated` 事件 + 前端 debounce）

---

## 一、背景与问题

### 1.1 当前行为

- `tool_scheduler._record_file_snapshot`（真实方法名，在 `for offset, forward in enumerate(forward_ops)` 循环内逐条落库）在**工具调用成功后实时**把反向快照写入 `file_snapshots` 表，但此时 `stable=0`。
- `runner._publish_stable_file_changes` 在 **turn 成功路径末尾** 才把 `stable=0 → 1`，并广播 `file_change_stable` 事件。
- `change_set_service.query_change_set` **只统计 `stable=1` 的快照**（设计契约：「未定稿不可展示、不可撤销」）。
- 前端 `useChanges` 初始全量拉取 + 监听 `file_change_stable` → 触发 `refresh()`。

### 1.2 用户痛点

对话进行中 Agent 跑 write_file / patch / delete，文件已落盘、快照已写入、diff 数字已可算，但 Changes 抽屉**全程空白**，只能等 turn 结束才一齐冒出。用户无法在运行中知道 Agent 正在改什么，也无法在运行中及时撤销误改的文件。

### 1.3 目标

1. turn **运行中**实时显示文件变更（不依赖 turn 结束）。
2. 运行中点「撤销」立即恢复磁盘文件 + 从列表移除。
3. 点「保留」立即从列表移除。
4. 失败 / 取消 turn 的变更与成功 turn 等价（可见、可撤销）。
5. checkpoint 过滤保留。

## 一之一、Task 隔离约束（用户补充决策）

**文件变更必须按 `task_id` 严格隔离**：不同 task 的变更集互不串扰（查询、展示、撤销、保留均只作用于当前 task）。

### 现状核查（已确认天然隔离）

- 后端 `change_set_service.query_change_set / keep_file / revert_file` 均以 `task_id` 为入口，经 `_turn_ids_until(task_id, ...)` 取该 task 下的 turn 集合再查快照；跨 task 的 turn 不会混入。
- API 层 `GET /tasks/{task_id}/changes`、`keep`、`revert` 均带 `task_id`。
- 前端 `useChanges(taskId)` 经 `selectEventsForTask(s, taskId)` 只取当前 task 事件，且消费时校验 `event.payload.task_id === taskId`；`revert` / `keep` 均带 `taskId`。

### 方案落点

- 新增的 `file_change_updated` 事件 payload **必须携带 `task_id`**（§3.1 已规划），前端按现有 `file_change_stable` 同款模式过滤（见 §4.1），不跨 task 触发 refresh。
- 后端 `query_change_set` 改为 `list_any_by_turns`（§3.3）后仍由 `task_id` 收敛 turn 集合，**隔离边界不变**。

### 隔离边界与代价（需评审确认）

- **workspace 共享场景**：若同一 workspace 被多个 task 共用，且两个 task 编辑**同一文件路径**，按 task 隔离后各自变更集独立——task A 撤销该文件只影响 task A 的变更集条目与磁盘该文件；task B 的变更集条目仍保留，但磁盘文件已被 task A 回退。这是「按 task 隔离」的语义代价，非 bug。
- **撤销的磁盘副作用不隔离**：`revert_file` 改的是磁盘文件（按 workspace_root 定位），跨 task 共享同文件时，task A 撤销会改到 task B「正在看」的磁盘状态。方案不为此加锁（超出本次范围），依赖「用户按 task 顺序操作」的常识；如需强隔离需前端在 running 态禁用跨 task 并发撤销，本次不做。

## 二、核心设计决策

### 2.1 拆开 `stable` 的「可见性」与「可撤销性」

现状 `stable=1` 同时承担两职：可见性开关 + 可撤销性开关。本方案将其拆开：

| 维度 | 当前 | 方案后 |
|------|------|--------|
| 可见性 | `stable==1` | `stable>=0`（所有快照都可见，含运行中 `stable=0`） |
| 可撤销性 | `stable==1` | `stable>=0`（运行中 `stable=0` 也可撤销，因为 C 方案要求） |

> 注：q3 决策要求「失败/取消 turn 也 stable」，这是终态 stable 收口；q0 的「运行中可撤销」指 turn 仍 running 但用户点撤销（此时 `stable=0`）。两条都要求「可撤销性不依赖 stable」。`mark_stable_by_turn` 在 turn 终态（成功/失败/取消）调用，仅用于让变更集在终态后保持可查询、可审计；运行中（`stable=0`）撤销由 `latest_any_by_path` 支持。

### 2.2 写入时机不变，只改读路径

`stable` 字段仍在 turn 终态时才置 1（不改变 `tool_scheduler` 落库逻辑），只新增「含 unstable」的查询路径。改动最小、风险最低。

### 2.3 增量广播而非前端轮询

`tool_scheduler` 落库成功后，经 `RuntimeEventBus` 同进程 `publish` 一条 `file_change_updated` 事件（携带 `task_id / turn_id / path / action`）。前端 `useChanges` 收到后 debounce 200ms 再 `refresh()`，避免 SSE 抖动导致列表闪烁。

> **语义边界**：`file_change_updated` 仅作「增量通知」，**不持久化**（不入 `runtime_events` 表，也不走 `runtime_event_service` 落库），专供运行中实时刷新；前端回放（replay）/历史查询不包含它。终态仍由 `file_change_stable`（持久化）覆盖。

## 三、后端改动

### 3.1 新增事件类型 `file_change_updated`

**`apps/backend/app/models/enums/event_type.py`**
- 新增枚举值 `FILE_CHANGE_UPDATED = "file_change_updated"`。

**`apps/backend/app/models/payload/file_change_updated_payload.py`**（新建）
- `FileChangeUpdatedPayload(RuntimeEventPayload)`，字段：
  - `task_id: str` — 变更所属任务。
  - `turn_id: str` — 产生变更的轮次。
  - `path: str` — 相对 workspace 的文件路径。
  - `action: str` — 变更动作 `created` / `modified` / `deleted`。

**`apps/backend/app/models/payload/registry/runtime_event_payload_registry.py`**
- 注册 `FILE_CHANGE_UPDATED → FileChangeUpdatedPayload`（与 `FileChangeStablePayload` 同构）。

### 3.2 `file_snapshot_crud.py` 新增两个「含 unstable」查询

与现有 `list_stable_by_turns` / `latest_stable_by_path` 同构，仅去掉 `.where(FileSnapshotModel.stable == 1)`：

- `list_any_by_turns(self, turn_ids: list[str]) -> list[FileSnapshotRecord]`
  按 turn 集合查询全部快照（含未稳定），按 `seq` 升序。供 `query_change_set` 实时展示。
- `latest_any_by_path(self, turn_ids: list[str], path: str) -> FileSnapshotRecord | None`
  取给定 turn 集合内某路径的最新快照（含未稳定）。供运行中撤销查找。

### 3.3 `change_set_service.py` 可见性 + 可撤销性放开

- `query_change_set`：`list_stable_by_turns(turn_ids)` → `list_any_by_turns(turn_ids)`。
- `_require_latest_stable` 重命名为 `_require_latest`（或原地改）：内部 `latest_stable_by_path` → `latest_any_by_path`（接受 `stable=0`，满足运行中可撤销）。
- `keep_file` / `revert_file`：改用 `_require_latest`（同步放开，行为与 §2.1 一致）。
- 其余去重 / 按 path 取最新 / status 判定逻辑不变。

### 3.4 `runner.py` 失败/取消也 stable

当前 `_publish_stable_file_changes(task_id, turn_id)`（async）仅在 `run_turn` 成功路径末尾调用，且该方法**耦合**了 `mark_stable_by_turn` 与 `list_stable_by_turns`+广播 `file_change_stable`。需做两处改造：

1. **拆分方法**：拆出纯同步的 `_mark_stable_file_changes(task_id, turn_id)`（仅调 `FileSnapshotCrud().mark_stable_by_turn`，幂等，已 stable 不重复计），原 `_publish_stable_file_changes` 保留「mark + 广播」用于成功路径。
2. **失败路径（RUN_FAILED）**：在 `run_turn` 的 `except` 分支（约 line 366-382）`await _publish_stable_file_changes(...)` 或仅 `await _mark_stable_file_changes(...)`——此处是 async 上下文，可直接 await。
3. **取消路径（RUN_CANCELLED / 客户端断开）**：`cancel_turn`（同步方法，约 line 130-188）与 `_mark_turn_disconnected_if_running`（同步，约 line 388）均为同步上下文，无法 await async 方法。实现方式二选一：
   - (a) 在同步路径内直接 `FileSnapshotCrud().mark_stable_by_turn(task_id, turn_id)`（不经 runner 方法封装，因该 crud 方法是同步的）；
   - (b) 将 `mark_stable_by_turn` 封装为同步辅助函数并从两处同步调用。
   失败/取消路径**不广播** `file_change_stable`（避免误触发终态 UI 状态），仅收敛 stable 让变更可查询/可撤销。

### 3.5 `tool_scheduler.py` 落库后增量广播

- `ToolScheduler.__init__` 新增可选参数 `event_bus: RuntimeEventBus | None = None`（注入点，不破坏现有构造）。
- 真实落库方法为 `_record_file_snapshot(self, tool, observation, execution_context)`（非文档早期误写的 `_collect_file_snapshots`），它在 `for offset, forward in enumerate(forward_ops): crud.save(...)` 循环内**逐条**落库。广播插入点在该 `crud.save(...)` 成功之后、循环内，对每条快照 `publish` 一条 `file_change_updated` 事件：
  - `task_id` 取自 `execution_context.task_id`（`execution_context` 已携带 task_id，见 `runner._resolve_execution_context`）。
  - `turn_id` 取自 `execution_context.turn_id`。
  - `path` 取自 `forward.file_path`。
  - `action` 取自 `forward.operation.value`（`created` / `modified` / `deleted`；`moved` 视为 `modified`）。
- `_record_file_snapshot` 由 `ToolScheduler.execute` 在事件循环线程调用：整个调用链 `nodes.async_tools_node → run_tool_calls`（`runtime_operations.py:305`，同步）→ `run_calls_with_events` → `ToolScheduler.execute` → `_record_file_snapshot` 是**同一协程栈上的同步调用**，无任何 `run_in_executor`/`to_thread` 切换；即使 `execute_terminal` 走 `process` 子进程，结果也经 `result_queue.get()` 回到该事件循环线程读取。故当前 `ToolScheduler` 已处于事件循环线程，`event_bus.publish`（`queue.put_nowait`）能正常唤醒 SSE 协程，同源 publish 安全，无需 `call_soon_threadsafe`。
- **采集与广播分离（分层设计，非跨线程规避）**：`_record_file_snapshot` 只做**落库**，**不持总线、不 publish**。理由不是"跨线程唤醒风险"（当前同源，不存在），而是**职责分层与广播时机聚合**：
  - `ToolScheduler` 的单一职责是「权限校验 + 参数校验 + 隔离执行 + 落库反向快照」，不应耦合事件总线 / SSE 广播语义；把广播留在它内部会越界（违反分层纪律）。
  - 文件变更通知应和既有的 `TOOL_CALL_FINISHED` 同级：`ToolExecutionService.run_calls_with_events` 本就在每次 `self._scheduler.execute(...)` 返回后（`tool_execution_service.py:140` 循环内）发 `TOOL_CALL_FINISHED`，`FILE_CHANGE_UPDATED` 作为「该工具产生的文件变更」通知，在同层、同循环广播语义一致、聚合清晰。
  - 该层调用链由 `run_tool_calls` → 事件循环线程驱动，故广播点天然在事件循环线程；且 `task_id`/`turn_id`/`changes` 均随 `execution_context` / `observation` 可得，无需再从 `ToolScheduler` 透传总线。
  - 附带鲁棒性：未来若有人把 `ToolScheduler` 塞进线程池，`_record_file_snapshot` 会被带走而你未必察觉；广播留在 `run_calls_with_events`（明确由事件循环驱动）则不受影响。这是防御性收益，非当前必需。

### 3.6 `tool_system.py` 注入事件总线

广播方是 `ToolExecutionService.run_calls_with_events`（见 §3.5），故总线实例应注入 `ToolExecutionService` 而非 `ToolScheduler`：`ToolSystem.build()` 构造 `ToolExecutionService` 时，传入 `event_bus=service_depends.get_runtime_event_bus()`（进程级单例，由 `@lru_cache` 缓存，SSE 订阅端 `turns_api` / `runtime_event_service` 也用同一实例）。`ToolScheduler` 不再持有总线。`ToolExecutionService` 在每轮 `self._scheduler.execute(...)` 返回后、且 `observation.status == "success"` 且 `data["changes"]` 非空时调用 `event_bus.publish(FILE_CHANGE_UPDATED, ...)`。**严禁直接 `RuntimeEventBus()`**——那会创建与 SSE 端不同的全新实例，`publish` 的事件无人订阅，运行中广播静默失效。`tool_system` 为进程级单例，注入一次即可。

## 四、前端改动

### 4.1 `hooks/useChanges.ts` 监听新事件 + debounce

- 新增对 `file_change_updated` 事件的监听，与现有 `file_change_stable` 共用 `refresh()` 全量校准（**不写本地增量**，避免前端重复实现后端「去重 + 按 path 取最新」逻辑，防止漂移）。

- `revert` / `keep` 现有逻辑不变（调用 `changesApi.revert` / `keep`）。`revert` 失败时 `setError` 文案改为「文件已被 Agent 改动，无法撤销」（覆盖 §5.2 并发竞态）。

### 4.2 `components/right-panel/ChangeFileRow.tsx` tooltip 文案

- 撤销按钮 `title` 改为动态：task 处于 running 态时 `title="运行中撤销：后续步骤会读到旧内容"`；非运行中时 `title="撤销"`。
- 运行中撤销不弹确认框（q0 决策），直接调用 `revert`。

### 4.3 `ChangesDrawer.tsx` / `ChangesPanel.tsx` / `ChangeCheckpointSelect.tsx`

- **保持** checkpoint 过滤 UI 不变（q1 决策：保留）。
- 面板本身不改，数据由 `useChanges` 提供全量（含运行中 `stable=0` 快照）。

## 五、风险与边界（运行中 vs 运行后分开评估）

> 关键事实：`revert_file` 当前**无任何状态门禁**——不校验 task/turn 是否 running，只查 `latest_stable_by_path`。改成 `latest_any_by_path` 后，运行中撤销在技术上直接可行。风险不在「能不能撤」，而在「撤了之后系统状态是否自洽」。

### 5.1 运行后撤销（turn 已终态：成功 / 失败 / 取消）

终态后 Agent 不再写该文件，风险最小，仅剩两类：

| 风险 | 说明 | 解法 |
|------|------|------|
| 并发竞态（残余） | 用户在终态后、Agent 已彻底停止，理论无并发；但失败/取消 turn 可能仍在 flush 尾事件，极端时序下 `revert_file` 与最后一次落库竞态 → `PatchApplyError`(409)。 | `revert_file` 已有的 `_is_already_reverted` 幂等校验兜大部分；捕获 `PatchApplyError` 后前端 `setError("文件已被改动，无法撤销")`。终态后竞态窗口极小，可接受。 |
| 终态 stable 边界 | `mark_stable_by_turn` 幂等，重复调用安全；失败/取消路径也已补 `mark_stable`（§3.4），故终态后查询一定能拿到 `stable=1` 快照。 | 已实现，无需额外处理。 |

**结论**：运行后撤销基本无新增风险，与现网行为一致（现网本就只在终态后可见可撤）。

### 5.2 运行中撤销（turn 仍 running，快照 `stable=0`）

这是 C 方案引入的**新风险面**，也是唯一需要重点评估的部分。

| 风险 | 严重度 | 说明 | 解法 |
|------|--------|------|------|
| **(R1) 上下文/磁盘撕裂** | 高 | 用户点撤销即时回退磁盘，但 LangGraph checkpoint 内已落库的 `tool_message` 不被回退，前端 `ToolCallCard` 仍显示「操作成功」；Agent 后续 step 若再读该文件，会读到旧内容，与其记忆中「刚改过」不一致。 | 用户主动选择（q0 决策「不弹框直接撤」）。靠 `ChangeFileRow` tooltip 明示「运行中撤销：后续步骤会读到旧内容」。可选增强：在 `ToolCallCard` 上做「该文件已被撤销」的视觉标记（见 §八.4，本次不做）。 |
| **(R2) 并发写竞态** | 中 | 撤销同时 Agent 在另一线程又写同一文件 → `apply_all_with_diff` 抛 `PatchApplyError`(409)。 | `revert_file` 已捕获并 `raise`；前端 `useChanges.revert` 捕获 `PatchApplyError` → `setError("文件已被 Agent 改动，无法撤销")`。**不自动重试**（避免循环）；提示用户稍后重试或等 turn 结束。 |
| **(R3) 撤销"半成品"语义** | 中 | 运行中某文件可能已被连续改 2 次（write→patch），`latest_any_by_path` 只取最新一条快照反向 apply，只回退最后一步，不会一步回到 turn 起点。这可能是用户预期（撤最后一步）也可能不是（撤全部）。 | 与现网终态行为**一致**（终态也只撤最新一条）。本次不引入「多步撤销」复杂性；若需「撤到 turn 起点」为后续增强。文档需明示：运行中撤销 = 撤最新一次对该文件的变更。 |
| **(R4) 跨 turn 误撤护栏** | 低 | 运行中撤销若误传入其他 turn 的 `turn_ids` 集合，会撤到别的 turn 文件。 | `revert_file` 调用链始终是 `task_id → _turn_ids_until(task_id) → latest_any_by_path(turn_ids, path)`，边界由 task 收敛，无法越 task。与现网同款护栏，无新增风险。 |
| **(R5) 文件锁冲突** | 低 | Agent 正以 `process` 隔离模式（execute_terminal）持有文件句柄时用户撤销，理论上可能冲突。 | execute_terminal 一般不产生文件快照（snapshot_collector 仅对文件类工具收集，见 §八.2），故运行中撤销的 targets 几乎都是 thread 模式的文件工具，无 OS 级句柄冲突。 |

**运行中撤销总策略**：允许直接撤（无确认框），技术上 `revert_file` 复用现有 apply 逻辑零改动；风险靠「tooltip 提示 + 失败提示 + task 护栏」三道软防线兜住，不引入锁/重试/回退 checkpoint 等重机制（符合第零铁律「改动聚焦、不堆复杂度」）。

**补充边界澄清（审查确认安全）**：

- **D1 运行中撤销后同 turn 再 patch 同文件**：`query_change_set` 按 `seq` 升序、按 `path` 覆盖取最新——后续新快照（seq 更大、pending）会覆盖被撤快照（reverted），列表显示最新 pending 态，不会同时列出 reverted + 新 pending 两条。符合 §5.2 R3「只撤最新一次」语义。
- **D2 reverted 快照被终态 `mark_stable` 后是否重现**：`mark_stable_by_turn` 只过滤 `stable==0`、不检查 `status`，故 reverted 快照也会被置 `stable=1`；但前端 `ChangesTab` 仅渲染 `status === "pending"`，reverted/kept 均被过滤，**不会在 UI 重现**。API 层面 `query_change_set` 若该 path 无更新快照会返回 reverted 条目，靠前端 pending 过滤兜底。行为安全，依赖前端 pending 过滤契约。

### 5.3 运行后用户手动改了文件，撤销会冲突吗？

**会。** 但需先纠正一个机制事实（早期描述有误）：`revert_file` 的 apply 路径**不经 `validate_all`**（`apply_all_with_diff` 直接调 `_apply_operation`）；且反向 UPDATE 操作携带 `content=before`（来自正向 hunks 的 `+` 行），`_apply_operation` 的 UPDATE 分支在 `content is not None` 时**直接整文件 `atomic_write_text` 覆盖还原**，完全绕过 fuzzy hunk 匹配。因此真实行为是「整文件覆盖」而非「hunk 抠除」。

| 用户改法 | 真实结果 | 当前是否防护 |
|---------|---------|------------|
| 把文件改回 Agent 改之前的状态 | `_is_already_reverted` 判目标态达成 → **静默跳过**，标记 reverted（幂等，无副作用） | ✓ 安全 |
| 删了文件（原操作是 UPDATE） | `_apply_operation` UPDATE 分支读文件抛 OSError → `PatchApplyError`(409) → 撤销**被拒** | ✓ 已覆盖（R2：前端提示「文件已被改动，无法撤销」） |
| 原操作是 ADD（Agent 新建文件）、用户已删该文件 | `_is_already_reverted` DELETE 分支判「文件不存在即已还原」→ **静默跳过** | ✓ 安全（非报错，与早期误写「报错」相反） |
| **改了文件其它不相关区域（整文件已变，既非 before 也非 after 态）** | 反向 apply 会把**整个文件直接覆盖回 Agent 改之前的状态**，**用户的所有手动修改一并被抹掉** | ✗ **盲区（R6）** |

**R6（软冲突）最危险**：无报错，但用户的手动改动被整文件覆盖丢失。当前 `file_snapshots` 表无磁盘内容校验和字段，apply 前无法判断「用户是否动过文件」。

> 注：R6 并非运行中新引入——现网终态撤销也有同样盲区。本次方案强化「运行后可直接撤销」，应一并处理。

**R6 解法（已拍板：采用 A，轻量不改表）**：

- **解法 A 精确化（零表改动）**：不新增字段，复用反向 `op_json` 自带内容做三方态判定。
  `revert_file` apply 前，对每条 `PatchOperation` 用现有 `_is_already_reverted` 的同一比对逻辑，判断当前磁盘处于哪种态：
  - **当前磁盘 == before 态**（即 `operation` 反向应用的目标态）：说明文件已被还原/用户未改 → 静默跳过（现状幂等）。
  - **当前磁盘 == after 态**（即 Agent 改完后的样子，正是反向 op 要撤除的内容）：→ 正常 apply（现状成功路径，整文件覆盖回 before）。
  - **两者都不等**：说明用户手动改过文件（既不是 Agent 改完态、也不是还原态）→ **主动在 `apply_all_with_diff` 之前抛 `PatchApplyError`(409)**，提示「文件已被手动修改，请先备份或用 git 还原后再撤销」。
  - 判定依赖：现有 `_is_already_reverted` 已覆盖四态「目标态（before）」比对；需**补一个对称的「源态（after）比对」函数**（如 `_is_at_after_state`）：
    - UPDATE：`operation.content` 即 `before`；after 可从正向 hunks 的 `+` 行拼出（`_hunk_to_content_patch` 已有同款降级逻辑）→ 比对 `current == after` 可行。
    - DELETE（正向 ADD，Agent 新建）：after = 文件不存在 → 比对 `not exists` 可行。
    - ADD（正向 DELETE，重建文件）：after = `operation.content` 全文 → 比对可行。
    - MOVE：after = 源文件存在且目标已移到 new_path → 复用 `_is_already_reverted` MOVE 分支对称逻辑。
  - **无误拒风险**：仅当用户改动后文件恰好「整文件等于 before 或 after 态」时才会误判放行（概率极低，且放行结果也安全）。
- **解法 A 的盲区（已识别，本次放弃覆盖）**：反向 DELETE（正向 ADD）的 `reverse_v4a_operation` 分支无 `content`、无 hunks，**after（原 ADD 内容）完全丢失**，故「用户改了 Agent 新建的文件」场景 `_is_at_after_state` 无法比对内容——但此时 `_is_already_reverted` DELETE 判文件存在→False（需 apply），`_apply_operation` DELETE 分支**直接 `unlink` 无校验**，用户的改动会被直接删除。若要覆盖此场景需落库 after 全文（即解法 B 的 `after_checksum`/`after_content` 字段代价）。**本次决策：声明放弃该场景**，文档明示；如后续需要再升级到解法 B。
- **解法 B（已弃用）**：加 `after_checksum` / `after_content` 字段，精确覆盖 ADD 盲区但改动中等，本次不做。

### 5.4 事件频率

同一 turn 可能落几十个快照。前端 debounce 200ms 合并刷新，避免 SSE 抖动导致列表闪烁（与运行/终态无关，常驻优化）。

## 八、审计关注点（供评审）

1. **§2.1 中 `stable` 语义弱化**：放开后 `stable` 仅作为「终态收口标记」，不再作为可见/可撤销开关。是否有其他代码依赖 `stable=1` 作为「变更已确认」的业务语义（如 git 提交、审计导出）？若有需评估。
2. **§3.5 采集/广播分离（分层设计，已闭环）**：`_record_file_snapshot` 只落库不 publish，`ToolScheduler` 保持纯执行+采集职责；广播上移到 `ToolExecutionService.run_calls_with_events` 与 `TOOL_CALL_FINISHED` 同级发出 `FILE_CHANGE_UPDATED`。当前 `ToolScheduler` 已处于事件循环线程（整条 `async node → run_tool_calls → run_calls_with_events → ToolScheduler.execute` 为同协程栈同步调用，`execute_terminal` 子进程结果也回到该线程读取），故同源 publish 本就安全，无需 `call_soon_threadsafe`；分离主因是**分层纪律与广播时机聚合**，附带对未来线程模型演进的鲁棒性。总线注入点随之改到 `ToolExecutionService`（见 §3.6）。execute_terminal 不产生文件快照（`changes` 为空早退），不影响实时广播覆盖。
3. **§4.1 全量 refresh 成本**：运行中每次 debounce 后全量 `GET /changes`，turn 长、文件多时是否有性能压力？当前 `change_set_service` 已做按 path 去重，量可控。
4. **撕裂一致性**：§5.1 的撕裂是否需要在 `ToolCallCard` 上做「该文件已被撤销」的视觉标记？当前方案未做，仅 tooltip 提示。是否需在审计中确认可接受。
5. **R6 软冲突（运行后用户改了文件）**：§5.3 已拍板采用解法 A（零表改动三方态判定）。需审计确认：
   - 新增的「源态（after）比对」函数 `_is_at_after_state` 对 UPDATE/DELETE/ADD/MOVE 四态的 before/after 判定是否完备（UPDATE 的 after 由正向 hunks `+` 行拼出、DELETE 的 after=文件不存在、ADD 的 after=`operation.content`、MOVE 复用对称逻辑）。

   - 「用户改后文件恰好等于 before/after 态」的极低概率误放行是否可接受（放行结果安全）。
