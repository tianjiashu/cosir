# 工具系统待完善清单

本文件记录 `apps/backend/app/tools` 工具系统当前尚未覆盖、需要后续实现的能力缺口。缺口来源于对成熟 coding-agent（OpenCode）机制的对照分析，作为后续工具系统迭代的事实源。

参考资料：

- `coding-agent-docs/opencode/questions/opencode-skill-execution-timeout.md`
- `coding-agent-docs/opencode/questions/opencode-tool-error-handling.md`

优先级约定（沿用 AGENTS.md 协作原则）：

- **必须做**：属于第一阶段生产级验收范围，当前实现存在明确缺口或死代码。
- **建议做**：能显著提升健壮性和可维护性，可在必须项之后排期。
- **以后做**：需要跨层架构改动，第一版预留方向即可，不强制落地。

---

## 一、必须做

### 1. 超时后终止整个进程树

**背景**：OpenCode 通过 `Shell.killTree()` 在超时/取消时终止子进程及其全部后代，确保资源释放。

**现状**：`app/tools/execute.py` 的 `_stop_process` 只对 spawn 出的直接子进程执行 `terminate()` / `kill()`。若工具 handler 内部又通过 `subprocess` 派生了孙进程（典型如 shell 类工具），超时后这些孙进程会残留，形成僵尸进程或继续占用资源。

**缺口**：缺少进程组级别的终止能力。

**建议方案**：

- spawn 子进程时建立独立进程组（POSIX 下 `os.setsid()`）。
- 超时或取消时对整个进程组发送信号（`os.killpg(pgid, SIGTERM)`，宽限后 `SIGKILL`）。
- Windows 平台使用等价的进程组终止机制（如 `CREATE_NEW_PROCESS_GROUP` + `taskkill /T`），保持跨平台一致（AGENTS.md 要求兼容 Windows 与 Mac）。

**涉及文件**：`app/tools/execute.py`。

---

### 2. 超时与失败在执行事实中区分

**背景**：OpenCode 用 `<bash_metadata>` 标签把超时/取消状态单独标注，便于 LLM 理解发生了什么。

**现状**：

- `app/tools/execution/store.py` 已预留 `timed_out` 状态（`create_execution` 的 `completed_at` 判定集合中已包含），但目前不可达。
- `app/tools/execution/lifecycle.py` 的 `running` 迁移集合为 `{"completed", "failed", "cancelled"}`，不包含 `timed_out`。
- `app/tools/executor.py` 超时后统一走 `_handle_failure`，标记为 `failed`。
- `app/tools/execute.py` 的 `ToolExecutionResult` 仅有 `status` / `content` / `error`，不携带错误种类。

**缺口**：超时被当作普通失败，`timed_out` 成为死代码；模型与恢复逻辑无法区分"超时（可能可重试）"与"确定性报错（不可重试）"。

**建议方案**：

- 给 `ToolExecutionResult` 增加 `reason` 字段（枚举：`timeout` / `handler_exception` / `subprocess_start_failed` / `serialization_failed` 等）。
- `execute.py` 超时分支返回 `reason="timeout"`。
- `executor.py` 依据 `reason` 将生命周期标记为 `timed_out`，并写入对应执行事实。
- 同步在 `lifecycle.py` 的 `running` 迁移集合放开 `timed_out`。
- 让 `ToolObservation` 携带错误种类，供上层区分处理。

**涉及文件**：`app/tools/execute.py`、`app/tools/executor.py`、`app/tools/execution/lifecycle.py`、`app/tools/results.py`、`app/tools/types.py`。

---

### 3. 工具错误结构化分类

**背景**：OpenCode 的 `ParsedAPICallError` 以 `type` + `isRetryable` 对错误分类，屏蔽差异并支撑上层决策。

**现状**：当前所有工具错误扁平化为 `status="error"` + 一段自由文本，runtime 无法据此判断是否应重试或如何恢复。

**缺口**：缺少错误类型化，无法驱动差异化恢复策略。

**建议方案**：以第 2 项引入的 `reason` 字段为最小落地载体，将错误分类贯通到 `ToolObservation`，为后续重试与恢复逻辑提供结构化依据。

**涉及文件**：与第 2 项一致。

---

## 二、建议做

### 4. 默认超时可配置 + 边界缓冲

**背景**：OpenCode 默认超时 2 分钟且支持环境变量覆盖，并对计时加 `+100ms` 缓冲避免边界误判。

**现状**：`app/tools/types.py` 中 `timeout_seconds` 写死默认 `10.0`，无全局默认或环境变量兜底；`execute.py` 中 `process.join(timeout_seconds)` 到期即终止，无缓冲。

**缺口**：默认值偏短（对 shell/构建类工具不足）且无法集中配置；缺少边界缓冲。

**建议方案**：

- 引入全局默认超时环境变量（如 `CODING_AGENT_DEFAULT_TOOL_TIMEOUT_SECONDS`），工具级 `timeout_seconds` 覆盖全局默认。
- 在 `join` 判定处增加极小宽限（如 `+0.1~1s`），降低边界误杀概率。

**涉及文件**：`app/tools/types.py`、`app/config/`、`app/tools/execute.py`。

---

### 5. 错误可重试标记与有限重试

**背景**：OpenCode 依据错误可重试性 + `Retry-After` + 指数退避决定是否重试。

**现状**：工具层不产出可重试判断，无重试机制。

**缺口**：临时性失败（超时、子进程启动失败）无法自动恢复。

**建议方案**：

- 在 `ToolExecutionResult` 增加 `retryable: bool`：`timeout` / `subprocess_start_failed` 标记为可重试，`handler_exception` 标记为不可重试。
- 重试编排放在 runtime / workflow 层（有限次数 + 退避），工具层只负责产出结构化的可重试判断，保持职责单一。

**涉及文件**：`app/tools/execute.py`、runtime / workflow 层。

---

## 三、以后做

### 6. 进度感知的动态超时

**背景**：OpenCode 的 `resetTimeoutOnProgress` 在收到进度通知时重置超时计时器，支持长任务。

**现状**：当前为 spawn + 结果文件架构，子进程无法把"进度"信号回传父进程以重置 `join` 计时。

**缺口**：长时间任务只能依赖固定超时，易被误杀。

**建议方案**：新增子进程到父进程的进度通道（pipe / queue），父进程收到进度时重置超时窗口。属于较大改造，作为后续增强。

**涉及文件**：`app/tools/execute.py` 及相关进度事件通道。

---

### 7. Doom Loop 重复调用检测

**背景**：OpenCode 检测最近 3 次相同工具 + 相同参数的调用，触发用户介入，防止无效循环。

**现状**：`app/tools/execution/idempotency.py` 的幂等键可安全复用"已完成"的重复调用（防止副作用重复），但不检测重复调用"模式"本身。

**缺口**：无法识别 LLM 陷入反复调用同一工具的无效循环。

**建议方案**：在 runtime / workflow 层实现调用模式检测（最近 N 次工具名 + 参数比对），命中后触发人工确认或终止。不属于工具层职责。

**涉及文件**：runtime / workflow 层。
