# 第二阶段建设优先级

本文档用于承接第一阶段基础 runtime 已跑通后的后续建设顺序。目标不是继续堆功能点，而是把项目从“可演示的本地 Agent 原型”推进到“可持续完成真实开发任务的桌面 coding-agent 基线”。

本文档只讨论第二阶段优先级，不替代 `docs/production-acceptance.md` 中的生产级验收标准。第二阶段的重点是先补齐会阻断真实使用的关键能力，再逐步扩展成熟 coding-agent 的高级能力。

## 当前阶段判断

当前项目已经具备以下基础事实：

- 本地 Python 后端 + Tauri/React 桌面端的总体架构已经建立。
- 后端已具备单 Agent、单 Task、ReAct-like Workflow 的基础 runtime。
- 后端已支持真实 DeepSeek / OpenAI-compatible 流式模型调用。
- 后端已支持 SSE 事件推送、最小状态持久化、日志落盘和基础 checkpoint 记录。
- 工具系统已具备最小执行边界，但当前可用工具仍非常少。
- 桌面端已具备聊天主链路，但大量侧边能力仍处于 mock / 占位状态。

因此，第二阶段不应再把重点放在“证明能调用模型”上，而应放在“让整个系统能长期稳定完成真实开发任务”上。

## 第二阶段目标

第二阶段的目标可以概括为一句话：

把当前项目从“模型可用的 Agent 骨架”升级为“具备真实工程执行闭环的本地 coding-agent 基线”。

这意味着第二阶段优先解决以下问题：

- 用户不应再手动照顾后端进程。
- Agent 不应只有 `safe_read` 级别的只读能力。
- 危险能力不应只发审批事件，而应完成真实审批闭环。
- checkpoint 不应只会记录，还应支持恢复与回看。
- 上下文增长不应只靠失败保护，而应支持继续执行。
- 复杂任务不应全部压在单 Agent 上。

## 优先级总览

第二阶段建议按以下顺序推进：

### P0：必须优先完成

- 本地一体化进程托管
- 最小可用工具集
- 权限审批闭环
- checkpoint 恢复闭环

### P1：紧随其后

- context compaction
- subagent 基线
- MCP 基线接入
- 前端状态面与右侧面板去 mock

### P2：在 P0/P1 基线稳定后推进

- 审查 / 测试闭环工作流
- 更强恢复 / 重试 / provider fallback
- 多模态输入
- 更完整的可观测性与成本分析

## P0 建设项

### 1. 本地一体化进程托管

这是第二阶段的第一优先级。

当前项目虽然定义上是一个本地桌面应用，但实际运行仍接近“前端壳 + 手动启动 Python 后端”。这不符合项目愿景，也会直接削弱可用性。

必须做到：

- Tauri 负责启动、探活、停止、重启本地 Python 后端。
- 前端不再依赖“用户先手动起服务”。
- 后端启动失败时，客户端能明确展示错误原因和日志入口。
- 后端退出、端口冲突、依赖缺失、配置缺失时，客户端能给出结构化状态。
- 后端进程状态应纳入前端状态管理，而不是只做一次性 health check。

验收口径：

- 用户启动桌面应用后，无需进入命令行手动启动后端。
- 后端异常退出时，前端能感知并提示。
- 日志和健康状态可在客户端中查看。

非目标：

- 第二阶段不要求完整 sandbox。
- 第二阶段不要求跨平台安装器完全成熟。

### 2. 最小可用工具集

当前 runtime 已有工具边界，但真实工具能力远远不够。没有工具集，Agent 只能回答，不能完成开发任务。

第二阶段最小工具集建议：

- 文件读取：已具备，继续保留。
- 文件写入：新建、覆盖、追加、原子写。
- 文件编辑：按 diff 或 patch 修改文件，而不是整文件粗暴覆盖。
- 目录浏览：列目录、判断文件是否存在、获取元信息。
- 文本搜索：项目内搜索、文件定位、符号定位。
- 命令执行：受控 shell 执行，支持超时、取消、stdout/stderr 捕获。
- Git 只读能力：状态、diff、log。
- Git 写能力：受审批控制的 add/commit/branch 等能力。

验收口径：

- Agent 能完成小型真实开发任务，而不仅是读代码后回答。
- 每个工具都有 schema、权限等级、超时、错误处理和日志。
- 模型不能绕过 Tool Scheduler 直接执行能力。

非目标：

- 第二阶段不要求一开始就支持所有外部工具生态。
- 第二阶段不要求并发工具调用。

### 3. 权限审批闭环

当前系统已经能产生 `tool_approval_required` 事件，但还没有真正的批准 / 拒绝动作闭环。这意味着危险工具实际上还不可用。

必须做到：

- 前端能展示审批请求详情。
- 用户能批准或拒绝。
- 审批结果能回传后端。
- Runtime 能等待审批、恢复执行或按拒绝分支结束。
- 审批要有任务、步骤、工具名、参数、权限等级、理由和时间戳。
- 审批结果要进入日志和事件存储。

优先纳入审批的能力：

- 文件写入
- 文件编辑
- 命令执行
- Git 写操作
- 网络访问

验收口径：

- 任务在审批点可以暂停并继续。
- 拒绝后不会静默失败，而是有明确 observation / event。
- 审批历史可追踪。

非目标：

- 第二阶段不要求复杂审批策略引擎。
- 第二阶段不要求组织级权限系统。

### 4. Checkpoint 恢复闭环

当前 checkpoint 主要是“记录”，还不是“恢复系统”。成熟 coding-agent 的 checkpoint 价值在于可恢复、可回看、可回退。

必须做到：

- 关键阶段自动生成 checkpoint。
- 客户端可查看 checkpoint 列表和摘要。
- 任务中断或应用重启后，可以恢复到最近可用状态。
- 用户能显式选择一个 checkpoint 重新启动任务。
- 至少支持任务状态恢复，不要求一开始就支持完整文件回滚。

checkpoint 最低应覆盖：

- 当前 Task / Turn / Step 状态
- 当前消息上下文摘要
- 工具调用历史
- 当前 Agent / Workflow 阶段
- 审批等待状态

验收口径：

- 应用重启后，未完成任务状态可恢复或可解释。
- 用户能看见 checkpoint，不是只有后端知道它存在。

非目标：

- 第二阶段不要求完整的文件级回滚系统。
- 第二阶段不要求像 git 一样的精细时间旅行。

## P1 建设项

### 5. Context Compaction

当前系统只有上下文预算保护，没有真正 compaction。成熟 coding-agent 一旦进入长任务，没有 compaction 就很难持续工作。

第二阶段建议先做文本任务 compaction 基线：

- 接近阈值时自动触发压缩。
- 保留用户目标、已确认决议、当前计划、关键文件、关键工具结果、未解决问题。
- 压缩记录可查看。
- 失败时保留原上下文，不破坏当前任务。

验收口径：

- 长任务在压缩后仍能继续完成。
- 压缩后的输出不是只有模糊摘要，而是可继续执行的运行上下文。

### 6. Subagent 基线

Subagent 是成熟 coding-agent 的重要分水岭，但不应过早做复杂多 Agent 编排。第二阶段建议只做最小基线。

建议第一批 subagent 角色：

- reviewer：审查问题与风险
- tester：生成并执行测试
- researcher：只读检索与信息汇总

必须做到：

- 主 Agent 可派发子任务。
- subagent 有独立任务状态、事件流、取消边界和结果摘要。
- subagent 结果必须回到主 Agent 汇总，不做平行失控系统。

验收口径：

- 一个主任务可以显式调用 reviewer / tester 子任务。
- subagent 失败不会拖垮整个 runtime。

### 7. MCP 基线接入

MCP 是项目愿景中的核心能力，但第二阶段应先做“稳定接入基线”，不是一开始就追求大而全。

建议范围：

- MCP server 注册 / 启用 / 禁用
- tools / resources 发现
- schema 校验
- 调用超时与错误隔离
- 危险能力接入审批系统

验收口径：

- 至少接入一个真实 MCP server。
- MCP 失败不会影响主 Agent 主链路。

### 8. 前端状态面去 mock

当前桌面端主聊天链路已可用，但右侧面板、历史、项目、输出、来源、checkpoint、subagent、MCP 等面板仍有大量 mock / 占位。

第二阶段建议优先去掉与 runtime 事实直接相关的 mock：

- Checkpoint 区块
- Context 区块
- MCP 区块
- Subagent 区块
- Outputs / Sources
- 后端运行状态

验收口径：

- 右侧面板展示真实任务数据，而不是静态示例数据。
- 用户可以通过 UI 理解任务正在发生什么。

## P2 建设项

### 9. 审查 / 测试闭环 Workflow

这是从“能执行任务”到“能稳定交付代码”的重要一步，但前提是 P0/P1 已经打稳。

建议形态：

- implement
- review
- test
- fix
- re-review / re-test

这一步要复用 subagent 和工具系统，而不是另起一套平行逻辑。

### 10. 恢复 / 重试 / Provider Fallback

成熟 coding-agent 不会把一次模型失败直接等同于任务失败。

第二阶段后段可开始建设：

- provider 请求超时与重试
- rate limit backoff
- 工具失败后的重试策略
- provider fallback
- 结构化失败分类

### 11. 多模态输入

你已经明确后续要支持图片、文档。这个应进入第二阶段后段，而不是抢在 P0/P1 前面。

原因很简单：

- 如果 runtime 的工具、审批、恢复、上下文都不稳，多模态只会放大复杂度。
- 多模态应该建立在稳定的任务状态和附件生命周期之上。

### 12. 可观测性与成本分析

第二阶段后段应补充更完整的运行诊断：

- token usage
- provider latency
- tool latency
- 错误分类
- 任务耗时
- 任务成本估算

这部分对“能否长期优化模型与工具策略”非常关键。

## 不建议在第二阶段优先做的事项

以下事项可以做，但不应排在前面：

- 大规模 UI 美化
- 复杂插件市场
- 多模型路由优化
- 向量数据库
- 远程部署形态
- 完整多模态工作流
- 复杂 DAG 编排编辑器

这些都不是当前阻断真实可用性的第一矛盾。

## 推荐推进顺序

建议按以下顺序执行：

1. Tauri 托管后端进程，完成本地一体化运行。
2. 补齐最小可用工具集。
3. 打通审批闭环。
4. 打通 checkpoint 恢复闭环。
5. 实现 context compaction。
6. 实现 subagent 基线。
7. 接入 MCP 基线。
8. 去掉前端关键面板 mock。
9. 再推进 review/test/fix workflow。

## 第二阶段完成标志

第二阶段完成，不意味着项目已经达到最终成熟产品形态，而意味着它跨过了“原型期”。

第二阶段完成时，项目应达到以下状态：

- 用户启动桌面应用即可使用，不需手动照顾后端。
- Agent 能读、写、改、搜、执行受控命令，并受审批保护。
- 长任务可以恢复、可以压缩、可以继续。
- 复杂任务可以拆给子 Agent。
- MCP 能作为真实扩展入口，而非规划概念。
- UI 展示的是运行事实，而非大面积 mock。
- 系统已经具备完成真实小型开发任务的稳定闭环。

## 结论

第二阶段的本质不是“继续加功能”，而是补足成熟 coding-agent 必需的运行能力层。

真正决定项目能否跨过原型期的，不是再多接一个模型，也不是再多做一个漂亮面板，而是以下四件事是否优先做对：

- 后端托管
- 工具系统
- 审批闭环
- 恢复闭环

这四项是第二阶段最应该先打穿的主线。
