# 前端对话与工具 UI 改造方案

> 本文是 `apps/desktop` 的前端改造设计，不修改后端工具、Workflow、Context、Snapshot 或 SQLite。目标是把当前“所有工具都使用通用兜底卡片”的实现，重组为成熟的 Assistant UI 运行时 + 可注册的工具 UI + 少量领域展示适配。

## 1. 结论

第一版采用下面的边界：

```text
Tauri 桌面应用
└── React/Vite UI 进程
    ├── AssistantRuntimeProvider
    ├── useAssistantTransportRuntime
    ├── state converter
    ├── Thread / Composer
    └── backend-only tool UI registry
            │ localhost Assistant Transport
            ▼
        FastAPI 后端进程
        ├── ConversationStateSnapshot（唯一 Transport 快照事实源）
        ├── ConversationEventProjector
        ├── Agent Runtime / Workflow
        └── ToolExecutor / 本地工具进程
```

- 后端拥有运行、工具执行、文件修改、取消、错误、快照和持久化事实。
- 前端拥有渲染、折叠展开、滚动、输入框、局部视觉状态和错误提示。
- 前端不执行工具、不修改文件、不把 `localStorage` 或 React state 当作对话事实。
- Assistant Transport 是本机 React 与 FastAPI 之间的进程边界，不引入公网服务、认证、多租户或客户端工具执行。
- `ConversationStateSnapshot` 是前端唯一输入。前端把它转换为 assistant-ui 消息；转换结果只是不可持久化的 UI 视图。

这不是在现有 `Thread` 组件上继续添加工具名分支，而是把职责拆开：Transport 适配、消息转换、工具注册、通用工具状态、工具结果布局、Thread 组合分别拥有清晰边界。

## 2. 事实基线

### 2.1 当前仓库事实

当前桌面端已经具备：

- `useAssistantTransportRuntime`，使用 `protocol: "assistant-transport"`。
- `AssistantRuntimeProvider`、`ThreadPrimitive`、`ComposerPrimitive`。
- `lib/assistant/contract.ts` 描述 Transport state。
- `lib/assistant/converter.ts` 把后端消息转换为 assistant-ui 的 text、reasoning、tool-call parts。
- `defineToolkit` + `Tools` 的 backend-only 工具注册方式。
- `@assistant-ui/react-markdown`、`@base-ui/react`、`lucide-react` 和现有 shadcn 风格 UI 封装。
- 当前所有 coding-agent 工具都绑定到同一个 `ToolFallback`，无法根据结果数据提供差异化展示。

后端工具注册名不是全部等于 Python 类名。第一版必须以 `toolName` 为绑定键：

| 后端工具 | Transport `toolName` / toolkit key | 后端展示声明 |
|---|---|---|
| `ReadFileTool` | `read_file` | `trace`、不可展开、`none` |
| `ListDirectoryTool` | `list_directory` | `trace`、可展开、`list` |
| `SearchFilesTool` | `search_files` | `trace`、可展开、`list` |
| `ApplyPatchTool` | `apply_patch` | `standalone`、可展开、`diff` |
| `ReplaceTool` | `patch` | `standalone`、可展开、`diff` |
| `WriteFileTool` | `write_file` | `standalone`、可展开、`diff` |
| `DeleteTool` | `delete` | `standalone`、不可展开、`none` |
| `ExecuteTerminalTool` | `execute_terminal` | `standalone`、可展开、`terminal` |

`ToolDisplayHints` 是后端静态展示声明；`ToolObservation.data` 是经过展示预算治理的 UI 结构化数据；`content` 是给模型的文本通道，不能被前端拿来重新解析成 UI 事实。

### 2.2 Snapshot 对前端可见的工具 part

后端 `tool-call` part 的核心字段为：

```ts
type SnapshotToolCallPart = {
  type: "tool-call";
  toolCallId: string;
  toolName: string;
  status: "pending" | "running" | "completed" | "failed" | "cancelled";
  args?: Record<string, unknown>;
  result?: unknown;
  error?: unknown;
  presentation?: Record<string, unknown>;
  data?: Record<string, unknown> | null;
  isError?: boolean;
  approvalRequestId?: null;
};
```

其中：

- `presentation` 来自后端 `ToolDisplayHints`，决定 surface、是否可展开和布局提示。
- `data` 是给 UI 的结构化结果，例如 `directory-list`、文件变更数据、`terminal-result`。
- `result` 是工具执行结果事实；失败和取消时后端会清空结果并写入错误信息。
- `status` 是后端生命周期事实，不能由前端根据“有没有结果”猜测。
- `approvals` 当前必须为空对象，第一版不实现前端审批卡片。

前端 converter 应把 `presentation`、`data` 和后端 `status` 放入 assistant-ui tool-call 支持的 `artifact` 字段，作为 UI-only artifact 传给 renderer；不要把展示数据塞进模型 `result`，也不要让工具 renderer 读取后端内部快照或重新请求工具。

推荐的 UI artifact 形状：

```ts
type CodingAgentToolArtifact = {
  kind: "coding-agent-tool";
  backendStatus: "pending" | "running" | "completed" | "failed" | "cancelled";
  presentation: Record<string, unknown>;
  data: Record<string, unknown> | null;
  error?: unknown;
};
```

`artifact` 只是 converter 产生的渲染输入，不是新的事实源；刷新、切换任务或重新连接时仍以服务端 snapshot 为准。

## 3. Assistant UI 与流式边界

Assistant UI 官方的 Assistant Transport 是“状态流式协议”：后端流式发送完整 Agent state 的增量，前端 runtime 应用 `set` / `append-text` 操作，再由 converter 把当前 state 转成 UI 消息。它不是前端轮询，也不是把一次完成后的 JSON 当成聊天消息。

前端必须保持以下链路：

```text
用户输入
  → add-message command
  → useAssistantTransportRuntime 发起本机 SSE/Transport 请求
  → 后端创建 ConversationRun
  → backend workflow 产生 conversation events
  → ConversationEventProjector 更新 snapshot
  → set / append-text 流给前端
  → runtime 更新本地 Transport state
  → converter 生成消息视图
  → ThreadPrimitive 增量渲染
```

### 3.1 文本流

- 用户发送后，前端通过 `pendingCommands` 先显示乐观用户消息。
- 后端创建 user/assistant 消息骨架后，助手 text/reasoning 通过 `append-text` 增量更新。
- converter 将 text/reasoning part 的后端 `running/completed` 映射为 assistant-ui part status。
- `MessagePartPrimitive.Text` / 现有 `MarkdownText` 负责流式文本显示；不要在前端自行拼接 token、计时或复制另一份 assistant 文本。
- assistant 消息在 `run.status` 未到终态时保持 running；成功、失败、取消分别映射到 assistant-ui 的 complete/incomplete 语义。

### 3.2 工具流

工具调用不是一次性“工具结果消息”，而是 assistant 消息中的 tool-call part：

```text
tool_call_created       → part=pending，显示准备执行
tool_call_status_changed
  pending → running     → 显示执行中
  running → completed   → 显示成功结果
  running → failed      → 显示失败原因
  running → cancelled   → 显示已取消
tool_calls_settled      → 进程重启/运行终止时补偿收束未决 part
```

renderer 应优先读取 `artifact.backendStatus`，因为 assistant-ui 的通用 tool status 是 UI runtime 语义，而后端 `pending/running/completed/failed/cancelled` 才是本项目的生命周期事实。

### 3.3 取消、断连和重启

- “停止”按钮继续使用 assistant-ui 的取消动作，同时调用现有 `/runs/{run_id}/cancel`，显示“正在停止”，等 snapshot 发送 `cancelled` 后再显示“已取消”。
- 浏览器连接断开不能被前端伪装成成功；后端仍负责把 run 及未决工具收束为失败或取消事实。
- 窗口重载或前端重启时，先从 `/tasks/{task_id}/assistant/state` 读取完整 snapshot，再创建 runtime；不能用旧 React state 继续发送。
- 当前支持连接期间的实时状态流，以及重新进入页面时从 snapshot 重新水合；当前没有运行中断线后的无缝流式续传 API，不应在前端伪造 resume 能力。
- Tauri/FastAPI 后端启动失败、崩溃或重启属于应用生命周期问题，前端只显示连接错误和入口级恢复提示；不在前端新增后台执行器或恢复队列。

官方依据：

- [Assistant Transport](https://assistant-ui.com/docs/runtimes/custom/assistant-transport)
- [Message primitive](https://assistant-ui.com/docs/primitives/message)
- [MessagePartPrimitive](https://assistant-ui.com/docs/api-reference/primitives/message-part)
- [Tool UI](https://assistant-ui.com/docs/tools/tool-ui)

## 4. 目标前端结构

建议把当前文件重组为下列职责。文件名可按项目命名规范调整，但职责不要重新合并到一个大组件中。

```text
apps/desktop/
├── components/assistant/
│   ├── assistant-runtime.tsx       # runtime/provider 装配，不包含工具布局分支
│   ├── toolkit.tsx                 # backend-only toolkit 注册表
│   └── tool-ui/
│       ├── tool-artifact.ts        # artifact 类型守卫与安全读取
│       ├── tool-state.ts           # pending/running/success/error/cancelled 视图状态
│       ├── tool-status-row.tsx     # 统一状态、图标、错误摘要、时长
│       ├── tool-activity-card.tsx  # trace 工具的通用折叠卡骨架
│       ├── tool-result-card.tsx    # standalone 工具的通用卡片骨架
│       ├── read-file-tool.tsx
│       ├── list-directory-tool.tsx
│       ├── search-files-tool.tsx
│       ├── file-change-tool.tsx    # ApplyPatch / patch / WriteFile 共用
│       ├── delete-tool.tsx
│       ├── execute-terminal-tool.tsx
│       └── unknown-tool.tsx        # 未注册工具的安全兜底
├── components/assistant-ui/elements/
│   ├── thread.aui.tsx              # Thread/Composer 结构组合
│   ├── tool-group.aui.tsx           # assistant-ui part grouping
│   └── ...
└── lib/assistant/
    ├── contract.ts                 # Transport wire 类型
    ├── converter.ts                # 唯一 snapshot → assistant-ui 映射
    └── transport-errors.ts         # Transport 错误映射
```

`thread.aui.tsx` 只负责 Thread、MessagePrimitive、ComposerPrimitive、分组与通用 part 插槽；工具的字段读取和布局不再写在 `switch (part.type)` 中。

## 5. 组件策略：复用优先

### 5.1 必须复用的现有能力

- 对话运行时：`@assistant-ui/react` 的 `AssistantRuntimeProvider`、`useAssistantTransportRuntime`。
- 消息和流式渲染：`ThreadPrimitive`、`MessagePrimitive`、`MessagePartPrimitive`、现有 `@assistant-ui/react-markdown`。
- 工具注册：assistant-ui 的 `defineToolkit` + `Tools`，工具 entry 使用 `type: "backend"` 和 `render`，不使用已废弃的旧 component-tool API。
- 折叠：当前项目已经安装并封装的 `@base-ui/react/collapsible` / `Collapsible`。
- 按钮、提示、骨架：现有 shadcn 风格 `Button`、`Tooltip`、`Skeleton`。
- 图标：现有 `lucide-react`，图标名优先使用后端 `presentation.icon`，未知图标回退到固定的通用图标。

### 5.2 不自研的能力

- 不手写 diff 算法、行号对齐、统一/并排 diff 布局。引入一个与 React 19 和项目许可兼容的成熟开源 diff renderer；第一候选为 `react-diff-viewer-continued`，安装前以其当前 peer dependency 和锁文件为准，若不兼容再选同级成熟库。
- 不手写 Markdown、代码高亮、复制按钮，继续复用 `@assistant-ui/react-markdown` 和现有代码块能力。
- 不手写折叠状态机，复用 Base UI Collapsible。
- 不为目录树引入自研虚拟化；第一版只渲染后端有界的当前页，条目超过页面预算时遵守后端 `page` / 截断事实。
- 不引入 Zustand/React context 保存第二份对话事实；工具卡片只从当前 part props 和 artifact 计算视图。

### 5.3 允许自定义的范围

只自定义 coding-agent 特有的“数据到布局”适配：标题文案、状态行、目录条目、文件变更摘要、终端输出容器。它们使用现有 primitive 和成熟库，不承担执行、权限、恢复决策或持久化。

## 6. 工具 UI 设计

所有 renderer 都必须覆盖 `pending`、`running`、`completed`、`failed`、`cancelled` 五个后端状态，并处理 `data` 缺失、未知 `kind`、展示预算截断和未知字段。未知工具使用通用兜底，不显示原始 JSON 作为主界面。

### 6.1 ReadFileTool：不可展开的活动行

后端声明不可展开、`expand_layout=none`。前端不得增加“查看内容”“打开内容”按钮，也不得把 `content` 中带行号的模型文本渲染给用户。

```text
◉ 读取文件  src/auth/login.ts                         [进行中]
  第 1–500 行

✓ 读取文件  src/auth/login.ts                         [已完成]
  第 1–500 行 · 共 812 行 · 文件大小 24 KB
```

渲染来源：

- `args.path`、`args.offset`、`args.limit` 只用于摘要。
- 若成功数据包含 `total_lines`、`file_size`、`next_offset`，显示为辅助元信息。
- 失败显示后端错误摘要（不存在、目录、二进制、非 UTF-8 等）。第一版不显示工具级重试入口，因为当前 `retryable` 没有进入 Transport snapshot。
- 不展示 `result.content`，不从字符串解析行号。

### 6.2 ListDirectoryTool：直接子项列表

后端只列目标目录的直接子项，不递归。默认折叠；展开时用现有 Collapsible 展示当前页。

```text
▸ 查看目录  apps/backend/app/core                  [已完成]
  当前页 18 项 · 还有更多条目

展开：
  📁 context/       dir
  📁 tools/         dir
  📄 runtime.py     file
  🔗 shared         link
```

渲染来源：

- `data.kind === "directory-list"`。
- 条目只读取 `entries[].name/type/path`；主标题使用 workspace 相对路径，避免用完整绝对路径占据主视觉。
- `page.has_more` / `page.next_offset` 只显示“还有更多条目”，第一版不在前端自动发起下一次工具调用。
- 空目录与 offset 越界分别显示“目录为空”“当前页没有条目”。前端不能仅依据 `entries.length===0` 猜测两者。
- `include_hidden=true` 显示“包含隐藏项”；`include_globs` 的说明是“按条目名称过滤”，不能写成递归路径过滤。

### 6.3 SearchFilesTool：只显示文件路径

后端包含内容正则搜索和文件名 glob 搜索，前端根据 `args.target` 显示“搜索内容”或“查找文件”。第一版无论 `target`、`output_mode` 如何取值，结果区都只展示文件路径。

```text
▸ 搜索内容  login  · src                         [已完成]
  当前显示 3 个文件

展开：
  src/auth/login.ts
  src/api/auth.ts
  apps/desktop/auth/session.ts
```

渲染来源：

- `data.files[].path` 是前端唯一消费的结果字段。
- 后端在生成 `data.files` 前已经把内容搜索中的多个命中归一为去重后的文件路径；前端仍应按路径去重作为防御性处理。
- `line_number`、`content`、`context` 等搜索引擎内部字段不会作为 UI 输入；如果未来出现在兼容 payload 中也必须忽略。
- 文件名搜索同样只消费 `files[].path`，不显示其他搜索内部字段。
- `pattern`、`target`、`path` 用于摘要；后端没有可靠独立的精确总数时，只显示“当前显示 N 个文件”，不承诺总命中数。
- 结果被预算截断、分页或后端文本提示表明不完整时显示“结果已截断/可继续查看”，不能把当前页当完整搜索结果。
- 没有匹配显示“未找到匹配”；非法正则、路径错误显示失败状态。

### 6.4 ApplyPatchTool：多文件 Diff 卡片

后端 `apply_patch` 是多文件 V4A patch，直接执行。使用 standalone 卡片，默认展示摘要，Diff 展开内容交给成熟 diff renderer。

```text
┌ 应用补丁                                      ✓ 已完成 ┐
│ 2 个文件 · +18 −6                                  │
│ ▾ src/auth/login.ts                 +12 −4           │
│ ▸ src/auth/session.ts                +6 −2           │
└─────────────────────────────────────────────────────┘
```

`data.kind === "file-changes"` 时使用 `data.changes[]` 和 `data.diff_stats`：

- 每个文件按 `path/new_path/status` 分组。
- `before` / `after` 交给 diff 库，禁止前端自行计算差异。
- 使用 `+` / `−`、文件状态和语义标签表达变化，不能只依赖红绿颜色。
- 若 `syntax_errors` 存在，按文件和行列显示检查错误。
- 失败但带有部分变更事实时显示“执行失败，部分变更可能已经应用”，不能把失败渲染成“未修改”。
- 不提供允许、确认、取消修改、重新应用或撤销按钮；后端当前没有对应 Transport command，也没有前端回滚权限。

### 6.5 ReplaceTool：单文件 Diff，注册名是 `patch`

Python 类是 `ReplaceTool`，但后端注册名为 `patch`。前端 toolkit 必须绑定 `patch`，标题使用“替换文本”，不能绑定一个不存在的 `replace`。

```text
┌ 替换文本  src/config.ts                         ✓ 已完成 ┐
│ 单文件已修改 · replace_all: false                     │
│ +9 −9                                                  │
│ ▸ 查看变更                                             │
└────────────────────────────────────────────────────────┘
```

- 仍使用 `file-change-tool`，不要为单文件替换再造一套 diff UI。
- `args.replace_all=true` 显示“替换全部匹配”；否则显示“要求唯一匹配”。
- 后端结构化数据没有替换次数，不显示“替换 3 处”等推断数字。
- 未匹配、匹配不唯一或写入失败直接展示后端错误；不提供前端重算或补救逻辑。

### 6.6 WriteFileTool：创建/修改 Diff 卡片

`write_file` 成功时通过 `data.kind === "file-changes"` 返回单文件变更，`status` 为 `added` 或 `modified`。

```text
✓ 创建文件  src/auth/types.ts
  新增 1 个文件 · +32 行
  ▸ 查看 Diff

✓ 修改文件  src/config.ts
  文件已重写 · +14 −8
  ▸ 查看 Diff
```

- `added` 显示“创建文件”，`modified` 显示“修改文件”。
- 覆盖文件必须有 Diff；不能只显示“写入成功”。
- 写入后语法检查失败时，标题为失败，但文案必须同时说明“文件已经写入，随后检查发现语法错误”。
- 第一版不显示工具级重试；不显示允许写入、取消写入、撤销或保留按钮。未来若加入恢复操作，必须先定义后端 command 和快照事实。

### 6.7 DeleteTool：不可展开的删除结果行

后端声明 standalone、不可展开、`expand_layout=none`。删除已经直接执行，前端不能增加确认、恢复或撤销。

```text
✓ 删除文件  src/legacy/auth.ts                         [已完成]
⚠ 删除目录  src/legacy · recursive=true                [失败]
  目标不存在或权限不足
```

- 始终显示目标路径和删除类型。
- `recursive=true` 明确写“递归删除目录”，但不推导影响数量。
- 文件可能有删除前快照，但目录和链接不一定有同样的结构化 Diff；不伪造被删内容或数量。
- 失败显示后端错误摘要；不把删除动作包装成待确认状态。

### 6.8 ExecuteTerminalTool：独立终端卡片

后端在本机 workspace 范围内执行命令，合并 stdout/stderr，输出已经脱敏并受预算限制；超时会被强杀并作为失败观察返回，后端内部会标记其可重试，但该字段当前没有进入 Transport snapshot。第一版不提供工具级重试。终端卡片独立展示，输出默认折叠。

```text
┌ 执行命令  npm test                         ✓ 已完成 ┐
│ workspace: apps/desktop · exit code: 0              │
│ ▸ 查看输出                                          │
└─────────────────────────────────────────────────────┘
```

展开：

```text
$ npm test

✓ auth.test.ts
✓ session.test.ts

24 passed
exit code: 0
```

- 命令本身永远可见，来自 `args.command`；工作目录来自 `data.workdir` 时作为次级信息显示。
- 输出只读 `data.kind === "terminal-result"` 的 `output`，不从模型 `content` 解析。
- 显示 `exit_code`、`timed_out`、`truncated`；`truncated=true` 必须显示“输出已截断”。
- 后端当前未把每个 stdout chunk 建模为 snapshot 事件，因此前端只渲染当前 snapshot 中可用的有界输出；不伪造实时尾部流。
- 用户停止后显示“正在停止”，收到 `cancelled` snapshot 后才显示“已取消”。
- 后端 deny-list 拒绝的危险命令显示后端错误；前端没有“强制执行”按钮。

## 7. Toolkit 注册策略

工具 UI 使用 assistant-ui 官方 backend toolkit 方式：renderer 只声明 `render`，不声明 `execute`。这保证工具仍由 FastAPI 后端执行。

第一版采用“静态分组、后端细节声明”的单一职责策略：

- toolkit entry 的 `display` 是前端静态注册配置，决定 assistant-ui 的 inline/standalone 分组；八个已知工具必须按上方后端 `ToolDisplayHints.surface` 对齐。
- 后端 `presentation.surface` 不在 renderer 运行时重新决定分组；它只作为一致性校验输入，不能与前端静态 `display` 形成两个可变事实源。
- `presentation.expandable`、`expand_layout`、`default_open`、`verb`、`icon` 供通用工具 UI 使用，决定卡片细节，不改变消息分组。
- 如果开发环境发现前端注册配置与后端静态声明不一致，记录可诊断错误并使用前端已注册的安全布局；不要在各个 renderer 中分别修正分组。
- 第一版不实现“后端动态改变 inline/standalone”的能力。未来若确有需求，必须先设计统一的 converter/分组适配层，再整体替换静态策略。

示意结构：

```tsx
const codingAgentToolkit = defineToolkit({
  read_file: { type: "backend", render: ReadFileToolUI },
  list_directory: { type: "backend", render: ListDirectoryToolUI },
  search_files: { type: "backend", render: SearchFilesToolUI },
  apply_patch: { type: "backend", display: "standalone", render: FileChangeToolUI },
  patch: { type: "backend", display: "standalone", render: ReplaceToolUI },
  write_file: { type: "backend", display: "standalone", render: WriteFileToolUI },
  delete: { type: "backend", display: "standalone", render: DeleteToolUI },
  execute_terminal: { type: "backend", display: "standalone", render: ExecuteTerminalToolUI },
});
```

这里的 `display: "standalone"` 由 assistant-ui 控制工具是否在折叠工具组外呈现；`read_file`、`list_directory`、`search_files` 不填写该字段，使用 trace 默认值。后端的 `presentation.surface` 保留在 artifact 中用于一致性校验和通用兜底，但不在运行时覆盖 toolkit 分组。

未知工具必须使用 `UnknownToolUI`：显示工具名、执行状态和安全错误摘要；不显示完整参数和原始 JSON，不让未知工具逃逸到没有状态处理的默认分支。

## 8. 状态与错误模型

### 8.1 统一状态行

`ToolStatusRow` 是展示组件，不是状态机。它只把 artifact 中的后端状态映射为视觉：

| 后端状态 | 视觉 | 用户文案 | 允许动作 |
|---|---|---|---|
| `pending` | 中性、静态 | 准备执行 | 无 |
| `running` | spinner | 正在执行 | 对话级停止 |
| `completed` | success/中性 | 已完成 | 展开结果（若后端允许） |
| `failed` | error | 执行失败 + 后端摘要 | 无工具级动作 |
| `cancelled` | warning/中性 | 已取消 | 无 |

当前工具级 `retryable` 事实存在于后端 `ToolObservation`，但没有进入 `ToolCallStatusChangedEvent`、`ConversationStateToolCallPart` 或 `ConversationStateSnapshot`，因此第一版前端不能展示工具级重试按钮。前端只展示失败事实；未来若支持恢复，必须先由后端把可重试事实和 command 契约完整纳入 Transport，不能根据工具名、HTTP 状态或错误文案自行推断，也不能新增客户端私有 command。

### 8.2 展示预算

- 前端不扩大后端 `DisplayDataBudget` 已经裁剪过的 `data`。
- 长列表、长 Diff、终端输出只渲染 snapshot 给出的内容，并显示截断事实。
- `JSON.stringify` 只允许出现在开发诊断或未知数据的低优先级详情中，不能成为主要 UI。
- `content`、`reason`、异常堆栈和内部快照不作为前端展示数据的替代品。

## 9. 输入区与对话布局

第一版仍是普通文字输入：

- 多行输入。
- `Enter` 发送，`Shift + Enter` 换行。
- 发送期间发送按钮变为停止按钮。
- 当前 `thread.aui.tsx` 中的 `ComposerAddAttachment` 需要从可见 Composer 中移除；只保留未来接入官方 attachment adapter 所需的扩展边界，不实现附件上传和附件 Transport 契约。
- 用户消息使用 assistant-ui 的 optimistic pending command 视图立即出现。
- assistant text/reasoning 流式显示；工具 part 插在 assistant message 的自然位置。
- ReadFile、ListDirectory、SearchFiles 使用 trace 活动行/可折叠组；文件变更、删除、终端使用 standalone 卡片。
- 最终 assistant 文本只总结结论、变更和验证结果，不重复完整工具输出。

## 10. 不做的事情

本次前端改造明确不做：

- 不在前端执行任何工具或 shell。
- 不增加前端审批、允许修改、确认删除、撤销、恢复、重新应用能力；后端 snapshot 的 `approvals` 仍为空。
- 不修改 ConversationStateSnapshot 结构来适应 UI；如需新的事实，必须另行进行后端契约决策，本方案不偷偷扩展。
- 不从 `content` 反解析结构化工具数据。
- 不把 `presentation/data` 写回后端 context、Conversation facts 或 SQLite。
- 不引入第二套 SSE、event store、客户端 timeline 或轮询机制。
- 不通过工具名在 Thread 根组件里不断追加特殊判断。
- 不实现自研 Diff、Markdown、代码高亮、虚拟列表或通用弹层。

## 11. 实施顺序

这是一次前端职责重组，顺序固定为：

1. 先冻结并补齐前端 Transport 类型：完整表达 snapshot tool-call 的 `status/presentation/data`，确认与后端 schema 一致。
2. 重写 converter 的 tool-call 映射：保留 `result/isError/argsText` 的 assistant-ui 语义，同时把 `presentation/data/backendStatus` 放入 `artifact`。
3. 抽出 `tool-artifact`、`tool-state`、`tool-status-row`，先让未知工具和所有状态有稳定兜底。
4. 用 assistant-ui backend toolkit 注册八个工具 renderer，删除八个工具对通用 `ToolFallback` 的绑定。
5. 实现三类共享布局：trace activity、standalone result、file change；再接入各工具数据 renderer。
6. 接入成熟 diff renderer，只处理后端提供的 `before/after`，不改变文件事实。
7. 将 `thread.aui.tsx` 收缩为 Thread/Message/Composer 组合，移除当前可见的 `ComposerAddAttachment`，并保留 assistant-ui 的 grouped parts。
8. 通过真实 Transport 流验证首屏加载、文本增量、工具状态迁移、失败、取消、重新进入时的 snapshot 水合和未知工具；不把当前能力描述为断线后的无缝续传。

每一步都应保持前端可运行；但不通过兼容层长期保留旧的“所有工具走 Fallback”路径。旧组件在新 registry 验收后删除或仅保留给未注册工具使用。

## 12. 验收清单

### Transport / snapshot

- [ ] 只通过 `useAssistantTransportRuntime` 连接后端。
- [ ] 使用 assistant-transport 协议的 `set` / `append-text` 流。
- [ ] converter 是唯一 snapshot → assistant-ui 映射点。
- [ ] UI artifact 不会回写后端，也不进入 context、SQLite 或下一次命令的事实输入。
- [ ] `presentation/data/status` 未丢失，未知字段安全忽略。
- [ ] 首屏先读服务端 state，再创建 runtime；task 切换不会串历史。

### 对话流式

- [ ] 用户消息在 pending command 阶段立即可见。
- [ ] assistant text/reasoning 随 `append-text` 增量更新。
- [ ] 工具 pending/running/completed/failed/cancelled 与 snapshot 同步。
- [ ] 停止按钮等待后端 cancelled 事实，不把断开连接当成功。
- [ ] 后端不可用、流错误、重启均可见且不丢用户输入。

### 工具交互

- [ ] ReadFile 永远不可展开、不显示正文。
- [ ] SearchFiles 只显示去重后的文件路径，不显示命中行/内容/context。
- [ ] ListDirectory 只显示直接子项，并区分空目录与 offset 越界。
- [ ] ApplyPatch / patch / WriteFile 使用统一成熟 Diff renderer。
- [ ] Delete 不可展开、不提供确认/撤销。
- [ ] ExecuteTerminal 显示命令、退出码、超时/截断，输出折叠且不伪造实时流。
- [ ] 第一版没有工具级重试按钮；未来恢复能力需先进入后端 Transport 契约。
- [ ] 未知工具有安全兜底。

### 组件与维护性

- [ ] 没有在 Thread 根组件继续堆叠工具名分支。
- [ ] 没有自研 Diff/Markdown/折叠/弹层/虚拟化能力。
- [ ] 工具 renderer 仅渲染 backend tool，不含 `execute`。
- [ ] 前端仍是本地桌面 UI 进程，FastAPI 仍由 Tauri 管理，未引入云端或分布式依赖。
