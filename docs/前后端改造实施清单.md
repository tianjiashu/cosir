# 前后端改造实施清单

## 文档目标

- 将当前“首页直接输入创建单轮 task”的实现，改造为“按 workspace 创建 task，task 内支持多轮连续对话”的完整闭环。
- 明确前端、后端、共享协议和数据表层面的改造范围。
- 作为后续拆分技术方案、接口设计和代码实现的执行清单。

## 核心实体边界

- 后端去掉 `session` 语义。
- 核心主键边界收敛为：
  - `workspaceId`：任务归属工作区
  - `taskId`：连续对话容器
  - `turnId`：一次对话运行
- `turnId` 的定义是：一次用户发起输入后，到本轮 assistant 输出、tool 调用、状态收束为止的完整运行单元。
- 同一个 task 可以有多次 turn；每次用户新发一轮输入，都会生成新的 `turnId`。
- `stream` 协议围绕 `turnId`；`taskId` 负责历史聚合，不直接承担实时流边界。

## 显示与运行边界

- `message`：用户可读内容单元，面向展示与交互。
- `event`：运行时事实记录，面向 runtime、恢复、排序与诊断。
- `timeline`：message 与 event 的显示投影，作为 UI 渲染模型。
- 第一版建议约束：
  - 一个 `turn` 只有一条 user message。
  - 一个 `turn` 最终最多归并出一条 assistant final message。
  - assistant streaming delta 属于 event，不作为独立 message 落地。
  - tool / status / approval 先作为 event 投影成 timeline item。

## 一、目标闭环

1. 用户点击“新建任务”。
2. 客户端进入“新建任务页面”。
3. 用户选择 workspace。
4. 用户输入首条消息并发送。
5. 系统创建 task。
6. 主区进入该 task 的对话页。
7. 左侧对应 workspace 下立即回显该 task。
8. 用户后续点击历史 task 时，可以继续在该 task 内多轮对话。
9. 删除 workspace 时，级联删除其下所有 task 及关联记录。

## 二、后端接口改造

### 1. workspace 接口

- `GET /workspaces`
- `POST /workspaces`
- `DELETE /workspaces/{workspace_id}`

### 2. task 列表接口

- `GET /workspaces/{workspace_id}/tasks`

### 3. 新建任务接口

- `POST /workspaces/{workspace_id}/tasks`
- 语义：发送首条消息时创建 task。

### 4. 继续对话接口

- `POST /tasks/{task_id}/turns`
- 语义：给已有 task 追加一次新的对话运行。
- 职责边界：
  - 只负责创建 turn
  - 初始状态为 `pending`

### 5. task 查询接口

- `GET /tasks/{task_id}`
- `GET /tasks/{task_id}/events`
- `GET /tasks/{task_id}/turns`
- 后续可考虑补充：`GET /tasks/{task_id}/timeline`

### 6. turn stream 接口

- `GET /turns/{turn_id}/stream`
- 语义：订阅该 turn 的实时运行流。
- 长期协议：
  - 如果 turn 是 `pending`，则启动运行并开始推流
  - 如果 turn 已经在 `running`，则接入当前流
  - 如果 turn 已经 `completed / failed / cancelled`，则回放已有事件并结束

### 6. 删除接口语义

- `DELETE /workspaces/{workspace_id}`
- 级联删除范围至少包括：
  - tasks
  - turns
  - steps
  - events
  - checkpoints
  - runs / trace / 其他绑定记录

## 三、后端数据表改造

### 1. 新增 `workspaces` 表

建议字段：

- `workspace_id`
- `name`
- `root_path`
- `created_at`
- `updated_at`

### 2. 改造 `tasks` 表

建议补充：

- `workspace_id`
- `title`
- `last_message_preview`
- `status`
- `created_at`
- `updated_at`

说明：

- task 不再只是“一次执行记录”，而是“多轮对话容器”。

### 3. 新增或重构 `turns` 表

每次用户继续对话新增一条 turn，至少包含：

- `turn_id`
- `task_id`
- `input_text`
- `status`
- `created_at`
- `updated_at`

说明：

- `turnId` 表示一次对话运行。
- 如果现有 durable run 表可承载该语义，应直接升级为 `task -> many turns`；否则新增明确的运行记录表。
- turn 状态至少需要：
  - `pending`
  - `running`
  - `completed`
  - `failed`
  - `cancelled`

### 4. 改造 `events` 表

建议补充：

- `turn_id`
- `sequence`
- `message_id`
- `tool_call_id`
- `parent_event_id`（如需要）

说明：

- 现有 event 结构不足以支撑连续 timeline、稳定排序和恢复。

### 5. 级联删除规则

- 删除 workspace 时，所有下游记录必须一并删除。
- 不能只删除 workspace 主记录或只从展示层移除。

## 四、后端运行时改造

### 1. 改造 task 运行语义

- 当前实现偏向“pending task 跑一次”。
- 需要升级为：
  - task 是容器
  - turn 是一次输入对应的一次对话运行
  - 同一个 task 可以有多个 turn

### 2. 增加“追加 turn 并运行”能力

- 第二轮消息不能继续映射成新 task。
- 需要明确追加 turn 后的运行创建、状态推进和 SSE 订阅逻辑。
- turn 创建和 turn 启动要分离：
  - `POST /tasks/{task_id}/turns` 只创建 pending turn
  - `GET /turns/{turn_id}/stream` 决定启动 / 接入 / 回放

### 3. 改造 durable run 存储

- 当前如果是“一 task 一 run”，必须升级成“一 task 多 run”。
- 审批恢复、断点恢复、运行日志和 LangGraph 生命周期都要按 `turnId` 对齐；如果底层仍保留 `run` 存储概念，需要明确 `turnId` 与内部 durable run 的映射关系。

### 4. 改造 event 生成链路

- 用户首条消息
- 后续 turn
- assistant delta
- tool started / completed
- run status

这些事件都需要更稳定的关联字段和排序依据。

### 5. 明确 stream 协议

- 需要定义：
  - 创建首个 turn 后如何建立流
  - 追加新 turn 后如何建立流
  - `GET /turns/{turn_id}/stream` 按状态执行启动 / 接入 / 回放
  - task 历史 timeline 与 turn 实时流如何拼接
  - 如何避免历史 event 重复回放
  - 如何保证同一个 turn 不会被重复启动

### 6. tool 事件时序下沉

- tool started / completed 应尽量靠近实际工具执行边界。
- 避免“工具先执行，再统一补发 started/finished”的伪实时事件。

### 7. workspace 删除服务

- 删除逻辑应收口到明确的 service。
- 不应由 API 层散落拼接多表删除逻辑。

### 3. 新增 turn 共享类型

### 4. 改造 event 共享类型

- 增加 timeline 关联字段。
- 保持前后端单一事实源。

### 5. 新增 API 路径常量

- workspace CRUD
- workspace 下 task 列表
- append turn
- task 下 turn 列表

## 六、前端 Store 改造

### 1. 新增 `workspaceStore`

至少管理：

- workspace 列表
- 折叠状态
- activeWorkspaceId
- workspace 删除

### 2. 改造 `taskStore`

当前扁平结构需要升级，至少支持：

- workspace 归属
- activeTaskId
- activeTurnId
- optimistic task
- task 创建中 / 失败 / 已正式化状态

### 3. 改造 `eventStore` 或 timeline store

- 支持同一 task 下多轮 timeline。
- 不能每次发送新输入就清空历史 events。
- 需要能按 `turnId` 识别一次新对话运行的局部事件，并合并到同一 task timeline 中。

### 4. 新增 optimistic 状态

- optimistic task
- optimistic user message

## 七、前端页面与组件改造

### 1. 新建任务页面

需要具备：

- workspace 选择
- 首条消息输入
- 发送创建 task

### 2. Sidebar 改造

- 从 mock 数据改成真实 workspace 树
- workspace 支持折叠 / 展开
- workspace 下显示多个 task
- 支持删除 workspace
- 支持 optimistic task echo

### 3. TaskList 改造

- 从静态列表改为 workspace 作用域列表
- 点击 task 后恢复并继续该 task

### 4. InputBar 改造

需要区分两种语义：

- 在新建任务页：发送首条消息 = 创建 task
- 在 task 对话页：发送消息 = append turn

### 5. ChatPanel 改造

- 从单轮拼接视图改成连续 timeline
- 按 event 顺序显示 message / tool / status
- 同一 task 下可显示多个 turn 的连续结果

## 八、前端 Hook / Service 改造

### 1. `useTask`

拆成两类核心动作：

- `createTaskWithFirstMessage`
- `appendTurnToTask`

### 2. `services/api`

增加：

- workspace CRUD
- workspace 下 task 查询
- append turn
- task 下 turn 查询

### 3. SSE 连接策略

- 新建 task 后接入该 turn stream
- 继续对话时不能用“清空历史后重连”的粗暴方式
- 需要明确当前激活 `turnId` 的订阅与历史 task timeline 加载顺序
- 前端重连同一个 `turnId` 时，语义必须是“接入或回放”，不能再次启动执行

### 4. 页面状态流

- 需要明确谁持有当前页面模式：
  - 空状态页
  - 新建任务页
  - task 对话页
- 点击 sidebar 历史 task 后，需要明确：
  - 何时切换 activeTaskId
  - 何时加载历史 events / runs
  - 何时连接新 stream

## 九、删除 workspace 的前端交互

### 1. 删除前确认

- 二次确认弹窗

### 2. 删除成功后

- 左侧移除 workspace
- 如果当前正停留在被删 workspace / task：
  - 主区退回空状态或新建任务页

### 3. 删除失败后

- 恢复 UI 状态
- 显示错误提示

## 十、推荐实施顺序

1. 先定领域边界和共享契约
   - 去掉 session
   - workspace / task / turn / message / event / timeline 边界
   - workspace / task / turn / event / api shared types
2. 再改后端存储与运行时
   - workspace
   - task 挂 workspace
   - task -> many turns
   - event 关联字段
   - workspace delete cascade
3. 再定并实现 API
   - workspace CRUD
   - workspace 下 task 列表
   - append turn
   - task 下 turn / event 查询
   - turn stream
4. 前端 store 与页面状态流改造
   - workspaceStore
   - taskStore
   - activeTurnId
   - timeline / event store
   - 页面模式状态
5. 回显与 SSE 打通
   - optimistic task
   - optimistic user message
   - assistant streaming
   - append turn stream（围绕 `turnId`）
6. 最后补删除链路和验收

## 十一、最小验收清单

- 能创建 workspace
- 左侧能展示历史 workspace，且可折叠
- workspace 下能看到多个 task
- 点击“新建任务”能进入新建任务页面
- 选择 workspace 并发送首条消息后能创建 task
- 左侧立即回显新 task
- task 标题默认取首条消息摘要
- 点击历史 task 可继续对话
- 第二轮消息不会创建新 task，而是创建新的 turn
- timeline 不会被清空
- 每次新一轮对话都能分配新的 `turnId`
- 每次新 turn 都能通过 `turnId` 独立订阅实时 stream
- 重连同一个 `turnId` 不会导致重复执行，只会接入已有流或回放已有事件
- 删除 workspace 后，其下 task 与相关记录全部删除

## 十二、当前未展开但需注意的点

- workspace 名称与 root path 是否允许重复
- task 标题摘要的截断规则
- 删除 workspace 是否需要“不可恢复”提示
- workspace 删除后的日志、trace、artifact 是否也纳入同一删除策略
- timeline projection 是前端做还是后端做
- 现有 `session` 数据如何迁移、清理或一次性废弃
