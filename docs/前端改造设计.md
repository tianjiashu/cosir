# Cosir 前端改造设计：服务端快照驱动的对话与工具活动 UI

## 1. 文档目的

本文是 `apps/desktop` 的前端改造设计文档，目标是把桌面端收敛为一个稳定的
Assistant UI 渲染器：用户看到对话正文、工具活动、文件变更和验证结果；Agent、工具、
审批、checkpoint、ChangeSet 和对话事实仍由本机后端负责。

本文只设计前端，不改变后端领域模型、工具执行链、快照 owner 或 Transport API。
实现时如果发现文档与代码事实不一致，以当前代码为准，并在同一次改造中修正文档；
不能为了让 UI 看起来完整而在前端补造后端没有提供的状态。

### 1.1 资料边界与优先级

本设计使用三类资料，但它们的职责不同：

1. `docs/交互建议.md` 是产品交互目标，规定用户应该看到什么、默认展开什么以及哪些
   操作不应出现在第一版。
2. `apps/backend` 是协议和事实来源，规定 state 字段、状态枚举、工具展示数据和流的
   生命周期。
3. Assistant UI 官方文档是 React 运行时和组件 API 的事实来源，规定
   `useAssistantTransportRuntime`、converter、primitives 和 tool UI 的正确用法。

因此，交互建议不能覆盖后端事实；Assistant UI 不能被当成领域状态机；前端不能通过
猜测或本地副作用弥补快照缺字段。

官方依据：

- [Assistant Transport](https://www.assistant-ui.com/docs/runtimes/custom/assistant-transport)
- [Message primitive](https://www.assistant-ui.com/docs/primitives/message)
- [Tools](https://www.assistant-ui.com/docs/tools)
- [Streamdown](https://www.assistant-ui.com/docs/guides/streamdown)
- [Composer primitive](https://www.assistant-ui.com/docs/primitives/composer)

## 2. 运行边界与数据归属

### 2.1 进程和生命周期

```text
Tauri 主进程
  └─ supervisor 启动、探活、停止和恢复本机 FastAPI 子进程
       └─ FastAPI / Assistant Transport
            ├─ LangGraph Runtime / Workflow
            ├─ Tool Runtime
            ├─ ConversationEventProjector
            └─ ConversationTaskSnapshotService ── SQLite

Tauri WebView / React renderer
  └─ AssistantRuntimeProvider
       └─ useAssistantTransportRuntime
            └─ Thread / Composer / Message parts / Tool UI
```

- React 运行在 Tauri WebView/renderer 进程。
- Agent、工具和状态快照运行在 Tauri supervisor 管理的本机 FastAPI 进程。
- 对话事实和服务端 snapshot 存在后端管理的 SQLite；前端 React state 只是不可持久化
  的渲染副本。
- 前端不启动 Agent、不执行工具、不写 SQLite，也不把 `localStorage` 当作对话数据源。
- Tauri 负责后端启动、停止、探活和崩溃恢复。后端崩溃后由 supervisor 恢复进程；前端
  显示连接/恢复状态，重连后通过任务 snapshot 重新 hydrate，不自行恢复消息事实。

### 2.2 页面级数据与对话数据

页面级 workspace、task、provider、model CRUD 仍走已有 API client。对话唯一使用：

- 首屏：`GET /tasks/{task_id}/assistant/state`。
- 发送：`POST /assistant`，由 `useAssistantTransportRuntime` 发起。
- 取消：`POST /runs/{run_id}/cancel`，由停止按钮显式调用；不能把断开 HTTP 连接当成
  后端取消。

Assistant Transport 的 thread 身份固定映射为 `task-{taskId}`。新对话由后端根据
`workspaceId` 和命令创建 Task，响应头返回新的 `X-Cosir-Task-Id` 与
`X-Cosir-Thread-Id`；前端只消费这些身份，不生成第二套业务身份。

## 3. 后端当前契约事实

### 3.1 Assistant Transport 请求和流

当前后端入口是 `apps/backend/app/assistant_transport/assistant_api.py`：

- `POST /assistant` 接收 `AssistantTransportRequest`。
- 当前业务命令是 `add-message`；消息只接受非空 text parts。
- 请求需要 `taskId`/`workspaceId`、`providerId`、`modelName` 和命令 `commandId`。
- `commandId` 用于幂等；重复命令不能在前端自动变成第二个 run。
- 一个 Task 同时只能有一个 active run；后端返回 `RUN_ALREADY_STARTED` 时前端应显示
  明确错误，不自行排队或重试。
- 后端通过 `assistant_stream.create_run` 和 `AssistantTransportResponse` 发送
  `text/event-stream`；运行执行与 HTTP 订阅解耦，断开连接不等于取消 Agent。
- 前端应把 runtime 的 `protocol` 明确设置为 `"assistant-transport"`，因为后端使用
  Assistant Transport SSE 编码。不能把响应当 JSON，也不能重新引入旧 SSE/eventStore
  链路。

`useAssistantTransportRuntime` 只在 UI 适配层使用，不能把 assistant-ui 类型泄漏进
`core`、`service`、`storage` 或工具层。

### 3.2 Snapshot 的固定形状

`ConversationStateSnapshot` 位于
`apps/backend/app/assistant_transport/state/conversation_state_snapshot.py`，顶层 key
必须严格为：

```ts
type TransportState = {
  messages: TransportMessage[];
  run: { runId: number | null; status: string };
  approvals: Record<string, never>; // 当前必须为空对象
  context_usage: number;
  usage: {
    input_tokens: number;
    output_tokens: number;
    total_tokens: number;
    cache_hit_tokens: number;
    cache_miss_tokens: number;
    reasoning_tokens: number;
  };
  error: { code: string; message: string; retryable: boolean } | null;
};

type TransportMessage = {
  id: string;
  runId?: number | null;
  role: "user" | "assistant";
  status: string;
  endReason: string | null;
  parts: Array<TextPart | ReasoningPart | ToolCallPart>;
};
```

快照由 `ConversationTaskSnapshotService` 唯一负责读取、校验、持久化、进程内 working
copy 和订阅发布。前端不得把 converter 产出的 `ThreadMessage[]` 回写后端，也不得把
Assistant UI 的状态重新序列化成领域事实。

### 3.3 Part 和状态事实

后端投影器只会产生以下三类 UI part：

| 快照 part | 字段 | 前端语义 |
|---|---|---|
| `text` | `text`, `status: running/completed` | 用户输入或 assistant 正文；正文可以增量追加 |
| `reasoning` | `text`, `status: running/completed` | assistant 推理通道；只按后端是否提供来显示 |
| `tool-call` | `toolCallId`, `toolName`, `status`, `args`, `result`, `error`, `presentation`, `data`, `isError` | 工具活动和结果；不能在客户端执行 |

工具状态是 `pending`、`running`、`completed`、`failed`、`cancelled`。终端 run 状态由
后端的 `RunStatusChangedEvent` 投影，至少要正确表达 `pending`、`running`、
`completed`、`failed`、`cancelled`；未知状态不能静默转成成功。

`approvals` 当前被后端校验为必须为空，第一版不实现审批按钮、确认弹窗或虚构的
“待确认”状态。

顶层 `error` 是 snapshot 的固定保留字段，但当前 projector 没有把已知 workflow error
投影到这里；当前可用的错误事实来自 HTTP 错误体以及 tool-call part 的 `error` 字段。
前端必须保留对非空顶层 `error` 的兼容渲染，但不能把 `error: null` 当作“本轮没有任何
错误”的充分证据，也不能为了展示错误在客户端写入这个字段。

### 3.4 Snapshot 流的正确理解

后端先用一次 root `set` 回填当前完整 snapshot，再发布已提交的 mutation：

- 结构、状态、工具结果和完整替换使用 `set`。
- 文本增量使用 `append-text`。
- `ConversationEventProjector` 只把 workflow event 投影为 snapshot mutation。
- `ConversationTaskSnapshotService` 提交 SQLite、更新 working copy 后才通知订阅者。
- `AssistantTransport` 在订阅前回填基线，避免连接建立时漏掉 run 初始化事件。

因此“流式”不是前端定时轮询或把完整字符串反复替换，而是后端提交的
`append-text` mutation 持续更新同一个 assistant text/reasoning part；工具卡片则在
tool-call part 的 `set` 更新中从 pending/running 迁移到终态。

当前后端 `TransportAssistantService.stream` 的 `idle_timeout` 默认是 5 秒。长模型调用
如果连续 5 秒没有 snapshot mutation，HTTP 流可能提前结束，而 run 仍可能是 pending 或
running。前端不得把这种 EOF 当成 completed，也不得用原命令再次 POST（同一
`commandId` 会触发幂等冲突）。本次仅前端改造的防御策略是：保留最后一个服务端 state，
在发现 run 非终态时显示“连接暂时中断/正在恢复”，重新 GET snapshot；直到拿到终态前
保持非成功视觉状态。真正的无缝续订需要后端提供 resume/subscription endpoint 或调整
idle timeout，列为后续跨层契约工作，不在前端偷偷模拟。

## 4. 总体前端架构

### 4.1 运行时组成

目标组件树：

```text
TaskPage
  └─ AssistantScreen (按 taskId 重建)
       ├─ useAssistantInitialState(taskId)
       └─ AssistantRuntimeProvider runtime={useAssistantTransportRuntime(...)}
            └─ ThreadPrimitive.Root
                 ├─ ThreadPrimitive.Viewport
                 │    └─ ThreadPrimitive.Messages
                 │         └─ MessagePrimitive.Root
                 │              └─ MessagePrimitive.Parts
                 │                   ├─ StreamdownTextPrimitive
                 │                   ├─ assistant-ui Reasoning
                 │                   └─ Tool UI / ToolFallback
                 └─ ComposerPrimitive.Root
                      ├─ ComposerPrimitive.Input
                      └─ ComposerPrimitive.Send / ComposerPrimitive.Cancel
```

运行时、converter、Transport 类型和工具 renderer 分离：

- `lib/assistant/contract.ts`：只放后端 wire state 的 TypeScript 类型。
- `lib/assistant/converter.ts`：纯函数，只做 wire state → assistant-ui message 的映射。
- `components/assistant/assistant-runtime.tsx`：创建 runtime、注入 task/model 信息、
  处理初始 state、错误和取消的边界适配。
- `components/assistant-ui/elements/thread.aui.tsx`：组合官方 primitives，不保存对话
  事实，不写状态机。
- `components/assistant-ui/tools/*`：按后端 `presentation` 和 `data.kind` 渲染工具卡片。

### 4.2 Initial state 与 task 切换

首屏流程必须是：

1. `useAssistantInitialState(taskId)` 请求后端 snapshot。
2. 请求完成后才创建 `useAssistantTransportRuntime`，避免 runtime 先以空 state 启动
   再把空 state 当作历史。
3. `key={taskId}` 重建 runtime，清除上一个 Task 的不可持久化 UI 状态。
4. Task 切换时取消旧的首屏请求写入，旧响应不能覆盖新 Task。

这只是在前端维护 runtime 基线，不是建立第二个事实源。若首屏请求失败，显示连接错误
与重试入口；重试重新读取服务端 snapshot，而不是使用旧 React state 拼接。

## 5. Runtime 与 converter 设计

### 5.1 `useAssistantTransportRuntime` 配置原则

运行时配置固定采用：

```ts
const runtime = useAssistantTransportRuntime<TransportState>({
  initialState,
  api: `${backendBaseUrl}/assistant`,
  protocol: "assistant-transport",
  converter,
  body: async () => ({
    taskId,
    workspaceId,
    providerId: selection.providerId,
    modelName: selection.modelName,
    reasoningEffort: selection.reasoningEffort,
  }),
  prepareSendCommandsRequest: async (request) => {
    // Assistant UI 会自动带上 state；后端 AssistantTransportRequest extra=forbid，
    // 这里必须在唯一的发送边界剥离它，不能把 state 当作后端请求契约。
    const { state: _state, ...backendRequest } = request;
    return addStableCommandId({ ...backendRequest, taskId, workspaceId });
  },
  onResponse: readTaskIdentity,
  onError: handleTransportError,
  onCancel: handleTransportCancel,
});
```

`body` 必须符合安装版本的异步 body 类型；`prepareSendCommandsRequest` 是强制的
请求适配边界，因为 assistant-ui runtime 默认会把本地 `state` 放进请求体，而当前
后端 `AssistantTransportRequest` 使用 `extra="forbid"` 且不接受该字段。实际实现必须
以安装版本的类型为准；上面的片段只表达边界，不是直接复制的最终代码。

明确决策：

- `capabilities.edit` 保持关闭。交互建议第一版没有编辑、分支、撤销；后端也没有为
  edit command 提供事实闭环。
- 不注册前端工具 executor。后端工具已经执行并通过 tool-call part 回传，前端只注册
  renderer；不能把 `defineToolkit` 当作客户端执行入口。
- 不启用 attachments adapter。第一版不提供附件按钮，布局只保留未来扩展位置。
- `add-tool-result` 不属于当前业务路径；前端没有工具执行结果需要回传。
- `onError` 只能将传输错误显示给用户并保留可重试提示，不能把本地错误伪造为后端
  `completed` 或覆盖 canonical message。
- `onCancel` 只处理 UI 连接/队列状态；真实 run 取消必须调用后端
  `/runs/{run_id}/cancel`。

### 5.2 Converter 的单一职责

converter 接收：

```ts
(state, metadata: {
  pendingCommands: AssistantTransportCommand[];
  isSending: boolean;
  toolStatuses: Record<string, ToolExecutionStatus>;
}) => {
  messages: ThreadMessage[];
  isRunning: boolean;
  state?: ReadonlyJSONValue;
}
```

converter 只允许做以下工作：

- 按 `role` 创建 user/assistant `ThreadMessage`。
- 把 `text`/`reasoning` part 的 `running/completed` 映射为 assistant-ui 的 part status。
- 把后端 tool-call 字段映射为 assistant-ui tool-call part，保留 `toolCallId`、
  `toolName`、`args`、`result`、错误和展示数据；具体映射见下节，不能把后端字段原样
  塞进 assistant-ui 未声明的顶层字段。
- 把后端 run/message 终态映射为 assistant-ui `MessageStatus`。
- 消费 `pendingCommands` 做短暂的用户消息乐观显示；后端首帧到达后必须由 canonical
  snapshot 接管，不能永久留存 pending 副本。
- 只有当顶层 `state.error` 非空时才映射为错误展示；当前后端通常通过 HTTP 错误和
  tool-call part 表达错误，不能从 `error: null` 推断“无错误”。

converter 禁止：

- 按工具名推导工具结果或执行状态。
- 从 `content`、日志或 message 文本反推工具调用。
- 修改、合并、排序或删除服务端 canonical messages。
- 将未知 part 当作 text 或将未知 run status 当作 complete。
- 读取 SQLite、调用 API、操作 workspace 或写 localStorage。

### 5.3 状态映射

| 后端事实 | assistant-ui 映射 | 用户可见语义 |
|---|---|---|
| message `pending/running` | `status.type = running` | 正在执行；若没有更具体活动则显示“正在思考…” |
| message `completed` | `status.type = complete` | 已完成 |
| message `cancelled` | `status.type = incomplete`, `reason = cancelled` | 已取消 |
| message `failed` 且原因属于断连/取消 | `incomplete/cancelled` | 已取消或连接中断 |
| message `failed` 其它原因 | `incomplete/error` | 失败，显示安全错误摘要 |
| 未知状态 | `incomplete/other` | 协议状态未知，不能显示成功 |

`endReason` 是后端中性事实，前端只按稳定映射表解释；不能把任意字符串拼成看似可靠的
用户提示，也不能显示异常堆栈。

### 5.4 Tool-call 到 assistant-ui 的精确映射

Assistant UI 的 `ToolCallMessagePart` 没有后端的五态 `status`、`presentation`、`data`
或独立 `error` 顶层字段。converter 必须按当前安装版本的类型做显式适配：

```ts
const backendStatus = part.status ?? "pending";
const artifact = {
  backendStatus,
  presentation: part.presentation ?? {},
  data: part.data ?? null,
  error: part.error ?? null,
};

return {
  type: "tool-call",
  toolCallId: part.toolCallId,
  toolName: part.toolName,
  args: part.args as ReadonlyJSONObject,
  // 后端快照提供的是已解析对象，不是原始参数增量；这里只生成稳定的展示文本。
  argsText: JSON.stringify(part.args ?? {}, null, 2),
  artifact,
  ...(backendStatus === "completed" && part.result !== undefined
    ? { result: part.result, isError: false }
    : {}),
  ...(backendStatus === "failed"
    ? {
        result: {
          kind: "tool-error",
          message: part.error ?? "工具执行失败",
          data: part.result ?? null,
        },
        isError: true,
      }
    : {}),
  ...(backendStatus === "cancelled"
    ? { result: { kind: "tool-cancelled" }, isError: false }
    : {}),
};
```

上面是字段语义示意，最终类型以 `@assistant-ui/core` 为准。`artifact` 是 UI-only
扩展数据，工具 renderer 从中读取 `backendStatus`、`presentation` 和 `data`；
`argsText` 是 assistant-ui 必需字段，不能省略。renderer 显示 pending/running/终态
时读取 `artifact.backendStatus`，不要把后端五态伪装成 assistant-ui 的
`running/complete/incomplete/requires-action`。后端五态到 UI 的规则是：

| 后端 tool status | assistant-ui 字段 | renderer 视觉 |
|---|---|---|
| `pending` | 无 `result`，`artifact.backendStatus = pending` | 准备执行 |
| `running` | 无 `result`，`artifact.backendStatus = running` | 执行中/loading |
| `completed` | `result`，`isError = false` | 成功 |
| `failed` | 错误对象作为 `result`，`isError = true` | 失败 |
| `cancelled` | 取消对象作为 `result`，`isError = false` | 已取消 |

这只是消息 part 的 UI 映射，后端 snapshot 中的五态仍然是唯一生命周期事实。

## 6. 对话 UI 设计

### 6.1 Composer

使用官方 `ComposerPrimitive`，不自研输入状态机：

- `ComposerPrimitive.Input` 使用多行 textarea。
- Enter 发送，Shift+Enter 换行；键盘行为交给 primitive。
- idle 时使用 `ComposerPrimitive.Send`。
- run active 时使用 `ComposerPrimitive.Cancel` 作为 UI 停止入口，并在同一操作中调用
  后端 cancel API；按钮文案为“停止”，请求返回前可显示“正在停止”。
- 模型/provider 未选定时，发送入口禁用并显示已有 model selector 的校验提示；后端
  `MODEL_SELECTION_REQUIRED` 仍是最终兜底。
- 第一版不渲染附件按钮、不渲染编辑/重试整轮/撤销修改按钮。

### 6.2 Assistant 正文和 reasoning

- 正文使用 `MessagePrimitive.Parts` 的 render function 识别 `text` part。
- 使用 `@assistant-ui/react-streamdown` 的 `StreamdownTextPrimitive` 渲染 Markdown，
  使不完整 Markdown 在流式增长时稳定显示；不手写 Markdown parser 或代码高亮器。
- 使用 Streamdown 的 `caret` 表达仍在增长的正文；part 完成后由后端状态关闭 caret。
- link safety、允许协议和外部 URL 策略在 Streamdown renderer 统一配置。
- reasoning 使用 assistant-ui 已有 reasoning primitive/element；只有快照存在
  `reasoning` part 时才显示，不能前端凭空创建思考内容。
- 用户消息不渲染成 assistant 气泡，不显示后端内部状态或工具细节。

### 6.3 采用“对话主线 + 活动卡片”

工具 part 仍属于 assistant message 的 parts pipeline，不单独建立日志页面。这样可以
保持工具发生位置与 Agent 正文的时间顺序，并由后端 snapshot 的 `messages[].parts[]`
作为唯一排序依据。

连续的只读检查工具可以使用 assistant-ui 的 grouped parts / collapsible 组合成“正在
检查代码”区域；文件变更、删除和终端工具保持独立卡片。分组只改变视觉布局，不能改变
part 顺序和事实数量。

## 7. 工具 UI 设计

### 7.1 通用 renderer 规则

工具 renderer 使用 assistant-ui 的工具解析机制和现有 `ToolFallback`，不在每个工具中
复制一套生命周期状态机。后端已提供：

- `presentation`: 来自 `ToolDisplayHints`，包含 `verb`、`icon`、`surface`、
  `expandable`、`expand_layout`、`default_open`。
- `data`: 只面向客户端的结构化展示数据；UI 不从 `result` 或模型文本猜展示字段。
- `status`: 工具的五态生命周期。

优先级：注册过专用布局的 `toolName` 可使用该布局；否则按
`presentation.expand_layout`/`data.kind` 选择通用布局；再否则使用安全的
`ToolFallback`。不要把后端当前工具名硬编码成一棵越来越长的 if/else 树。

使用成熟组件：

- assistant-ui：`MessagePrimitive.Parts`、tool resolution、`AuiIf`、message error。
- shadcn/ui 或项目已有 Base UI：Card、Badge、Collapsible、Button、Tooltip、ScrollArea。
- 图标：已有 `lucide-react`，图标名由后端 `presentation.icon` 经过受控白名单映射。
- Markdown：Streamdown。
- Diff：引入成熟、开源、支持 React 的 diff renderer（实现阶段锁定一个依赖，例如
  `react-diff-viewer-continued` 或等价方案）；禁止手写 diff 算法、行配对和语法高亮。
- 终端输出：使用成熟的 ScrollArea/Collapsible；不为输出内容自研虚拟终端，因为后端
  已经返回脱敏、有界文本，不需要把它当作可交互 shell。

### 7.2 生命周期展示

| status | 默认视觉 | 内容规则 |
|---|---|---|
| `pending` | 灰色、准备执行 | 显示后端提供的动词、工具对象和必要参数摘要 |
| `running` | loading | 显示正在处理的对象；终端可展示实时尾部 |
| `completed` | 中性色/绿色 | 显示结构化摘要；详细数据默认折叠，按后端 `default_open` 决定 |
| `failed` | 红色/警告 | 显示后端错误摘要；不能显示原始 JSON 或堆栈 |
| `cancelled` | 中性取消 | 显示已取消；不能显示成失败或成功 |

状态文案和颜色必须同时有文字/图标/`+`/`−` 等非颜色信息，满足无障碍和交互建议。

### 7.3 只读检查布局

适用于 `read_file`、`list_directory`、`search_files` 等 `expand_layout = details/list`
的工具：

- 默认是一行轻量活动项，显示后端 `verb`、相对 workspace 路径、搜索模式或分页摘要。
- 默认折叠；只有后端 `data` 提供的结构化 items 才能展开。
- ReadFile 不显示文件正文；它返回给模型的带行号内容不是用户阅读区域。
- ListDirectory 只显示后端当前页的直接子项，不假设递归或完整目录。
- SearchFiles 只显示后端结构化返回的文件路径，按路径去重；不前端补造命中行、总数
  或上下文。
- 结果受后端预算/分页约束时显示“结果已截断/可继续查看”，但不把当前页说成全量。

### 7.4 文件变更 Diff 布局

适用于 `data.kind = "file-changes"` 或 `expand_layout = "diff"` 的
ApplyPatch、patch/Replace、WriteFile：

- 独立 Diff 卡片，默认显示文件数、`diff_stats` 的新增/删除行数和每文件摘要。
- 多文件按 `data.changes[]` 顺序分组；首个文件可按后端 `default_open` 自动展开。
- 使用 `before`/`after` 和 `insertions`/`deletions` 渲染成熟 diff 组件；不要把完整
  `content` 当普通聊天文本。
- 用标准 diff 颜色和明确的 `+`/`−` 标记；不能只依赖颜色。
- `status` 为失败但 data 已显示部分变化时，明确写“部分变更已应用”或使用后端实际
  error/data 事实，不能显示“文件未修改”。
- 不显示允许修改、取消修改、重新应用、撤销或保留按钮；文件工具已经由后端直接执行。
- Replace 使用后端注册名 `patch` 的 `presentation.verb` 和 data，不在 UI 中假设存在
  “ReplaceTool” 名称，也不猜替换次数。
- WriteFile 根据后端 `changes[].status` 显示创建/修改；写入后语法检查失败时保留
  “文件已写入，随后检查发现语法错误”的事实提示。

### 7.5 文件删除与移动

ApplyPatchTool 的文件删除和移动作为普通文件变更显示在 Diff 布局中，不设独立 renderer。
目录删除不受支持；删除和移动的路径、结果与 Diff 都以后端快照为准。

### 7.6 Terminal 布局

适用于 `data.kind = "terminal-result"` 或 `expand_layout = "terminal"` 的
`execute_terminal`：

- 命令永远可见；输出默认折叠，running 时可展开实时尾部。
- 只显示后端已脱敏且有界的 `output`。
- 明确显示 `exit_code`、`timed_out`、`truncated`；耗时只能在前端确实测得时显示，
  不能伪造后端耗时。
- 后端 deny-list 拒绝的命令显示失败，不提供“强制执行”。
- 用户停止后先显示“正在停止”，直到后端 snapshot 迁移为 cancelled；不能立即把
  running 本地改成 completed。

### 7.7 重试边界

交互建议要求：只有后端标记可重试时才显示“重试”。这条要求保留为产品验收条件，
但当前代码事实是 `ToolObservation.retryable` 尚未进入 `ToolCallStatusChangedEvent` 或
`ConversationStateToolCallPart`，且 `/assistant` 没有 retry command。因此本次仅前端
改造不能声称已经支持该按钮，也不能自行补一个客户端重跑路径。

前端 renderer 预留唯一的能力门槛：当后端未来在 `data` 或 `error` 中正式声明
`retryable: true`，并同时提供幂等 retry command/endpoint 后，才显示重试；按钮调用该
正式命令。当前版本没有该字段或命令，所以不显示重试。这样既不违反交互建议的“后端
标记才显示”，也不伪造当前后端没有的能力。该跨层契约应在后续后端任务中单独确认，
不是本文的前端补丁。

## 8. 错误、连接和取消

错误分三层展示：

1. **Transport 请求错误**：解析 `{error:{code,message,retryable}}`，显示安全文案；
   不显示堆栈，不吞掉 commandId/runId。
2. **Snapshot `error`**：这是固定保留字段。只有非空时由 converter 映射为消息错误
   区域；当前后端常规错误并不从该字段投影，不能把它当作所有错误的事实来源，也不能
   永久追加重复错误消息。
3. **工具失败**：展示 tool-call 的 `error`/`data`，状态为 failed；不要把工具失败
   误认为整轮失败，除非后端 run 也已进入 failed。

连接状态只表达传输连接事实：连接中、已断开、恢复中。若后端进程仍运行，前端可以
重新连接并重新 GET snapshot；不能在本地重新创建 assistant message 或重放工具。

取消流程：

```text
点击停止
  → 禁止重复点击，显示“正在停止”
  → POST /runs/{runId}/cancel
  → 后端先发取消信号，再以原子状态迁移落库并投影
  → snapshot tool/run/message 变为 cancelled
  → UI 收到 canonical 状态，关闭 running/caret
```

取消失败时保持“停止请求失败”的错误状态，不能用前端本地状态覆盖后端 run。

## 10. 实施顺序

1. 先冻结并生成 TypeScript `TransportState` 类型，和后端 snapshot 校验逐字段核对。
2. 重建 initial-state → runtime → provider 的生命周期，先验证 Task 切换和首屏历史。
3. 用官方 `MessagePrimitive.Parts` + Streamdown 接通正文/推理流式显示。
4. 接通 pending command 的短暂乐观用户消息、错误回填和后端 canonical 接管。
5. 建立通用 tool-part 状态壳，先接 `presentation` 与五态生命周期。
6. 依次实现 details/list、diff、terminal 三种成熟组件布局；文件删除和移动作为文件变更展示在 diff 布局中。
7. 接通 stop/cancel 和连接恢复提示。
8. 删除旧 SSE、eventStore、useSSE、timeline projector、客户端 Tool 执行链和重复的
   assistant state 适配；不保留双链路或 feature flag 回退。

## 11. 验证与验收标准

### 11.1 自动化验证

- TypeScript strict build、ESLint 通过。
- converter 单测覆盖空 snapshot、历史消息、流式 text/reasoning、五态 tool-call、
  未知状态和错误状态。
- Transport 集成测试覆盖首屏 root set、append-text、tool set 更新、命令幂等、模型未
  选择、active run 冲突和后端错误。
- Playwright 覆盖：用户消息立即显示、正文增量增长、工具卡片由 pending → running →
  completed/failed/cancelled、Diff 展开、终端输出折叠、停止后显示取消。
- 明确验证前端没有发起工具执行请求，也没有把快照写回后端。

### 11.2 交互验收清单

- 输入区是多行文本；Enter 发送、Shift+Enter 换行；执行中是停止。
- 用户消息先显示，assistant 正文和 reasoning 逐步增长；不是等待完整响应后一次性出现。
- 工具活动嵌在对话主线；只读检查可折叠，变更是 Diff，删除独立，终端独立。
- 完整 JSON、原始参数和有界原始输出只在详情中出现，不作为主要界面。
- 第一版没有附件、审批、允许修改、撤销、恢复、前端确认或客户端执行。
- 所有显示事实都能追溯到 snapshot message/part 或 backend display data。

### 11.3 第零铁律检查

完成实现前必须回答：

- 是否仍然存在两套消息事实或旧 SSE/eventStore？若存在，删除并收敛到 Assistant
  Transport。
- 是否把复杂能力交给 assistant-ui、Streamdown、shadcn/Base UI 和成熟 diff 组件？
- 是否有新增的自研 diff、Markdown、工具执行、状态机或持久化层？有则移除或改为复用
  成熟库/现有后端能力。
- converter 是否仍是纯边界映射？任何领域判断都应回到后端。
- UI 是否能在后端状态新增时安全显示“未知”，而不是静默成功？
- 是否只做了第一版需要的交互，没有为附件、审批、撤销、恢复提前堆叠未验证抽象？

## 12. 明确不做的事情

- 不改后端 snapshot schema 来迁就某个 React 组件。
- 不在前端执行文件工具、Terminal 或任何 MCP/tool。
- 不把 `localStorage`、React state、assistant-ui thread state 当作对话事实。
- 不把完整工具 JSON、原始日志和内部错误堆栈当作主要 UI。
- 不提供后端没有支持的审批、确认、撤销、恢复、编辑、重试命令；重试只在后端正式
  提供 retryable 字段与幂等命令后启用。
- 不保留旧 SSE、eventStore、`useSSE`、timeline projector 或双协议回退。
