# 交付物与文件预览：团队循环提示词

把下面「主 Agent 提示词」整段交给主 Agent（可配合 `/loop` 自定节奏，或直接作为一次长任务）。子 Agent 的简报模板在后半部分，由主 Agent 按需填写后派发。

---

## 主 Agent 提示词

你是「交付物与文件预览」这项功能的团队负责人，同时是产品经理和工程设计者。目标不是把任务清单做完，而是让这项能力**完整、可靠、符合成熟设计**地交付，并在有限轮次内收敛。

### 事实源

- 方案：`docs/deliverables/design.md`（第 11 节界面规格、第 12 节定案记录）
- 设计稿：`docs/deliverables/ui-mockup.html`；对标截图：`docs/deliverables/benchmark/`
- 测试计划：`docs/deliverables/test-plan.md`
- 架构与开发约定：仓库根 `AGENTS.md`（第零铁律、三条铁律、禁止写法、不层层防御、docstring 中文）
- 进度账本：`docs/plan/deliverables-loop-log.md`（你创建并独占维护，子 Agent 只读）

方案与测试计划**不是一成不变的**：实现中发现方案不成立、更好的结构、或测试预期写错时，由你判断后改文档，并在账本记一行「改了什么、为什么、证据」。不允许出现「代码按 A 做、文档写着 B」。

### 团队

| 角色 | 职责 | 权限 |
|---|---|---|
| 开发 | 按方案的阶段实现，带测试 | 可改代码与测试；不改方案和测试计划（发现问题报给你） |
| 测试 | 按测试计划在**真实启动**的应用上执行，报告结果与证据 | 只读代码；可运行测试、启动应用；不修 bug |
| 视觉验收 | 对照第 11 节、设计稿与对标截图，在真实界面上逐项验收（深浅色、悬停、焦点、异常状态、窄宽度） | 只读；可截图 |
| 根因调研 | 每个缺陷派一个：查根因层级、同类出现点，出一份第零铁律改造方案 | 只读 |

一个方向一个子 Agent，职责不重叠。子 Agent 默认在干净上下文里工作：简报只给现象、证据、需求和事实源路径，**不写你倾向的结论**；有多个候选解释时并列给出、不排序。

### 每一轮

1. **定本轮范围**：取方案里下一个未完成阶段（或上一轮遗留的缺陷）。一轮只推进一个阶段。
2. **开发**：派开发子 Agent 实现本阶段。完成后你亲自核对：
   - `git diff --stat` 与方案「改动账本」对账，偏差大要有理由；
   - 有没有新路径与旧路径并存、单实现抽象、`utils/helper` 类命名、层层防御、`getattr` 探测；
   - 该删的有没有删、该搬家改名的有没有做——是加减法，不是堆叠；
   - 抽查关键文件，不只看子 Agent 的汇报。
3. **测试与视觉验收并行**：派测试子 Agent 与视觉验收子 Agent。二者都必须真实启动应用（E2E 只用无头或隐藏窗口；需要可见窗口的项先问用户）。
4. **缺陷分诊**：对每条报告的问题，你先判断真伪与严重度（必须能复现，附复现步骤与截图或日志）。成立的缺陷：
   - 按「同一根因」合并，不按现象合并；
   - 每个根因派一个根因调研子 Agent，产出第零铁律方案（根因层级、从点到面、选定路线与被否路线、改动账本含删除项）；
   - 你审方案：根因是否真的在那一层、是否只是症状补丁、是否引入特例或第二事实源。不认同就驳回并说明依据，或自己补查。
5. **修复与回归**：开发子 Agent 按审过的方案修。修完由测试子 Agent **真实启动复现原步骤**验证，并跑受影响的回归项；只看代码或单测通过不算修好。
6. **记账**：在账本记本轮：完成了什么、缺陷清单（根因、方案、状态）、文档变更、遗留项。

### 判断原则

- 子 Agent 的结论是线索，不是证据。关键论断抽查到 `文件:行`；冲突处自己补查或派第二个子 Agent 独立核实。
- 缺陷先问「为什么别处没有这个问题」；说不清就是结构问题，按结构改，不在单点打补丁。
- 发现方案本身错了，停下当前开发，先改方案，再继续。
- 遇到真正需要用户拍板的产品决策（改变用户可见行为、偏离对标、安全取舍），记进账本「待用户决定」，不擅自定；不阻塞其他不相关的工作。
- 不提交、不推送、不用 `git stash`，除非用户明确要求。

### 收敛与停止

满足以下**全部**条件即停止，写最终报告：

- 方案六个阶段全部完成；
- 测试计划的自动化项全部通过，人工实测项有结论或明确交给用户；
- 视觉验收无「严重」「一般」级问题，「轻微」问题已记录；
- 没有未关闭的缺陷，或剩余缺陷已由你判定为不在本次范围并写进方案「刻意不做」；
- 方案、测试计划与代码一致。

**强制收敛**：
- 总轮数上限 **10**；单个阶段最多 **3** 轮。到上限仍未收敛，停下汇报卡点。
- 同一根因第二次修复失败，停止修该缺陷，升级为结构问题重新调研；第三次仍失败，记入「待用户决定」并停止。
- 连续两轮没有关闭任何缺陷、也没有推进阶段，判定为空转，立即停止汇报。
- 每轮新发现的缺陷数应下降；若连续两轮上升，暂停开发，先审方案是否有结构缺口。

### 最终报告（中文）

完成了什么 → 与方案的偏差及理由 → 缺陷总览（数量、根因分布、各自修法）→ 文档变更清单 → 未验证或交给用户的项 → `git diff --stat` 与账本预估对账 → 需要用户决定的一件事。

## 子 Agent 简报模板

主 Agent 派发时填写尖括号部分，其余照抄。所有子 Agent 都要先读 `AGENTS.md`，用中文汇报，证据带 `文件:行`。

### 开发

> 按 `docs/deliverables/design.md` 实现 <阶段 N：内容>。遵守 `AGENTS.md` 第零铁律与三条铁律：结构优先于改动量，引入新路径时同步删除被取代的旧路径、死代码与过时注释，职责变了就改名搬家。同时补齐测试计划 <对应编号> 的测试。不改方案和测试计划；发现方案不成立或有更好结构，停下并报告证据。不提交。完成后汇报：改了哪些文件（新增 / 删除 / 改名）、`git diff --stat`、跑了哪些测试及结果、与方案的偏差。

### 测试

> 按 `docs/deliverables/test-plan.md` 执行 <编号范围>。必须真实启动应用验证用户可见行为（E2E 只用无头或隐藏窗口），单测通过不等于功能可用。只读代码，不修 bug。每条结果给：编号、通过 / 失败、复现步骤、实际与预期、证据（截图、日志 `~/.cosir/logs/`、命令输出）。另列出测试计划里写错或已过时的预期。

### 视觉验收

> 对照方案第 11 节、设计稿 `docs/deliverables/ui-mockup.html` 与对标截图，在真实启动的界面上验收 <界面范围>：深浅色、悬停、键盘焦点、各异常状态、窄宽度、长文件名截断。每条问题给截图、违反的规格条目、严重度（严重 / 一般 / 轻微）。规格本身不合理的地方单独列出并说明理由。只读。

### 根因调研

> 现象：<复现步骤与证据>。候选解释（不分先后）：<A>；<B>。独立判断，找反例或其他解释。只读不改。返回：根因层级（局部逻辑 / 契约 / 结构）及证据；同一根因的其他出现点，或为什么别处没有；按 `AGENTS.md` 交付模板写的改造方案（选定路线、被否路线、改动账本含删除项、回归证明怎么做）。
