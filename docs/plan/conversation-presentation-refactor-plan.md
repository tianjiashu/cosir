## 1 目标与路线

对话界面应让用户快速看清：Agent 在做什么、需要自己做什么、已经产生什么结果、执行是否结束。工具调用是执行记录，不意味着每次调用都需要一个可见卡片。

采用前端展示投影重构：在同一入口决定内容顺序、工具可见性、摘要、异常提示和折叠策略，继续复用 assistant-ui、现有 Markdown、工具详情、审批、终端、diff 与虚拟列表。后端继续拥有运行与工具事实；本次后端代码范围仅补齐网页提取“部分成功”的结构化结果。现有契约不支持准确的挂起原因与最终答复分段，按 5.2、6.2 明确收紧展示承诺，不用前端猜测补出新的业务事实。

主要行为变化：

- 用户消息采用深色圆角气泡；助手消息保留无气泡正文，增大阅读字号和段落间距。
- 运行时正文按原序稳定显示，段落之间以轻量摘要承载工具活动；正常结束后按明确的末段布局规则收起此前过程；这不代表新增了“最终答复”语义标记。
- `wait_messages` 正常调用不占默认过程行、不进入工作次数统计，当前等待状态由运行事实承接。
- 用户中止使用中性“已停止”提示，保留已生成正文和已产生的结果；停止请求中、单工具取消与运行失败分别表达。
- 工具调用完成不等于结果正常；折叠摘要必须保留明确的非零退出、部分失败等信号。
- 普通 Agent 来信采用“来源 + 展开”的轻量行，行上不放原文；后台结论更新原调用与既有看板，不重复插入完整消息。内部系统通知不全部暴露给用户。

### 1.1 按第零铁律比较路线

| 路线 | 做法 | 结果 |
|---|---|---|
| 局部补丁 | 在 JSX 隐藏 wait，调整错误卡颜色，单独改 CSS | 工具行、统计、当前动作、折叠和估高各自判断，后续同类工具需要多处修改；无法解决流式正文迁移与等待语义 |
| 展示投影重构，选定 | 工具外壳策略在现有目录声明，结果语义从结构化数据派生，回合投影统一决定可见结构 | 规则与消费方一致，保留现有业务边界；改动范围包含呈现与必要结果契约，不扩大到调度重写 |

任务按重构执行：根因是展示模型没有表达“执行记录、可读活动、需要操作、持久结果”的区别，不是单个工具卡写错。终态不增加通用策略引擎、插件框架、工厂或第二套 runtime。

### 2.1 调查覆盖与停止边界

本次“看全”指这项改造的事实生产、传输、状态恢复和全部相关 UI 消费方向，不宣称逐行审读了仓库中无关业务。

| 工具或内容 | 默认形态 | 展开或独立保留 |
|---|---|---|
| `wait_messages` | 正常调用不显示历史工具行，不计入工作摘要 | 当前等待状态；调用失败时的短提示；原始执行记录可在既有观测入口查看 |
| 文件读取、搜索、目录、网页搜索与提取 | 与所属叙述邻接的灰色摘要 | 原调用行、目标、结构化结果、异常 |
| 命令与浏览器、终端操作 | 紧凑活动行或活动组 | 活动控制、按需输出、必要的资源入口 |
| `task_status`、发送消息、委派、Fork | 紧凑记录，可参与活动组 | 返回结论、收件方、打开任务与有效控制 |
| 文件改动、配置草稿、Team 执行结果 | 结果区 | 改动清单、草稿、Team 状态；沿用各自事实源 |
| 审批与终端、浏览器交接 | 常显操作区 | 说明和决定按钮，不依赖展开过程才能操作 |

`task_status` 有返回结论和打开任务操作；`browser_tabs` 可以改变宿主标签状态；`terminal_list` 有会话摘要。它们不归入纯控制隐藏策略。MCP 与 skill 根据实际结果展示，不因结果简单而全部隐藏。

### 3.2 汇总与显露

1. 工具默认策略只在现有前端 `tool-catalog` 声明。普通工具为正常活动，wait 为纯控制；错误、用户操作、有效后台状态等动态事实覆盖默认可见性。
2. 正常完成的 wait 不产生空行、空摘要、工作计数或无意义的折叠箭头。执行短暂 pending/running 时可在当前活动标题表达准备等待；真正挂起只认 activity，不能由工具名宣布挂起。
3. 普通工具按单条 canonical 消息中的原序组织，以正文作为活动组边界；不跨正文合并，不跨消息、分页或 Run 合并。
4. 思考仍按独立可折叠内容处理，不能变成面向用户的进展说明。其出现不要求每个工具单独成卡；合并时保留详情原序。
5. 过程内的活动组摘要使用目录动词和明确分隔符，例如“读取文件 4 次 · 搜索 2 次”。计数表示调用次数，不解析命令推算文件数，不把同一工具的结果投影重复计数。
6. 消息头不展示工具次数汇总；存在失败或部分结果时，在“查看过程”按钮中提示“有异常记录”。过程内的活动组摘要保留具体问题计数。wait 的失败也必须可见。整轮停止导致的多条取消以中性计数汇总，不渲染成连续红色错误卡。
7. 历史异常用“存在异常记录”等措辞，不宣称问题仍未解决；整轮结局由 outcome 决定，不能由工具错误计数决定。
8. 当前必要的停止、转后台、审批、交接入口位于可见活动或操作区；打开详情等低频操作可以折叠。相同调用只保留一处主要交互控件，避免两张审批表或重复请求状态。

## 4 对话结构与折叠

### 4.1 运行中

```text
                                  ╭──────────────────────╮
                                  │ 帮我检查这次改动      │
                                  ╰──────────────────────╯

正在检查调用链

我先读取实现和测试，确认取消信号由谁处理。
⌕  读取文件 4 次 · 搜索 2 次                    › 查看

后台任务的收尾需要继续验证。
⌘  正在执行测试                                ■ 停止

需要你操作的事项                              按实际事实显示
已产生的改动或草稿                            按实际结果显示
```

正文始终按原顺序追加，不能因下一次工具调用到达就在两个容器间迁移。每个正文 part 从出现起就在同一顶层槽位，键为 message ID + part index；不能只保留 key 却换父容器。活动组按原序连续调用区间建立，键取区间首个原始 toolCallId（含暂时不可见的纯控制调用），正文和 reasoning 构成边界；显示策略变化不改变组身份，追加工具不重置开合。

正文保持可读，成功工具详情默认折叠。首期不再以“最近四个原始 part”自动隐藏正文；长过程通过工具压缩与用户主动收起控制。保留消息级虚拟列表，不同时引入块级虚拟化；以长回合夹具验证实际渲染成本。

### 4.2 正常结束

```text
用时 3 分 22 秒                         › 查看过程
──────────────────────────────────────────────────

回复正文……

文件操作 · 涉及 2 个路径                       › 查看改动

复制答复    Fork    更多
```

仅当这条消息带 completed outcome 且存在末段正文时，默认收起末段之前的过程，结果区独立可见；用户已手动调整开合时遵守其选择。无末段正文时保留所有已生成正文，不能收成只有状态的一行；纯文本回复全部保留。无过程则无“查看过程”入口；单次调用与多次调用遵循相同规则。

末段指最后一个非正文 part 后的连续 text，仅作为完成后的阅读布局，不命名为业务“最终结论”；按钮使用“复制回复”。当前 wire 不含模型响应边界，连续两次模型正文也可能同在这段里。中止、失败及无 outcome 的历史助手消息不据此自动隐藏正文；同 Run 较早的消息不伪造完成或重复耗时。严格识别最终答复需要新增后端持久分段事实，本次不为视觉目标扩大到这一契约。

### 4.3 停止后

```text
■ 已停止 · 用时 3 分 22 秒              ▾ 查看过程
──────────────────────────────────────────────────

已经生成的进展与正文……
回复可能尚未完成。

⌕  读取文件 4 次 · 搜索 2 次                    › 查看
⌘  测试命令已取消                              › 记录

已有文件操作记录                         › 查看变更

复制已生成内容
```

停止使用中性图标和灰色文字，不加大块红底、不为整段正文加删除线、不淡化已发生的改动。没有正文时显示“已停止，尚未生成回复”；不补造 Agent 总结，不把部分输出标成结论。

停止和失败默认保留过程叙述，成功工具仍以摘要呈现；用户可主动收起。停止落定不突然清空正在阅读的内容。

“继续”沿用输入框当前执行入口：空草稿且当前运行可恢复时显示继续；有草稿则发送新输入。只读界面不提供写入操作。历史消息不各自增加恢复按钮。

### 4.4 Agent 来信与其他输入

用户需要知道有新的协作信息以及从哪里查看，不需要阅读全部内部沟通过程。主 Agent 的进展说明和答复承担面向用户的解释；辅助来信保留可追溯性，不与主答复使用同等视觉重量。

| 输入或事件 | 主对话呈现 | 事实边界 |
|---|---|---|
| 另一个 Agent 发来的普通消息 | 灰色小图标、来源名，默认收起全文 | 复用带 source 的 canonical 消息，不按 role=user 画成人类用户气泡 |
| 父 Agent 的委派、追加要求、Team 节点输入 | 同一种来源行；在子任务阅读器可展开原文了解任务来由 | 当前 source 不能区分所有用途，统一写“来自 X”，不猜测上下级关系或消息类型 |
| 子 Agent、Fork、Team、后台命令的结束结果 | 更新原调用和既有后台列表；需要了解时打开对应结果或任务 | `background_result` 不是一条新的普通来信，不重复复制其模型正文到对话 |
| 配置变动、内部续跑提示、其他 system_notice | 不新增对话条目 | 已有运行状态、资源面板表达用户需要知道的后果；不能把内部通知协议原文直接呈现 |
| 用户尚未并入的输入 | 输入框附近的紧凑排队区 | 与其他 Agent 的来信分开，保留立即发送、编辑和撤回；排队不代表 Agent 已处理 |
| 审批或交接 | 常显操作区 | 仅由明确的等待决定事实触发；普通来信中的问句不自动变成用户审批 |

普通来信收起态示意：

```text
↳ 来自 代码审查 Agent ›

我会结合这条信息，继续核对取消路径。
```

展开后，来源与入口保持原位，正文在其下按正常阅读字号显示，不加第二层气泡或嵌套卡片：

```text
↳ 来自 代码审查 Agent                                 ▾ 收起
  取消处理还需要检查后台收尾……
  原始消息全文，可选择、复制并打开其中的链接。
                                             打开来源任务
```

具体规则：

1. 预览是原文的短摘录，不是模型生成摘要。用现有 Markdown 能力提取可读文字，去除预览中的块级排版；宽屏一行，窄屏最多两行，不展示大标题、表格或代码块。完整内容只在展开时渲染。无法形成有效预览时只显示来源与“查看消息”。
2. 来源使用消息中的名字快照，不随来源改名回写历史。名字长时截断，完整名可访问；source 不足以证明是子任务时不统一称“子 Agent”。
3. 展开与打开来源任务是两个不同动作。展开不离开当前对话；打开来源复用 `useOpenTask`，按 Task 类型进入侧栏对话或工作台，不新建第二个导航入口实现。
4. 来信没有编辑重跑、重新发送、点赞或恢复按钮；展开后可复制原文。来源被删除或打开失败不影响阅读、复制这条已保存消息，不为每行预先查询来源存活。
5. 开合按 Task + message ID 存入已有 disclosure store，估高采用同一默认形态。多条来信默认逐条紧凑显示，首期不跨 canonical 消息重新聚合或去重，不改变分页和回复锚点。
6. 来信到达不自动展开、打开面板、抢焦点或强制滚到底部；不默认弹 toast、播放声音或增加未读中心。沿用当前阅读锚点与回到底部入口，刷新历史不冒充新到达提醒。
7. 消息出现表示已经投影进对话，不代表模型已读完、理解或完成处理。只写“来自 X”，不用“已读/已处理/已采纳”回执；不根据正文内容猜优先级、任务成功或用户必须回复。
8. 如果主 Agent 判断消息需要用户决定，应通过已有面向用户的沟通或明确交互流程提出；前端不因为来信包含“请确认”就自动显示操作卡，也不默认把用户下一条输入改投给消息来源。

上述样式只需调整前端来信组件、开合和估高；当前消息 source 与 parts 足够，不增加后端消息类型，不解析 `<agent_message>`、`<background_result>` 等模型协议标签。

### 4.5 用户注意力与多处展示

- **需要用户处理的事项优先。** 当前审批、交接和阻断错误要容易找到；常规活动、Agent 来信和执行细节降低视觉重量。用户已经展开的内容不因后台更新被自动收起。
- **同一事实有一个主要详情入口。** 原调用承载执行详情，后台看板承载当前工作清单，主答复解释结果。三处允许短引用或状态镜像，不各复制一份长结果，不新增“收到结果”卡、完成 toast 与消息全文三重通知。
- **后台工作已结束不等于目标成功。** 看板的 completed 主要表达结果交付完成，取消也属于已结束项。看板汇总使用“已结束”，逐项保留取消或收尾状态；成功与否由子任务、Team 或命令的真实结果解释。未关联出准确对象时不显示假的“3/5 全部成功”。
- **结果常显指摘要和入口常显。** 文件操作的路径数、调用次数、草稿或 Team 的身份与状态保持可见；长文件清单、diff、大段配置和流水线详情按需展开。审批所需内容与操作仍按审批组件规则可达，不能为了紧凑省略关键决定信息。
- **排队输入保留用户控制。** 用清楚的“排队中/即将处理”区分已并入消息；不为统一深色气泡把排队项伪装成已发送并处理的用户消息。挂起时普通发送仍排队，现有立即发送入口可用，不借样式改写调度语义。
- **面板变化由用户决定。** 普通来信和结果不自动切换子任务、终端或浏览器面板。必要交接通过现有可见操作入口完成，不因为消息来源具备某种资源就自动打开它。
- **精简不依靠难读的灰字。** 灰色用于层级，字体与对比度仍满足阅读；来源、展开、复制和打开任务均可通过键盘访问。正文的长内容通过展开控制高度，不把字号缩到工具元信息以下。

首期沿用现有后台看板和消息流，不增加统一通知中心、未读计数、消息紧急程度分类、自动摘要模型调用或直接回复其他 Agent 的新功能。

## 5 状态与取消语义

### 5.1 状态矩阵

| 情况 | 显示 | 行为 |
|---|---|---|
| 首输出前／仅 reasoning | “正在思考”，有真实内容才可展开 | 轻量介绍区，规则见 §14；不是模型内部阶段事实 |
| 已有正文或工具记录后的运行 | 当前动作或“正在处理” | 正文原位增长，不保证此时文本是最终答案 |
| Run 挂起 | 主标题“等待继续” | 挂起原因未持久化，不从历史工具或后台列表猜原因 |
| 存在有效用户决定（可与挂起并存） | 对应调用“需要你确认／操作” | 操作区常显；这是调用事实，不宣称它就是当前 Run 挂起原因 |
| 存在后台工作（可与挂起并存） | 看板显示“运行中／收尾中” | Task 范围的工作清单，不冒充本轮等待清单或精确进度 |
| 停止请求在途 | “正在停止…” | 禁重复提交；继续接收最终输出与状态，不在 HTTP 返回后直接认定已停止 |
| 当前 Run cancelled | “已停止 · 用时…” | 保留内容和结果，中性呈现 |
| 单工具 cancelled，Run 仍活动 | 仅对应工具“已取消” | 不结束整轮、不禁其他有效操作 |
| 工具 failed，Run 仍活动 | 局部错误或摘要异常记录 | Agent 可继续，不等同整轮失败 |
| 调用完成但存在非零退出或部分失败 | 明确结果提示 | 共享结构化结果解释，不按 completed 隐藏异常 |
| Run failed | “运行失败”及可读错误 | 错误色局部强调；保留已生成内容，按当前资格恢复 |
| `endReason=runtime_restarted` | “运行已中断”并说明后端重启 | 不归因于用户；按既有恢复机制处理 |
| 连接中断或快照暂不可用 | 对话级连接提示 | 保留最后快照，不将断连解释为 Run 取消 |
| 停止请求被明确拒绝 | 请求失败及重试 | 解除禁重，保留真实执行状态，不伪造终态 |
| 请求断网、是否受理不明 | “状态待同步”及连接提示 | 沿用重连同步核对，不自动重放请求、不宣布操作已失败 |
| 停止与正常完成竞争 | 以最终快照为准 | 已正常完成则正常呈现，不因点过停止而覆盖 outcome |
| 正常结束 | “用时…” | 按 4.2 收起过程；无末段正文时保留全部正文，结果常显 |
| 取消或失败后恢复 | 恢复当前运行状态 | 同一 Run 继续，旧 outcome 被清除；不生成假的新用户消息或独立执行段 |

### 5.2 事实与优先级

消息结局读该消息的 outcome；当前活动只应用到现有消息渲染上下文指定的末条回复。临时“正在停止”仅在当前活动仍未落定时覆盖显示，终态快照优先于请求标记。连接状态位于对话层，不能替代消息结局。

已确认现有事实不足以可靠推导当前 Run 的等待原因：`awaitingUser` 可以属于历史待决定调用；Team 原提案调用与批准后实际等待 Run 可以不同；`background_tasks` 是 Task 范围，且部分原调用可能在未加载历史。因此首期不做“猜测后回退”，统一将 suspended 主标题写为“等待继续”，已有待决定卡和后台看板分别表达自己的事实。精确“正在等待哪些工作”若后续成为需求，应由 prepare_input 的挂起决策记录原因及关联身份，再由实时/冷重建共用投影，不能在 JSX 扫描补丁。本次不增加这份持久契约。

同一时刻可同时存在等待用户、后台工作和已产生结果。这些维度不能压成一个互斥枚举后丢失信息；主标题表达当前主要状态，其余事实通过紧凑辅助行或操作区保留。

停止来源当前不足以可靠区分用户、父级传播等所有情况，因此采用“已停止”。仅有明确事实时显示具体中断原因，不从前端点击历史、中文错误文本或日志猜测。

### 5.3 停止边界

- Task 停止会撤销本 Task 的后台结果登记，包含更早 Run 的登记；取消活动 Team，并向子 Task 异步传播。不能沿用“后台工作不随 Task 停止”的旧注释。
- 主 Run 停止落定不证明每个下游资源已瞬间停止。子任务、Team、后台条目分别显示其实际状态，必要时保留收尾提示。
- 停止不回滚已写文件、已发送消息或其他副作用。结果区只展示已有结构化事实，不额外承诺“全部修改已保存”或“没有产生副作用”。
- 交互终端属于 Task，Run 停止不等同关闭终端；浏览器标签属于宿主，也不因本轮停止而自动消失。是否仍有命令或资源活动读其现有事实源，不从 Run 结局推断。
- Run 停止不等于所有 HITL 事项撤销。普通待决定占位和交接可在 Run 终态后仍接受决定，并唤醒或开启 Run；Team 提案另受 Task 停止的取消规则约束。UI 必须按调用/Team 各自事实保留或关闭入口，不能用统一“停止后禁止所有按钮”处理。对仍有效的决定说明“提交后 Agent 会继续处理”，不伪装成只读历史。
- 停止后排队消息仍按既有队列规则处理，本方案不改变队列消费、立即发送或撤回语义，也不把它们藏成已完成消息。
- 用时继续采用 `outcome.durationMs` 与 `activity.startedAt` 的口径，包含 Run 生命周期内等待；不称为纯模型执行时间，不新增分段计时。终态耗时为必填非负整数；缺失属于协议缺陷，不补零或编造。

## 6 目标实现结构

### 6.1 所有权

```text
后端持久事实和现有快照
  消息 / 工具状态 / display_data / awaitingUser / background / outcome
                          ↓
前端适配与纯投影
  工具外壳策略 + 结果解释 + 顺序内容块 + 当前状态 + 结果和操作位置
                          ↓
React 呈现
  正文 / 活动摘要 / 现有调用详情 / 操作卡 / 结果 / 状态标题
```

- `tool-catalog.ts`：继续拥有工具名、动词、图标和意图，增加最小默认过程呈现策略。首期只需普通活动与纯控制两种，不预留多套模式。
- `display_data.kind` 的纯数据解释：从已有解析结果得到非零退出、部分失败等展示信号，调用行与组头共享。可拆具体纯函数文件，不新建通用策略引擎。摘要按有信号的调用数统计，细项数留在详情。
- `turn-layout.ts`：拥有顺序块、分组、计数、结果和操作位置；隐藏规则在此收口。投影不依赖 React、不读墙钟、不修改原消息。
- 消息级状态投影：消费现有 outcome、当前 activity 和调用级待决定事实，供状态标题和操作资格使用。它只是展示结果，不持久化第二份运行状态。
- `thread-message-parts.ts`：明确为 UI 投影准备所需字段。后台布尔标记可保留为 UI 信息；不为了凑 Transport 类型创建假的 `BackgroundWork`。渲染和估高消费同一投影输入。
- Task 分桶的命令暂态 store：复用现有 Zustand，独立于可卸载 runtime 和详情组件，统一承载多个表面的停止/决定/转后台反馈。会话只向它提交 canonical 对账；切换 Task 不清空，删除 Task 时清理。它不写入业务 snapshot，不承担执行或重试，不挤入只负责开合的 disclosure store。具体见 6.4。
- 现有 kind 视图：继续渲染专业详情与资源操作。仅在相关语义共享需要时抽出纯解释函数，不重写终端、diff、图片或 Team 内核。
- `AgentInboundMessage`：只负责带来源消息的紧凑预览、全文展开和来源导航；身份仍由现有 Thread 的 source 分流决定。它不拥有消息接收、后台结算、回复路由或任务状态，不为视觉统一把这些不同事实合成一种消息。

### 6.2 最小后端变更

网页提取展示数据固定带结构化 `partial: boolean`，从现有结果事实构造。前端从它生成“部分成功”，删除该结果对中文 `status_hint` 的判断和重复文案来源；不添加通用 `ui_card`、`ui_visibility` 或 severity 配置。

同步结果构造、消费视图、结果摘要、测试与展示契约。绿地项目不保留解析旧中文提示的兼容分支；已有本地数据如需重建或清理，在实施时明确处理受影响范围，不顺手清空无关数据。

本方案不改变 Run 状态机、工具五态、取消传播、恢复入口、模型协议、数据库表或消息身份。无需为工具隐藏增加后端 kind。

### 6.3 布局与动作复用

所有正文使用稳定的顶层 part 容器；完成后的末段阅读布局只改变现有槽位的可见性与样式，不更换正文父容器。过程开关控制原槽位，不把旧正文重新搬进一个新 Collapsible。运行中不整体卸载正文；用户主动折叠的重型工具详情可继续按需卸载，开合由 store 保存。操作区独立于过程折叠，结果区在正常结束后置于答复下方；运行、挂起、中止时仍可见。

正常结束复制可见回复末段（无末段则全部正文）；停止、失败或无 outcome 时改为“复制已生成内容”，复制面向用户的正文，不把 reasoning、工具 JSON 和重复结果卡拼进去。Fork 保持已有消息寻址与资格判断；用量和诊断可进入更多菜单，保留可访问性和诊断信息。

只读对话复用同一投影和呈现，不生成第二套消息 UI。Agent 来源消息采用 4.4 的轻量行；读取、复制与来源导航保持可用，不出现编辑或恢复操作。两张配置草稿卡必须消费现有 interactive，不因 Workbench context 存在就展示编辑入口。后台看板与原调用共享详情实现，但分别读取自身约定的事实，不把结果交付终态当作任务成功。

### 6.4 多入口请求状态的统一归属

新增一个具体的 `lib/assistant/command-request-store.ts`（建议文件名），不新建通用命令框架。`task-commands` 仍负责 HTTP，TaskTransportSession 仍负责订阅；在命令发出边界原子登记暂态，在现有 canonical 提交边界对账。React hook 只订阅目标状态，不再各自存 busy。

记录键为 Task + 目标类型/ID + 操作；同一调用上的互斥操作共享禁重资格，例如正在转后台时不再并发提交取消。Task 停止记录开始时看到的 Run ID 只用于 UI 归属，不放进现有只按 Task 寻址的 HTTP 请求。它不是后端取消范围的保证；后端实际行为与最后快照始终优先。

| 操作及所有入口 | 暂态结束依据 | 特别约束 |
|---|---|---|
| Task 停止：Composer、runtime cancel | 原目标 Run 终态/不再是当前活动，或明确请求被拒 | 新 Run 不继承旧“停止中”；HTTP 202 不能直接清为“已停止” |
| 单调用停止：终端、子 Task、Team、后台行 | 对应调用/后台登记/领域执行状态已落定 | 组件卸载及 HTTP 返回均不清空；settling 与取消完成分开 |
| 转后台：foreground wait action | 当前 foreground_wait 消失并由 canonical 后台/终态事实承接，或明确请求被拒 | 前台与后台按钮不能同时可提交；不以“请求成功”冒充后台作业成功 |
| 批准/驳回：Team、其他决定卡 | 对应 awaitingUser、TeamRun/决定结果变化；200 表示服务已处理请求但视觉仍与快照对齐 | HTTP 先到、SSE 先到都不能重复提交；审批表单草稿仍留在各领域表单，store 不接管配置编辑 |
| 交还：等待卡、终端/浏览器 banner、关闭浏览器标签 | 对应决定/交接事实落定 | 三处共享状态；无 React hook 的关闭入口也走相同命令边界 |

- 暂态只需表达“请求中/等待状态同步”和失败反馈，不复制工具状态机；按请求 token 隔离迟到的回调，已被快照清理的请求不得被 HTTP 回调复活。
- HTTP 明确拒绝解除禁重并展示可读原因；网络中断但是否受理不明时通过既有重连/同步核对，不自动重放决定或副作用命令，不直接宣布执行失败。
- 对账读取 canonical 原始状态及已有领域状态，不读已转换的展示字符串。不把分页未加载的调用当作已消失；范围不完整时保留待同步状态，返回该任务后依现有订阅更新。
- 普通切换任务、收起详情、虚拟卸载和渲染恢复不丢请求状态；Task 删除统一清除请求、disclosure 和行高缓存。不增加每个请求的轮询或额外 SSE 连接。
- 删除各入口被替代的局部 stopping/busy 路径；请求开始、拒绝和落定使用既有 frontendLog、traceId，日志不成为事实源。

### 6.5 文件结果的准确表达

当前聚合将删除优先级称为“最终状态”，同时累加多次调用的行数，但展开只展示最后一次 diff。删除后重新创建、同一文件反复修改时，标题、统计与详情可以互相矛盾。这属于同一个“压缩结果却丢失语义”的问题，本次在呈现层修正。

采用“文件操作 · 涉及 N 个路径 · M 次调用”的摘要。按路径索引已有操作，展开保留每次操作和对应原始 diff；同一路径多次修改不相加后冒充净增删，不再以删除/移动等级推算最终状态。多个操作时显示“多次操作”，单次操作可显示其真实新增/修改/删除/移动及行数。移动保持原记录中的源路径 → 目标路径，不新造跨调用重命名追踪算法。

范围按这条 canonical 助手消息，不叫“本轮最终改动”：一个 Run 可以有多条助手消息，历史也可以只加载一部分。终端命令、MCP 或失败的 apply_patch 可能产生未投影的文件副作用，界面只承诺“已有记录”，不承诺完整工作区 diff。需要工作区实际状态时查看文件或通过现有终端工具核验；本次不新增工作区 diff 功能、扫描器或后端文件事务。

文件与单次操作的开合也使用已有 disclosure store，键绑定消息/调用/路径，替换 ChangesCard 的本地 openPaths。调用详情和结果区可复用同一 diff 内核，但默认只在结果区展开一次长内容，调用行保留定位入口。

## 7 样式和滚动约束

| 元素 | 初始规格 |
|---|---|
| 用户消息 | 浅色主题近黑底白字，圆角约 20–24px；深色主题独立校验对比度；附件保留原入口 |
| 助手正文 | 15–16px，行高约 26–28px；叙述和答复同字号，段落留白优先于容器底色 |
| 活动摘要 | 13–14px、中性灰、小图标与明确分隔符；可展开入口支持键盘与焦点态 |
| Agent 来信 | 与活动摘要同级的无气泡行；来源与预览清楚分隔，窄屏最多两行；展开正文恢复正常阅读字号 |
| 状态标题 | 普通完成、等待、中止用中性色；运行失败局部错误色；审批与交接沿用轻量强调 |
| 对话宽度 | 首期保持统一 48rem；消息、输入框、新对话页共用宽度 |
| 分隔与容器 | 状态与内容可用细分隔线；普通活动不增加外框；操作卡、结果与专业详情保留适当底面 |
| 动效 | 短促折叠动画，遵守减少动态效果设置；停止后结束活动动画，避免用强闪烁表达等待 |

以上尺寸是视觉验证起点，不从截图像素直接推断 CSS 尺寸。

- 保留现有顶部锚点与虚拟列表，不重新开启每 token 自动滚到底部。
- 折叠覆盖继续存于 Task 分桶的 disclosure store；活动组加入稳定键，虚拟卸载不重置用户选择。
- 字号、间距、摘要和结果区顺序改变后同步 `message-height-estimate.ts`，渲染与估高消费同一投影和 disclosure 默认值。在 canonical 消息内容/渲染上下文或 disclosure 变化时按 message ID 失效实测缓存；宽度变化继续沿用现有整桶失效。仅失效受影响消息，不因每个 token 清空全部历史高度；避免离屏晚到结果仍用旧高度。挂载行继续由现有 ResizeObserver/TanStack 实测，不复制测量系统。
- 共享 Markdown 的对话样式限定在对话作用域，避免影响文件和配置预览。用户气泡内的链接、代码、附件胶囊须单独验证对比度。
- 长回合完成收起、展开旧记录、历史前插、切换任务、面板改变宽度时保持阅读锚点。新调用追加不能重挂整段正文或丢失选择。

## 9 实施阶段与验收

### 阶段一 明确纯投影与结果契约

落实工具默认策略、UI 输入、结果信号解释、稳定顺序分组、文件操作记录和状态投影；补齐网页 partial。恢复原定路径展示契约，更新工具/kind 表，先让现有缺失文档的守卫通过。使用固定数据验证等待、取消、异常与结果，不接入新的样式分支作为长期旁路。

完成条件：纯函数测试能说明每个事实为什么显示在当前位置；调用行与摘要的状态、计数和异常提示一致；无须解析正文或中文提示判断状态。

### 阶段二 接入回合 UI 与命令状态

替换过程呈现，接入状态标题和中性停止样式，调整气泡、排版与 Agent 来信；接入按 Task 分桶的请求 store，覆盖工具行、看板、交接和 Team 决定。同步删除被替代分支，保持单一生产路径。普通来信保持现有消息投影，后台结果和系统通知不新增对话记录。

完成条件：运行、等待、正常完成、中止、失败五类界面可审阅；原有审批、交还、停止、转后台、打开资源、复制与 Fork 仍按权限和资格工作。

### 阶段三 验证共享表面和滚动

同步估高、折叠存储和只读消费方，校准长对话、长回合、主题与窗口尺寸。修正只读草稿入口，接上 Task 删除清理。更新相关设计文档、AGENTS.md 中已变化的边界描述及注释；字段/布局细则仍放专门契约与本文，不继续堆入 AGENTS。

### 必须覆盖的用例

| 类别 | 验收用例 |
|---|---|
| 纯控制 | 连续多次 wait 成功不刷屏、不增工作计数；wait 失败仍可诊断；仅 wait 的消息不留空过程框 |
| 分组 | 正文→工具→正文、单调用、多调用、交替 reasoning；追加工具不移动正文、不丢开合 |
| 结果语义 | 命令非零退出、图片部分失败、浏览器失败及 skipped 步骤、网页 partial、MCP 单服务错误；未知 kind 保留通用行 |
| 完成布局 | 空末段正文、连续模型正文、只有工具、只有 wait、结构化输出、同 Run 多条回复；不伪造最终结论或隐藏全部正文 |
| 文件记录 | 同路径多次修改、删除后重建、移动后修改；每次 diff 可追溯，统计不冒充净差异；部分落盘无展示数据时不宣称无改动 |
| 用户操作 | 等审批、等交接、后台与审批并存；收起过程后必要入口仍可见，决定只提交一次；普通 HITL 与交接在 Run 停止后仍可有效，Team 另按自身状态收敛 |
| 整轮停止 | 未产生正文、正文中途、工具执行中、后台等待中、审批中停止；保留已有正文和真实结果 |
| 竞争与失败 | 停止请求失败、重复点击、停止与完成竞争、断连后重连；最终状态以快照为准 |
| 局部取消 | 取消单工具后 Agent 继续；Task 停止后的多调用取消不刷出一排红卡 |
| 下游与资源 | Team、子任务、后台结果迟到和收尾；交互终端及浏览器资源不被错误标为已关闭 |
| 恢复 | cancelled/failed 恢复同一 Run，旧结局清除；重启中断明确，刷新不伪造消息时间 |

### 请求暂态的实现细化

- **HTTP 收尾不能依赖过期观察，连接生命周期问题，高置信度。** `finishCommand` 复用有效的紧凑命令事实，覆盖 HTTP 返回后没有新 SSE 的收敛；不保留完整消息或终端输出。复核发现离开 Task 后旧 completed 快照会误清新停止，已补事实有效期：当前连接收到 full 才可登记，主动替换、关闭、EOF、异常、resync 都失效。`TaskTransportSession.hasCanonicalState` 与 `onCanonicalStateInvalidated` 归连接句柄所有；重连等待 full 期间迟到历史页仅可更新展示，不能恢复命令结算资格。旧观察者/旧流收尾不能失效新连接事实。待确认请求仍跨界面保留，Task 删除才统一清理。

同类入口处理范围：全局 Task status stream、TeamRun 状态观察与工具停止按钮仍保留，它们负责未挂载对话的领域状态收敛，不属于重复 canonical 提交；手动 HTTP 读取不能无序导入活 FrameStore，因为协议没有 snapshot revision，界面刷新继续走既有 attach full。未改变后端数据或新增业务事实源。

性能取舍：正文帧不读取未变历史 parts，工具索引引用稳定，命令事实复用；仍需遍历当前消息 parts、当前后台条目和待确认请求。工具载荷变化时会复制工具 Map 并生成紧凑命令事实，full/分页仍重建窗口成员；本轮不引入复杂持久化 Map 或另一个全局索引框架，也不宣称所有工具输出流都已实现恒定复杂度。
