# 第二阶段迭代路线图

本文档在 `docs/第二阶段建设优先级.md` 的基础上，进一步把第二阶段拆成可执行的阶段路线，并明确指出：当前项目里哪些能力已经存在，但还不成熟，不符合生产级标准。

本文档面向中国个人开发者的本地桌面 coding-agent 场景，默认重点是：

- 单机本地一体化可用
- 真实开发任务可闭环
- 可恢复、可审批、可诊断
- 可持续扩展到 MCP、subagent、context compaction

## 当前项目状态判断

当前项目已经跨过“纯概念设计”阶段，也跨过了“只能本地 echo”的阶段，但还没有跨过“原型期”。

更准确地说，当前项目处于：

```text
真实模型已接通
+ 基础 runtime 已建立
+ 聊天主链路可跑
- 工程执行能力不足
- 客户端产品面不完整
- 恢复/审批/扩展能力未闭环
```

因此，第二阶段不应再围绕“再多接一个模型”展开，而应围绕“把现有骨架补成可长期使用的本地 coding-agent 基线”展开。

## 已有但不成熟的能力盘点

下面这些能力不是“完全没有”，而是“已经有雏形，但离生产标准还有明显距离”。

### 1. 后端健康检查已存在，但后端托管未完成

当前已有：

- 后端 `/health` 接口
- 前端 `useBackend` 健康检查 Hook
- 本地脚本可并行启动前后端

当前不足：

- 桌面端不能真正托管 Python 后端进程
- 不能自动拉起、停止、重启、守护后端
- 不能处理端口冲突、依赖缺失、异常退出等完整生命周期
- 当前仍接近“用户手动照顾后端”

为什么不达生产标准：

- 本地桌面应用不能要求用户先手动启动服务
- 后端状态不是运行时真实托管状态，只是 HTTP 可达性

### 2. 工具系统边界已存在，但真实工具能力太弱

当前已有：

- Tool Registry
- Tool Scheduler
- 工具 schema
- 模型可见工具定义
- 工具调用事件流

当前不足：

- 当前实用工具几乎只有 `safe_read`
- 没有成熟的写文件、改文件、搜索、执行命令、git、目录操作能力
- 工具链还不足以支撑真实开发任务

为什么不达生产标准：

- coding-agent 不能只有“读代码 + 回答”
- 没有最小工具集，就没有真实工程执行能力

### 3. 权限审批边界已存在，但审批闭环未完成

当前已有：

- approval policy
- `tool_approval_required` 事件
- 前端 ToolCallCard 中的审批请求展示

当前不足：

- 用户不能真正点击批准或拒绝
- 后端不能等待审批后继续执行
- 没有审批状态恢复、审批历史、拒绝分支闭环

为什么不达生产标准：

- 危险工具能力不能只有“提示需要审批”，必须能真实审批
- 没有审批闭环，很多写能力无法安全上线

### 4. Checkpoint 已记录，但恢复能力未闭环

当前已有：

- checkpoint 持久化
- checkpoint 事件
- 任务状态与步骤状态持久化

当前不足：

- 客户端几乎没有真实 checkpoint 视图
- 不能从 checkpoint 恢复任务
- 不能显式选择 checkpoint 继续执行
- 文件级回滚完全未落地

为什么不达生产标准：

- checkpoint 的价值在于恢复，不在于“数据库里有记录”
- 任务中断后不能真正回到可用状态

### 5. Context 预算保护已存在，但 compaction 还没有

当前已有：

- context budget guard
- 超限保护

当前不足：

- 没有上下文压缩策略
- 没有保留关键信息的压缩摘要
- 没有压缩记录回看
- 没有压缩后继续执行的闭环验证

为什么不达生产标准：

- 长任务一旦靠近上下文上限，只能失败或硬截断
- 没有 compaction，真实开发链路无法长期持续

### 6. ReAct-like Workflow 已可跑，但 Workflow 体系还不成熟

当前已有：

- 默认 ReAct-like Workflow
- 基础 step continuation 控制
- 串行 tool call
- 模型输出和工具观察回注

当前不足：

- 只有单一主 workflow 真实可用
- review / test / fix / plan-and-execute 都还没有可运行实现
- continue / retry / recover / delegate 虽有架构定位，但未形成完整策略集

为什么不达生产标准：

- 成熟 coding-agent 不是“只有一个模型循环”
- 缺少工作流层的任务闭环能力

### 7. LangGraph 已接入，但使用深度仍偏浅

当前已有：

- step controller 的 LangGraph 窄接入

当前不足：

- 还没有承载完整 workflow graph
- 没有承载 checkpoint、interrupt、subgraph、resume 这些核心能力
- 当前只是 graph-backed insertion point

为什么不达生产标准：

- 现阶段更像“预留未来能力”，还不是“真正依托 LangGraph 的生产级工作流运行时”

### 8. 模型接入已真实可用，但 provider 层仍偏单薄

当前已有：

- DeepSeek / OpenAI-compatible 流式接入
- 工具 schema 序列化
- 基础 stream parser

当前不足：

- provider fallback 没有
- rate limit / backoff 没有
- usage / token / latency 诊断不足
- thinking / tool behavior / provider 差异适配还比较薄

为什么不达生产标准：

- 单一 provider 成功不等于模型层成熟
- 成熟系统必须能处理供应商抖动、限流和失败恢复

### 9. 桌面端主聊天链路已具备，但整体产品面仍大量占位

当前已有：

- 输入框
- 聊天区
- SSE 增量展示
- 状态标签

当前不足：

- 右侧面板大面积 mock
- sidebar 项目/任务/插件/历史很多仍是静态数据
- outputs / sources / checkpoint / MCP / subagent 区块未真实接数据
- 模型与权限状态展示仍偏占位

为什么不达生产标准：

- 成熟 coding-agent 不只是能聊天，还要能让用户理解任务状态、来源、工具、恢复点和变更面

### 10. MCP 有明确目标，但当前还处于未接通状态

当前已有：

- 架构定位
- 目录和文档边界

当前不足：

- 没有真实 server 注册/启停
- 没有 tools/resources 发现
- 没有 schema、权限、超时、错误隔离闭环

为什么不达生产标准：

- 对项目愿景来说，MCP 还是规划项，不是运行能力

### 11. Subagent 有概念边界，但执行层尚未落地

当前已有：

- 概念边界已经在 AGENTS 和设计文档中明确
- 明确要求复用 Agent / Workflow / Runtime

当前不足：

- 没有 child run / child task 真实执行实现
- 没有主子 Agent 汇总协议
- 没有取消、失败恢复、状态展示闭环

为什么不达生产标准：

- 复杂任务仍然只能堆在单 Agent 上

## 第二阶段里程碑拆分

第二阶段建议拆成四个里程碑，每个里程碑都必须形成可验证增量，而不是只堆代码。

## 里程碑 M1：本地一体化运行

目标：

- 桌面应用真正托管本地 Python 后端
- 用户启动桌面应用即可进入可用状态
- 后端状态、错误和日志可见

范围：

- Tauri 进程托管后端
- 后端启动、探活、停止、重启
- 启动失败错误面
- 客户端真实后端状态管理
- 本地 env / secret 读取路径固化

本里程碑要解决的“已有但不成熟项”：

- 后端 health check 有了，但进程托管没完成
- 本地运行依赖脚本，不是应用能力

验收标准：

- 不打开终端也能启动系统
- 后端崩溃后前端能提示
- 用户能从客户端定位日志

## 里程碑 M2：最小工程执行能力

目标：

- Agent 能完成小型真实开发任务
- 不是只读，不是只回答

范围：

- 写文件
- 编辑文件
- 搜索
- 目录操作
- 命令执行
- git 只读与部分写能力
- 工具权限等级定义
- 工具日志与错误归因

本里程碑要解决的“已有但不成熟项”：

- 工具系统边界存在，但可用工具太少

验收标准：

- 可完成若干小项目验收案例
- 工具失败可定位
- 工具不会绕过调度器

## 里程碑 M3：审批与恢复闭环

目标：

- 危险能力能安全上线
- 任务失败或中断后能恢复

范围：

- 审批请求 UI
- 批准 / 拒绝动作
- 审批结果回传
- runtime 等待审批并恢复
- checkpoint 列表展示
- checkpoint 恢复
- 重启后未完成任务恢复

本里程碑要解决的“已有但不成熟项”：

- 审批只发事件，不可操作
- checkpoint 只记录，不可恢复

验收标准：

- 写操作必须经过审批
- 用户拒绝后任务有清晰分支
- 应用重启后可恢复到最近 checkpoint

## 里程碑 M4：长任务与扩展基线

目标：

- 系统具备持续执行长任务和扩展能力的基线

范围：

- context compaction
- subagent 基线
- MCP 基线接入
- 右侧面板和状态面去 mock
- 输出、来源、checkpoint、MCP、subagent 数据接通

本里程碑要解决的“已有但不成熟项”：

- context 只有预算保护，没有压缩
- subagent 只有概念边界，没有执行能力
- MCP 只有规划，没有运行
- 前端很多区域只有静态占位

验收标准：

- 长任务可压缩后继续运行
- 主 Agent 可调用 reviewer / tester 子任务
- 至少接通一个真实 MCP server
- 右侧面板展示真实运行数据

## 建议实施顺序

推荐按下面顺序推进：

1. M1 本地一体化运行
2. M2 最小工程执行能力
3. M3 审批与恢复闭环
4. M4 长任务与扩展基线

原因很简单：

- 没有 M1，系统不算真正桌面应用
- 没有 M2，系统不能完成开发任务
- 没有 M3，危险能力不可安全上线
- 没有 M4，系统无法持续跑长任务，也无法进入成熟 coding-agent 形态

## 不建议提前推进的事项

以下事项不建议抢在 M1-M4 之前：

- 大规模 UI 美化
- 复杂插件市场
- 多模型智能路由
- 远程云端架构
- 高级多模态工作流
- 复杂 DAG 可视化编辑器
- 组织级权限体系

这些事项不是当前阶段的第一矛盾。

## 第二阶段完成后的目标形态

第二阶段完成后，项目应达到：

- 对用户来说，它是一个真正可启动、可使用的本地桌面应用
- 对 Agent 来说，它具备最小工程执行能力，而不只是回答能力
- 对风险控制来说，它有审批、恢复、日志和状态边界
- 对长任务来说，它有 compaction、checkpoint 和子任务分担能力
- 对后续扩展来说，它具备 MCP、subagent、workflow 扩展基线

## 结论

第二阶段最重要的不是“新增多少能力名词”，而是把已经出现雏形但还不成熟的能力真正补成闭环。

当前项目最典型的状态是：

- 有模型，但模型层还不够稳
- 有工具边界，但工具还不够能干活
- 有审批事件，但审批还不能完成动作
- 有 checkpoint，但 checkpoint 还不能救场
- 有 UI 骨架，但 UI 还没承载足够多运行事实

这正是第二阶段最应该解决的问题。
