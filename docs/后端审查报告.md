审查报告
一、逻辑漏洞
漏洞 1【中】_fail_delegation 不传 child_task_id，与 _finalize_result 契约分裂

delegation_executor.py:466-470 mark_failed(delegation_id, error, runtime_event_loop=...) 未传 child_task_id，而 _finalize_result 失败分支 :552-557 传了 child_task_id。
在 execute 中，create_child_task（L158-166）成功但 create_turn/run_child 抛异常时，child_task 已存在，却无法把 child_task_id 落到 delegation 记录 → 前端无法跳转、取消级联（delegation 表驱动递归）找不到 child_task。
建议：execute 引入 known_child_task_id，create_child_task 成功后赋值；所有失败路径统一传入 _fail_delegation。
漏洞 2【中】外层 except Exception 无条件 _fail_delegation，可能覆盖已终态

delegation_executor.py:275-293 + delegation_crud.py:126-172（update_status 无状态守卫，get 后无条件 update）。
若 run_child 内部已把 delegation 推进到 completed/cancelled 后仍抛异常（终态化后清理/日志/事件阶段异常），外层 except 会再 mark_failed 把终态倒退覆盖为 failed。并发语义下存在竞态覆写。
建议：update_status 加 expected_statuses CAS 条件更新（对齐 turn_crud.cancel_if_active）；或 _fail_delegation 前先读状态，仅 active 时推进为 failed。
漏洞 3【低】tool_cancelled 分支 error 前缀重复

delegation_executor.py:548 error=f"delegate_task child cancelled: {error}" 会写入 content 与 error，与 _child_error 风格不一致，文本冗长。

重复 1【中】child_task_id 传播散落：正常终态路径传、失败路径不传，行为分裂（即漏洞 1，建议用 known_child_task_id 单点收口）。

重复 2【低】error = result.error or "<fallback>" 模式出现 3 次（L512/531/551），Rule of Three 边界，可留可抽。

三、逻辑冗余

delegation_executor.py:560-590，三处调用（L247/293/558）全传 "failed"；docstring 已声明只服务失败分支。status 是死参数。
建议：移除 status 形参，文案硬编码或提取常量 _CHILD_FAILED_STATUS = "failed"。
冗余 2【中】_fail_delegation 的 if not delegation_id: return 死分支

delegation_executor.py:463-464。该方法仅在 acquire 成功且 delegation_id 已赋值（L155）后调用；acquire 失败走 L152-153 提前 return。docstring 中「acquire 失败直接跳过」是对时序的误读。

delegation_executor.py:88（函数体内）vs :19（顶部 get_delegation_service, get_turn_service）。get_task_service 无循环导入风险。
