### 1. subagent 委派深度判定写反，`delegate_task` 永远被拒绝 ✅已验证
- **复核状态（2026-08-17）：✅ 已修复** — `delegation_executor.py:132` 的 depth 来源改为 `depth=1 if self._parent_task.is_child else 0`（取自 `TaskRecord.is_child` 持久化事实而非 profile 运行时字段）；主 Agent 顶层 task `is_child=False` → depth=0，`0 >= max_depth(1)` 不成立，委派不再确定性失败。配套测试：`test_delegation_executor.py:1063`（主 Agent 正向委派成功）、`:996`（子 task 递归委派被 `delegation_depth_exceeded` 拒绝）。
- [delegation_executor.py:132](file:///h:/coding-agent/apps/backend/app/core/delegation/delegation_executor.py#L132) 主 Agent 发起委派时 `depth=0`（子 task 为 1）；[delegation_policy.py:34](file:///h:/coding-agent/apps/backend/app/service/delegation/delegation_policy.py#L34) 判定 `depth >= max_depth` 即拒绝；而 [delegation_context.py:37](file:///h:/coding-agent/apps/backend/app/service/delegation/delegation_context.py#L37) `max_depth` 默认 1。
- 结论：主 Agent（`main_agent=True`）→ `1 >= 1` → **每次委派确定性失败**。subagent 能力整体不可用，单测只测了 policy 本身、从未覆盖 executor 主路径，缺陷漏网。
- 修复：`depth` 语义改为「已发生层数」（主 Agent 取 0），或判定改 `depth + 1 > max_depth`；补主 Agent → delegate_task 端到端测试。

## 四、低（P3）—— 规律性归纳

- **失效 docstring 系统性残留**（签名演进未同步）：core 5 处、service 4 处（含 docstring 与实现自相矛盾，如 `turn_workspace_resolver` 同段写「返回 None」和「抛 KeyError」）。四段式规范反而放大了这类漂移的伤害。
- **只增不减的集合泄漏**：`_trace_by_run` 反查表、`_cancelled_turn_ids`、`_closed`、`_producer_turn_ids`——进程级单例内的慢性泄漏，建议统一在终态收口清理。
- **死代码/复制残留**：空死文件 `turn_prepare_service.py`、`workspace_index_service.py`；`system_prompt_context.py` 整类无消费方；codegraph 四处 `workspace_payload` 复制残留的线程名/目录名（排查时指向错误模块）；系统提示词错别字 "emjio" 原文进模型。
- **恒真/恒假死逻辑**：`isinstance(RuntimeMessage, SystemMessage)` 恒 False（防重复守卫失效）；`can_delegated` 的 `description is not None` 恒 True；`getattr(operations, "_current_turn_id")` 属性名写错导致日志 turn_id 恒 None。
- **token_estimator 中文系数取 3 字符/token，与自述「1 字符≈1~1.5 token」矛盾**，纯中文低估 66-75%——直接影响 context compaction 决策的输入。
- **日志规范偏离**：多处 `%s` 拼接式 logging、中文长句作 event 字段、`exc_info=True` 代替 `.exception()`；API 中间件把非 GET body 全量写日志无大小预算。
- **规范类**：`api/schemas/` 20 个文件 PascalCase（D12 遗留）；AGENTS.md 与代码漂移（入口实为 `app.py` 非 `main.py`、`api/depends/dependencies.py` 实为 `api/dependencies.py`、未收录 `changes_api.py`/`hook/`/`codegraph/`）。

## 五、测试盲区（结构性风险）

1. **hook / codegraph / redaction / token_estimator 零直接测试**——本次发现的「关停复活」「query 畸形」「脱敏绕过」全是单测能拦的类别。
2. **测试策略重单元轻链路**：三个最高价值能力（subagent S1、审批悬空 H3、compaction 未接线）都是「单测通过但端到端不可用」。缺「主 Agent → delegate_task 成功」「审批拒绝后下一轮模型请求合法」这类链路测试。
3. WorkspaceEventBus 的跨线程发布与二次订阅两个场景是测试盲区。

## 六、值得肯定的设计

- **分层与契约纪律**：`ToolDefinition` 单一事实来源 + `execution_mode` 分级隔离、Protocol 依赖倒置（`ToolTraceRecorder`）、`importlib` 触发路由注册避坑（注释把坑讲透）。
- **并发意识高于平均**：CAS 条件更新（`claim_pending`/`complete_if_running`）、`BEGIN IMMEDIATE` 原子额度、事件 sequence 锁+重试、`inflight_registry` 的 singleflight 近乎教科书。
- **安全基本面扎实**：CRUD 全参数化 + LIKE 转义（无 SQL 注入面）；路径三道闸（设备名→边界 resolve→reparse point）；delete 双重 resolve 防 TOCTOU；bootstate 的 mkstemp+fsync+os.replace+脱敏是全仓工程质量最高的文件。
- **docstring 四段式覆盖率与注释密度**（意图说明、设计权衡记录）在同类项目中是标杆水平。

## 七、总体评价与修复优先级

**总评：架构设计水准明显高于平均（各模块 B ~ B+），但存在「写了没跑通」的关键断点和系统性脱敏缺口，与项目「第一版按生产级深度验收」的自我要求有落差。**

核心问题四条主线：
1. **端到端断点**：subagent 深度写反（#1）、审批/compaction 未接线（#10）——最高价值能力实际不可用；
2. **数据正确性**：file_snapshot seq 跨 turn 冲突（#2）——撤销会还原到错误状态；
3. **脱敏防线缺口**（#4 族）——安全问题，非体验问题；
4. **asyncio 线程/生命周期语义复制走样**（#6/#7/#20 族）——正确范式在库中已存在但未强制收口。

**建议修复顺序**：#1（一行修复+补链路测试）→ #2（数据正确性）→ #4 族（脱敏）→ #6/#7（事件总线）→ #5/#8/#9（终态一致性）→ #12（fsync 一行）→ #10（审批接线前必须先修悬空 tool_calls）→ 其余按迭代消化。每个修复绑定回归测试提交，避免「修复无回归证明」。
