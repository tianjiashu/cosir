# code-simplification：执行一轮精简

## 定位

- **规则的唯一事实源**是随本 skill 发布的 [references/simplification-standard.md](references/simplification-standard.md)（下称「标准」），它与本 skill 一起演进。本 skill 只编排流程：每一步读标准的哪一节、用什么工具、在哪里停下等人。
- 本 skill **不复制**标准条款，只引用编号（如 §5.3、F1、G2）。两者不一致时以标准为准，并把不一致写进报告的「标准修订建议」。
- 本 skill 不绑定任何项目、语言或工具链。项目相关的信息（工具链命令、状态存放位置）在运行时从目标项目中发现，并记录在项目自己的状态目录 `.simplification/` 里。
- 首轮通读一遍标准；之后各阶段按需读它引用的章节。
- **不夹带修复**：发现的缺陷只记录（标准 §1）。人类要求当场修复时，修复走项目自己的修复流程、单独提交与说明，不写进精简报告，也不计入本轮评级。

## 目标项目状态

每个目标项目在**仓库根目录的 `.simplification/`** 下保存自己的精简状态，不放在 skill 里。该目录须纳入版本控制：下一轮靠报告里的种子与扩散范围接着往下走。

| 文件 | 内容 |
|---|---|
| `.simplification/project-profile.md` | 项目画像（标准 §0）与构建、静态检查、测试命令，首轮创建，之后修订 |
| `.simplification/reports/YYYY-MM-DD.md` | 每轮执行报告（标准 §9）；同日多轮加后缀 `-2`、`-3` |
| `.simplification/plans/YYYY-MM-DD.md` | 可选：关卡一的计划，候选多、需要人类离线审阅时写 |
| `.simplification/scripts/` | 全部检测器与指标采集器：索引 `README.md`、总入口 `run-all`、各脚本，跨轮复用、按需演进（见下方「检测脚本」） |

## 检测脚本

检测器与指标采集器集中在 `.simplification/scripts/`，只经总入口 `run-all` 运行（`--json` 机读输出，`--metrics` 只跑采集器）；分档、指标三层、约定与演进见 [references/detection-scripts.md](references/detection-scripts.md)。下文 `<run-all>` 指项目的总入口命令。脚本只给线索：没报不等于没有问题（业务规则的语义重复只能按标准 §4.2 人工枚举），报了也要结合上下文确认。项目 CI 已由 lint 拦截的 L1 类问题，不在精简轮重复处理。

## 运行前提

- **运行环境**：git 仓库；随附脚本需要 Node.js 18 以上，没有 Node 时，按脚本注释说明的逻辑手工完成同样的统计。
- **对比基线**：本轮所有「行为不变」的证明与指标对比，都相对一个开始时冻结的基线进行。基线可以是干净的 HEAD，也可以是带未提交改动的工作区快照（见下方「执行方式」）。
- **基线测试通过**：在基线状态上先跑一遍测试与静态检查。基线就失败的，停下报告，因为安全网不成立，无法证明等价。
- **目标环境能力**：能派独立子 Agent 时，按「独立复核」一节使用；不能时走该节的退路。

### 执行方式

开始前请人类三选一；人类已在指令中说明的，直接采用。

| 方式 | 适用 | 对比基线 | 提交落在 |
|---|---|---|---|
| **当前分支** | 工作区干净，想把精简直接接在当前开发之后 | 当前 HEAD | 当前分支 |
| **新建分支**（推荐） | 工作区干净，想整体审查、必要时整体丢弃 | 当前 HEAD | 从 HEAD 切出的 `simplify/YYYY-MM-DD` |
| **冻结快照** | 工作区有未提交改动，不想先清理 | 工作区快照 | 当前分支；人类要求时也可新建分支 |
| **不提交** | 人类要求精简过程中不提交 | 当前 HEAD 或工作区快照 | 不提交；报告按变换分节，每节写变换编号、涉及文件与等价论证，代替逐变换提交 |

**冻结快照**的做法：

```bash
snapshot=$(git stash create)   # 只生成快照提交，不改动工作区、暂存区和 stash 列表
git update-ref refs/simplification/YYYY-MM-DD-base "$snapshot"   # 固定引用，避免被垃圾回收
```

- `git stash create` 不包含未跟踪文件；未跟踪文件参与构建或测试时，在报告中注明。
- 有未提交改动的文件（`scope.mjs` 输出的 `dirtyFiles`），本轮**只读不改**，不进入任何提交，避免把人类的改动混进精简提交。
- 本轮期间人类不应再改动工作区；如有改动，基线即失效，停下重新冻结。

前三种方式都视为授权在对应分支内**按变换提交**（标准 G3）；不推送、不合入，合入由人类在验收后决定。目标项目对分支命名或提交另有规定时，从其规定。

## 流程

每个阶段结束时，在对话里用一两句话说明进展。两个关卡**必须**停下等人类答复。

### 0. 准备

1. 读标准当前版本，记下版本号。
2. 读 `.simplification/reports/` 下最新一份报告：本轮基准、遗留与待确认项、下一轮候选种子（挑种子的起点之一）、上一轮的修订建议是否已处理。
3. 按「执行方式」确定方式，冻结对比基线，记下当前 HEAD（即「本轮基准」）与对比基线；然后跑基线测试。

### 1. 项目画像与工具链（标准 §0）

- 首轮：按 §0 的 8 个维度建立画像，每个结论注明来源（文档、代码、人类说明）。**不要求先给仓库做全局功能分解**：仓库再大再乱，这一步的全局判断都最容易出错，范围从局部种子推导（阶段 2）。画像里只写能验证的事实；架构文档里已有的分解可以照抄，但不要为了选范围去造一张。
- 同时记录**工具链**，供后续阶段使用：
  - 构建、静态检查（类型检查、lint）、测试的命令；
  - 检测器与采集器：找出项目已有的死代码检测、重复检测、复杂度与依赖统计、相关 linter 规则；首轮按 detection-scripts.md 的配方为它们写包装脚本（产出候选的是检测器，产出 E5–E7 整体数值的是采集器），登记到 `.simplification/scripts/README.md`，并建立总入口 `run-all`；之后各轮核对索引是否仍与项目工具一致；
  - 查找来源依次为：项目的 Agent 指引与贡献文档、构建与包管理配置、CI 配置。找不到的标为「无」，不要临时引入新工具。
- 画像与构建、静态检查、测试命令写入 `.simplification/project-profile.md`，检测器只登记在索引里，不在画像中重复。之后各轮核对是否仍成立，有变化就修订并在报告中标出。
- 有无法从文档或代码确定的维度，**先问人类**，得到答复前不进入下一阶段。

### 2. 种子与基线（标准 §6.2、§7）

**一轮从一个种子出发**：一个文件、一个目录或一处符号。不要求先给仓库做全局分解。

**全仓只读扫描**：`<run-all> --json > <临时目录>/repo-candidates.json` 不传范围（全量，只为挑种子），它不用于本轮执行。

**排序列出候选种子**：

```bash
node <skill目录>/scripts/seeds.mjs --candidates <临时目录>/repo-candidates.json --days 90
```

表按路径前缀粗排，给出每个分组（默认前两段路径）的候选数、文件数、生产行数、候选密度、近期提交数与热点文件。分组只是筛子，不是能力定义：从密度最高的几行里挑一个具体的文件或目录当种子。把表、人类的痛感、上一轮留下的候选种子一并摆出来，给出「本轮种子」与依据；仓库太大时可以缩到 `--depth 3` 再看一层。

**取范围与基线**：

```bash
node <skill目录>/scripts/scope.mjs --seed <种子路径> --json > <临时目录>/scope.json
<run-all> --json --scope <临时目录>/scope.json > <临时目录>/candidates.json
<run-all> --metrics --json --scope <临时目录>/scope.json > <临时目录>/collected.json
node <skill目录>/scripts/metrics.mjs snapshot --scope <临时目录>/scope.json --candidates <临时目录>/candidates.json --collected <临时目录>/collected.json --out <临时目录>/before.json
```

- 脚本只按路径取种子的文件；调用方、数据流与同一事实源的别处由你按 §6.2「扩散」补齐（`scope.json` 的 `coChange.pairs` 是同一事实源的线索），补到的路径作为额外的 `--seed` 传进去，不用手改 scope.json。
- 种子在关卡一一并确认；人类换种子时重做本阶段的基线与范围。
- 指标按 detection-scripts.md「指标三层」取值：E1 改动前证据取 `coChange`；E4、E8 由 `metrics.mjs` 按条款数候选（检测器下界）；E5–E7 取项目采集器，没有 E7 采集器时退回缩进近似；其余按标准 §7 人工统计，标注「估算」。
- `metrics.mjs snapshot` 在工作区干净时记录 HEAD，有未提交改动时自动对工作区做快照，因此三种执行方式下的前后对比都只反映本轮改动。
- 临时文件放在会话临时目录，不写进仓库。

### 3. 识别候选（标准 §4、§5.1、§5.2）

1. **读候选**：阶段 2 的 `candidates.json` 就是本轮范围的候选清单，不再重跑（挑种子时的全仓清单不用于本轮执行）。一档结果直接列为候选；二档结果逐项按 §5.2 假死清单、§4.3 四步判定确认。
2. **枚举业务不变量**（标准 §4.2）：在范围内列出「谁能写哪些字段、状态经哪几步流转、这条政策在哪些分支判定、派生值由什么推出」，逐条数表达点，得到 M1 候选。业务代码的收益主要从这里来，检测器给不出这类候选。
3. **补脚本**：发现某项检查以后还会重复、且可以确定性完成，按 [references/detection-scripts.md](references/detection-scripts.md) 写成检测器、登记到索引，再重新运行总入口。
4. **人工判断**：阅读范围内的代码，对照 §4.1–§4.4 独立判断。三档条款完全依赖这一步；一档、二档条款也要留意脚本漏报的地方。不要因为检测器没有输出就跳过阅读。

- 每个候选标注：变换编号、位置、自主等级（§6.3）、假死排除结果、是否需要独立复核（见下文）。无法排除假死的降为 L3。

### 4. 呈报计划 —— 关卡一

先说明**本轮种子与依据**（seeds 表里的一行即可，含扩散后的文件数），再给出三张清单：L1 将直接执行、L2 待确认、L3 只建议。每个 L2 附一句等价论证要点。

L2 按业务链路分组呈现，一条链路一组，人类可以按链路整组通过或整组否掉，不必逐条读。人类换种子也由他定，换后按阶段 2 重做范围与基线。

**停下，等人类确认 L2 清单。** 人类删减或否决的项，记入报告「遗留与待确认」。

### 5. 执行（标准 §6.4）

- 先 L1，后已确认的 L2，按 §6.4 的顺序自底向上执行。
- 每个变换：完成 §5.3 风险自查 → 按 §5.4 验证 → 需要时独立复核 → 单独提交。提交说明写变换编号与等价论证。
- 需要先补特征测试的变换（标准 §5.4：等价性靠推理的 M1、M3、M7、M9、F1–F6）在没有覆盖时，先补测试并单独提交，再做变换；L1 与纯文件移动不补，用类型检查与全量测试证明等价。测试代码不作为精简对象，只在被删行为的断言需要同步删除时改动。
- 执行中发现判断不成立、验证失败或复核存疑：回滚该项，降为 L3 记录，不改换做法强行完成。

### 6. 迭代

重新运行 `run-all`，直到范围内不再出现新的 L1 候选。新出现的 L2 候选不在本轮执行，记入报告留给下一轮。

### 7. 验收与报告 —— 关卡二（标准 §8、§9）

```bash
node <skill目录>/scripts/scope.mjs --seed <同阶段 2 的全部种子> --since <本轮基准> --json > <临时目录>/scope-after.json
<run-all> --json --scope <临时目录>/scope-after.json > <临时目录>/candidates-after.json
<run-all> --metrics --json --scope <临时目录>/scope-after.json > <临时目录>/collected-after.json
node <skill目录>/scripts/metrics.mjs snapshot --scope <临时目录>/scope-after.json --candidates <临时目录>/candidates-after.json --collected <临时目录>/collected-after.json --out <临时目录>/after.json
node <skill目录>/scripts/metrics.mjs compare <临时目录>/before.json <临时目录>/after.json
```

1. 重新跑全部测试与静态检查。
2. 按 §8 逐项自查 G0–G7，按 §7 给出评级。
3. 按 §9 模板写报告，保存到 `.simplification/reports/`，并作为最后一个提交（不提交方式下留在工作区）。「本轮基准」填第 0 阶段记录的 HEAD，「对比基线」填冻结的基线。
4. 在对话中给出结论、评级和报告路径。

**停下，等人类验收。** 是否合入、如何合入由人类决定。下一轮依赖这份报告确定范围，因此报告须随分支一起合入。

### 8. 沉淀

- 检测脚本的误报、漏报和新发现的可脚本化检查，按 [references/detection-scripts.md](references/detection-scripts.md) 的「演进」直接改进脚本。
- 本轮遇到的误判、不可测的指标、标准与项目规范的冲突、本 skill 流程的问题，都写进报告的「标准修订建议」。不自行修改标准或本 skill。

## 独立复核

判断依据：**这个变换的正确性有多少靠推理、而不是靠测试证明。**

| 需要复核 | 不需要复核 |
|---|---|
| 防御类 F1–F6 | L1 变换 |
| 合并类 M1、M3 | 构建与全量测试通过的纯文件移动 |
| M9 冗余执行 | §5.3 相关风险点已全部被测试覆盖的 L2 变换 |
| 涉及并发、资源生命周期、异常传播的变换 | L3 项（不执行） |
| 任何有风险点只靠推理论证、没有补测试的变换 | |

做法：

- **时机**：变换执行并验证之后、提交之前。
- **不锚定**：复核者先只拿到 diff、相关代码与标准 §5.3，独立找反例；之后再给它作者的等价论证，让它指出遗漏。简报模板见 [references/review-brief.md](references/review-brief.md)。
- **按批次**：同一模块的待复核变换打包交给一个复核者，控制成本。
- **结论处理**：「成立」的照常提交；「存疑」或「有反例」的回滚并降为 L3，不与复核者争辩。
- **退路**：环境不能派子 Agent 时，在报告中把这些变换标为「未独立复核」，提请人类在关卡二重点审查。

## 中止条件

遇到以下情况，停止本轮，按已完成的部分出报告并说明原因：

- 基线测试或静态检查本身就失败；
- 人类在关卡一否决全部 L2，且没有 L1 候选；
- 执行中出现无法回滚到干净状态的失败。
