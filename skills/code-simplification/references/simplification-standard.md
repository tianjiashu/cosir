# 代码与架构精简标准

> - **版本**：1.5（2026-11-01），变更记录见附录 B
> - **适用范围**：通用代码开发，不绑定具体项目、语言、框架或工具链
> - **读者**：执行者是开发 Agent，验收者是人类评审方
> - **使用方式**：每完成若干轮功能开发后，Agent 按 §6 执行一轮精简，产出 §9 执行报告交人类验收
> - **术语**：**必须** 表示强制；**应当** 表示默认，偏离须在报告中说明理由；**可以** 表示允许

---

## 0. 前提：项目画像

**所有精简判断都以项目的实际情况为前提。** 同一段代码，在一个项目里是必要的契约或防御，在另一个项目里可能是死代码或过度设计。不了解项目，就无法判断谁是观察者、哪里是信任边界、什么可以删。

Agent **必须**在首轮执行前建立项目画像，之后每轮复用，项目情况变化时更新。事实来源依次为：项目自身的文档与规范、代码与配置、人类说明。无法确定的维度**必须**询问人类，不得猜测。

| 维度 | 要回答的问题 | 影响的判断 |
|---|---|---|
| 产品形态 | 是库、服务、桌面或移动应用、命令行工具，还是脚本？ | 对外契约的范围（§3）：库的公开接口有未知调用方，应用内部代码只有本仓调用方 |
| 运行拓扑 | 单机还是分布式？单用户还是多租户？有哪些进程、服务，它们之间用什么接口？ | 跨进程契约在哪里；并发、一致性、鉴权类防御是否必要 |
| 信任边界 | 不可信的输入从哪里进入：用户、网络、文件、外部系统、持久化数据？ | 哪些校验与防御该保留（§4.3） |
| 生命周期阶段 | 绿地、快速迭代，还是稳定维护？数据、配置、接口是否需要向后兼容？ | 旧路径与兼容分支能否删除（D9）；持久化格式能否破坏性修改 |
| 外部观察者 | 谁在消费它的输出：其他团队、客户端、数据分析、运维监控？ | 哪些接口、字段、日志受保护（§3） |
| 质量要求 | 可靠性、性能、安全、合规有哪些硬要求？ | 哪些失败安全路径、性能特化路径必须保留 |
| 规模与协作 | 代码规模、团队人数、模块归属？ | 合并与抽象的收益是否大于协作成本 |
| 项目规范 | 有哪些架构文档、编码约定、最高原则？结构性改造走什么流程？ | 与本标准冲突时以项目规范为准；L3 项交给该流程 |

画像写在每轮报告开头（§9）；与上一轮相比有变化的维度要标出。

**画像不要求先给仓库做全局分解。** 仓库可能很大很乱，而「系统由哪些能力组成」这类全局判断正是最容易出错、错了还会一路错下去的判断。所以画像只记录能验证的事实（产品形态、拓扑、信任边界、生命周期等），**范围从局部种子推导**（§6.2），不从画像里的分类推导。已经清楚的能力边界可以写进画像供人读，但它不是机读契约，也不是开工前提。

## 1. 目标与约束

**目标**：在逻辑完全相同的前提下，让代码架构更简洁、更高效，从而更容易演进和迭代。

- **简洁**：读者找到真实逻辑的路径更短；概念、层次、事实源、防御层，以及表达同一知识的位置更少。
- **高效**：下一次同类改动更容易做、更难做错；同一逻辑不做冗余执行。

**两条硬约束**，任一不满足，改动都不得合入：

1. **行为不变**：§3 定义的外部可观察行为在改动前后完全一致。
2. **不引入逻辑缺陷**：不只是既有测试通过，还要排除测试覆盖不到的潜在缺陷（§5.3）。

**不属于本标准**：功能开发、缺陷修复、行为调整、风格统一或格式化、测试体积治理（合并测试文件、清理冗余断言、为覆盖率补测试）。测试代码只作安全网，不是精简对象（§5.4）。精简中发现的缺陷只记录、不修复；会改变行为的精简建议（如把吞掉的异常改为显式失败）只提出、不执行。

**衡量**：验收门槛（§8）决定改动能不能合入；评价指标（§7）衡量收益大小。删除的行数属于评价指标，且权重最低。

**语言中立**：文中出现的工具名、关键字均为示例。执行者应当选用目标语言中的等价物；没有等价工具时可以人工统计，并标注为「估算」。

## 2. 原则

| 编号 | 原则 | 说明 |
|---|---|---|
| P1 | 语义保持 | 每一步都必须是可论证等价的变换，能说清「为什么行为不变」 |
| P2 | 先定观察者 | 是否「死」、是否「可合并」取决于谁能观察到它，观察者范围由项目画像（§0）确定；不清楚时按「有观察者」处理 |
| P3 | 按知识判重复 | 以「同一知识、同一变化原因」判定重复，不看文本是否相似 |
| P4 | 小步可回滚 | 一个提交只做一类变换。改动面大小不受限制，大范围改造拆成一串可独立验证的等价变换完成 |
| P5 | 加法减法并重 | 引入新结构时，同步删除被取代的旧路径、旧测试、旧文档 |
| P6 | 位置即语义 | 代码所在目录应表达它属于哪个功能、被谁共用 |
| P7 | 可读优先于短 | 不用更晦涩的写法换取更少的行数；跳转层数增加即为负收益 |
| P8 | 不确定即不动 | 拿不准是否等价时，不做该变换，只记录 |
| P9 | 只守信任边界 | 校验与防御只放在不可信输入进入的边界；内部各层信任上游契约，缺失就让错误暴露，不层层设防 |

## 3. 行为边界

观察者的范围由项目画像（§0）确定。

| 类别 | 内容 | 处理 |
|---|---|---|
| 对外契约 | 公开 API、对外部调用方的签名、协议、序列化格式、错误码、命令行参数、配置项语义 | 受保护；本仓无引用也不得视为死代码 |
| 副作用 | 文件、数据库、网络、消息、进程操作 | 受保护 |
| 可观测性 | 结构化日志事件、监控指标、埋点 | 受保护；不得为精简而删除 |
| 失败安全 | 超时、重试、取消、资源释放、优雅退出、并发保护，前提是它们守的是真实存在的失败 | 受保护；守的失败不可能发生时，按 §4.3 处理 |
| 非功能性质 | 复杂度量级、并发安全性、运行效率 | 不得退化；消除冗余执行（M9）带来的改善是允许的收益 |
| 内部实现 | 私有函数、内部参数、中间抽象、局部结构 | 可以自由变换 |

## 4. 变换目录

### 4.1 删除类：它还有观察者吗？

| 编号 | 对象 | 判定条件 | 处理 |
|---|---|---|---|
| D1 | 死引用 | 未使用的导入、局部变量、依赖包 | 删除 |
| D2 | 死符号 | 函数、类、常量、导出、文件没有任何引用，包括动态引用（§5.2） | 删除 |
| D3 | 死参数 | 函数体不读取；或所有调用方传同一个值、从不覆盖默认值 | 删除参数，把值固定进函数体 |
| D4 | 透传参数 | 参数只是被逐层原样传递，只有最底层使用 | 让最底层直接获取，或收敛为一个上下文对象 |
| D5 | 死返回值 | 所有调用方都不读取返回值 | 改为无返回值；顺带确认调用方是否本应检查结果（若是，按缺陷记录） |
| D6 | 死分支 | 条件恒真或恒假 | 删除 |
| D7 | 死字段 | 字段只写不读，或只读不写 | 删除；只读不写的先确认是不是缺失实现 |
| D8 | 死链路 | 无订阅的事件、不触发的回调、不读取的配置、无消费者的接口、取值恒定的开关 | 生产方与消费方求差集，删除两端残留 |
| D9 | 旧路径 | 新实现已接管，旧实现、兼容分支、旧测试仍在 | 确认无残留调用方、项目画像不要求兼容后，整体删除 |
| D10 | 死文档 | 描述已不存在逻辑的注释、文档、示例 | 删除或修正 |

### 4.2 合并类：它们是同一件事吗？

**先列业务不变量，再判重复。** 文本重复交给工具就能发现（§5.1 二档），业务知识的重复却几乎不表现为文本相似：同一条政策可能一处是 `if/else`、一处是配置表、一处是 SQL 条件。所以进入本节判断前，先在范围内枚举业务不变量，再逐条数表达点：

- 谁能写这份数据的哪些字段，写入口有几个；
- 这个状态由什么触发、经哪几步流转，同一转换规则写在哪几处；
- 这条业务政策在哪些分支被判定；
- 这个派生值由哪些事实推出，有没有第二处重复推导。

表达点超过一处且因同一原因变化的，即为 M1。清单是 M1 的输入，不写清就不可能发现业务规则重复；只靠文本相似度找重复，找到的永远是注释与格式化层面的东西。

| 编号 | 对象 | 判定条件 | 处理 |
|---|---|---|---|
| M1 | 真重复 | 同一业务规则、协议、算法在多处表达，且因同一原因改变；文本相似只是线索，判定依据是上文的不变量清单 | **必须**收敛为一处 |
| M2 | 偶然相似 | 结构相似，但服务不同业务、各自演化 | **不得**合并；可以只抽取与业务无关的机制 |
| M3 | 相似逻辑 | 主干相同，细节不同 | 按下方四步法改造 |
| M4 | 薄包装 | 只有一个调用点，名字也不比内联后的代码更清楚 | 内联 |
| M5 | 透传层 | 方法、门面、代理只是原样转调 | 删除中间层，调用方直接用真实实现 |
| M6 | 单实现抽象 | 接口、基类、工厂、策略只有一个生产实现（测试替身不计） | 折叠回具体类型；出现第二个真实实现时再提取 |
| M7 | 多事实源 | 同一事实存了多份：冗余字段、手工缓存、重复存储的派生状态 | 收敛为唯一事实源，其余改为计算或投影 |
| M8 | 自造轮子 | 存在等价的标准库或成熟库能力 | 先用测试锁住行为，再替换 |
| M9 | 冗余执行 | 同一值重复计算；同一数据重复读取或请求；转换后立即转回；结果被丢弃的计算 | 计算一次并复用，删除往返与无用计算。前提是复用的值在两次使用之间不变，重复执行也没有被依赖的副作用。**不得**用新增缓存实现，缓存会引入新事实源（需要时按 L3 呈报） |

**相似逻辑四步法（M3）**，每一步都保持行为不变：

1. **对齐**：统一几份代码的命名、语句顺序与结构，让差异集中到固定位置。
2. **差异显式化**：把每个差异点提为局部变量或小函数，使主干逐字相同。
3. **合并主干**：用 diff 确认几份主干完全一致后再合并。
4. **差异参数化**：值不同的，用参数、配置或表驱动；某一步行为不同的，传函数或策略；骨架相同、步骤不同的，用模板方法或管道；类型不同、操作相同的，用泛型。差异多且杂时停止，回头判断是否属于 M2。

**合并时机**：遵守「事不过三」，第三次出现、差异轮廓清楚后再抽象。M1 不受此限，发现即收敛。

**合并后自检**：出现以下任一情况，说明抽象边界错了，应当拆回重复状态重新判定：

- 参数里有两个以上布尔开关；
- 函数内部按调用来源分支；
- 调用方要读懂抽象内部才知道怎么传参；
- 新增一种变体时要修改抽象本身，而不是只新增配置或实现。

### 4.3 防御类：这一层该守吗？

层层设防是 AI 生成代码的高发问题。多余的防御看起来「更安全」，实际上会掩盖上游契约、把真实错误变成静默的错误结果，还让同一个不变量散落在调用链的多处。

**判定步骤**，对每一处校验、守卫、异常捕获、重试或降级依次回答：

1. 它守的数据或失败从哪里来？是否来自项目画像（§0）中的信任边界？
2. 不在信任边界上时，上游契约、类型系统或调用方是否已经保证它不会发生？
3. 它捕获之后，有没有承担明确的语义（转换、收敛、补偿），还是只是「包一层」？
4. 它守的失败真实发生的概率和代价有多大？是否已在别处由一次原子操作或一次边界校验覆盖？

| 编号 | 对象 | 判定条件 | 处理 |
|---|---|---|---|
| F1 | 不可能情形守卫 | 上游契约、类型或调用方已保证，仍检查空值、类型、范围；为不可达分支写的报错或默认值 | 删除，信任上游 |
| F2 | 重复校验 | 同一不变量在调用链上多层校验 | 只保留信任边界一处 |
| F3 | 过宽或无语义的捕获 | 捕获范围过宽（捕获一切），或捕获后只是原样抛出、只是包一层；捕获的异常不可能抛出 | 删除捕获，或收窄到确有处理语义的异常类型 |
| F4 | 吞异常与静默降级 | 捕获后只记录或返回默认值继续执行；能力缺失、配置缺失时悄悄跳过或返回空结果 | 被吞的失败**不可能发生**时，删除；**可能发生**时，改为显式失败属于行为变更，按 L3 只提建议 |
| F5 | 异常转手 | 返回空值 → 上层抛出 → 再上层捕获 | 收敛为一处抛出、一处处理 |
| F6 | 叠加的重试与超时 | 多层叠加的重试或超时；对非瞬时错误重试；对进程内同步调用套超时 | 只在真正不可靠的外部边界保留一层 |

**注意**：F 类变换只有在被守护的情形**确实不会发生**时才是等价变换。删除一层防御前，必须写明「谁保证了它不会发生」（§5.3）。守的是真实失败的防御属于 §3 受保护的失败安全，不得删除。

### 4.4 归位类：只看位置，能看懂它是什么吗？

**判定问题**：只看目录树、不读代码，必须能回答：

1. 系统有哪些功能，各自在哪个目录？
2. 修改功能 X 要动哪几个目录？（理想情况是一个）
3. 某段公共逻辑被谁共用，从它的位置能看出来吗？
4. 新成员不借助搜索，能否猜出某功能的文件位置？

这四个问题答得出来，说明目录结构能自解释；答不出来也不影响开工——范围从局部种子推导（§6.2），不需要先画出全仓功能图。

**组织规则**

| 编号 | 规则 | 要求 |
|---|---|---|
| S1 | 按功能优先 | 顶层应当按功能或领域划分，功能内部可以再按技术层划分 |
| S2 | 一起改的放一起 | 一次需求应当集中在少数目录；频繁跨多个目录修改，说明划分维度错了 |
| S3 | 一起用的放一起 | 依赖一个模块，不应被迫连带依赖无关内容 |
| S4 | 共置 | 测试、样式、类型、功能私有的工具，应当与功能代码放在一起 |
| S5 | 明确入口 | 目录应当通过统一入口暴露公共接口，其余视为内部实现 |
| S6 | 依赖方向 | 公共模块**不得**依赖功能模块；功能之间的依赖应当少且显式 |
| S7 | 粒度适中 | 单个目录文件过多时按子功能拆分；单文件目录或嵌套过深时合并 |
| S8 | 命名语义 | 目录名必须表达内容，不得使用 `misc`、`temp`、`new`、`v2` 等无语义名称 |

**公共逻辑抽象规则**

| 编号 | 规则 | 要求 |
|---|---|---|
| C1 | 抽机制，不抽策略 | 与业务无关的「怎么做」（重试、分页、序列化）可以公共化；业务规则留在所属领域 |
| C2 | 抽稳定部分 | 易变的逻辑不得放进公共层 |
| C3 | 最近公共祖先 | 公共逻辑放在所有使用者最近的公共上层，不得一有复用就上提到全局 |
| C4 | 禁止垃圾桶目录 | `utils`、`common` 一类目录持续膨胀时，必须按能力拆成有领域名称的模块 |
| C5 | 接口最小化 | 公共抽象暴露的接口应当尽量小 |
| C6 | 名字说明职责 | 起不出说明职责的名字（如 `BaseManager`、`processData`）时，不应抽象 |

**文件移动**：移动与内容修改**必须**分开提交，并使用版本控制的移动命令；引用路径由工具批量更新；一次只搬一个模块。

## 5. 判定与验证

### 5.1 检测手段

**工具优先**：能由编译器、静态分析工具或脚本确定性完成的检查，应当交给工具，不依赖 Agent 逐个阅读判断。工具结果按可信程度分三档：

| 档 | 含义 | 处理 |
|---|---|---|
| 一档：工具定论 | 结论本身就保证等价，如编译器报告的未使用导入与局部变量、编译型语言中的私有死符号、常量条件 | 可以直接执行；有安全自动修复的使用自动修复 |
| 二档：工具给候选 | 可能是假死或有意为之，如未使用的导出、动态语言中的死符号、类型检查器报告的多余比较、宽捕获与空捕获、文本重复 | **必须**按 §5.2、§4.3 逐项确认 |
| 三档：只能判断 | 依赖语义与项目理解，如透传层、多事实源、重复校验、等价论证，以及 M1 的语义层——文本不同的同一业务规则 | 由人或 Agent 判断 |

- 某项检查会在各轮重复出现、且可以确定性完成时，应当沉淀为项目自己的检测脚本复用，而不是每轮重新判断。
- 工具只是辅助：工具没有报告，不等于不存在问题；执行者仍须阅读范围内的代码独立判断，工具结果也须结合上下文确认。
- 删除符号前**必须**全文搜索，包括字符串形式的引用。
- 覆盖率只作为线索：没覆盖到不等于不可达，**不得**作为删除依据。

### 5.2 假死清单

以下情形看起来没人引用，实际可能仍在使用。删除前**必须**逐项排除：

- 反射与动态分发：按字符串查找、注册表、依赖注入、插件、装饰器注册；
- 框架约定：路由、生命周期钩子、按命名约定调用的方法、序列化器读取的字段；
- 入口点：主函数、命令、定时任务、脚本、构建与部署配置引用的文件；
- 跨进程、跨服务、跨语言的消费者；
- 低频路径：灾难恢复、数据迁移、清理任务、优雅退出、错误兜底；
- 只被测试使用的代码：要区分是测试辅助（移进测试目录），还是功能未接线（不是死代码）。

### 5.3 缺陷风险自查

测试通过只能证明「已覆盖的路径没变」。L2、L3 变换（§6.3）的等价论证**必须**逐项说明下表中的相关风险点；测试覆盖不到的，补测试或给出推理论证。

| 风险点 | 典型触发 | 自查问题 |
|---|---|---|
| 异常语义 | 内联、合并、M5、F3、F4、F5 | 异常的类型、抛出时机、捕获方是否不变？有没有新吞掉或新暴露异常？ |
| 防御前提 | F1–F6 | 「它不会发生」由谁保证：类型、上游校验、调用方约定？该保证在所有调用路径上都成立吗？ |
| 副作用顺序 | 内联、合并主干、M9 | 写入、外部调用、日志的顺序和次数是否不变？短路求值是否仍成立？ |
| 求值时机 | D3、M9 | 原本每次都重新求值的值（时间、随机数、可变状态、外部读取），有没有被改成只求一次，或者反过来？ |
| 边界与空值 | D6、F1、F2、M3 | 空集合、空值、零、极值、未知枚举值的处理是否不变？ |
| 并发时序 | F1、F2、M9 | 锁的范围、「检查」与「使用」之间的间隔、跨线程可见性是否不变？双重检查是否在防竞态？ |
| 资源生命周期 | 内联、M5、F3 | 打开与关闭、获取与释放、订阅与取消是否仍成对，时机是否不变？ |
| 状态共享 | M3、M9、公共抽象 | 原本独立的状态是否被合并成了共享状态？被删的拷贝是否在防别名修改？ |
| 动态查找 | D2、D8、文件移动 | 移动或重命名是否破坏了按名字、路径、约定的查找？ |
| 类型与相等性 | 合并、泛型化 | 隐式类型转换、数值精度、相等与哈希语义是否不变？ |

### 5.4 验证等级

| 变换 | 最低验证要求 |
|---|---|
| D1、D10 | 编译或类型检查通过 |
| D2–D7、D9 | 类型检查 + 单元测试 |
| M4–M6、M9、F1–F6 | 单元测试 + 集成测试；M9 必要时对比性能数据 |
| M1、M3、M8 | 改造前已有覆盖各个变体的测试，改造后全部通过 |
| D8、M7 | 集成测试或端到端测试；必要时对比新旧输出 |
| 文件移动 | 构建 + 全量测试通过，历史可以追溯 |

**特征测试的适用范围**：不是所有变换都要先补测试。风险由工具兜住的变换——L1 类（D1、D10、编译器可证明的 D6、私有作用域内的 D2–D5）与纯文件移动——按上表的最低验证等级执行即可；被改区域没有覆盖时不补测试，直接以编译或类型检查加全量测试作为等价证明。等价性靠推理的变换（M1、M3、M7、M9、F1–F6）在被改区域没有覆盖时，**必须**先补特征测试锁住当前行为，再执行变换。

**测试代码不是精简对象**：测试只作安全网，不为降低测试体积、合并测试文件或清理冗余断言单独执行变换。与本标准相关的情形只有两种：被删行为的断言随生产代码同步删除（G4）；测试侧的重复 fixture 或辅助代码挡住了生产代码的移动或合并时，最小幅度调整以腾出位置。

## 6. 执行规程

### 6.1 触发

执行一轮的条件：人类明确下达指令，或目标项目约定的周期到达。Agent **不得**在功能开发途中插入精简；开发中发现的候选，记入当轮交付说明。

### 6.2 范围：种子、扩散与封口

**范围不从「先给仓库画一张能力地图」产生。** 仓库再大再乱，Agent 对全局结构的判断都不可靠；画错一次，后面每一轮都跟着错。所以范围从一个**具体的种子**出发，向外扩散，到边界封口。选在哪、扩到哪、停在哪：

**种子：本轮从哪下手。** 种子是一个文件、一个目录或一处符号，不是「某个能力」。从前几名里挑一个，依据是下列信号（`seeds.mjs` 给出可比数值，按路径前缀粗排）：

- **候选密度**：单位代码量里有多少候选（§5.1 的检测器已产出候选，这里只按目录聚合）；
- **变更热度与共变度**：近 N 轮这里被改过几次、一次需求平均牵动几个目录（E1 的直接证据）；
- **命名与事实源分裂**：同一概念两套词、同一链路两套日志前缀、同一字段两处写——最便宜、误报最低，直接对应 E2；
- **人类痛感**：人类指定的位置、缺陷记录、项目规范里的遗留项。

分组只是粗排手段，**不是能力定义**；排名只用来挑前几个种子，不要求先给全仓分类。可以全仓只读扫描、跑检测器来排名，**不得**扫完直接动手改。人类指定种子时跳过排名。

**扩散：改到哪。** 从种子出发只沿三种边向外一层：调用链（谁调它）、数据流（同一份事实谁写谁读）、同一事实源（同一张表、同一配置项、同一状态机在别处的第二份表达）。扩散出的文件集合就是本轮范围；不必给它起名字，报告里写「种子 + 扩散路径」。

**封口：在哪停。** 到跨进程或跨服务契约（接口、数据格式、消息、命令与配置语义）与被多个外部消费者引用的共享模块为止。跨出封口线的重复按 M1 处理时只改种子这一侧，另一侧记为待办留给下一轮：**读范围可以大于改范围，改范围不行**。

- **种子太大时**：一轮只做种子内候选密度最高的一到两个模块，其余留给下一轮；不因为选了种子就把它做完。
- **复检（可选前扫）**：选种子前可对「上一轮基准以来变更过的文件」（`scope.mjs --base`）做一次只读快扫，确认新代码没留下新债；发现的问题并入候选清单参与挑种子，不在本轮直接修改。
- **扩散不到的发现**：只记录，不修改。

### 6.3 自主等级

| 等级 | 变换 | 要求 |
|---|---|---|
| **L1 直接执行** | D1、D10；编译器可以证明的 D6；只在私有作用域内的 D2–D5 | 执行后在报告中列出 |
| **L2 先报后做** | 跨模块的 D2–D5、D7、D9；M1、M3–M6、M9；F1–F3、F5、F6，以及被吞失败不可能发生的 F4；目录调整 | 先列候选与论证，人类确认后执行 |
| **L3 只报不做** | D8、M7、M8；需要新增缓存的冗余执行；被吞失败可能发生的 F4；涉及 §3 受保护行为或跨进程、跨服务契约的变换；无法排除假死的候选 | 只写建议，交给项目的结构性改造流程（§0），由人类决定是否立项 |

目标项目可以收紧等级；放宽须由人类明确授权。

### 6.4 步骤

1. 读取本标准当前版本，以及上一轮报告中的项目画像、基准提交与遗留项。
2. 建立或核对项目画像（§0）；有无法确定的维度时，先询问人类。
3. 按 §6.2 取种子、扩散、封口，按 §7 采集基线指标。
4. 按 §5 产出候选，逐项标注变换编号、自主等级与假死排除结果；无法排除假死的降为 L3。
5. 呈报计划：L1 清单、L2 待确认清单、L3 建议清单。等待人类确认 L2。
6. 自底向上执行，先 L1 后 L2，大致顺序为：死引用 → 死符号 → 死参数与返回值 → 死分支 → 过度防御 → 薄包装、透传层、单实现抽象 → 重复与相似 → 数据流与冗余执行 → 目录归位。每个变换完成 §5.3 自查与 §5.4 验证后单独提交，提交说明写明变换编号与等价论证。执行中发现判断不成立的，立即停止该项并记录，不得改换做法强行完成。
7. 每轮删除都可能让新的代码变成死代码，因此重新检测，直到不再出现新的 L1 候选。新出现的 L2 候选并入下一轮，或再次呈报。
8. 按 §8 自查验收，按 §9 产出报告。

### 6.5 行为约束

- 不扩大范围，不夹带功能修改或缺陷修复。
- 精简过程中不得新增防御代码；需要补的校验只能放在信任边界上，并在报告中说明。
- 不为改善指标而选择变换：指标是结果记录，不是执行目标。
- 证据必须可复核：搜索命令及结果、测试名称、工具输出摘要都要写明，让人类无需重做即可核对。
- 验证失败、回滚、放弃的变换必须如实列出。
- 不自行修订本标准，只在报告中提出建议。

## 7. 评价指标

只在改动范围内统计，记录改动前后的数值。按对迭代成本的影响分四级权重，一级最高。

| 级 | 编号 | 指标 | 定义 | 方向 |
|---|---|---|---|---|
| 一 | E1 | 变更扩散度 | 一次同类需求需要修改的文件数或目录数；用历史共变数据，或模拟一次同类改动来估算 | ↓ |
| 一 | E2 | 知识表达点数 | 同一规则、事实、不变量在代码中的表达位置数 | ↓，目标为 1 |
| 二 | E3 | 跳转深度 | 从入口到真实业务逻辑经过的间接层数，抽样典型路径统计 | ↓ |
| 二 | E4 | 单实现抽象数 | 只有一个生产实现的接口、基类、工厂、策略 | ↓ |
| 二 | E5 | 重复代码率 | 重复代码块占比，用重复检测工具统计 | ↓ |
| 二 | E6 | 依赖健康 | 循环依赖数，加上违反 S6 的依赖边数 | ↓，目标为 0 |
| 三 | E7 | 复杂度 | 改动范围内函数圈复杂度、认知复杂度或嵌套深度的最大值；超过项目阈值的函数数一并记录 | ↓ |
| 三 | E8 | 冗余点数 | 符合 M9（冗余执行）与 F1–F6（过度防御）判定条件的位置数 | ↓ |
| 四 | E9 | 规模 | 生产代码净删除行数（测试代码单独统计，补特征测试导致的增加不算退化）、直接依赖数 | 删除越多越好；替换自造轮子增加依赖属于正收益 |

**评级**：

- **有收益**：至少一项一、二级指标有可核对的改善（估算须写明推导），且没有退化。
- **仅清理**：只有三、四级指标改善，且没有退化（如只含 L1 的轮次）。
- **有得有失**：存在退化，但更高级别的改善覆盖了它（例如 E3 下降而 E7 上升），必须写明论证。
- **无收益**：没有改善，或者退化的级别不低于改善的级别。

**叙述顺序**：业务代码的收益优先。一轮精简先写收敛了哪些知识表达点（E2）、降低了哪些变更扩散（E1）、去掉了哪些冗余与防御（E8），规模（E9）放在最后作为结果记录。删除行数概括不了一轮精简，不得用作主结论。

通过 §2 P7 所禁止的手段取得的改善，不计入评级。

## 8. 验收门槛

全部满足才通过，任一项不满足即不通过。

| 编号 | 门槛 |
|---|---|
| G0 | **前提成立**：报告附项目画像；观察者、信任边界、兼容要求的判定都以画像为依据 |
| G1 | **行为不变**：全部既有测试通过，满足 §5.4 的验证等级，§3 受保护行为未改变 |
| G2 | **不引入缺陷**：删除类已按 §5.2 排除假死；L2、L3 变换完成了 §5.3 自查；防御类变换写明了「谁保证它不会发生」；§5.4 要求补特征测试的变换已补并单独提交 |
| G3 | **提交规范**：一个提交（不提交时为报告中的一节）只含一类变换，附变换编号与等价论证；不混入行为修改与缺陷修复；文件移动与内容修改分开 |
| G4 | **同步删除**：被取代的旧路径、旧测试、旧文档已删除，注释与文档同代码事实一致 |
| G5 | **红线不退化**：E6 不增加；E7 最大值不上升；覆盖率不下降；静态分析告警不增加；不新增单实现抽象、无语义目录与防御代码 |
| G6 | **结构合规**：合并产生的抽象通过 §4.2 自检；公共逻辑符合 C1–C6；目录能回答 §4.4 的判定问题 |
| G7 | **确有收益**：评级为「有收益」；只含 L1 的轮次为「仅清理」；或为「有得有失」且论证经评审确认 |

**结论**：

- **通过**：G0–G7 全部满足。
- **有条件通过**：G5 的某项例外经评审确认，其余门槛全部满足。
- **不通过**：其他所有情况。G0、G1、G2 不允许例外。

## 10. 文档演进

本标准依据执行实践持续修订。

- **修订触发**：误删或误合并；指标无法度量，或度量结果与实际收益不符；门槛过严（反复需要例外）或过松（通过的改动事后证明是负收益）；自主等级与实际风险不符；项目画像维度不足以支撑判断；出现未覆盖的变换类型；与目标项目规范的冲突具有普遍性。
- **提出与批准**：Agent 在报告中提出建议并附实践依据，人类批准后修订。
- **保持中立**：修订内容不得绑定具体项目、语言或工具。
- **编号稳定**：条款编号一经发布，不复用、不改义；废弃条款保留编号并标注「已废弃」。
- **版本号**：增删条款或调整门槛、权重时升次版本号；改变整体结构时升主版本号；措辞修正只记入变更记录。
- **自身精简**：本文同样适用本标准。条款重复、长期未被引用，或案例已被条款吸收时，应当合并或删除。
