# 检测脚本

文中的 § 编号与条款编号均指 [simplification-standard.md](simplification-standard.md)。

**能交给脚本的检查，不交给 Agent 逐个判断。** 每轮都靠阅读代码去找候选，既慢又不稳定；写成脚本后结果可重复、可复核，下一轮直接复用。

**但脚本只是辅助。** 脚本只能发现写进去的规则，项目里总有它覆盖不到的情形。Agent 不能把「脚本没报」当作「没有问题」，仍要阅读范围内的代码独立判断；脚本报出的结果也要结合上下文确认后再执行。Agent 自己发现、脚本漏掉的问题，如果可以确定性检测，就回头改进脚本（见「演进」）。

## 三档分工

| 档 | 含义 | 典型条款（示例） | 谁来做 |
|---|---|---|---|
| **一档：工具定论** | 编译器或确定性工具的结论本身就保证等价 | D1 死引用与死依赖、编译型语言的私有 D2、D6 常量条件；E5–E7 指标；S8 无语义目录名 | 工具或脚本直接给结论；有安全自动修复的直接用，Agent 只复核结果 |
| **二档：工具给候选** | 工具能找出可疑点，但可能是假死或有意为之 | 导出与动态语言里的 D2、D3、D7、D10；F1（类型检查器的多余比较、不可达告警）、F3、F4（宽捕获、空捕获、原样重抛）；M1/M3 的**文本层**（相似的代码块，不含语义重复）；M6（实现数统计） | 脚本产出候选，Agent 按 §5.2、§4.3 逐项确认 |
| **三档：只能判断** | 依赖语义与项目理解 | D4、D5、D8、M4、M5、M7、M9、F2、F5、F6、目录与抽象规则、全部等价论证；M1 的**语义层**——文本完全不同、却在表达同一条业务规则（按 §4.2 的不变量清单人工枚举，任何检测器都给不出） | Agent |

二档和三档之间的边界会随项目推移：很多看似要判断的检查，结合项目约定后可以脚本化。例如按项目的注册方式核对动态引用、配置项「定义 − 读取」求差、事件「发布 − 订阅」配对、统计接口的生产实现数。

**一类始终脚本化不了的东西：业务规则的语义重复。** 同一条政策写成三处不同的代码（一处 `if/else`、一处配置表、一处查询条件）时，文本相似度检测永无输出。这类候选只能按标准 §4.2 的不变量清单人工枚举，不要指望新增检测器解决；把预算投在清单的枚举上，而不是在重复率工具的阈值上调参。

## 集中管理

目标项目的全部检测器都集中在 `.simplification/scripts/` 管理。Agent 每轮只通过这里运行检测，不在仓库各处直接调用零散的工具。

```text
.simplification/scripts/
├── README.md        # 检测器索引：唯一的登记处
├── run-all.<ext>    # 总入口：按索引依次运行全部检测器
└── <检测器脚本>      # 每个检测器一个文件
```

- **项目已有的工具也要登记**：死代码工具、linter 规则、类型检查器等不搬动、不复制，但要在这里写一个薄包装脚本去调用它。包装脚本负责传入本轮范围、选定相关规则，并把结果转成统一输出。
- **索引** `README.md` 每个检测器一行：名称、文件、档位、对应条款、包装的项目工具（如有）、已知局限、最近修改原因。新增、修改、删除检测器时同步更新索引。
- **总入口** `run-all` 接受范围文件（`scope.json`），按索引运行全部检测器，把所有候选合并为一份结果，输出到会话临时目录。单个检测器失败时记录并继续运行其他检测器，最后以非零状态退出，以便发现问题。
- **语言**：总入口与检测器使用项目已有的运行时；同一项目内尽量统一用一种。
- `project-profile.md` 的工具链只记录构建、静态检查、测试命令，检测器一律指向这份索引，不重复登记。

## 何时写脚本

识别候选时，按以下顺序：

1. **先复用**：项目已有的工具（linter 规则、类型检查器、死代码工具）和 `.simplification/scripts/` 中已有的脚本。
2. **再包装**：项目已有工具能检测的，写薄包装脚本接入总入口，不重新实现工具已有的能力。
3. **再新写**：某项检查可以确定性完成、且以后各轮还会用到，而现有工具做不了时，写新脚本。
4. **一次性的判断**不写脚本。

## 脚本约定

- **依赖**：只用项目已有的运行时与依赖。需要引入新依赖时，先问人类。
- **只读**：检测脚本只报告，不修改代码。自动修复走项目已有工具的修复命令，不在检测脚本里实现。
- **范围**：接受文件清单参数（如 `scope.json` 中的 `files`），只扫描本轮范围；不传时全量扫描。
- **统一输出**：每个候选一条，至少包含变换编号、位置（文件:行或符号）、证据（命中的规则或原因）。
- **头部说明**：写明检测目标、对应的变换编号与档位、依赖的项目约定、已知的误报与漏报。
- **登记**：写进 `README.md` 索引后才算接入；没有登记的脚本，总入口不运行。

## 演进

- 发现误报或漏报时修正脚本，并同步更新头部说明与索引中的已知局限。漏报包括 Agent 阅读代码时发现、但脚本没有报出的问题。
- 新增或修改脚本**单独提交**，排在本轮变换提交之前；在报告的「检测脚本变更」中说明改了什么、为什么。
- 修改脚本后，在上一轮报告记录的候选上回放一次，确认没有丢掉原本能发现的问题。
- 脚本同样适用本标准：重复的合并，长期不用的删除。
- 检测脚本属于项目自己的状态，由 Agent 按以上约定维护；标准与本 skill 仍只提建议、不自行修改。
