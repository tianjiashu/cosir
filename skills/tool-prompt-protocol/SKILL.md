# 工具提示词协议

## 概述

工具提示词是 Agent 的全部世界知识来源：它看不到实现，只看到 schema 与系统提示词。协议的唯一目标是——**在尽可能少的 token 内，让 Agent 拿到做下一步决策所需的一切信息**。信息缺失导致幻觉，信息冗余同样导致幻觉（噪声稀释注意力，重复处两份必然漂移）。

写之前先调研，调研不足就是猜。

## 一条判据决定信息去留

不要按「这是 ID 还是文本」「这是开发者术语还是用户语言」划分，按**Agent 是否会用它做决策**划分：

- **缺失会让 Agent 下一步动作做错 → 必须进模型可见通道。** 例：`task_id` 是 Agent 互相寻址的键，必须进 schema，哪怕它看起来像内部标识。
- **只影响人排查问题 → 不得进。** 例：`tool_call_id`、原始异常堆栈、内部产物路径、耗时。走 `display_data` 或日志。

判据只有这一条。凡是靠「这看起来像内部信息」删字段的，都是在删 Agent 的决策依据。

## 三层归属：一条信息只有一个位置

| 信息类型 | 唯一位置 |
|---|---|
| 单个参数的含义、格式、边界、示例 | 该字段的 `Field(description=...)` |
| 何时选它、何时不选它、与兄弟工具的分界 | 工具 `description` |
| 跨工具族的横向纪律（专用工具优先、并行读取、浏览器页面即数据） | 系统提示词 `tool_layer` |
| 过程叙述与收尾（怎么和用户协作） | 系统提示词 `work_layer` |

两条反向规则同样重要：

1. **兄弟工具的互斥选择写在被放弃方**，不要只写在系统提示词里。模型是逐个读 `description` 决定调谁的，系统提示词不在那个决策视野内。例：`find_files` 描述结尾写 "Use search_content to search inside file contents."；`terminal_start` 点名 `execute_terminal` 而后者不反向点名，因为对方只出现在子 Agent 的工具集里——取舍理由写进源码注释，注释给 reviewer 看，不占模型 token。
2. **横向纪律不上移进每个工具描述**。同一句「别用 shell 读文件」写进六个文件工具描述，就是六份会各自漂移的副本；它只该在 `tool_layer` 出现一次，由工具族条件决定是否注入。

## 工作流

### 第 1 步：读实现，按此顺序

1. `execute` 实现——真实行为、是否有状态、副作用、是否阻塞。
2. 参数模型——字段真实语义、默认值、取值范围。
3. **错误与超时分支——最有价值的素材。** 模型最常踩的坑已经以错误文案的形式存在（「范围太大超时，收窄重试」），必须前移成描述，否则模型每次都要先失败一次。
4. 兄弟工具的 `description`——划清边界，并决定是否点名。
5. `content` 的组织方式——输出侧提示词，见下。

不准凭工具名推断行为。也没读实现就不要下笔。

### 第 2 步：定归属

按上表把每条信息放进唯一位置。写之前先问：这句删掉，Agent 会做错什么？答不出来就删。

### 第 3 步：撰写

硬规则：

- **模型可见文本一律英文**，包括字段描述与例子。源码里保留中文注释作为译文供 review（发送给模型的只有英文）。
- **模型可见说明只写在字段描述里。** schema 生成边界会剥离根对象与 `$defs` 的模型级 `description`，所以类 docstring 只服务源码阅读，不能当作说明的投递渠道。
- **每个字段必须有 description，且描述的是作用不是复述字段名。** 字段描述之间不得互相包含。
- **跨工具共享的字段描述一处定义、各模型复用**（模块级常量或工厂函数），不在每个 args model 里各写一遍。
- **工具描述只承载选择与执行语义**：何时用、何时不用、与兄弟工具的分界、副作用与阻塞特征、结果怎么读（行号、分页标记、状态枚举）。不承载参数取值格式、参数清单、平台细节——「参数怎么填」归字段，「结果怎么读」归工具描述。
- **格式契约只写在一处**，即对应字段的描述，工具描述只指回它，绝不重复（否则两处必然漂移）。
- **例子判据**：合法取值空间无法用一句话说明时才给最小可运行例子（结构化格式、嵌套结构、多字段协同、glob/正则）；标量语义自明的参数（`limit`/`offset`/`timeout`）禁止给例子——例子占 token 且诱导模型照抄具体数值。
- **多行例子每行必须自带 `\n`**，否则字符串字面量拼接会塌成一行，模型照抄即被解析器拒绝。
- **动态事实不进字面量**：随配置或平台变化的事实（可用 shell、数量上限）由投影阶段同源注入——收窄 `enum`、改写字段描述，与来源同一次生成。不写死在常量里：工具描述随 Task 固化进 `tasks.tool_schemas`，写死就是长期错误。
- **点名兄弟工具的前提是两边可能同时出现在该 Agent 的工具集里**。指一个它没有的工具，等于制造幻觉。
- **不写不改变行为的句子**：「请确保」「注意要」「务必」这类让模型更谨慎却不给它新信息的词，纯 token 开销。

### 第 4 步：输出侧同样受协议约束

`ToolObservation.content` 是模型唯一消费的文本通道，按同一判据裁剪：

- 只放 Agent 后续决策需要的事实（结论、数量、下一页游标、失败原因与下一步）。
- 内部路径（`.cosir/tool-artifacts/<uuid>.txt`）、调用 id、原始异常文本留在 `display_data` 或日志。
- 反面样板：把绝对路径、字节数、耗时写进正文。正面样板：`lines 10-42 of 380` / `[end of file]` / `next offset`。

## 自查清单

交付前逐条过：

- [ ] 每条信息都能回答「缺失会让 Agent 做错什么」，答不出的已删
- [ ] 工具描述里没有单个参数的说明，参数说明里没有工具选择建议
- [ ] 结果长什么样（行号、分页标记、状态枚举）仍留在工具描述里，没被当成参数说明删掉
- [ ] 格式契约只出现在一处
- [ ] 没有中文、没有靠 docstring 投递的说明、同层字段描述不重复
- [ ] 例子确实必要，且多行例子每行带 `\n`
- [ ] 没有写死会随配置或平台变化的事实
- [ ] 点名的兄弟工具在该 Agent 工具集里真实存在
- [ ] `content` 里没有内部路径、调用 id、原始异常

## 与测试的分工

协议约束「写的时候」，测试守「改的时候」。以下规则已由全量守卫测试覆盖（`tests/test_strict_tool_contract.py` 的 `test_registered_tool_prompts_are_english_and_documented`）：模型可见文本无 CJK、每个字段有非空描述、同层字段描述不重复、工具描述非空且无首尾空白。新增文案规则时优先加进这个守卫，而不是只写进文档靠人记。
